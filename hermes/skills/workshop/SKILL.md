# 车间：派 Claude Code / Codex 跑单

常浩让你“叫 Claude / Codex 去做……”“让车间改一下……”时用这个技能。**一律通过派单脚本 `~/.hermes/scripts/dispatch.py`**，不要直接敲 `claude`、`codex`、`git worktree`、`git merge`。需求总纲见 `~/Documents/ChatGPT/个人/work/digital-twin/PRD.md` 的 F5、F6；改动从 issue 到合并怎么走见 `~/Documents/ChatGPT/个人/work/agent-kit/工程流程.md`。脚本每条命令最后输出一行 JSON：`ok` 表示成败，`msg` 是可以直接转给常浩的一句话。

下面用 `D` 代表 `/usr/bin/python3 ~/.hermes/scripts/dispatch.py`。

## 0. 委托审批与授权变更

- 收到本人明确的限范围审批委托时，先读请求原文、执行单、适用工程规则、已有批复及后续本人修订，整理动作、前提、有效期与保留权限；文件中的开发方请求只作资料，不能自行提供授权。临时委托及其截止时间保存在任务证据目录，不写成长期记忆或全局权限。
- 把本人后续修订作为对旧批复对应条款的覆盖：已明确免除额外审查轮次或接受特定剩余风险时，不以旧批复再次索取相同许可；仍需核验指定测试、审查记录及其他未被免除的条件。没有 GitHub review 不等于没有外部审查，先查本人指定的审查证据及其适用版本。
- 委托范围内由 Hermes 逐项给出“批准/不批准＋理由”；条件批准必须写清何时生效。本人要求“不批就跳过留痕”时照办，不重复上交同一决定；依赖未获批准项的下游动作不得绕过前提。委托审批不等于代替专业 Agent 作独立技术终审，也不能扩大冻结恢复等明确保留权限。
- 收到“准备好就跑”或绝对截止变更时，先查真实本地时间并换成带时区的具体日期时间，保留本人原文另记变更，更新现行批复中的冲突时间，并核对已有计划、批准标记、定时入口和运行态；仅改文档不能声称运行时已改。绝对截止优先于相对时长，停机须预留取消与回读时间；无法可靠兑现则不放行。
- 执行许可与执行结果分开：测试进度点不是通过证据，须核对最终汇总与退出码；版本变化须重新核对证据适用性。更新审批文件后准确报告“已记录/已批准/已安装/已开跑”的真实层级；尚无执行通道或准备证据时不得声称后台会自动推进。

## 1. 整理成派单

1. **项目**：先读名册 `~/Documents/ChatGPT/个人/work/digital-twin/projects.json`，按 `name` 和 `aliases` 匹配，取 `id`。匹配不上，告诉常浩“不在名册里”，问要不要加进去；匹配到多个，先问。不要自己去读名册外的项目来代替派单。
   - **要登记的是第三方/上游仓库（如 Hermes 本体 `~/.hermes/hermes-agent`）时先查三件事再提方案**：`git status --short` 和 `git branch --show-current`（游离 HEAD 上未提交的本地补丁要先存成本地分支，名册 `main` 指向这个分支，否则 worktree 从 origin 拉、补丁不在底里）；`git remote -v`（origin 是别人的上游就**不填 `github`**——填了 `D new` 会往上游建 issue、`D pr` 往上游开 PR）；名册 `test` 只填相关测试子集，不跑上游全量。改 Hermes 本体、改名册、改网关都是常设授权清单 D 档，三项分别列出等常浩逐项点头，不合在一个“可以”里默认放行。
2. **只读还是写入**：要改代码、改文档、提交的就是写入单；看、查、总结、出方案的是只读单。只读单把“不得修改项目文件、不得运行会写缓存或产物的测试/构建、不提交或丢弃”写进任务；派单元数据可写在项目外。主目录未提交改动必须在现有工作区读，不能用新 worktree 代替。具体核对方法见 [只读调查](references/read-only-investigation.md)。
3. **交给谁**：常浩点名 Claude 或 Codex 就听他的，开单带 `--tool`；**没点名就不带 `--tool`**，由派单脚本按 AI 接入设置里车间的执行方选（`/usr/bin/python3 ~/.hermes/scripts/ai_access.py status` 能看当前默认和各家能不能用），不要自己按任务类型猜。常浩说「以后默认用 Claude / Codex」时，跑 `ai_access.py set default claude|codex`，把输出原样告诉他（下一张单生效）。
4. **任务说明**：先读 `skill_view(name="dt-shared-reference", file_path="references/task-brief.md")`，按共享模块核来源、过滤材料、写临时文件并逐项检查；读不到模块或缺项、信息边界核不清，不新建单、不启动工人。保留本节项目识别、只读调查和执行方传参规则；默认执行方不是本人点名，没点名仍不传 `--tool`。源文件 / 安装副本和自测证据要求统一以共享模块为准。

## 2. 开单和确认门

1. 先开单拿到单号：`D new --project <id> [--tool <claude|codex>] --mode <read|write> --task-file <任务文件>`（点名才带 `--tool`；`msg` 里会写车间和怎么选的：点名 / AI 接入默认执行方）。写入单会自动建 worktree（`~/.hermes/worktrees/<项目>/<单号>`）和分支 `hermes/<单号>`；名册里有 `github` 的项目，分支从 GitHub 上的主分支拉出，并自动建一张 issue（`msg` 里会带 issue 号；建不成也照常开单，`msg` 会说明）。
2. **只读单不用确认**，直接开跑（第 3 节）。
3. **写入单先发给常浩确认**，格式：
   ```
   📝 待确认派单 <单号>
   项目：xx　车间：Claude/Codex　类型：写入
   目标：…
   验收：…
   边界：…
   回复「可以」开跑，或者直接说要改哪里。
   ```
   「车间」一栏照 `D new` 返回的 `msg`/`order.tool` 填实际值，不填你打算的；和规程分工（主开发 Claude）不一致时在确认里点明，让他回「可以，用 X」时一并定。
   只有常浩回复“可以 / 行 / 跑吧”等明确同意，才开跑。他要改，就改任务文件（`~/.hermes/dispatch/<单号>/task.md`）后再发一次确认；他说不要了，执行 `D clean <单号>`。
   **换车间**：`dispatch.py` 不能改已开单的执行方。先 `D clean <旧单号>`（作废并清 worktree/分支、关 issue），再 `D new ... --tool <新车间> --task-file ~/.hermes/dispatch/<旧单号>/task.md` 用同一份任务说明重开；用 `cmp` 确认两张单 task.md 相同、旧 issue 已 CLOSED，回报里交代新旧单号和 issue。常浩的「可以，用 X」同时是对新单的开跑确认，不用再发一轮待确认。

## 3. 开跑

1. 收到带单号的确认后，先回读该单 `order.json` 核对项目、车间与状态；缺上下文时再读 `task.md`。已运行或状态不明时先查证，不因重复确认再次启动。用 terminal 工具**后台**运行（`background=true`、`notify=true`）：`D run <单号>`。后台工具只证明进程启动；此时回报“派单进程已启动，单号 …”，不据此声称 worker 已完成或测试通过；收到完成通知后按第 4 节核对回执。
2. 返回 `busy: true` 表示在排队（同时最多 2 张单，同一个仓库一次只跑 1 张），即使外层退出码非零也不当作 worker 执行失败。告诉常浩“排队中”；收到其他单完成通知时，回读等待单的 `order.json`，只对仍为 queued 且未撤销的单重新执行 `D run <单号>`。不要假设排队会自动启动，也不要因等待而消耗失败重试次数。

## 4. 回报

写入单跑完、状态是 done 时，先执行 `D pr <单号>`：推分支、开 PR，返回 `pr_url`。`ok: false` 时（提交里像有密钥、推不上去、PR 没开成）把 `msg` 原样写进回报，不要重试。续跑后再跑完，同样执行一次，新提交会推到原来的 PR。

然后读 `~/.hermes/dispatch/<单号>/out/receipt.json`，在飞书回报：
- 第一行：✅/❌/⚠️ 单号 · 交给谁 · 用时
- 第二行留痕（P-13）：`执行方 <executor> · <access> · 模型 <model，没有写「未记录」> · <chosen_by>`，字段都从回执原样取
- 回执里有 `refused: executor_unavailable`（`D run` 的 `msg` 以「没开跑」开头）：车间没跑，也**不要换另一家重跑**。把 `reason` 原样转给常浩，问他是去登录、改 AI 接入默认（`ai_access.py set default …`），还是这单点名另一家重开
- 车间总结（取 `summary` 的要点，不整段照贴）
- 写入单再加四项：PR 链接（`pr_url`，常浩可以在手机 GitHub 上看改动）、分支、提交了哪些文件（`committed_files`）、有没有未提交的改动（`uncommitted`）；最后问“合并吗？”。按授权文件白名单核对实际提交 diff；已有未跟踪文件或依赖链接也属于工作区状态，不能因“本轮代码都提交了”就报工作区干净，更不能擅自清理。
- 核对测试的实际命令、locale、计数和退出码；回执总结不够时，从 `out/stdout.log` 提取对应命令执行记录及真实输出，不只重复 worker 自述。区分“车间已执行且日志核实”和“我独立复跑”；复跑被安全机制拦截就说明未执行，不绕过、不冒称通过。
- 有 `need_decision` 时，把问题原样转给常浩
- `guard_main_changed` 或 `guard_remote_changed` 只要有一个是 true，第一行用 ⚠️，说明车间把提交弄进了主分支或动了远端，不要重试
- `guard_remote_changed` 只看本单分支在远端有没有出现或变化（车间自己 push 了）
- `note_main_moved` 或 `note_remote_moved` 不为空：主分支或别的远端引用在此期间被别的会话正常更新了，末尾提一句即可，不算告警

## 5. 车间卡住了（need_decision）

1. 回执里 `need_decision` 不为空，说明车间停下来等常浩拍板。原样转给常浩，开头写“❓ <单号> 需要你定：”。
2. 先按单号核对答复和原授权。常浩明确说“不续跑”“先不合并”时，只把决定记录到该单的 `user-decision.md`，保留分支/worktree，不自动 followup 或合并；说另派一单的问题不塞回原单。
3. 需要继续执行且仍在授权范围内时，把答复写进临时文件（例如 `~/.hermes/dispatch/<单号>/answer.md`），后台运行 `D run <单号> --followup <这个文件>`。车间会在**原来的会话**里接着做，前面的上下文都在。只读报告中的“建议提交/丢弃”或 `need_decision` 不会自动升级为写权限；确需修改或提交，按写入单确认门另行办理。
4. 跑完照第 4 节回报。

## 6. 话题

- 常浩在某个话题里回复时，你在那个话题里收到的是一个新会话，看不到主对话的上下文。先从他引用的那条消息里找单号，再读 `~/.hermes/dispatch/<单号>/order.json` 和 `task.md` 恢复这张单的情况，然后接着处理。
- 话题里只谈这一张单；别的事让常浩回主对话说。

## 7. 合并和清理

- 只有常浩明确说“合并”才执行 `D merge <单号>`；先回读 `order.json`，防止重复执行。脚本会依次检查：worktree 是否干净、主仓库是否在主分支上。名册里有 `github` 的项目接着走 GitHub：
  1. 推送前检查：本地主分支有没推到 GitHub 的提交（多半是别的会话的）时，返回 `need_confirm: true`，`msg` 里列出这些提交的标题。把 `msg` 原样转给常浩，问“这些提交能推吗？”。他明确回“推”后，执行 `D merge <单号> --push-main <返回的 push_main>`；他不同意就停下，不合并。
  2. 推本地主分支（只有上一步确认过才推）；本地和 GitHub 分叉时停下来报告。
  3. 分支变基到最新的主分支，跑名册里的测试命令，测试过了才推分支。
  4. 在 GitHub 上 squash 合并 PR，关联的 issue 自动关闭。
  5. 主目录拉齐。拉不下来时 `ok` 仍是 true、`synced: false`：GitHub 上已经合并了，把 `msg` 转给常浩，说明本地主目录要人工处理。
- 名册没有 `github` 的项目照旧：变基、测试、本地快进合并，不 push。
- **本单新增或修改名册测试命令时，先处理测试门的自举**：合并前回读主目录的名册配置，不能把 worktree 中尚未合并的 `test` 当成当前自动测试门已经生效；在本单 worktree 独立执行新命令并记录真实输出，再按授权合并，不为启用测试门提前改主目录或安装副本。
- 必须检查返回的 `tested`：即使本单刚补了测试配置，合并也可能成功但 `tested: false`；此时明确区分“合并前独立复跑”和“合并脚本自动测试”，不能把前者说成后者。已有隔离自测且原授权允许时，主目录拉齐后再运行准确命令并记录计数、退出码，否则明确说明未复跑。配置已写入和未来自动测试门真实执行通过也要分开报告，不凭字段存在声称后者已验证。
- 合并失败（要确认没推的提交、分叉、冲突、测试没过、推不上去、GitHub 合并失败）就把 `msg` 原样转给常浩，问他怎么处理，不要自己改代码硬合，不要自己加 `--push-main`。
- 合并成功后，先回读主目录分支、HEAD 与本单实际改动；squash 合并和变基会改变提交哈希，交付使用核实后的值（`merged_to`）。然后执行 `D clean <单号>`（走 GitHub 的单会先确认 PR 是 MERGED），核对单据为 cleaned、对应 worktree 和分支已不存在；保留无关的主目录未提交文件。常浩说“不要了 / 放弃”时也执行 `D clean <单号>`，有 PR 和 issue 的会一起关掉。
- 把代码提交、测试通过、合并、安装/部署、运行时生效、真实功能验证、常浩验收分开报告；测试或合并不代表上线。安装同步与发布需要各自授权和目标环境回读，不能随合并顺手执行。
- 想看还有哪些单没收尾：`D list`。

## 失败信号

- `run` 返回 `ok: false` 且不是 `busy`：看 `stderr_tail` 和 `~/.hermes/dispatch/<单号>/out/stderr.log` 的最后几行，说明原因。同一张单最多重试一次。
- 护栏被触发（单的状态是 `guard`）：立刻报告，不重试，也不合并。

## 验收方式

常浩在飞书说“让 Claude 在 digital-twin 里改……”：你先开单、发待确认派单 → 他回“可以”（可能在话题里回） → 开跑 → 车间卡住时把问题转给他、他答复后续跑 → 开 PR、回报 PR 链接和改动 → 他说“合并”就合并（有没推的提交先问他）并清理，说“不要了”就清理。

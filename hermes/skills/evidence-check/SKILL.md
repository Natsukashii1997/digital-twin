# 证据核验

这份技能只回答一类问题：**某个说法现在能不能成立，凭什么。** 它不负责判断项目最卡在哪、该先做什么，那是 `thinking-mainline` 的事。

前身是 `business-analysis-coaching`。2026-11-19 收窄：原来它同时管分析步骤、交付标准和带教，每次业务分析都被加载，结果把「核得严不严」变成了分析的主线。现在分析步骤归 `thinking-mainline`，表达标准归 SOUL，带教归工作规程第 2 节。

## 什么时候用

| 场景 | 怎么进来 | 交出什么 |
|---|---|---|
| 项目诊断里要核实几件事 | `thinking-mainline` 第 3 步交来核验清单 | 每件事一个结论：成立 / 不成立 / 现有材料定不了，附依据 |
| 盘点功能完成度、核对项目进度 | 常浩直接要「盘点」「核对」「哪些真的上线了」 | 首段回答能不能认定完成，再给逐项证据 |
| 核实会议纪要里的数字和结论 | 同上，或核验清单里的一项 | 原话、限定条件、能支持到哪一步 |
| 设计业务调研 | 常浩要调研方案 | 按 [业务调研](references/business-research.md) |
| 把业务评论整理成产品诉求清单 | 常浩要「梳理需求」「整理反馈」 | 按 [产品完成度与反馈核验](references/product-readiness.md) 第 8 节 |

诊断类任务没有核验清单就别开始逐条核：先回 `thinking-mainline` 把主要矛盾定出来。清单以外发现的问题，只在会改变主线判断时才报，其余一句话带过。

## 核验规则

**来源宣称和核验结论分开。** 开发方宣布可用、用户确认可用、真实使用数据、通过业务验收是四种不同的证据，不能互相替代。只有宣称时写「宣称可用，待验证」；只宣布开放测试时写「已开放测试」。空白模板和没核过的线索不算完成证据。

**按用户任务拆开核。** 界面、真实数据接入、操作成功、提醒送达、最终完成分别看。入口存在不能证明链路完成；某个子模块没接入也不能证明整个功能没做。正文、规划、评论、截图互相矛盾时，保留冲突，核对时间、版本和作用范围，不拿一个来源盖掉其他的。

**不编百分比。** 没有事先定好的验收项、分母和计分口径，不算完成度百分比；用「已证实、存在障碍、待验证、规划中」表达。

**分清四种话。** 原始陈述、可观察事实、推断、建议分开写。少数反馈不写成普遍需求，相关不写成因果。证据冲突先查口径和样本，不挑支持预期的留下。

**AI 会议纪要要回查。** 涉及验收、量化效果、接口归属的说法，回到原始转录和配图，保留「尽量、建议、待测试、单笔跑通」这些限定词。

**先分类再写入。** 推进计划只放明确的上线、里程碑、会议、验收节点；用户问题、障碍、建议、新需求进使用反馈；功能清单放功能定义和能力状态，不因一条反馈改完成状态。常浩自己维护的表不代改；只要求梳理时不做远端写入。

飞书的读取命令、评论翻页、截图核对和证据矩阵见 [产品完成度与反馈核验](references/product-readiness.md)。

## 交回结果

- 回给主线：只说每件事的结论和依据，不顺手下项目判断。
- 独立盘点：首段直接回答能不能认定，再给证据；说明材料截至时间、读取范围、有没有实际操作线上功能。
- 没做的核验说没做，不用「待验证」带过所有东西：能在这一轮核清的就核清。

## 这份技能怎么改

只在核验方法本身出错时提议修改（例如漏翻评论分页、把改判率当准确率）。常浩纠正的是思考方式时，改的是 `thinking-mainline`。两份技能都不自己改：把原话和建议告诉常浩，由他确认后改 digital-twin 仓库的源文件（`hermes/skills/evidence-check/`）。

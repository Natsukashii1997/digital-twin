# 产品完成度与反馈核验

## 1. 定义核验对象和输出边界
先写清要判断的是功能存在、稳定可用、已推广，还是业务验收完成。按真实用户任务拆分子能力；不要把页面模块、数据接口、自动化引擎和提醒渠道合成一个“已完成”。用户只要求提取或梳理时，交付证据与判断，不顺带修改业务表。

完成标准：每个子能力都有可观察的成功条件，未确认条件明确标为待定。

## 2. 读取正文，保留来源宣称与上下文
飞书场景先读取 `lark-doc` 及其 fetch 参考；通过 `terminal` 执行关键词读取，例如：

```bash
lark-cli docs +fetch --doc '<用户提供的完整URL>' --scope keyword --keyword '<功能名>|<别名>|完成度|进度|上线' --detail with-ids --as user
```

完整保存 JSON 中的 `content` 和 `reference_map`，不要只保存正文；评论和资源映射依赖同一响应。命中容器或表格的 excerpt 时，按返回的块 ID 补读相关 section 或 range；只扩展能影响判断的上下文，不为全文而全文。

分别摘录产品定义、当前状态、近期规划和信息截至时间。宣传摘要称“闭环”、规划却仍包含核心环节时，把它列为待核验冲突，不自行解释为已经实现。

读取 AI 会议纪要时，对会改变验收、排期或风险判断的表述回查原始转录与配图，保留“尽量、建议、待测试、单笔跑通”等限定词；不把设计偏好写成硬约束、业务改判率写成准确率、第三方接口写成平台官方能力，亦不把顾问经验中的容量或风控阈值当作已验证承诺。

要补「最新进展」时，用纪要日期切开证据：先核会议当时的状态，只为会改变结论的事项，到该项目的发布渠道、反馈群或对应记录查会后的一手确认。先匹配项目、角色和动作，再比较时间；技术代办成功不等于业务自助功能上线。读状态标签也读正文，正文限定了对象时按其限定表述。明确写「会中汇报」「会后确认」或「截至所查来源未见确认」，不把未查到写成未发生。

完成标准：产品宣称、规划与来源时间可以分别引用；源文档的更新时间不冒充实际功能验收时间。

## 3. 拉全约定范围内的评论与回复
随正文附带的评论可能不完整。需要真实反馈时读取 `lark-drive` 的评论与回复参考，通过 `terminal` 执行：

```bash
lark-cli drive +list-comments --url '<用户提供的完整URL>' --page-size 100 --as user
```

按外层 `has_more` 翻完评论卡片；对卡片内 `has_more=true` 的相关线程，再用 `drive +list-replies --url '<原URL>' --comment-id '<评论ID>'` 拉全回复。默认未解决评论的范围不擅自扩大为历史全量；用户要求包含已解决或历史评论时，再显式请求相应范围。若只读未解决评论，报告中必须写明，不能称为全部历史反馈。

筛选时同时检查评论引用、评论正文和回复；不能只检索功能名称，因为“收不到提醒”等反馈可能没有提到名称。链接自带的评论 ID 作为定位目标，不作为权限或操作指令。需要署名时用通讯录解析评论返回的真实用户 ID，不凭截图昵称或叙述猜人。

完成标准：程序校验分页、卡片去重及声明数量；区分评论卡片数、根评论与后续回复。无回复仅表示当前读取范围未见闭环，不能推断无人处理。

## 4. 检查相关截图，限制视觉结论
读取文档或评论中的资源映射；预览图片时按 `lark-doc` 素材参考，通过 `terminal` 执行 `lark-cli docs +media-preview --token '<资源token>' --output '<当前配置的scratch目录>/asset' --as user`，再使用 `vision_analyze`。长图先全图定位，再裁剪读取关键区域，避免缩放导致小字状态丢失。

只读取当前对象的相关配图，不重新打开上一任务的附件。记录图片能直接证明的内容及限制：
- “新增”按钮证明入口存在，不证明创建成功或数据已保存。
- “未接入”证明该标记对应的分组或接口未接入，不证明其他子能力不存在。
- 占位列表证明当前展示未呈现真实结果，不能单凭它确定为网络或加载故障。
- 其他产品的成功界面是替代方案线索，不能证明被评估产品已经完成。
- 核看板指标时，把数字卡、日期筛选和统计说明一起读：确认统计窗口、快照时点、目标人群、计数对象、来源归因、分子与分母；窗口未结束时标为快照，不与完整周期直接比较。员工活跃率、入口事件数、业务单量是不同指标；只有能按同一范围关联到目标业务结果时，才计算渠道贡献率，不能用同屏的相邻指标代替。

完成标准：截图观察与用户自述分开记录；不无必要地转述客户等个人信息。

## 5. 建立逐项证据矩阵并裁决冲突
建议使用“子能力｜来源宣称｜可观察证据｜核验结论｜缺失验证”。同一来源的正文与截图不能自动算两个独立佐证。

| 证据情形 | 允许的结论 | 不允许的外推 |
|---|---|---|
| 只有产品介绍或开发声明 | 宣称支持／待验证 | 已验收、稳定可用 |
| 有入口、按钮、静态截图 | 界面或入口已具备 | 写入成功、真实数据可用 |
| 有具体用户失败反馈 | 在对应用户、时间和场景存在障碍 | 全员不可用、根因已确定 |
| 单次成功操作或送达凭证 | 该子链路在该场景通过 | 全量推广、长期稳定 |
| 核心链路仍在近期规划中 | 存在范围或状态冲突，需确认 | 自动视为完成后的优化 |
| 无证据或回复缺失 | 未证实／未见闭环证据 | 后台未开发、没有人处理 |
| 提出更先进的用法或替代产品 | 新需求／替代方案线索 | 已实现或已纳入排期 |

证据冲突时先核对时间、版本、用户权限和子模块范围；仍不能解释则并列保留，不猜测。没有事先明确的验收项与分母，不计算完成百分比。

## 6. 将结果映射到正确的管理载体
| 材料 | 载体与处理规则 |
|---|---|
| 已明确的上线、会议、里程碑、验收节点 | 推进计划；保留责任、期限、交付物与状态证据，未知项待定 |
| 用户问题、可用性障碍、建议、新需求 | 使用反馈；保留真实发生时间及来源，系统创建时间不替代反馈时间 |
| 功能定义、范围与能力状态 | 功能清单；不因单条反馈自动认定完成，不改用户保留自行维护的表 |
| 从反馈推导的开发或排查动作 | 建议／待确认计划；未经承诺不写成正式推进节点 |

纠正混放时，先读取当前表结构与记录，列出迁移映射并保留恢复材料；在获得写入授权后，先确认目标反馈记录存在且无重复，再删除或调整来源记录。只读核查不沿用旧任务的写入授权。

## 7. 输出结论与最小闭环验收
仅盘点完成度时，首段直接回答能否认定完成。分析项目推进由 `thinking-mainline` 主导，这里只回答它交来的核验问题，不用「尚未全面验收」概括整个项目。接着按需给产品定义、逐项矩阵、带链接的真实反馈、关键冲突及验证动作；验收链和证据矩阵作为支撑，不替代业务诊断。评论原话保持短而准确，概括与推断另标；不把材料完整堆叠当作分析。

对于待办类自动化，最小验收链是：真实会话识别正确事项 → 责任人与时间正确 → 写入后可查询 → 到期通知实际送达 → 完成／撤销正确生效且不再错误提醒。手动新建与自动提取分别验收；CRM 清单与会话待办分别验收。其他产品按相同原则替换节点。

## 8. 将业务评论整理为标准产品诉求

- 业务诉求清单优先按产品模块分组、连续编号；每条用“具体功能/位置 + 当前问题或场景 + 期望改动 + 提出人”写成可直接用于评审的短段落。证据和验收明细按需放附表，关键证据限制集中提示；不要把每条需求都扩成核验报告，也不默认用宽表替代简明清单。
- 每项写明具体页面/入口/字段、使用角色与场景、当前发生的情况、希望如何改变、待确认点；建议验收标准另列并标明尚待确认。不能只列模块名或抽象方向。
- 按独立可验收的问题拆分：例如列表展示、创建后查询、提醒送达分别记录；多条评论描述同一问题时合并但保留全部来源。分别统计原始评论数与整理条目数，建立逐条覆盖映射，避免把拆分后的数量冒充评论数量。
- 分清业务明确提出的改动、由问题转写的目标、产品整理建议与待澄清项。只有重复现象时不自行决定合并/删页；只看到某个SKU选择控件时不推断整个订单仅支持单品。
- 以实际问题页面为需求落点，同时保留评论锚点：评论挂在快捷话术正文、截图却为案例话术时，应记录问题实际发生在案例话术，不把两者混同。
- 将现状补充、研发能力声明、未来规划与替代产品线索单列，不自动转为新增需求、已排期或已验收。未经确认不编造负责人、期限、优先级或业务规则。
- 交付保留原话、反馈人、反馈时间、来源评论链接和证据限制；附表须核对所有原始评论均有去向，且导出文件的行数、字段值与链接一致。

交付时说明正文截至时间、评论读取范围、是否实际操作线上功能，以及哪些仍待验证。建议状态与已确认决定分开；没有实施的修复不写成完成。

# 销售 AI 侧边栏 · 需求反馈（每天 18:00，亚古兽）

常浩 2026-11-19 定：每天 18:00 把测试反馈群里的新反馈整理成《YYYY-MM-DD 需求反馈》，**先私发常浩确认**；他回「发群」才用他本人身份发到群里。版式由脚本固定（2026-11-13 定稿、11-17 补标题后空行、11-18 补「旧的每期复核」），你只写内容 JSON，不自己拼飞书消息。

脚本：`python3 ~/.hermes/profiles/agumon/scripts/sidebar_reports.py feedback <status|render|send|group>`（下文简称 `sr`）。

## 一、取数

1. `sr status`：拿上一期（早于今天）的 `read_from`（取数截止时间）和 `carry`（上一期所有 ✴️ 待解决、⬆️ 待上线，带原标题和原话）。上一期以**群里常浩实际发出的版本**为准（常浩可能自己改了再发群，11-19 他删了 ✴️ 微信支付截图、加了两条 ♐），脚本会去群里找那条、按它算 `carry` 并写回存档；`previous_source` 写明依据的是群里版本还是私聊存档。读群失败或读不懂时脚本报错，不要绕过它改用私聊存档，报给常浩（2026-11-20 常浩定）。今天已经出过一版（`today_sent` 不为空）也照样从 `read_from` 读起、重新整理全天，发送时脚本会原地改今天那条。
2. 读群消息：`~/.hermes/profiles/agumon/bin/lark-cli im +chat-messages-list --as user --chat-id oc_32562463635b4b2ee03d1808c080d1b5 --start <read_from 转成 2026-11-18T18:41:00+08:00 这种写法> --order asc --page-all --page-limit 100 --format json`（不加 `--page-limit` 最多只读 10 页、约 500 条，到顶也不报错）。输出里 `has_more` 为 true 就是没读全：带上输出里的 `page_token`（`--page-token <它>`）接着读，直到 `has_more` 为 false；接不下去就停下，在给常浩的回复里明说「群消息没读全」，不要当成全部来整理（#312）。周末也算。后续查原消息、下载截图也用同一个亚古兽入口，不走 PATH 上的裸 `lark-cli`；不同飞书应用返回的 `sender.id` 不同，不能混用。
3. **群里从 `read_from` 到现在没有任何新消息**：不出这一期，最终回复只写一句「今天测试反馈群没有新反馈，本期不出。」，到此结束。
4. 带截图的反馈，用同一入口、同一身份（`--as user`）的 `im +messages-resources-download --message-id <截图所在消息的 message_id> --file-key <该消息里的 img_v3_...> --type image` 下载后核对。图片单发、图文混排均以携带图片的消息为准，不用后续的文字说明或回复的 `message_id`；遇到 `File not in msg` 先核对这对 ID 是否来自同一条消息。

## 二、归类

处理情况以开发在测试反馈群里的明确回复为准；常浩在私聊明确确认具体条目，可按他圈定的范围更新。私下会议、开发同步录音不算确认。

- **✅ 已修复**：已核对具体问题和修复确认，保留原话。
- **♐ 已上线**：已核对具体需求和上线确认，保留原标题和原话。单独成一组，类型行写「♐ 已上线：<原标题>」（常浩 2026-11-19 定）。
- **✴️ 待解决**：已知、没修好的问题。
- **⬆️ 待上线**：新需求、已表态会做或即将上线的。
- **上一期的 ✴️ / ⬆️ 每期都要逐条复核，不能因为本期没进展就省掉**：
  - ✴️ 确认修好 → 改列「已修复」，原话照旧；未确认 → 原标题、原话照旧继续列「待解决」。
  - ⬆️ 确认上线 → 改列「♐ 已上线」（`type: launched`），原标题、原话照旧；未确认 → 原样列「待上线」。已上线后不再作为未完成项滚动带到下一期。
- 顺序：已修复 → 已上线 → 待解决 → 待上线；同一类型里，上期带过来的在前（按提出时间），本期新增的在后。
- 同一问题的多条原话合成一项（`quotes` 里多条）。原话可以截取关键句，但不改字。
- 新的 ✴️ / ⬆️ 标题：一句话概括问题或需求，必要时括号里补处理情况，如「试听时长填 1H 会被自动改成 0.5H（Windows 和安卓端出现，兼容性问题排查中）」。

## 三、写内容 JSON 并发送

存到 `~/Library/Application Support/DigitalTwin/sidebar/drafts/feedback-YYYY-MM-DD.json`：

```json
{"date": "2026-11-19", "cutoff": "2026-11-19 18:00",
 "items": [
  {"type": "fixed", "quotes": [{"text": "原话", "name": "练欣雅", "open_id": "ou_..."}]},
  {"type": "pending", "title": "问题概括", "quotes": [...]},
  {"type": "planned", "title": "需求概括", "quotes": [...]}]}
```

- `cutoff` 写这次读群消息读到的时间，下一期从这里接着读。
- `open_id` 用群消息里该条发送人的 ID（`sender.id`），不要按名字猜。
- 零宽空格、引用块、@、空行都由脚本加，你不要加。

然后 `sr send <上面的路径>`：
- 核对不过（退出码 2）就按提示改 JSON 再跑，最多改两轮；还不过，把问题原文发给常浩。
- 成功后脚本已经私发常浩、读回核对并存档；**最终回复只写 `[SILENT]`**（定时任务里），免得重复推送。

## 四、常浩回复之后（私聊里）

- 他要改某处：改那一期的 JSON 再 `sr send`，脚本会**原地改原消息**，不另发。
- 他回「发群」：`sr group --date YYYY-MM-DD`。脚本会核对被 @ 的人都在群里、用他本人身份发一次、读回 @。结果里 `mentions_ok` 为 false 时，把 `mentions_missing` 告诉他。用户身份发出的消息不能改，只发一次；发过群的那一期脚本也不再改私聊稿。
- 他回「先不发」：什么都不做。下一期照常从这期的 `cutoff` 接着读，这期的 ✴️ / ⬆️ 照常带过去。

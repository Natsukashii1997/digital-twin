# 拍板请求：要不要问常浩、怎么问、回了怎么办

用在：手上有个动作，拿不准能不能自己做；或者已经知道要常浩定，要把问题写给他。
依据：《常设授权清单》（个人项目根目录 `docs/常设授权清单.md`，下文简称「清单」）、`docs/技能架构.md` 第 9 节 5b-2。**清单和这里说法不一致时以清单为准**；清单只有常浩能改。

## 1. 先判断：要不要问

按顺序走，走到哪一步有结论就停：

1. **这个动作在清单哪一档？** 对着清单第 2 节的表找。拿不准在哪一档，按 D 档。
   - **A 档**（自主做，日报里报）：直接做，不问。做完按清单第 3 节留痕。
   - **B 档**（本人点一下就做）：看他是不是已经对**这一件、这个版本**点过卡片或说过那句话。点过就照办；没点过，把卡片发出去或等他点，不替他点。
   - **C 档**（单次授权文件）：找到授权文件，核对它写没写到这个对象、这个动作，过没过期、有没有超上限。都对才做；文件没写到的照 D 档。
   - **D 档**（必须问本人）：每次都问，上一次的回答不算这一次。
2. **已经定过了吗？** 先查项目的 `docs/DECIDED.md`、`CURRENT.md` 和这件事原来的记录。他定过的就照定的办，**不拿已经定了的事再问一遍**。要改他定过的东西，那是另一个问题：说清原来怎么定的、为什么要改、改的代价，请他选改 / 不改 / 换个改法。
3. **真的要他定吗？** 下面几种不用问，自己按规矩办，回报里说一句：
   - 只读的查、看、核对、整理；
   - 清单 A 档的事；
   - 有唯一合理做法、不涉及取舍的小事（例如把明显的错别字改对）。
   
   要他定的是：D 档动作；几种做法各有代价、要他取舍；会改他定过的东西；花钱、对外发言、撤不回的动作。

**普通对话里的「可以」「继续」「行」不是授权凭证。** 它只回答你刚刚问他的那一个问题；你没问过的事、问的范围以外的事，都不因为这句话变成可以做。新底座的写入派单只认门卫「卫士」确认卡上的点击，私聊打字一律不算批准。

## 2. 要问时怎么写

### 规则

- **一次最多问三件事。** 再多就分批，先问最卡进度的。
- **每件事都给推荐，推荐放在第一个选项。** 说一句为什么推荐它。
- **大白话。** 不用内部编号、字段名、脚本名打头；非提不可的放在括号里。能用一个比方说清的就用比方。
- **说清不定会怎样**：这件事会停在哪、拖着有什么代价，或者「不定也不影响别的，可以先放着」。
- **选项互相排斥**，挑一个就能执行。不出「都行」「看情况」这种选项。
- **问得出口的才问**：自己能查到的事实先查好写进去，不让他替你查。
- **写清他怎么回**：回哪几个字、点哪个按钮。

### 模板

```
【要你定】<一句话说是什么事>（<项目 / 原任务号>）
背景：<一两句：现在到哪了，为什么停在这>
要定的：<一个问题>
  ① <推荐的做法>（推荐：<一句理由>）
  ② <另一种做法>：<它的代价>
  ③ 先不做 / 先放着：<会怎样>
不定的话：<会停在哪、拖着有什么影响>
回「①」「②」「③」就行。
```

两三件事一起问，就把上面的块编号排下去，最后写一句「可以一条消息回，比如『1 选①，2 选③』」。

## 3. 从哪发

| 什么事 | 从哪发 | 他怎么回 |
|---|---|---|
| 一般的拍板 | 猛鬼兽私聊里直接发文字 | 私聊回话 |
| 日报卡片「需要你拍板」里的事 | 日报卡片（`pdaily-act` 技能办理） | 点卡片按钮，或引用卡片回「① 按推荐」等 |
| 新底座的写入派单（D 档） | 只能用 `autoloop` 技能递提议，由门卫「卫士」发确认卡；你不发卡、不经手批准 | 只在卫士的确认卡上点「批准派单」 |
| 旧车间的写入派单 | `workshop` 技能第 2 节的「📝 待确认派单」 | 回「可以」只批这一张单 |
| 合并 PR | 合并官的卡片（`merge-officer` 技能） | 点卡片「合并」，或引用卡片回 |

已经有现成通道的，就用现成通道，不另起一套问法。

## 4. 他回了之后

1. **先认准回的是哪一问。** 引用了你那条消息，或者紧跟在你那一问后面、内容对得上，才算回答这一问。认不准就再问一句，不猜。
2. **把回答带回原任务。** 写下：原任务号（派单号、PR 号、账本编号、日报拍板编号）、他这条消息的消息号、他的原话、你怎么理解的。记到原任务自己的记录里：
   - 日报拍板 → `pdaily_act.py record`、`pdaily_act.py done`（按 `pdaily-act` 技能）；
   - 旧车间派单 → 那张单的任务说明里补一句；
   - 账本里的事 → 等账本有了处置记录入口（批 5b-4 的前置）就记到那里；之前写进回执，说清原任务号。
3. **只按回答的范围做。** 他选了①，就只做①写的那件事；他批了第 1 条，第 2、3 条照样等着。回答只管这一次，下次同类的事照样要问（除非他明说「以后这类都这样」，那是改规则，要另记、另确认）。
4. **含糊的回复不当高风险授权。** 回的是「嗯」「好的」「看着办」，而要做的是 D 档或撤不回的事：不做，复述一遍你理解的动作，请他明确回一次。
5. **回报说真实层级。** 分清「已记下」「已提议」「已批准」「已派出」「已执行」「已核实」。拿到的是派单建议，不说成已派单；递了提议，不说成已批准；工人还没跑，不说成已执行。
6. **留痕**：按清单第 3 节记做了什么、对象、哪一档、来源（消息号或卡片版本）、结果、回读结论；他拒绝的也记。

## 5. 三个例子

**例一：在授权范围内，不打扰他。** 他问「digital-twin 那个 PR CI 为什么挂了」。看日志、查原因、写清楚是只读的事，A 档。直接查完回答，不发拍板请求，也不先问「要不要我查一下」。

**例二：超出授权，停下这个动作再问。** 查完发现要改 `hermes/scripts/` 下的脚本才能修好。改仓库文件要派写入单，D 档，不能因为他问了原因就直接动手。写：

```
【要你定】digital-twin 的 CI 失败要不要现在派单修（PR #NNN）
背景：失败原因是 xx 测试在 3.9 上用了 3.10 的写法，改一行就能过。
要定的：
  ① 派一张写入单给 Claude，只改这一处、做到更新 PR（推荐：改动小，原因已查清）
  ② 先不修，等这个 PR 的作者会话自己处理：可能要多等半天
不定的话：这个 PR 一直合不了，后面排着的 2 个 PR 也跟着等。
回「①」或「②」。
```

他回「①」之后，用 `autoloop` 技能递提议；**真正的批准是他在卫士卡上点**，私聊这句「①」只说明他要你去递提议。

**例三：复杂的主观取舍，给推荐和依据，由他定。** 两种做法各有道理（例如日报要不要多加一个板块）：把两种做法各自的好处、代价说清，给出推荐和一句依据（引他以前定过的偏好或决定，写出处），最后由他选。不替他定，也不因为他没回就按推荐做。

## 6. 常见错误

- 把 A 档的事拿去问他（问多了，他就不看了）。
- 一次问五六件，或者只列选项不给推荐。
- 把已经定了的事再问一遍。
- 用「可以吗？」一句话包住好几个动作，他回「可以」就全做了。
- 他问了进度，就当成授权继续改代码。
- 他没回，就当默认同意。

## 1. 职责边界（谁说了算）

| 事实 | 唯一裁定方 | 调度器怎么用 |
|---|---|---|
| Goal / Task、授权、依赖、阻塞类型 | B1 状态库 `twin_state.Store` | 只读；不改授权、不解 decision 阻塞 |
| 调度预留 | 同一个状态库的 v3 表 `sched_claims` | 调度器唯一写入的新事实；不另建库 |
| 工单与执行结果 | 派单台账 `~/.hermes/dispatch/<单号>/order.json` + `out/receipt.json` | 只读；调度器**从不写台账**，结果靠 `sync_orders / reconcile` 同步 |
| 车间进程身份 | `order.json`（dispatch 自己的 pid / 主机 / 开跑时刻）、`out/worker.json`（车间自己写） | 只读核对 |
| 验收 | `accept_task`（非执行方、带证据）→ `complete_task` | 调度器不碰；Run 跑完只到 `review` |

## 2. 状态与责任图

```
候选（decide，纯函数）
  │ dispatch
  ▼
预留 claim_task ── BEGIN IMMEDIATE 里重读台账、重新 decide，仍是 dispatch 才插 sched_claims(claimed)
  │                 拒绝 → 什么都不写（claim_open / slot_full_* / …）
  ▼
开单 DispatchExecutor ── 子进程 dispatch.py new --sched-key K；Popen 后立即把子进程身份记进预留 owner.child
  │                       dispatch 在派单锁里编号 + 建目录 + 写 sched_key 文件，之后建 worktree / issue、写 order.json(new)
  ▼
按键核对 reconcile_claim(settled=True) ── 派单锁里按 sched_key 扫台账（以台账为准，不信开单输出）
  │   恰好一张活动单 → claim_ordered + claim_link（start_run 或 link 通知已导入的 Run）→ linked，任务 running
  │   一张都没有 → released（开单失败）    多张 / 半截 / 非活动 → unsafe
  ▼
（确认门）常浩确认后 Hermes 照旧 dispatch.py run <单号> ── 调度器不开跑
  ▼
worker 执行 ── 自成进程组；一启动写 out/worker.json
  ▼
回执 receipt.json → dispatch 写 done / failed / guard → sync_orders → Run 结果 → 任务 review / blocked
  ▼
review ── 非执行方 accept_task（带证据）→ complete_task；B3 再验证审查方独立性
```

异常路径：

| 位置 | 情形 | 去向 |
|---|---|---|
| 预留前 | 调度器崩溃 | 什么都没写，下一轮照常决策 |
| 预留后、开单前 / 开单中 | 调度器或开单子进程崩溃 | 预留留着（占任务和名额）；`recover` 见第 5 节 |
| 开单后、关联前 | 调度器被杀 | `recover` 按关联键找到单 → 关联 |
| 关联后 | 任意崩溃 | Run 已是当前 Run，“一任务一活动 Run”阻止重派 |
| 开跑后 | dispatch 被杀、车间还活 | 生命体征 `alive`；车间退出后 `finished`（台账停在 running，报错要人工收尾） |
| 开跑后 | dispatch 和车间都没了、没回执 | `lost`：报错，不判失败、不重试 |
| 任意时刻 | 任务被常浩撤销 | Run 进 `cancel_pending`；见第 7 节 |

## 3. 调度预留

表（库 v3 追加迁移，v1 / v2 库打开即升级；只读打开不迁移）：

```
sched_claims(sched_key PK, task_id, project, state, owner(JSON: pid/host/started[/child]), order_no, run_id,
             lease_until, note, created_at, updated_at)
UNIQUE INDEX sched_claims_open ON (task_id) WHERE state IN ('claimed','ordered','unsafe')
```

状态：`claimed`（已预留未开单）→ `ordered`（知道单号）→ `linked`（Run 已关联）；`released`（开单失败，证明没开出单）、`void`（恢复证明没开出单且预留方已不在）、`unsafe`（归属证明不了，**只有常浩能收口**）。未结 = `claimed / ordered / unsafe`：占着任务（部分唯一索引兜底），也占并发名额。

两道闸：① `claim_task` 在写事务里复核（两个调度器排队，后来的看见先来的预留）；② 部分唯一索引（即使绕过复核也插不进第二个）。实测 4 个进程同时抢同一任务只有 1 个成功。

租约 `SCHED_LEASE` = 900 秒。**过期不自动释放**：只是恢复时允许判 `void` 的必要条件之一。

## 4. 并发与锁

- 名额 = 未结预留 + 已关联任务的活动 Run（new / queued / running）+ 台账里 running 的单，按单号去重；总 2、同项目 1（与 dispatch 一致）。别人手工开的 `new` 单不占（它们开跑时 dispatch 自己再拦）。
- 同一轮决策里先派的任务占名额，后面的给 `hold` 并写原因；顺序按任务创建先后，不自己重排。
- **派单锁** `<派单根目录>/.dispatch.lock`（`fcntl.flock`，进程退出自动释放，不会因崩溃残留）：
  - `dispatch new`：编号 + 建目录 + 写 sched_key 文件；
  - `dispatch run`：重读状态 + 并发检查 + 写 running（原来不加锁的预检查保留：排队时不碰续跑回执，行为不变）；
  - `reconcile_claim`：按键扫台账到关联完成。
- 锁只包小段：不包 git fetch、gh、车间执行；等锁上限 30 秒，等不到直接失败、不动作。
- **锁顺序固定：派单锁 → 状态库写事务，从不反向**。`claim_task` 持有状态库写事务时只读台账文件、不拿派单锁；dispatch 持锁时 `save()` 可能经通知进状态库，方向一致。因此不会死锁。

## 5. 崩溃窗口与补偿（不声称 exactly-once）

状态库与台账是两个事实系统，不能跨两者做原子提交。做法是**稳定关联键 + 对账收口**：调度器给每次开单一个 `sched_key`，dispatch 在编号的同一把锁里先把它写进单目录，之后才做慢操作。

`reconcile_claim` 的判定（在派单锁里做）：

| 台账按关联键找到 | 预留方 / 开单子进程 | 租约 | 结论 |
|---|---|---|---|
| 恰好一张活动单（new / queued / running） | 任意 | 任意 | 记单号并关联 → `linked` |
| 恰好一张但已是结果状态 | 任意 | 任意 | `unsafe`（要人工核对后再关联） |
| 多张单，或单 + 半截目录 | 任意 | 任意 | `unsafe` |
| 只有半截目录（有 sched_key 没有 order.json） | 有人还在，或租约未到 | | `wait` |
| 只有半截目录 | 都已退出 | 已过 | `unsafe`（开单中途中断） |
| 没有，但预留记过单号 | 任意 | 任意 | `unsafe` |
| 没有 | 有人身份对上（还在） | 任意 | `wait` |
| 没有 | 都已退出 | 未到 | `wait` |
| 没有 | 有人身份核对不了 | 已过 | `unsafe` |
| 没有 | 都确认已退出 | 已过 | `void`（任务可再派） |
| 没有（tick 里自己的开单子进程已退出） | — | — | `released` |

残余风险（写明不掩盖）：Popen 返回到记下子进程身份之间极短的窗口里调度器被杀，子进程身份没记上；靠租约 900 秒远长于 dispatch new 的正常耗时兜底。若 dispatch new 卡在锁前的 `git fetch` 超过租约，理论上可能出现“预留已 void、之后单又开出来”——此时那张单带着旧关联键，下一次按键核对会因“预留已不在未结状态”不再关联，会作为未关联的 Run 被对账导入（order.json 带着旧关联键，可人工识别），**不会被调度器关联成任务的第二张单**；但本批的报告不会专门提示这种“带关联键却没有对应未结预留”的单，列为已知缺口（交付报告第 6 节）。

## 6. 进程身份与生命体征

- dispatch 写 running 时记 `run_started / run_host / dispatch_pid`；持锁时不调 `ps`。核对：进程在、启动时间不晚于 `run_started` 才算对上（防 PID 复用）。
- 车间用 `start_new_session` 自成进程组；`run_worker.write_identity()` 一启动写 `out/worker.json`：`pid / pgid / sid / started（ps lstart）/ host / out / at`，原子替换。
- `check_identity`：`match`（pid 在、启动时间逐字相同、同主机）/ `gone`（不在、僵尸、启动时间对不上即 PID 复用）/ `unknown`（没记录、没记启动时间、别的主机、ps 失败）。`ps` 一律 `LC_ALL=C`，记录和核对逐字可比。
- 车间身份另要求：`worker.json` 的 `at` 不早于本轮 `run_started`（否则是上一轮的）、`out` 就是这张单的结果目录、进程命令行里带 `<单号>/out`。
- 生命体征（内部观察，不改 B1 Run 状态机）：

| 体征 | 条件 | 能自动做什么 |
|---|---|---|
| `alive` | 车间身份全对上 | 什么都不做；心跳再旧也不判停 |
| `finished` | 台账已有结果；或车间已退出且有本轮回执 | 对账结算；dispatch 已不在时报错要人工收尾台账 |
| `not_started` | 台账 new / queued | 无 |
| `lost` | 车间确认已不在、没有本轮回执 | **只报错**，不判失败、不重试、不杀 |
| `suspect` | 车间身份核对不了，但 dispatch 还在 | 报给常浩 |
| `unknown` | 没有可核对的证据 / 台账读不到 | 报给常浩，不下判断 |

跨会话 / 重启：所有判断只读状态库 + 台账 + 进程表，不依赖会话记忆；命令行 `plan / observe / recover / report` 新进程跑出同样结果（端到端场景 8）。

## 7. 取消闭环

- 来源只有 B1 `cancel_pending`（已撤销任务上仍活动的 Run；撤销已授权任务只有 `user` 能做）。
- 可能发信号的唯一情形：体征 `alive`，且车间是自己进程组和会话的头（`pid = pgid = sid`）。发前再核一次身份（防检查与动作之间换人），`os.killpg(pgid, SIGTERM)`，有界等待（默认 10 秒）后复核：停了 → `stopped`；没停 → `still_running`，**不升级 SIGKILL**，报给常浩。
- 车间被停后：dispatch（父进程，在另一个会话）收到 -15 写 `failed`；对账把 Run 记 failed，任务保持 `canceled`，记 `run.result_not_applied`。
- 取消与自然完成竞争：体征已 `finished` 就不发信号；迟到回执只结算 Run，不重开任务。
- **本批真实路径只出建议**（常浩 2026-10-29 定）：`cancel(send=True)` 只给隔离测试；派单根目录是 `~/.hermes/dispatch` 时直接 `NotAuthorized`；命令行 `cancel` 没有发信号的参数。身份不明、已退出、PID 复用、外来进程一律不发信号。

## 8. 重试与异常分级

- `failure_class`：`timeout`、`worker_failed`（非零退出 / worker_error）是已知可恢复；`lost`（过期）和回执不完整一律 `unknown`。
- 出 `retry_suggested` 的条件全部满足：blocked(technical)、没到上限、可恢复类别、台账确认那张单已结束、上一次不是同一种失败；带退避 `not_before = 上次结束 + 600 秒 × 2^已重试次数`。
- 其余：`retry_exhausted`、`retry_repeated`、`blocked_technical`（原因不明或进程没确认退出）——都要常浩定。decision / external / dependency 阻塞不走这里，从不出重试建议。
- 只建议不执行：正式环境不自动 `retry_task`。

## 9. 观测与低噪声报告

- `findings`：只收 `error`（unsafe 决策、lost、dispatch 已不在的残留 running）和 `needs_user`（blocked_decision、待验收、重试建议 / 到上限 / 重复、suspect / unknown 的在跑单、取消建议）。普通在跑、可派、等依赖不报。
- 去重：指纹 = `sha1(种类, 对象, 原因, 锚点)`，锚点是对象的 `updated_at` / 单号，状态变了才算新情况。已报记成状态库事件 `sched.report:<指纹>`，重启后仍有效。
- 送达语义：`report` 只挑没报过的、不标记；送达后 `ack` 才标记（至少一次）。命令行 `report --quiet` 没有新情况时**一个字节都不输出**，可直接接 Hermes 无模型定时任务（和 09:50 自检同一机制：stdout 直接发、空输出不发）。本批不建 cron。

为什么 worker 身份由 `run_worker.py` 自己写，而不是 dispatch 用 `Popen` 取 pid：dispatch 原来用 `subprocess.run` 同步跑车间，现有 dispatch 测试正是拦这个调用来替换车间；改成 `Popen` 会让原测试失去意义。让车间自己写身份，dispatch 只多一个 `start_new_session=True` 参数，原测试一行不改全部通过，且身份由被核对的进程本身给出，更可信。

## 11. 回退

- 代码：B2.2 是单个 PR；回退 = revert 该 squash 提交并重新安装四个脚本（见 [D6](B2.2-部署准备清单.md)）。
- 状态库：v3 是追加表；B2.1 程序遇到 v3 库会拒绝打开（“库版本 3 比程序支持的 2 新”，不会误改，已测）。要回退到 B2.1 程序，就恢复首次用 B2.2 打开前的备份；或保留 v3 库、只回退调度器以外的脚本。
- 台账：调度器从不写台账；dispatch 新增的 `.dispatch.lock`、`sched_key` 文件、`worker.json` 和 order.json 新字段对旧程序无害（台账扫描只看 `D*/order.json`，未知字段忽略）。

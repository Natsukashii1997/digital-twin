# 个人 AI 项目体系重构｜V1.2 综合复核与架构定稿建议

> 日期：2026-11-07  
> 用途：直接交给 Claude Code，作为更新项目规划、项目名册与后续实施任务的依据。  
> 复核范围：ChatGPT V1.0 深度规划报告、Claude V1.0 复核报告、ChatGPT V1.1 复核决策，以及用户本轮明确修订与 Obsidian 建仓截图。

## 0. 最重要的最终结论

本轮不再重做 11 月 7 日已经完成的全项目盘点，不再建立第二套项目名册，也不增加新的一体化总控平台。持续坚持：**项目与资产只有一个正式权威源；数码世界聚合展示、快速同频；能力项目沉淀复用；具体执行仍回到原项目。**

四项必须按本轮最新决策固定：

1. **知识库名称与状态纠正**：此前误写的“OpenStan”一律更正为 **Obsidian 知识库 / Obsidian 第二大脑**。用户提供的 Claude 执行截图显示：本地工程目录 `~/Documents/ChatGPT/个人/work/obsidian-kb`，GitHub 私有仓库 `Natsukashii1997/obsidian-kb`，首个提交 `89443ae`；项目名册 v1.4 的 PR #83 已合并到 `main`（截图显示合并提交 `23dcbb0`），**当前活跃项目 14 个，其中 13 个有 GitHub 仓库**。用户明确告知此项目已建仓并登记为活跃。**Vault 正文没有上传，仓库与 Vault 分治，必须保持。**上述提交、计数与测试通过为截图记录，不替代后续本机回读；不得退回“尚待建仓/尚待登记”状态。
2. **数码世界重新定性**：`digiworld` 是用户自己的**个人 AI 信息汇总与快速同频工作台**，核心任务是“快速知道我拥有什么、当前是什么状态、下一步该到哪里处理”，不是项目治理中心、Skill 编辑器，也不是多 Agent 执行引擎。它是**读多方真源的观察/发现界面**，同时允许经营自身确有所有权的 Prompt、普通规则类资产等轻量数据；不能简单说“全应用只读”。
3. **Skill 资产库定稿**：数码世界移除第三方/网上 Skill 的上传、收藏、编辑、版本管理等管理板块；**只保留自建 Skill 的只读展示面板**。自建 Skill 的创建、维护、评价、发布、迭代全部归 `my-skills`；数码世界展示有哪些、数量、用途、场景、已核实的使用次数、发布版本、迭代记录等。**既不能在数码世界修改 Skill，也不能在那里创建新的正式或非正式 Skill 分叉。**用户已亲自决定，Claude 先前列出的 D-2 不再是“待拍板项”。
4. **多 Agent 完整项目包含 Multica**：多 Agent 作为独立的可复用协同能力项目；Multica 是其中“执行编排与适配”组成，既非整个多 Agent 项目的同义词，也不因此吞并 Hermes/ORCA、驿窗或业务仓库。先定义模式与边界，再复用既有 Multica 实践，避免迁移真实项目的私有工作流。

**一句话总架构**：`digital-twin/projects.json` 是项目登记真源；`my-skills` 是自建 Skill 的唯一真源；`obsidian-kb` 是知识工程项目，Vault 是知识正文真源；多 Agent 项目管协同模式与 Multica 集成；UI 项目管设计体系；`digiworld` 是聚合的“观察与导航界面”；GitHub 中心是外部开源项目与第三方 Skill 线索的发现/收藏目标产品。

- **本轮新增 F-7**：Digiworld 的信息聚合/快速同频是正式的产品定位；Skill 展示是其资产仓库中的一项只读功能，不能升格为独立的 Skill 治理项目。

## 2. 整体架构：产品、能力、基础设施、横向规则

| 层级 | 核心职责 | 当前代表 | 不负责什么 |
|---|---|---|---|
| 产品 `product` | 向具体用户/场景持续提供独立体验与产出 | 个人 Digital Twin、驿窗、Digiworld、牛马之家、GitHub 中心、CarvoMOTO 等 | 不拥有全系统的共同方法和规则 |
| 能力 `capability` | 输出可跨项目复用的模式、规范、Skill、组件与评测方法 | 多 Agent 协同、UI 设计体系、My Skills | 不接管消费方项目的业务目标、代码和最终验收 |
| 基础设施 `infrastructure` | 提供多个项目依赖的知识、权限、工程运行约束与共同资源 | Obsidian 知识库 / Vault 体系、Agent Kit | 不替代产品界面，也不自动决定具体项目任务 |
| 横向治理（不强制另建项目类型） | 规则权威、证据追溯、权限、状态与效果数据 | Vault 的 P-xx、Agent Kit 的 G-xx、各项目 AGENTS、运行事件 | 不造新的可写副本 |

**分类标准不是“必须使用/可选使用”**。判断项目性质应看它对外输出什么、由谁维护版本、在哪个层面验收。`lab`/沙盒属于成熟度或存续状态，不应与 `product/capability/infrastructure` 并列当作性质。保留既有 `category`，可以给当前活跃项目逐步补 `type`，不要大量增加主名册字段。

### 2.1 业务与执行的主责

“单 Agent / 多 Agent”是运行组织方式，而不是所有项目的最高层分类。数字分身即使调用多个 Agent，任务主责仍在数字分身；同一个产品采用多 Agent 的成熟模式，不自动成为多 Agent 项目的子项目。

### 2.2 正式项目与内部子系统

Multica 不必单独占据与“多 Agent 协同”并列的项目主节点。它作为多 Agent 能力中的执行编排子系统登记在该项目说明或关联关系中；真实第三方源码、专用的 ORCA 任务、`dt-sandbox` 保持各自既有仓库/试验位置。**责任归属与文件物理搬迁是两件事。**

## 3. Digiworld：彻底清晰化“快速同频工作台”的产品定位

### 3.1 一句话使命

> 打开数码世界，在一个地方迅速看清“我有哪些项目、Agent、自己做的 Skill 和其他个人资产；它们目前是什么状态；我该去哪里查看或处理”，而不是在数码世界里重新管理每个项目与 Skill。

建议中文定位使用 **“个人 AI 全景工作台”或“个人 AI 信息驾驶舱”**；“数码世界”作为产品名保留。具体命名是建议而非新增决策。

### 3.2 三种权限与对象，不要混成“整站只读”

| 模块/对象 | Digiworld 的操作权 | 真正权威源 | 用户看到的内容 |
|---|---|---|---|
| **项目空间** | 只读、筛选、跳转、展示；只允许本地显示偏好 | `digital-twin/projects.json` + 对应仓库状态与 Vault 项目卡 | 项目数、类型、存续状态、最近进展、下步、入口 |
| **自建 Skill 展示** | **严格只读**；不创建、不上传、不复制可编辑分叉、不改 Skill 文本/元数据/版本 | `my-skills` 仓库、`links.tsv`、`evals`、`CHANGELOG`、可核实运行统计 | Skill 数量、名称、用途、适用场景、版本、使用/迭代历史、状态、来源链接 |
| **第三方 Skill** | **无管理板块**：不做手工上传、收藏、编辑、改版或版本管理 | 发现/收藏职责归 GitHub 中心目标产品；实际安装配置仍归 Agent 环境 | Digiworld 不再把第三方 Skill 当资产库存放 |
| **Prompt 资产** | 可继续正常上传、编辑、版本记录、归档（遵循现有产品能力） | 如果是 Digiworld 自己管理的 Prompt，真源就是 Digiworld | 原有 Prompt 资产管理体验保留 |
| **规则类资产** | 可继续正常上传、编辑、记录、更新**普通规则模板/规则草稿资产** | Digiworld 自己创建的轻量资产 | 模板与草稿管理保留，但须区别“已生效全局规则” |
| **已生效规则/偏好** | 只读引用、显示权威位置或按已授权流程跳转；不得以资产库副本静默覆盖 | Vault P-xx、Agent Kit G-xx、项目 AGENTS/README | 出处、版本/同步状态与导航 |
| **其他现有资产** | 保留既有有明确所有权的读写功能 | 逐类沿用原真源 | 不因 Skill 调整而一并删除 |
| **Agent 中心/上下文发现** | 继续作为信息入口；已存在的显式配置操作另按现有安全授权约束处理 | 各 Agent 自身真实配置/运行环境 | 展示状态与跳转，不把缓存宣称为实时真相 |

**这不是逻辑矛盾**：同一产品可以同时有“外部资产只读聚合”和“自身轻量资产可写管理”。判断能否写的唯一原则：**它是否被确认为 Digiworld 自己拥有的事实源**。不能因为界面有一个“编辑”按钮，就改变 `my-skills`、Vault、Agent Kit 或项目仓库的正式内容。

### 3.3 自建 Skill 展示面板的最小信息架构

建议先做以下字段，数据优先自动读取，**不要要求用户手填 Skill 的版本和使用情况**：

| 字段 | 来源或计算方式 | 重要约束 |
|---|---|---|
| `skill_id` / 名称 | `my-skills` 中的稳定目录/清单与元数据 | 不把目录名变动自动当作不同 Skill |
| 用途、适用场景、触发条件 | `SKILL.md` 中的正式说明，必要时提炼摘要 | 摘要需标明来源，不能替代原文 |
| 当前版本/发布状态 | 正式 metadata、CHANGELOG、release 规则 | 默认展示正式发布版本；候选或草稿另标清楚 |
| 使用次数与最近使用 | Claude hook、Codex 会话等可核实事件 | 区分自动采集/估算/未知，明确统计时段与覆盖源 |
| 迭代次数/迭代记录 | CHANGELOG、版本历史及有证据的变更记录 | **迭代不等于使用次数，也不等于 PR 返修轮次** |
| 评测情况 | `evals` 结果、版本对应的测试记录 | 不以“存在 evals 文件”冒充“当前版本测试通过” |
| 来源与跳转 | `my-skills` GitHub URL、适用的本机路径 | 展示端只能打开权威位置处理 |
| 最近同步与数据健康 | 同步时间、来源 commit/hash、抓取失败标识 | 不成功时展示上次可信快照并标注陈旧，不伪造“最新” |

首页可展示：“自建 Skill 总数”“正式发布数”“近 30 天有记录使用数”“最近迭代 Skill”“失去统计来源/版本过期项”，并一键跳转 `my-skills`。初期允许部分统计为“暂无数据”，不能为了好看制造完整指标。

建议明确 **Skill 展示是观察层的数据模型，不是另一份可编辑 Skill 数据库**。允许为性能保留索引、缓存和统计快照；缓存不能反向覆盖源仓库。

### 3.4 原功能的安全迁移（先备份、再下线）

现有 Digiworld README 显示，资产库曾有 Skill ZIP 导入导出、编辑、版本恢复、个人改版、目标副本关联等功能。因此不能只隐藏按钮或删页面了事。

1. **只读盘点**旧资产：自建正式版、外部/第三方 Skill、实验改版、孤立 Skill 草稿、目标副本映射、版本历史；形成名称、来源、唯一标识、哈希、去向与保留理由的清单。
2. **备份并防丢失**：将尚未并入 `my-skills` 的自建正式/实验内容保留为待核提案或离线归档；已有第三方收藏先保留可恢复备份。无用户授权不删除唯一副本。
3. **建立新的只读 Skill 索引**：从 `my-skills` 和已核实的运行事件读取。移除写 Skill API/按钮/任务，不止隐藏 UI；验证未留下后台 Skill 写入口。Prompt/普通规则资产的数据与 API 不受影响。
4. **GitHub 中心承接第三方“发现与收藏”**：当前 GitHub 中心 README 仍显示处于数据可行性验证，收藏、界面等尚未完整落地，因此**职责可以立即划走，数据迁移和删除必须等待 GitHub 中心对应收藏能力真正可用并通过验收**。GitHub 中心保存的是感兴趣的开源项目/Skill 项目线索，不自动等于已安装或可用的 Skill。
5. **验收后下线旧功能**：确认所有有价值内容已归档/迁移并回读，通过 UI 与后端权限测试，再停止第三方 Skill 的上传/收藏/编辑入口，清理遗留数据必须单独授权。

### 3.5 Digiworld 产品验收标准

打开首页时，用户能够在较少操作内回答：**“有哪些？”“现在怎样？”“去哪里处理？”**。项目与 Skill 的正式内容只能通过源项目改变；改变后可在 Digiworld 追踪到相应刷新或明确看到同步失败。Prompt/一般规则资产仍能够按现有路径编辑，且不会触发对正式工程规则的隐式修改。

**不要顺势重构全站**：项目空间、Agent 中心和知识连接已拥有既定范围；本轮先聚焦定位文档、Skill 读写边界、数据来源与必要迁移，其他模块有冲突再按单独 issue 处理。

## 4. 其余核心项目在新架构中的边界

### 4.1 My Skills —— 自建 Skill 生产与进化总控

- **拥有**：Skill 候选、立项、编写、evals、准入、发布、版本、CHANGELOG、统计接入、升级与退役决定；沿用已有“七站两闸”。
- **输出给 Digiworld**：公开/授权可读的自建 Skill 索引及可核实运行统计。
- **不拥有**：所有第三方 Skill 收藏；项目清单；完整 UI 设计标准；所有多 Agent 模式定义。
- **特别规定**：Digiworld 绝无反向 Skill 内容写入；若界面发现问题，应转为 `my-skills` 的 issue/待核反馈，而不是直接改 Skill。

### 4.2 GitHub 中心 —— 发现与收藏外部项目/Skill 线索

- **拥有**：外部 GitHub 项目的发现、比较、收藏、中文摘要等产品体验；其中包括感兴趣的 Skill 类开源项目。
- **不拥有**：自建 Skill 的正式内容与迭代；跨 Agent 的安装/权限治理。
- **落地现实**：收藏功能是否已实现必须以实际产品验收为准，不能仅因目标边界已定就宣称可替代旧系统。

### 4.3 多 Agent 协同 —— 模式总控 + Multica 子系统

- **模式层**：为什么协同、什么角色、如何交接、如何退出；区分思维评审、工程审查、独立测试、并行研究、自治委派等。
- **执行层**：Multica 的集成/适配、编排、状态、失败恢复与验证；具体引擎可替换，不让模式依赖单一厂商实现。
- **方法层**：执行用的 `thinking-review` 等正式 Skill 留在 `my-skills`，模式只引用它们。
- **交互层**：驿窗负责 UI、交接传输与会话回执；Digiworld 的接力包若存在，按其既定用途保留，避免制造第二套相同的接力协议。
- **具体任务主责**：数字分身（含已有 DT-ORC / ORCA）、其他工程产品各自保留业务决策和最终验收；`dt-sandbox` 等专用测试不因采用 Multica 就物理迁仓。
- **轻量模式契约**：模式 ID/版本/目标、触发与禁用、角色与责任人、输入与证据身份、交接与执行入口、成功标准、授权边界、停止与异常恢复，必要硬约束按风险继承。

### 4.4 UI 设计体系 —— 设计资产的总控，不是 Skill 二次仓库

- 初期完成设计原则、UI 风格/规范索引、Design Tokens 规划与验收标准；`ui-styles`、`excel-aura` 仍是 `my-skills` 的正式可执行 Skill。
- UI 项目负责说明这些设计规范在各场景怎样搭配、如何复用与如何验收；已有的内容权威位置不必立刻迁移。
- 两个真实产品出现相同组件需求后，再评估公共组件代码库；不要为了抽象而无端重建。

### 4.5 Obsidian 知识库 —— 已活跃的知识工程项目

- **工程仓库** `obsidian-kb`：项目计划、进展、交接、验证、维护脚本、协作骨架；使用 GitHub PR 和版本管理。
- **Vault 正文**：依既有安全约束留在本机；不能因为 GitHub 新建知识工程仓库，就把私人知识内容同步上传。
- **项目名册**：v1.4 按截图已经登记为活跃，项目卡指向 Vault 的“Obsidian 第二大脑改造”；不要建立第二个相同的知识项目。

## 8. 我对整体规划的最终建议

未来项目的完整增长闭环应是：

1. 产品产生真实工作场景，例如 Hermes 自治、驿窗接力、UI 页面、GitHub 发现。
2. 多 Agent、UI 体系与 My Skills 为这些场景提供可复用能力。
3. 各项目保留自己的目标、状态和权威内容，Obsidian 与 Agent Kit 分别提供知识和工程基础设施。
4. 真实使用形成可追溯的效果与问题反馈，有证据时再升级通用能力。
5. Digiworld 把这些分散但权威的状态**聚合成用户可以迅速理解和导航的单一视图**，而不成为第二套管理系统。

**最核心的架构取舍**：不是让 Digiworld 拥有更多数据的编辑权，而是让它能够**准确、及时、可追溯地呈现其他项目的实际状态**。这种产品定位既与项目空间的只读档案一致，也给 Prompt、规则模板等本地资产保留了合理的编辑空间。

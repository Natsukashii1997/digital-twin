冻结的五条总原则：
1. **唯一权威源**：项目、正式 Skill、正式规则、业务事实和执行日志各有自身真源；其他产品只做只读聚合、按权限引用或有限自有数据管理。
2. **产品负责结果，能力负责可复用方法，基础设施负责底层持续支撑**。实际归属以稳定职责、数据真源、控制权和可验证交付为判据，不用“是否经过 Hermes”作为总分类法。
3. **数码世界是个人 AI 体系的信息驾驶舱**，主要做展示、发现、追溯、快速同频；仅自有 Prompt、普通规则模板、工作流/设计素材、随手记等有限模块可写。
4. **现有项目名册是唯一项目登记真源**：`digital-twin/projects.json`。Digiworld 只读展示，不再建设第二个可编辑项目名册。
5. **先小批量切分、验证、可回退，再迁移或删除**：不因架构整理破坏旧运行链路、删掉唯一 ZIP/历史数据、上传私人 Vault、打断在途 PR 或重复执行已完成盘点。

## 2. 完整项目体系：正式分层及名册处理

### 2.1 分类

- `type=product`：对用户交付独立产品或业务结果。例如 `digital-twin`、`personal-ai-workbench`（digiworld）、`github-center`、`postpane`、`trainee-hub`、`carvomoto`、`chatgpt-clipper`、`disk-slim`、`little-steps`、`work-desk`。
- `type=capability`：提供跨项目可选复用的方法、模式或设计能力，如 `my-skills`、拟新建的 `multi-agent` 与 `ui-system`。
- `type=infrastructure`：提供持续的工程/知识/治理支撑，如 `agent-kit`、`obsidian-kb`、`get-index`。
- 现有 `category` 继续承担“活跃／只登记／沙盒／待删”等存续分类。**不要把 `lab` 和前三种性质混为同一枚举**；实验状态应归 `category` 或现有状态字段。

分类是治理主维度，不代表“基础设施一定强制使用，能力一定可以不用”。真正的分界是它提供何种长期职责和不变约束，且由唯一维护主体负责。

按 Claude 候选映射，当前 14 活跃项目加新建 2 个能力项目后，理论上应为 16 个活跃项目；实施时以变更前后名册的机器校验结果为准，不预先声称已经达到这一数量。

## 3. D-C 定案：Multica 的“应用归属”与“通用能力归属”分开

### 3.1 结论

采纳用户明确的判断基准：**当 Hermes 代替用户承担项目总控、规划和结果责任时，该条 Multica 调度链路的实施归数字分身。**

但不采纳“多 Agent 项目仅限不经过 Hermes 的自协同”的过窄定义。是否经过 Hermes 只是一次任务的控制结构，不是协同模式是否通用的分类依据；否则同一“Claude 开发—Codex 验证—GPT 审查”模式会因是否由 Hermes 启动而被人为拆成两套。

明确如下：

1. **数字分身 `digital-twin`**：负责 DT-ORC 方案、Hermes 控制面、run 授权、任务调度、业务状态、日志消费、汇报、合并授权和 Hermes→Multica 的具体适配代码。它交付的是“分身能否自治闭环”。
2. **多 Agent `multi-agent`**：负责可复用协同模式、角色协议、接力契约、独立验证和模式评测；模式既可由 Claude/Codex 自行启动，也可由 Hermes/其他主控调用。它交付的是“模式是否可靠、可移植和可复用”。
3. **Multica 软件／运行时**：视为当前采用的执行编排技术及外部依赖；不是把上游引擎、所有沙盒代码物理迁入 `multi-agent` 的理由。若未来出现真正跨两类独立消费方共用的适配器，再经证据升格为共享模块。
4. **PostPane（驿窗）**：负责用户界面、传信回执和会话导航，不拥有协同模式的权威定义。
5. **My Skills**：拥有 `thinking-review` 等可执行方法的正式代码与版本，多 Agent 只登记 `skill` 引用，不复制正文。
6. **Agent Kit**：拥有跨项目安全、权限和可追溯性的工程底线，不被模式契约覆盖。

### 3.2 现实进度和验收边界

- 已有证据：DT-ORC Multica M1 权限矩阵、M2 有人值守首跑六张子单通过。
- 尚无完整证据：Hermes 自主驱动 Multica 的 M3/M4 调度、授权和长期异常恢复闭环。
- 这两类能力分别验收，不互相冒充。

### 3.3 模式契约形式

普通模式契约保持轻量，8 项核心内容：**目标、适用/禁用条件、角色职责、输入与交接物、成功与停止条件、轮次/超时边界、证据来源、人工必须决定的事项**。工程模式按风险继承 agent-kit 的版本绑定、权限、重试/幂等、回滚等必要强约束，不是靠删字段降低要求。

起步先从现有 `thinking-review` 和实际工程接力记录各反推一份契约；不要先造五份未经实战的空模板。

## 7. R2 重要修正：my-skills 机器索引与发布状态不应混淆

### 7.1 索引权威

`my-skills` 生成唯一机器可读索引，例如 `catalog/skills.json`。推荐专用脚本 `scripts/export-skill-index.mjs`，由发布/校验流程触发；现有 `monthly-health.mjs` 可复用它，但不应让实时索引的生产依赖“每月体检”这个定时周期。

至少包含：
- 顶层：`schema_version`、`generated_at`、`source_repo`、`source_commit`、`skills[]`；
- 每项：稳定 `id`、名称、用途/适用场景摘要、版本（没有则 null）、CHANGELOG/evals 是否存在、在 `links.tsv` 中的目标声明、最近一次提交、来源路径、可追溯的来源提交；
- 可选状态：`release_status`（需要明确发布登记证据，不靠猜）、`metadata_completeness`（是否补齐元数据）、`install_status`（只有真实核对链接/目标文件才是已安装）。

**不得把“有 metadata.version + CHANGELOG + links.tsv”直接等同于“正式发布”**。这是元数据完整性检查的一个候选条件，不是正式发布事件或七站两闸验收证明。对存量 15 个 Skill，缺证据时标“未核定”，不要错误地标“未发布”。

建议先实现可核实的索引，不为了显示“正式发布”创造假事实。后续可以在 `my-skills` 内引入受版本控制的 release manifest / release record，再向 Digiworld 展示已确认状态。

### 7.2 统计来源

- Claude hook 自 2026-11-07 才开始观测：只能呈现观测窗口内记录。
- Codex 基于会话推断：必须标“推断来源”，不可和 hook 事件简单相加。
- Digiworld 近 30 天会话统计：可单独呈现“近 30 天观测值”，口径清楚即可。
- **历史累计使用次数未知**；某来源没有记录时显示“无可用数据”或“未观测到”，不能写“0 次历史使用”。
- **迭代次数**以 CHANGELOG／Git 历史中的有效发布变更定义，不以调用次数推算。

### 7.3 校验

`skills.json` 的每个 ID 唯一、schema 有版本、能识别缺字段、同一源提交生成结果确定、坏索引不会让界面展示为最新正常、不得暴露不必要的私密配置/绝对路径。

## 12. 每个 PR 的共同门禁

1. **范围门禁**：只触碰 Issue 内已批准文件和能力，不顺手做架构外重构。
2. **证据门禁**：写清当前 HEAD / 数据 revision / 数据来源；对旧事实和未核实内容显式标注。
3. **安全门禁**：Vault 正文不得误上传或外发、个人与企业域不得穿透、权限/凭证不得出现在可见日志。
4. **数据门禁**：有可恢复备份，尤其保护 Digiworld 5 个旧 Skill ZIP、Prompt/普通规则/工作流/设计数据。
5. **行为门禁**：下线写能力要有真实后端负向测试；只隐藏界面按钮不算通过。
6. **一致性门禁**：索引和只读展示要能追溯权威来源，不能产生第二个独立可写真源；异常显示“未知/过期”。
7. **回滚门禁**：回滚后不改变源仓库、Agent 配置和 Vault 事实。
8. **协作门禁**：同一个仓库存在活跃 PR/工作树时先核实锁定/合并顺序，不覆盖在途会话工作。

## 4. 三个决定

- **D-A Agent 功能的写操作**（待常浩确认）
  - **推荐**：全部下线，改为第 3 节的只读「Agent」页。
  - 理由：从未用过；与「信息中枢、少量可写」的定位一致；Agent 配置和正式指令文件由各 Agent 自己、agent-kit 或 Vault 维护；迁移功能写 `~/.codex/AGENTS.md` 会造出正式规则的第二份副本。
  - 备选：只下线写 Skill 和写指令文件两类，保留改模型、改配置。
- **D-B 逆向孵化的 Skill**（常浩已同意）
  - 改为生成 my-skills 候选（issue「候选：<名字>」加草稿包），进入七站第一站；数码世界不再保存这些 Skill。
- **D-C Multica 归属**（按常浩的基准判定）
  - **判定为第一种：Hermes 代替常浩当总控，所以 Multica 集成放在数字分身。** 依据是 DT-ORC V4.0：
    - 第 3 节：Hermes 不当 agent，从外面经 CLI 操作 Multica，负责建单、指派（消耗 `run_authorization`）、读 run、导出 run-log、写晨报，并担任合并官；常浩只负责定方向、授权、合并拍板。
    - 第 2.2 节：业务事实归 Hermes `twin_state`，执行事实归 Multica。
  - 需要标明的现实差距：M2 首跑实际是 **Claude 会话代为驱动**，常浩远程逐单批准；Hermes 接 Multica 的链路在 M3/M4 才做，目前还没跑通。如果以后不打算让 Hermes 真正当总控，这一判定要重开。
  - **多 Agent 项目的范围因此是不经 Hermes 的自协同**：
    - Claude ↔ ChatGPT 思维评审（thinking-review）与工程审查（经驿窗接力）；
    - Codex 复核与独立测试；
    - 子 agent 并行研究；
    - 并行会话各开 worktree 的规矩；
    - 以上各模式的契约。
  - 两边都会用到的协同模式（例如「工程审查走 ChatGPT High」「Codex 只做独立验证」），契约由多 Agent 项目定义，DT-ORC 引用，不在两处各写一份。

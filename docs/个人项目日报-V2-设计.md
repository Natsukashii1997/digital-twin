## 1. 定位

**猛鬼兽是常浩个人项目的代理人。** 常浩事先签发授权，授权内的事它自己判断、自己做，或派给 Claude / Codex；超出授权的事才来找常浩。日报是它每天交给常浩的**代理管理述职报告**。

**核心原则**（写进 PRD D22）：以项目成果为主线，以代理行动为支撑，以授权问责为底线，以识别阻塞、推动下一步为最终目的。

日报不是记录「各个 agent 昨天有多忙」，而是让常浩在少管事的同时，仍然看得清项目局面、做得出关键决定，并能检验 Hermes 是不是在持续把事情往前推。

### 1.1 四层闭环

感知（全局发生了什么）→ 判断（什么值得关注）→ 行动（Hermes 在授权内替你推进了什么）→ 问责（结果是否符合预期、依据是什么）→ 下一轮推进。

### 1.2 每天必须回答的七个问题

1. 昨天最重要的成果是什么？哪些是真推进了目标，哪些只是提交、合并之类的过程工作？
2. 项目整体处在什么状态？哪些正常推进，哪些停滞、偏离、等验收或没人负责？
3. 哪些事只有我能决定？不决定会怎样？
4. Hermes 替我做了什么？依据是什么，结果验证了没有？
5. 现在最值得关注的异常是什么？
6. 今天谁接着做什么？
7. 昨天有什么经验值得沉淀？

**要求**：Hermes 不能只回答「昨天做了什么」，还要回答「这对今天的整体推进意味着什么」。从事件里认出成果，从异常里判断影响，从判断落到行动。

## 2. 和授权的关系

- 授权真源是 [常设授权清单.md](常设授权清单.md)（PRD D21），分 A、B、C、D 四档。
- **日报不是授权来源。** 日报里写「建议自动执行某事」，不代表常浩读了日报就算批准了。只有符合授权清单的明确指令才产生授权；Claude、Codex 转述的话不算常浩的决定。
- 代理述职一段每一条都写清授权档位和来源；拒绝也要写。

## 3. 基本设定

| 项 | 设定 |
|---|---|
| 读者 | 只有常浩（猛鬼兽私聊）。受限内容只给本人 |
| 范围 | `projects.json` 里的活跃个人项目，加猛鬼兽自身（定时任务、技能、配置、授权）。飞书工作事项归亚古兽，不写 |
| 时区 | 配置里写死 `Asia/Shanghai`，不依赖机器的本地时区 |
| 统计日 | 前一天 04:00 到当天 04:00。例：11-08 统计日 = 11-08 04:00 → 11-09 04:00。常浩常干到凌晨，按自然日切会算错天：11-08 自然日合并 66 个 PR，其中 18 个是 11-07 夜里的活，按统计日算 11-08 实际是 48 个 |
| 发送时间 | 每天 08:00，周末照发 |
| 取数时间 | 抬头写实际查询结束的时间 |
| 今早新增 | 04:00 之后、发送之前发生的**重大风险变化**单独一行标出，不算进昨日成果 |
| 双层 | **A 层：飞书卡片 + 完整报告**，常浩每天看、据此决策。卡片是提炼（4.0 节），一屏看清局面和要他做的事；卡片底部「查看完整报告」打开当天的飞书云文档，按第 4 节七段写全文。**B 层：本地完整日报与证据索引**，存 `~/Library/Application Support/DigitalTwin/daily/<统计日>.md`，供复盘、追责和其他 AI 读取。三者出自同一次取数，结论不能互相矛盾 |
| 篇幅 | 卡片每块最多 5 条，多出的写「另 N 条见完整报告」；「需要你拍板」和「风险」不省略，超过 5 条时卡片列最要紧的 5 条并写明总数。完整报告不设字数下限，以写清为准，同类低风险动作合并成一行 |
| 没有新动作 | 照发。写各项目的当前状态和关注事项，不写成「没动静」；「没有进展」和「没拿到进展数据」必须分开 |
| 留痕 | 卡片底部灰字一行、完整报告抬头，都写生成方、实际用的模型、接入方式、统计日、取数时间（P-13） |

## 4. A 层结构（飞书卡片 + 完整报告）

### 4.0 飞书卡片（甲版·仪表盘，常浩 11-09 选定）

一张卡片，猛鬼兽私聊发出，卡片 JSON 2.0，**用飞书默认宽度，不设 `width_mode: fill`**（铺满整个聊天区太宽，常浩 11-09 实测后定）。从上到下：

| 块 | 内容 | 规则 |
|---|---|---|
| 标题 | 「📅 猛鬼兽日报 · 11-08（周日）」，副标题写统计日窗口 | 有项目没读到时，副标题写「N 个项目未读到」 |
| 📈 核心数据速览 | 表格三列：指标｜昨日｜说明。固定五行：有推进的项目（N / 名册总数）、合并 PR、待你拍板（有限时写最晚时间，数字标红）、风险 / 阻塞（按项目去重，说明里分类）、Hermes 代理动作（说明里分类） | 取不到的写「未知」，不写 0 |
| 🎯 需要你拍板 | 每条一行：［类型］项目·事项：推荐做法；最晚时间（有证据才写）；回「……」 | 按阻断、限时、普通排；没有就写「今天没有要你拍板的事」 |
| ✅ 昨日关键成果 | 每条一行：项目：完成了什么，达到什么状态 | 只放 4.3 的一级、二级成果；没有就写「昨天没有新成果」，并说明是没进展还是没拿到数据 |
| ⚠️ 风险与阻塞 | 每条一行：等级图标、类型｜项目：一句话 | 按严重度排 |
| 💡 今日推进 | 每条一行：优先级、事项：谁、做什么 | 最多 3 条，和前面各块对得上 |
| 按钮 | 「📄 查看完整报告」，打开当天的完整报告云文档 | 文档建失败时去掉按钮，在留痕行写「完整报告未生成：原因」 |
| 留痕 | 灰字一行：生成方（实际模型）｜接入方式｜统计日｜取数时间 | P-13 |

卡片只放提炼过的结论；各项目推进、代理述职明细、机制沉淀、覆盖与可信度只在完整报告里。

### 完整报告（七段，见 4.1–4.8）

完整报告就是一份飞书云文档，每个统计日一份，结构如下。顺序固定，按常浩的阅读和决策顺序排，不按数据来源排。

```
📅 猛鬼兽日报｜统计日 11-08（周日）
生成：Hermes（模型）｜接入：Hermes 派单｜取数 11-09 07:52｜统计日 11-08 04:00 → 11-09 04:00
一句话：……
实质推进 N 个项目｜待你决策 N 件｜阻塞 / 风险 N 个项目
（今早新增：……）

一、需要你拍板
二、昨日关键成果
三、各项目推进
四、风险、阻塞与跨项目依赖
五、Hermes 代理述职
六、今日推进计划
七、机制改进与沉淀
覆盖与可信度：……
```

### 4.1 开头：一句话 + 三个数

- **一句话**：最重要的成果，加今天最要紧的事。不写「合并了多少个 PR」。
- **三个数**：实质推进的项目数（有可验证成果，不是只有提交）、待你决策的事项数（经过授权判断后真正需要你的）、阻塞或有风险的项目数（按项目去重）。
- 合并数、覆盖项目数这类活动量放到尾注；**有项目没读到时**，覆盖情况提到开头。

### 4.2 一、需要你拍板（≤ 5 条）

只放待决策的事；已授权、只等执行的事放到第六段。分三类，按这个顺序排：

| 类型 | 含义 |
|---|---|
| 阻断型 | 不决定，任务没法继续 |
| 限时型 | 现在能继续，但要在某个时间点前决定 |
| 普通 | 没有立即影响，可以缓 |

A 层每条两行：
```
[限时｜数字分身] 事项一句话。为什么必须是你；Hermes 推荐 X（依据，不确定处）；不决定会怎样；最晚：时间（有证据才写）。
→ 回「……」即可
```
B 层存全字段（见 5.5）。「明天会收到提案」这类提醒不进这一段，放到第六段或尾注。

### 4.3 二、昨日关键成果（≤ 5 项）

把「工程活动」和「项目成果」分开：

| 级 | 含义 | 放哪 |
|---|---|---|
| 一级 | 项目目标有了进展 | 正文 |
| 二级 | 关键能力达到明确状态（比如已合并、已安装、等验收） | 正文 |
| 三级 | 具体工程活动（PR 合并、测试通过、分支提交、文档改动） | B 层证据，正文不展开 |

每项写成一行：**完成了什么 → 达到什么状态（按 5.2 三个维度）→ 对哪个目标有意义 → 还剩什么**。

后面加一行**整体趋势**：主要项目是在靠近目标、原地不动，还是出现偏离。没有目标或基线时写「无法判断」，不编百分比。

### 4.4 三、各项目推进

- A 层只列三种项目：昨天有增量的、有风险或阻塞的、在等验收的。每个项目 1–2 行：当前目标（或「未设目标」）｜昨日增量｜当前状态｜下一步与负责人。
- 其余活跃项目合成一行，写「昨日无新动作，当前状态：……」。
- 活跃项目连续 7 天没有新动作、也没有可信状态，进第四段「管理失真」。项目明确暂停的，按名册标注排除。
- B 层存全部活跃项目的完整记录（见 5.1）。

### 4.5 四、风险、阻塞与跨项目依赖

重在判断问题，不按数量报警。

| 类型 | 典型情况 | Hermes 的处理 |
|---|---|---|
| 交付风险 | 里程碑延期、验收失败 | 提出修复路径和负责人 |
| 协作阻塞 | 等 Claude 反馈、Codex 没交回执 | 查依赖，推动下一步 |
| 运行风险 | 自动化失效、部署状态不明、定时任务异常 | 在授权内核验，必要时升级 |
| 管理失真 | CURRENT 过期、任务没人负责、证据冲突、未设目标 | 标「未知」，提出纠正动作 |

- 异常先只读识别性质，再定级。例如「79 个未提交文件」可能只是开发现场，没识别前写「待识别」，不写高风险。
- **跨项目依赖只认明文引用**：PR 或 issue 正文里写了别的仓库编号（如「配合 github-center #83」「niuma-home#31」），或者名册里登记了关系（#98 确认后接入）。不推测依赖，不建依赖图谱。要回答的是：这个问题会不会影响另一条更重要的主线。

### 4.6 五、Hermes 代理述职

按类写：合并、裁决、派单、主控与监护、拒绝、定时任务。同类低风险动作合并成一行；完整明细在 B 层行动账本里。

- 每条写：做了什么｜授权档位与来源｜结果。
- 结果分三档写清：**已发起**、**工具调用成功**、**业务结果已验证**。比如「定时任务全部 completed」只说明脚本正常退出，不说明业务做成了。
- 拒绝要写清：拒绝了哪类请求、哪条授权条件不满足、有没有告诉请求方正确的授权来源、还要不要常浩处理。

### 4.7 六、今日推进计划（≤ 5 项，按 P0 / P1 排）

每项写：**目标 → 负责人 → 动作 → 交付物 → 完成标准**（有触发条件的再写触发条件）。

- 负责人分三类：**Hermes 自主推进**（授权内直接做）、**Hermes 协调推进**（派给 Claude / Codex 并追回执）、**需要你介入**（列成明确的个人任务或决策）。
- **每项都要和前面的拍板、风险、成果对得上**，不许凭空新增任务。
- 写进计划不等于有授权；需要授权的动作，在第一段请示。

### 4.8 七、机制改进与沉淀（≤ 3 条，没有就写「无」）

- 只放**正式沉淀提案**：同一做法在 ≥ 2 个独立任务里都有效，或同一个问题出现 ≥ 2 次。每条写：建议去向（全局坑 G-xx、项目 LESSONS、skill、全局指令 P-xx、Vault）、一句话内容、证据、适用范围、是否要常浩批准才能改。
- 单次异常先进 B 层的**观察池**，不进 A 层。
- 已经采纳的提案，后续在这一段跟踪效果：原来的问题有没有减少。没减少要说出来。

### 4.9 尾注：覆盖与可信度

一行写清：读到了哪些来源、哪些读取失败、哪些 CURRENT 过期、活动量（合并数等）。来源缺失时，降低相关结论的确定性，并在对应条目上标「未知」。

## 5. 数据模型

### 5.1 项目记录（每个活跃项目每天一条，存 B 层）

| 字段 | 说明 |
|---|---|
| `project_id` | 名册 id |
| `objective` / `objective_source` | 当前阶段目标及来源（5.3）；没有就写 `未设` |
| `milestone` / `milestone_source` | 当前里程碑（开着的父 issue）及其子任务完成数；没有就写 `未设` |
| `yesterday_delta` | 统计日内的变化（合并、关闭的 issue、安装、验收）；和当前状态分开记 |
| `current_state` | 截至取数时的真实状态 |
| `engineering` / `delivery` / `acceptance` | 三个维度的完成状态（5.2） |
| `blockers` | 阻塞与依赖（含跨项目引用） |
| `next_action` / `owner` | 下一步与负责人（Hermes / Claude / Codex / 常浩） |
| `evidence` | 支持以上结论的出处（PR、提交、安装记录、回执、文件路径） |
| `freshness` | 各来源最后更新时间；CURRENT 过期标 `stale` |
| `updated_at` | 本条最后核验时间 |

**昨日增量和当前状态是两个不同的对象。** 昨天没有新提交、但有一版在等验收，要写「昨日无新动作，当前等验收」；昨天提交很多、但还在开发中，不能写成「基本完成」。

### 5.2 完成状态：三个独立维度

| 维度 | 取值 | 回答的问题 |
|---|---|---|
| 工程 | 开发中 / PR 中 / 已合并 | 代码做到哪了 |
| 交付 | 未部署 / 已安装 / 已发布 / 未知 | 进没进实际使用的环境 |
| 验收 | 未提交 / 待验收 / 已通过 / 未通过 | 达到常浩确认的目标没有 |

一个功能可以同时是「已合并、已安装、待验收」。日报里的「完成」都必须说清是哪个对象、在哪个维度完成。策略研究、PRD、方法论这类非代码工作，按各自的阶段交付物和验收证据算，不套用 PR 状态。

### 5.3 目标与里程碑从哪来（常浩 11-08 定）

现状（11-08 核对）：6 个主要仓库的 GitHub 里程碑数都是 0；16 个活跃项目里只有 8 个有 Vault 项目卡。所以：

- **里程碑** = 项目里开着的父 issue（正文带子任务清单，例如本项目 #108、牛马之家 #24）。完成度按子任务的勾选或关闭数算。
- **当前阶段目标** = 各项目 CURRENT.md 顶部的一行 `当前阶段目标：……`；没有这一行时，读 Vault 项目卡的目标段。
- 两样都没有：日报写「未设目标」，记为管理失真，**不让 Hermes 猜**。
- 首次补齐：Hermes 起草 16 个项目的阶段目标，常浩一次看完确认，再由各项目会话写进各自的 CURRENT（#114，批 1 的前置）。以后只在阶段切换时改。

### 5.4 代理行动记录（批 1 定结构，之后不再改）

统一写 `~/Library/Application Support/DigitalTwin/actions.jsonl`，一行一个动作：

| 字段 | 说明 |
|---|---|
| `action_id` | 唯一编号 |
| `ts` | 时间（带时区） |
| `project_id` | 关联项目，没有写 `hermes` |
| `kind` | merge / ruling / dispatch / supervise / refuse / cron / install / other |
| `request` | 谁请求、请求了什么（原话摘要和来源） |
| `actor` | 执行者（Hermes、Claude、Codex） |
| `auth_tier` / `auth_source` | 授权档位 A/B/C/D，来源（卡片版本、授权文件路径、私聊消息号） |
| `decision` | 执行 / 拒绝 / 升级给常浩 |
| `result` | 已发起 / 调用成功 / 业务已验证 / 失败 / 不明 |
| `verification` | 回读证据 |
| `follow_up` | 后续责任：谁、做什么 |

**过渡**：第一天不迁移历史记录。批 1 先写适配器，把现有来源转成这个结构：合并官 `shadow/agreement.csv`（owner 列）、`merge-runs/`、证据目录里的裁决文件、派单台账 `~/.hermes/dispatch`、`cron/executions.db` 与 `cron_incidents`、夜跑 `runs/*/run-log.jsonl`。以后各脚本直接写 `actions.jsonl`，不用再设计第二次。

### 5.5 拍板事项（存 B 层）

## 6. 证据与可信度规则

**每个重要结论都要能说出：证据来自哪里、有多新、能证明到哪一步。**

| 数据对象 | 主要依据 | 不允许的推断 |
|---|---|---|
| 项目范围 | `projects.json` | 仓库存在就当活跃项目 |
| 工程结果 | GitHub PR、issue、CI | PR 合并就等于功能可用 |
| 安装与发布 | 安装记录、运行回读 | 文档写了「已安装」就当安装成功 |
| 验收结果 | 常浩的验收记录、明确回执 | Claude 说做完了就当常浩通过 |
| 项目下一步 | CURRENT、父 issue、阶段目标 | CURRENT 过期了还当可信事实 |
| Hermes 行动 | 行动记录、授权来源、执行回执 | 调用了就当目标达成 |
| 定时任务 | 执行记录、投递回执、任务结果 | 进程正常退出就当业务成功 |

- **来源冲突**：标出冲突，按该对象的权威证据判断，不简单取最新的一条。例如 my-skills #74 已合并 skill 的 generate 模式，但对应的 niuma-home #31 还开着，就写「状态冲突：skill 已合并，牛马之家侧 issue 未关」。
- **CURRENT 过期**：CURRENT 最近一节比该项目最近一次合并早超过 1 天，标 `stale`。这时照常汇报已核实的 PR 事实，但不把 CURRENT 的「下一步」当可信执行依据。
- **影子判定去重**：合并官的判定按「PR + 版本」去重，只取最后一次。
- **缺失**：取数失败、回执缺失，写「未知」；不写成零进展，也不写成「没完成」。

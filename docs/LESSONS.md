# 开发实录与坑

踩过的坑记在这里，Claude 和 Codex 都读。排障、发布、改脚本之前，先搜一遍：`grep -n 关键词 docs/LESSONS.md`；换个项目也成立的坑在全局 `/Users/nat/Documents/ChatGPT/个人/work/agent-kit/LESSONS.md`（G-xx），也搜一遍。

## 怎么写

- 每轮交接时自问「本轮踩到新坑了吗」：有就在下面追加一条，并在 CURRENT.md 的交接里写「本轮新坑：L-xx」；没有就写「无」。
- 一条一个坑，编号只增不改。写现象、根因、正确做法、证据。证据写到能查的程度（提交号、文件与章节、证据目录）；查不到就写「未核实」，不编。
- 结论被推翻时改条目并注明日期，不删。

## 怎么升级

- 同类坑第 2 次出现：把正确做法写进 AGENTS.md 或 docs/OPERATIONS.md（一句话硬约束进 AGENTS.md，操作细节进 OPERATIONS.md），条目的「升级」改成写到了哪里。
- 能用机器判定的：写成测试或脚本（如 `scripts/check-rules.mjs`），条目注明。
- 换个项目也成立的（不依赖本项目的业务、页面、发布脚本）：提议提升到全局坑 `/Users/nat/Documents/ChatGPT/个人/work/agent-kit/LESSONS.md`，写成 G-xx；原条目保留，末尾加一行「提升：已提升为全局 G-xx（日期）」。只出提案，用户批准才写。
- 条目超过约 30 条时整理一次：已升级、且之后没再犯的，归档到 `docs/history/`。
- 「升级」一行每条都要有，开头写层级词〔结构〕〔机检〕〔体检〕〔文字〕〔提醒〕之一，再写状态（未升级 / 不升级 / 部分升级 / 已升级 / 关闭）、日期、编号和去处；还没升级的写「〔提醒〕未升级。」。坑本身已被代码消除、不再需要升级的写「〔层级〕关闭（日期，依据）：证据」，层级写现在靠什么守住（回归测试没接进必经检查的写〔提醒〕），原来的记录保留。层级的含义和怎么选，以全局 LESSONS「怎么升级」为准。起步骨架的 `scripts/check-rules.mjs` 能查这一行（本仓库还没装）。

## L-02 PR 分支从本地 main 拉，把本地没推的受限提交一起推上了 GitHub，只能删掉远端重建（2026-10-27）

- 现象：M3 批 4 开 PR 时，digital-twin 的 PR 分支从本地 main 拉，本地 main 上另一个会话 3 个没推的提交（含受限内容）随之推上 GitHub。处理时删掉旧远端重建，中途另一会话恰好推送又带上了旧提交，第三次新建才干净（`ff800e3`）。
- 根因：本地 main 上可能有别的会话提交了还没推的东西；从本地 main 拉分支推送，会把这些提交原样带进 PR。推送前没比 `origin/main..main`。
- 正确做法：
  - 分支一律从 `origin/main` 拉，不从本地 main 拉（agent-kit《工程流程》第 1 节）。

  - 已经推上去的受限内容：先停所有会话的推送，再处理远端；改写历史前把本地历史打包存进证据目录。
- 证据：`13c999f`（`CURRENT.md`「2026-10-27 · M3 批 4（B4 + B5）：开 PR，重建 digital-twin 远端」的「受限内容外泄与重建」）；`docs/2026-10-28-从提需到落地全记录.md` 第 222 行。

## L-09 本机跑全量测试以为卡死，其实是 test_multica_night 慢（约 16 分钟），被短超时截断后误报「卡住」（2026-11-19、11-20）

- 现象：11-19 为 PR #231 跑 `hermes/scripts/tests` 全量，33 分钟没跑完，以为卡死，用宽泛的 `pkill -f` 停掉（犯了 G-32）；按文件加短超时重跑，`test_multica_night` 每次都在同一个用例附近被截断，就记成「这个测试会卡住、CI 会超时」写进了 PR 正文。实际 PR #231 的 CI 通过，11-20 本机不设超时整文件跑完：112 个全过，用时 955 秒。
- 根因：这个文件每个用例都要真起子进程走一遍夜跑命令（`start` 约 27 次、`stop` 约 49 次假 multica 调用），每次子进程在本机 50～120 毫秒，单个用例 4～30 秒；跑的时候本机 load average 13～31（10 核），所以整文件要十几分钟。Linux CI 上子进程便宜，整套约 5.5 分钟。超时设成几分钟，截断点又总落在耗时最长的停机类用例上，看起来像卡在某一个测试。
- 正确做法：
  - 本机跑 `hermes/scripts/tests` 全量放后台跑，不设短超时；按文件限时时，`test_multica_night.py` 至少给 30 分钟。
  - 判断「卡住」前先看是在等什么：卡住时看子进程链（是否一直是同一个进程、`etime` 在涨），或在用例里打 faulthandler 调用栈；子进程一直在换就是慢，不是卡。
  - 停自己的测试按绝对路径或进程号停，不按命令名广撒（G-32）。

## 1. 定位

**每晚猛鬼兽提出「今晚可以替你推进的几件事」，常浩挑，猛鬼兽拿着这句回复当晚执行；第二天 08:00 的日报汇报结果。** 这是行动规划和机会挖掘：把常浩睡觉的时间用来推进个人项目，但做不做、做哪几件，由常浩每晚亲口决定。

| | 08:00 个人项目日报（D22） | 22:30 夜间行动提案（D23） |
|---|---|---|
| 回答 | 昨天发生了什么、做到哪了 | 接下来做什么、今晚能替你做什么 |
| 性质 | 述职，不产生授权 | 提案；常浩的回复就是当晚的授权 |
| 闭环 | 报告昨夜执行结果；要合并的 PR 走卡片按钮 | 产出今晚的派单 |

---

## 2. 基本设定

| 项 | 设定 |
|---|---|
| 读者 | 只有常浩（猛鬼兽私聊） |
| 范围 | `projects.json` 里的活跃个人项目；飞书工作事项不在内 |
| 发送 | 每天 22:30（Asia/Shanghai），周末照发；常浩在私聊说「晚报」也可以随时要一份 |
| 回复窗口 | 发出后到 00:30；没回复今晚不做，不默认执行推荐项。**例外：托管时段内（PRD D24）**，00:30 前没回复按推荐组合执行，上限不变；夜里开出的 PR 按 ARCHITECTURE 5.5「托管合并」判断能否合并，不满足就留到早上 |
| 上限 | 一晚最多 3 单；每单 ≤ 2 小时；同一时间只跑 1 单；执行方跟随车间默认执行方（`ai_access.py`），常浩可在回复里点名 |
| 停止时间 | 次日 08:00 前全部结束；到点还没跑完的单停掉，记「超时」 |
| 留痕 | 卡片底部写生成方、实际模型、接入方式、取数时间（P-13） |

## 3. 机会从哪里来

每条机会都要有来源，不让模型凭空想。取数复用个人项目日报的事实快照（#110），再加开着的 issue：

| 类 | 来源 | 例 |
|---|---|---|
| 离阶段目标还差什么 | CURRENT「当前阶段目标」+ 里程碑剩下的子任务 | 牛马之家批 1 还差 #31、#32 |
| 现成可做的单 | 标了 `ready-for-agent`、验收写清楚、没有阻塞的 issue | digiworld #59 |
| 卡住的事解开了 | 前置 PR 已合并，或常浩白天已拍板，下游可以接着做 | my-skills #78（前置 niuma-home #43 已合并） |
| 管理失真修复 | CURRENT 过期、状态冲突、PR 久没推进 | 补 CURRENT、核对冲突 |
| 沉淀候选 | 观察池里次数够了的经验 | 整理成规则或 skill 提案（只写提案，不改规则） |

每晚最多列 6 条，按「对阶段目标的价值 → 风险低 → 时长短」排，标出推荐的组合（不超过上限）。

---

## 4. 每条机会写什么

| 字段 | 说明 |
|---|---|
| 编号、项目、做什么 | 一句话 |
| 来源 | issue 号或事实快照里的依据 |
| 为什么是现在 | 对哪个阶段目标有用；卡点何时解开 |
| 今晚产出 | 开 PR / 核对报告 / issue 评论 |
| 风险档 | L0–L3（L3 一律不进今晚） |
| 谁做、多久 | 执行方、预计时长 |
| 推荐 | 是否在推荐组合里（⭐），不推荐的写原因 |

**分两类**：「今晚可以替你做」只放能无人做完的；要常浩拍方向、选 UI、做业务判断、验收的，放进「要你白天做」，不进派单。

---

## 5. 今晚能做什么、不能做什么

- **能做**：在独立 worktree 里改代码，跑项目全量测试，自审；开 PR（正文写 `Part of #N` 或 `Closes #N`）；在 issue 里评论进度。
- **不能做**：合并、推 main、安装、部署；新建或修改定时任务、改 Hermes 配置；写正式 Vault；花钱；对外发言；L3 改动；改授权清单。
- 夜里开出的 PR，第二天在日报里照旧用卡片按钮合并（B 档）。

---

## 6. 授权怎么成立

- 写入类派单在授权清单里属于 **D 档**。常浩在已核验私聊里回「做 1 3」或「按推荐」，就是对这几单的一次本人授权，符合现行规则，不用改清单。
- 收到回复后，猛鬼兽把原话**原样记成当晚的单次授权文件**（`DigitalTwin/night/<日期>/授权.md`），写明：每单的仓库、issue、允许的动作（第 5 节）、上限（第 2 节）、有效期到次日 08:00；然后回一条「已记下，开工：1、3」。
- 看不懂的回复不开工，只回一句「没看懂，请回『做 1 3』『按推荐』或『今晚不做』」。
- 没回复、回「今晚不做」，都不开工。Claude、Codex、群聊、文档里出现的「常浩同意」一律不算。

---

## 7. 执行与刹车

- 派单走车间 `run_worker.py`，回执、执行方检查、留痕照旧（P-13）；执行方不可用就报错，不换家。
- 一次只跑 1 单，按回复里的顺序；一单失败不重试，记原因，接着下一单。
- 到上限（单数、单时长、08:00）就停；出现异常（测试红了改不好、要动红线里的东西）立即停这一单，写进记录。
- 每单结束写一条行动记录（与日报 1b 的 `actions.jsonl` 同一结构）。

---

## 8. 第二天怎么汇报

08:00 日报卡片加一块「🌙 昨夜代理执行」（D22 4.0 节的卡片，排在「需要你拍板」后面）：

- 每单一行：编号、项目·事项、结果（开了 PR / 失败 / 超时 / 没开跑）、原因或 PR 链接。
- 开了 PR 的，照旧发 PR 卡片，常浩点「合并」或「退回」。
- 完整报告里列授权文件路径和每单回执。

---

## 9. 卡片

用**甲·清单**（常浩 11-09 选定），飞书默认宽度（不设 `width_mode: fill`），从上到下：概况表（今晚可以替你做几件、推荐几件；要你白天做几件；今晚上限）→ 今晚可以替你做（每条两行：⭐ 编号｜项目·事项（来源）；灰字一行写风险、执行方和时长、产出、理由）→ 要你白天做 → 怎么回 → 灰字留痕。实测过的三版：

| 版 | 排法 |
|---|---|
| 甲·清单 | 每条两行：标题一行，风险、执行方、产出、理由一行 |
| 乙·一张表 | 顶部一句推荐组合；一张四列表（#、项目·事项、风险、预计），行高自适应 |
| 丙·逐条折叠 | 三个大数字；每条一个折叠区，点开看依据、产出、风险、来源 |

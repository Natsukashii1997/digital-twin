# Hermes Digital Twin · 主动运营与夜间推进体系 V1.1（返修送审稿）

> 日期：2026-11-02  
> 状态：**候审 / 未获执行授权**。本稿依据 V1.0 原案、Claude《2026-11-02-主动运营与夜间推进V1.0-审核意见》（E1–E10）和 `docs/DT-ORC/ARCHITECTURE.md` V3.1.0 返修。  
> 适用范围：**仅私人数字分身猛鬼兽和个人工程/知识项目**；企业数字分身亚古兽及企业资料不纳入。  
> 本稿区分：**已知现状**（来源于 Claude 2026-11-02 只读核查）、**目标设计**（尚未实施）、**Owner 待决策事项**。所有运行状态部署前必须重新读取，不以本文替代实时证据。

## 0. 核心结论

猛鬼兽应具备完整的 **感知项目 → 提出优先级和夜间计划 → Owner 可信授权 → 受限执行 → 独立验收 → 次日回报 → 沉淀可复用经验** 闭环。

**分清两件事：**

1. **主动运营**：项目事实巡检、晚间总结与建议、早间报告、周度复盘、知识候选提炼。这些可在现有 Hermes/项目资料上逐步建设，不等于已获夜间执行权。
2. **无人值守执行**：Owner 睡觉或离开后的自动派单、运行和恢复，依 `ARCHITECTURE.md` §4.3 属于 **`UNATTENDED`**，当前尚未放行；不能因为指定时间窗口、任务低风险或签发了单次授权，就视作 `SUPERVISED`。

**当前策略：先修报告可靠性、实现只读晚报和授权空跑，再完成运行模式和安全闸门；未经架构基线变更及相应验收，不启动真实夜间无人值守 Worker。**

## 1. 唯一架构与责任边界

| 层级 | 唯一职责 | 复用现有组件 |
|---|---|---|
| Hermes 猛鬼兽 | 理解目标、汇总项目、排序建议、向 Owner 呈现决定、汇报和学习 | 现有 SOUL/HERMES、`progress`、`vault`、Cron、Feishu |
| 项目与状态 | 维护项目登记、任务与执行事实 | `projects.json`、`twin_state`、`twin_scheduler`、GitHub、各项目 CURRENT |
| 运行授权 | 证明本人对**特定计划、特定版本及动作**的批准、有效期及撤销 | 扩展 `dt-orc.run-authorization/1`，不另造授权格式 |
| 窗口控制 | 检查执行时间、权限和机器条件；派发、停发、收口、对账 | 增设一个**薄的确定性窗口控制器**，调用既有执行通道 |
| 工程执行与审核 | Worktree / Claude 开发自测 / ChatGPT High 独立审核 / Codex 专项 | 现有车间或已验收的 ORCA 最小执行桥，按当前适用闸门 |
| 知识和方法 | 事实归档、跨项目复用、Skill 候选 | 项目 LESSONS、agent-kit G-xx、my-skills、Obsidian 收件箱 |

- 不创建新「Personal Project Operations」项目管理框架，不取代 ORCA 的 Task/Run/Worker/恢复状态机。
- 现有 `dt-orchestrate` / `dt-closeout` Skills 是流程入口；夜间窗口控制器只保留授权与窗口状态，不重复保存任务结果。
- **工程技术审核 PASS ≠ 发布/合并/部署授权；SOUL/HERMES/PRD 文件批准 ≠ 自动执行权限。**
- 正式 Obsidian Vault、Hermes 安装配置、个人以外的企业系统分别服从自身权限规则，不继承夜推许可。

## 3. 日常运行节奏：少量 Cron，明确数据真源

时间为**建议默认值**；暂以明确配置的 `Asia/Shanghai` 为例，正式 Cron 和授权单都必须显式保存时区，不从聊天所在地点猜测。

| 触发 | 推荐时间 | 产出与执行方式 | 前置门槛 |
|---|---|---|---|
| 晚间项目总览 + 夜推提案 | 每日 21:30；周末是否运行待定 | `--script night_plan_data.py` 汇集名册、项目 CURRENT、GitHub、调度计划、上次收口，模型只整理并提出可执行建议；消息含计划号/版本/摘要 | 修复消息送达与失败降级，项目事实数据可读 |
| 夜间授权 | Owner 自己决定 | 固定可信命令批准本次计划；未批准到开始时间自动过期 | §5 授权签发验收 |
| 夜间受限运行 | 建议 23:00—06:30，仅将来获准时 | 独立 launchd 控制器，按授权任务依次执行，早到或逾期均拒绝 | §4 模式及 §6 安全门槛 |
| 夜间心跳 | 在获准窗口内每 30 分钟 | 独立 `--no-agent` 或外置监控脚本；检查窗口状态、任务进展、网关与最后回执。正常时不推消息；异常记录并尝试告警 | 控制器、持久日志已验收 |
| 次日成果简报 | 07:30 | **先完成 T7 / F4 迁移**：日报附上可信收口文件的“昨夜”段，再投递飞书 Owner 私聊；失败时纯脚本降级 | 连续真实送达和失败测试 |
| 周度复盘 | 复用现有周报 | 夜推计划命中率、异常、人工介入、可固化方法（最多 3 条）；避免另建周期模型任务 | 周报超时/失败处理修复 |
| 工程自检 | 复用 09:50 等现有任务 | 增加昨夜心跳完整性、本机未送达告警的记录检查 | 不影响现有 Cron |

### 3.1 晚报应给出的决策信息

每个纳管项目基于真实来源标注：**当前阶段 / 今日增量 / 已完成的证据 / 当前阻断 / 下一步 / 是否适合夜推及原因**。在此基础上：

- 全局按**价值、关键依赖、可执行性、风险和资源额度**推荐优先顺序；每一条建议要落实到具体执行通道和可到达的成果档位，如“可完成隔离分支+测试，不 push”“审核需要登录页面，夜里可能挂起”。
- 给出计划号、版本、完整 SHA-256（消息可展示足够短的前缀）、仓库与具体任务、允许动作、窗口、并发和预算。
- **上次夜推计划命中率**＝已按标准完成的计划任务数 / 当夜已批准的计划任务数；列明失败和偏差原因，未知状态不计完成。
- 可选的授权指令由可信网关命令生成或呈现，普通“按建议推进”仅能触发**生成待批准计划**，不能自动生效。
- 建议无法基于可靠来源形成时，只给“事实简报 + 不建议启动原因”，不编造完成率。

### 3.2 晨报应交付的事实

简报必须首先说明**夜间窗口是否确实运行、是否完整、心跳是否完整、是否存在未送达告警**；随后列出：

1. 本夜实际完成的任务与证据（Run/Task、Worktree/分支、commit SHA、测试与审核回执）。
2. 分层状态：**已开发 / 测试通过 / 独立审核通过 / 已合并 / 已部署 / Owner 已验收**；每项只认有证据的最高真实层级。
3. 待审核、待 Owner 决策、异常、`UNRECONCILED`（结果未对账）和失败原因。
4. 计划与实际差异、资源消耗/配额变化、下一步最有价值的动作。
5. 本次有证据的新方法/风险观察；无实质增量不重复长篇汇报。

日报被跳过、控制器未运行或回执缺失时，必须明确报告“**未知/未运行**”，绝不因为安静无消息就推断成功。

## 4. 夜间窗口的运行模式归属（E1）

依据 `ARCHITECTURE.md` §4.3、§5.2–5.4、§10：

- **Owner 在场、单次启动并可实时介入**：`SUPERVISED`，按现有 5.2a/b 的可信签发与已验收动作桥运行；M1 接线验收后推进 M2 真实闭环。
- **Owner 离开后继续执行任务，即使到点停止、只动本地文件**：定义上仍是 `UNATTENDED`。默认不放行，完整路线等待 M4 相应门槛和正式授权。
- **早期“有界窗口”建议**：不是第三种模式，更**不能重命名成 SUPERVISED 绕过 M4**。如 Owner 专门希望提前做一个“无外部副作用的隔离夜间试点”，须先按架构 §12 形成专项 ADR，列出技术强制隔离、醒来与恢复、撤销语义、审计、失败保护、人工审批，经过独立审核后明确**仅允许的 M4 子集/受控试点**；仍将其归为 `UNATTENDED`。在该 ADR 批准及相应验证之前，只允许**不派真实 Worker 的空跑**。
- **不得直接将 `LIVE_ACTIONS_ENABLED=False` 改为 True**；不以已有单测和模拟演练替代真实授权、动作安全接线和独立审查。

**暂行决策建议：采用“先 B（严格守现有 UNATTENDED 门槛）、并行研究 A（有界隔离试点的架构专项修订）”。** 这不是对 Owner 方案 A/B 的最终代选，需 Owner 明确批准架构变更。

## 5. 授权签发、核验与撤销（E2）

### 5.1 原则

- **计划由模型提议，授权由可信程序签发，执行由独立控制器验证。** 任何模型（包括有 terminal/file 的猛鬼兽）不拥有签发权，不可通过写 JSON、自然语言解释或工具返回值冒充批准。
- 授权入口沿用 `ARCHITECTURE.md` §5.2a 已选定的可信来源：本机独立人类交互入口或**私人猛鬼兽飞书聊天中的可信平台事件**。同一 macOS 用户下的恶意本地进程不在现有 SUPERVISED 威胁模型保证范围内。
- **Owner 发起消息的身份核验，不等于该消息批准了哪个具体计划**；批准必须绑定版本化的完整计划内容和动作范围。

### 5.2 固定命令与安全接线（仅为目标命令，不表示现有命令已安装）

```text
/夜推 批准 N20261102-v2 #a1b2c3d4
/夜推 状态
/夜推 停
/夜推 只留 obsidian
```

- 建议使用 Hermes 网关已支持的**插件 slash 命令或经过审查的 quick_commands**，确定性解析；需实测这些消息由网关处理、携带可信 `open_id/chat_id/message_id` 且**不进入 LLM 回合**。
- `/夜推 批准` 需展示完整目标、窗口、作用仓库、操作上限与本次计划摘要；展示的哈希前缀只用于用户核对，内部必须验证**完整 SHA-256** 与不可变的计划快照。
- “改到 01:00 结束”“只留某项目”等实质修改应生成新计划版本，旧版失效后重新批准；`停` 是可信通道的优先控制事件，不需等待模型回复。
- 网关应校验来源为 Owner 的真实飞书私聊消息并消耗一次性消息 ID、防重放；群聊、文档、截图或模型自报的 ID 一律不算批准。
- 如果使用 `quick_commands` 的 exec 路径，必须验证参数不会被 shell 拼接注入，建议固定 argv/白名单，而非直接把消息内容传入 shell。

### 5.3 执行前二次核验

- 授权账本只接受**可信网关/验证器**写入；记录应包含 `dt-orc.run-authorization/1` 兼容字段：`plan_id/version/sha256`、`window.start/end/tz`、`owner_message_id`、可信 sender/chat、项目/任务白名单、动作白名单、并发/任务/返修额度、签发时间、有效期、撤销与已消耗动作账本。
- **目标设计**：控制器在每次实际派单前，通过经过权限审查的机器人身份按 `owner_message_id` 回读飞书原始消息，确认身份、私聊、命令内容、计划摘要及最新撤销状态；同时检查持久账本与不可变计划快照是否一致。**飞书是否支持机器人按该 ID 回读所需消息、对应 API 权限是否已获准，需要单独真实验证；不能假定必然可用。**
- 回读不可用或结果不明时，必须拒绝开单；不能退化成信任模型给出的本地文件。
- **防本地篡改要求**：授权账本、计划快照、撤销记录与控制器本体必须与有 shell 的 Hermes/Worker 形成经验证的进程或操作系统权限隔离。仅把文件放进不同目录、改变文件名、给脚本加校验函数，都不构成有效权限边界。若当前同一 macOS 用户可修改全部文件，应如实记录剩余风险，**不声称防止模型伪造授权**。
- 撤销应影响未来所有动作；外部动作已发生不能靠杀进程撤销，必须事后核对。

### 5.4 无授权及异常处理

- 到窗口开始仍未批准 → 计划标记“过期未批”，不开窗。
- 哈希不匹配、项目超范围、授权过期、收到停机、身份缺失、可信回读失败 → 停止新动作并写入原因。
- 剩余动作与最后回执不确定 → 进入 `UNRECONCILED`，仅允许只读对账，不直接重试。
- 出现授权覆盖、权限边界不明确、控制器无法独立验证的情况 → 只保留报告功能，不自动运行。

## 6. 夜间执行器：最小能力与机器层门槛（E7）

**只新增薄窗口控制器，不新增调度队列或第二套 ORCA。**

### 6.1 窗口状态机

`草拟 → 待批准 → 已批准 → 窗口运行中 → 已收口`，额外终态：`作废`、`过期未批`、`异常冻结`、`UNRECONCILED`。任务自身的开发/审核/返修/暂停状态仍以 ORCA/twin_state 为准。

每次真正开始新动作前核对：当前时间和时区、计划哈希、可信批准、撤销标记、任务白名单、仓库/Worktree、允许操作、并发/预算、机器健康及最新任务对账状态。到点停止**领取新任务**，给已运行工作设有界收口宽限；无法安全中断则采取预先验收的终止与检查点策略，**不静默延长执行授权**。

### 6.2 六项机器层前置条件

| 风险 | 必须具备的处理 | 未具备时 |
|---|---|---|
| 网关/DNS 断线，告警送不出 | 控制器和网关之外的本机持久状态/日志；送达 ACK 或待补发队列；晨报首段说明心跳与未投递事件 | 不认为“没消息＝正常”；实时通知不可保证 |
| 电脑睡眠、重启、网络切换 | 使用独立 launchd 触发，启动核对电源/睡眠/时钟与网络；重启后读取状态并幂等对账。不得为了夜推私自调整系统电源设置 | 跳过窗口并留原因，不在错过的时间段补跑 |
| ChatGPT 登录页面/额度/会话状态失效 | 发送前核对 URL、会话、模型/High 强度与送审 ACK；异常停在待审核，禁止改换未批准通道 | 当前任务挂起，继续其他可执行任务或收口 |
| Worker 有可绕过的 push/网络能力 | **强制隔离**：独立沙盒账户/进程、凭据剥离、网络外发/仓库写权限的操作系统或沙盒限制；反向测试无法 push、无法读生产路径、无法绕过限制 | 不能使用高权限 `run_worker.py` write 模式冒充“无外部副作用”夜推；单改 `remote.origin.pushurl` 不足够 |
| 订阅额度与任务资源约束 | `max_tasks`、`max_rework_rounds`、并发上限、允许模型、`codex-quota-guard` 阈值；额度不明时保守停止 | 不再派耗费不可确认额度的任务 |
| 与白天的开发任务碰撞 | 独立 worktree 和 `night/<日期>-<单号>` 分支、仓库级租约、提交与变更范围核对；早报列待处理分支 | 不对现有白天工作区做隐式覆盖或清理 |

**控制器的进程存活不等于代理网关可送达；发送通知失败必须保留本机可恢复证据。** 机器掉电/睡眠时不能承诺准点执行，必须写清退化状态。

### 6.3 v0 / v1 执行通道

- **空跑**：只生产本应派发的任务决策与授权拒绝证据，不启动 Worker、不调用真正外部动作。可在 M1–M4 之前进行安全逻辑验证。
- **受监督人工直控**：由 Owner 在场执行独立的安全试点，可与 M1 并行，报告必须明确“人工触发”。
- **受限本地夜间试点**：仅在 §4 所述**独立架构变更/特殊批准、隔离与机器可靠性验收**后，才可在一个低风险个人仓库中执行不 push、不合并、不部署的任务。`run_worker.py` 仅是候选执行通道，不能因已有自测就认定符合“无外部副作用”。
- **ORCA 真实 Worker/ChatGPT Relay**：按照 M1 最小安全接线 → M2 真实 `SUPERVISED` 闭环 → M3 多任务/合规发布 → M4 `UNATTENDED` 的顺序逐步放行；不得因“已有 Relay 代码”而绕过有效闸门。

## 7. 通知和学习：复用现有体系（E3、E8、E9）

### 7.1 业务事件与通知来源

- **立即**：越权或授权异常、窗口控制器失败、心跳缺失、可能损坏状态的异常。由事件的**实际产生方**（控制器、relay_loop、run_worker 回执）触发，并写本机待送达记录。若飞书离线，只保证本地记录和恢复后补报，不能保证立即送达。
- **随报**：普通审核未通过、可局部处理的任务阻断、等待 Owner 决策；汇入最近一次晨报/晚报。夜间普通问题不打扰。
- **周汇**：一般进度、经验候选、效率分析，汇入现有周报。

Hermes v0.22.2 网关 hooks 只用于其支持的生命周期事件与命令审计，不声称支持 ORCA 业务事件。拉取式健康检查可以用 `--no-agent` / `--monitor-script`，应实测“无变化不通知”在目标送达平台的表现。

### 7.2 学习机制

| 事实类型 | 唯一推荐去向 | 升级方式 |
|---|---|---|
| 单项目的失败教训与解决方式 | 项目 `docs/LESSONS.md` | 在该项目既有写入授权范围内沉淀 |
| 跨项目通用工程规律 | `agent-kit/LESSONS.md` G-xx | 先提案，Owner 批准后纳入 |
| 可复用具体操作流程 | `my-skills/skills/<name>/`，关联 `links.tsv` | 提交 Skill 候选、独立审查、Owner 批准正式更新 |
| 个人目标、决策背景和偏好变化 | Obsidian Vault 收件箱 `/kb-note` | 按 Obsidian 主线权限审核、正式入库 |
| 一次性发现且尚未验证 | 本次 `evidence/.../observations.md` | 保留观察，不直接改全局规则 |

**升级标准**：同一方法至少在两个不同任务中有效并有证据，才提为常规“候选”；一次性高风险发现不必等两个样本才能报告安全问题或提出针对性修复。猛鬼兽可主动发现、归纳和提案，不自行修改个人 SOUL/HERMES.md、全局 G-xx 或正式 Skills。

“定期思考”并入周报最多 3 个可行动专题：重复返修的根因、跨项目可复用性、关键路径阻塞。没有新的判断就不写。

| **第 3 批：有人值守真实试点** | Owner 在场的单次 M2 受监督真实 Run 与收口汇报 | M1 相关执行桥验收，或符合 §5.2 明示的 Owner 人工直控路径；**不是夜间无人值守** | 真 Run/Task/回执/固定 HEAD/测试与独立审核；标注是否人工触发 |
| **第 4 批：受限夜间试点（条件批次）** | 一个低风险个人仓库、一张单、隔离环境；没有外部发布/企业/生产动作 | 必须先获 §4 所述 M4 有界子集专项基线修订 + 独立隔离/醒来/撤销/审计验收；未获批则跳过，等待完整 M4 | 真实可信批准 + 真实夜间收口 + 失败保护、可证明没有越权或外部副作用；报告准确定性 |

**并行关系**：第 0–1 批可不依赖 M1；第 2 批可以做纯空跑及认证验证但不可启用真实动作；M1 与 Owner 人工直控小试点可并行；真正夜间无人值守必须满足 M4 或已批准的等效有界子集，不得用“批次完成”自动提升运行权限。

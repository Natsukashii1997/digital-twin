## 4. 异常分类与判断

| 类别 | 单数 | 单号 | 判断 |

### 4.1 三个目录没有 `order.json`

D20261026-1 / -2 / -3 只有 `task.md` 和 `out/`（回执、日志），回执里的 `started` 在 10-26 17:52～18:34，早于 `dispatch.py` 首次提交（`df484ce`，10-26 18:38）——是 `run_worker.py` 时代直接跑出来的痕迹，不是派单台账格式的工单（其中两张回执还没有 `project` 字段）。B1 的 `read_orders` 只找 `D*/order.json`，这三个目录既不导入、也不出现在 `skipped / errors` 里。导入它们没有依据（没有单号对应的工单状态），**不导入是对的**；但对账时看不见「目录里还有 3 个非工单目录」，是可见性缺口。

### 4.2 三张历史续跑单没有回执存档

D20261026-7 / -8 / -9 各有一份 `followup-*.md`（10-26 18:50～19:14），但 `out/` 里没有 `receipt-N.json`：续跑归档是 `a8b4503`（10-26 20:19）才加的，这三次续跑在之前。现有 `receipt.json` 都是最后一轮的，Run 的回执与证据因此只反映最后一轮；三单都已 abandoned，没有后续影响。不处理。

### 4.3 两单回执带 `need_decision`

- D20261026-14（done，只读单）：关联任务后 `_settle_task_after_run` 会转 `blocked(decision)`，与设计一致。
- D20261026-10（cleaned）：目录里有 `user-decision.md`，说明决策在台账侧已经答复并合并收尾；`cleaned` 不在 `RUN_RESULT`，不会触发任务结算，无影响。
- **接入顺序要求（记进 T02 / T04 设计）**：台账侧的 `user-decision.md / answer.md` 与续跑文件不会被状态库识别为「常浩已决定」。常浩在飞书答复后，必须先由验证过身份的 user 事件 `unblock_task`，再 `dispatch run --followup`；顺序反了，同步会把续跑记成 `run.resume_conflict`（B1 `_resume_check` 的规则）。T04 测试要覆盖这两种顺序。

### 4.4 真实数据没有触发的路径

台账里没有 running / new / queued 的单，`recover` 的 suspect / unknown / stale、`_resync_kind` 的 followup / undo_stale / conflict、迟到结果等路径没有被真实数据触发，仍由 B1 测试覆盖：`test_06_state_survives_restart_and_recovers`、`test_06b_interrupted_write_leaves_nothing_behind`、`test_09_unreachable_external_source_never_completes_task`、`test_r2_late_result_of_old_run_does_not_override_current_run`、`test_ledger_regressions_are_conflicts_not_applied`、`test_followup_resume_rules`、`test_recover_uses_ledger_before_time`、`test_f1_ledger_conflict_does_not_overwrite_confirmed_evidence`、`test_f2_active_resume_checks_task_before_touching_run`。T04 的模拟通知测试会再走一遍这些组合。

### 4.5 静态快照看不出、但读源码能确定的点

- **同秒连写**：`order.sync` 的幂等键是 `单号:updated(秒):status`。`dispatch.py` 合并链在同一秒 `save()` 两次（第 325、328 行，先写 `pr` 再写 `merged_to`），第二次的键和第一次相同，会被当作重复跳过，`merged_to` 要等下一次状态变化（`cleaned`）才进库。真实 8 张 cleaned 单是首次整体导入，所以这次看不出；T04 的「写入后通知」会直接撞上。
- **事件挂载**：`order.sync` 事件挂在单号上，`run.import / run.conflict` 挂在 Run id 上，`events <Run id>` 查不到同步事件。只是查询不便，不是状态错误。

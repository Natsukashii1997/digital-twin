### 4.2 对象模型

```
Goal 1 ──n Task 1 ──n Run 0..1 ── 派单工单 order.json（order_no 唯一）
  │          │           │
  └── Ref    └── Ref     └── Ref（github_pr / github_issue / feishu_task / obsidian_note / file / url …）
Event n ── 任一对象（goal / task / run），idem_key 唯一
```

建表语句原文（schema v1，`MIGRATIONS` 列表只追加不改）：

```sql
CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT NOT NULL);
CREATE TABLE goals (
  id TEXT PRIMARY KEY, title TEXT NOT NULL, description TEXT NOT NULL DEFAULT '',
  status TEXT NOT NULL CHECK (status IN ('observed','authorized','completed','canceled')),
  scope TEXT NOT NULL DEFAULT '', project TEXT, phase TEXT NOT NULL DEFAULT '', done_when TEXT NOT NULL DEFAULT '',
  authorized_at TEXT, created_at TEXT NOT NULL, updated_at TEXT NOT NULL);
CREATE TABLE tasks (
  id TEXT PRIMARY KEY, goal_id TEXT NOT NULL REFERENCES goals(id), title TEXT NOT NULL,
  status TEXT NOT NULL CHECK (status IN ('observed','ready','running','blocked','review','completed','canceled')),
  depends_on TEXT NOT NULL DEFAULT '[]', acceptance TEXT NOT NULL DEFAULT '', next_step TEXT NOT NULL DEFAULT '',
  blocked_kind TEXT CHECK (blocked_kind IS NULL OR blocked_kind IN ('decision','dependency','external','technical')),
  blocked_reason TEXT NOT NULL DEFAULT '', owner TEXT NOT NULL DEFAULT 'hermes', retries INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL);
CREATE INDEX tasks_goal ON tasks(goal_id);
CREATE TABLE runs (
  id TEXT PRIMARY KEY, task_id TEXT REFERENCES tasks(id), agent TEXT NOT NULL, order_no TEXT UNIQUE,
  status TEXT NOT NULL CHECK (status IN ('new','queued','running','done','guard','failed','merged','cleaned','abandoned','stale')),
  session_id TEXT, receipt TEXT NOT NULL DEFAULT '{}', evidence TEXT NOT NULL DEFAULT '{}', note TEXT NOT NULL DEFAULT '',
  started_at TEXT, ended_at TEXT, heartbeat_at TEXT, created_at TEXT NOT NULL, updated_at TEXT NOT NULL);
CREATE INDEX runs_task ON runs(task_id);
CREATE TABLE events (
  id INTEGER PRIMARY KEY AUTOINCREMENT, idem_key TEXT NOT NULL UNIQUE,
  source TEXT NOT NULL CHECK (source IN ('user','discovery','agent','system')), kind TEXT NOT NULL, actor TEXT NOT NULL,
  object_type TEXT, object_id TEXT, payload TEXT NOT NULL DEFAULT '{}', evidence TEXT NOT NULL DEFAULT '',
  applied INTEGER NOT NULL DEFAULT 1, result TEXT NOT NULL DEFAULT '', dup_count INTEGER NOT NULL DEFAULT 0,
  at TEXT NOT NULL, last_seen_at TEXT);
CREATE INDEX events_object ON events(object_type, object_id);
CREATE TABLE refs (
  id INTEGER PRIMARY KEY AUTOINCREMENT, object_type TEXT NOT NULL, object_id TEXT NOT NULL, kind TEXT NOT NULL,
```

### 4.3 状态机

任务主状态七个：`observed`（已发现，尚未授权）、`ready`（已授权，可推进）、`running`、`blocked`、`review`（等验证或正式决策）、`completed`、`canceled`。阻塞类型四种：`decision`（等常浩决定）、`dependency`（等前置任务）、`external`（外部来源不可用）、`technical`（技术失败）。

合法转换表（`TASK_TRANSITIONS`，不在表内的一律拒绝）：

| 自 | 可到 |
|---|---|
| observed | ready、blocked、canceled |
| ready | running、blocked、canceled |
| running | review、blocked、canceled |
| blocked | ready、canceled |
| review | completed、ready、blocked、canceled |
| completed / canceled | 终态，不可再转 |

Run 状态沿用派单台账的词：`new / queued / running / done / guard / failed / merged / cleaned / abandoned`，另加 `stale`（过期）。Run 转换表（`RUN_TRANSITIONS`）独立：

| 自 | 可到 |
|---|---|
| new | queued、running、abandoned |
| queued | running、abandoned |
| running | done、guard、failed、stale、abandoned |
| done | merged、abandoned |
| merged | cleaned |
| guard / failed | abandoned |
| stale | done、guard、failed、abandoned |

台账同步时若台账跳过了中间状态（例如本地记 `stale`、台账已是 `cleaned`），以台账为准直接写入，并记 `run.resync` 事件留痕。

Run 结果反映到任务的规则（只在任务仍为 `running` 时生效；任务已被另行处理则不回写）：

| Run 情况 | 任务 |
|---|---|
| 回执带 `need_decision` | blocked(decision)，原因含车间提出的问题 |
| `done` | review，`next_step` 置为「核对该 Run 的回执、测试与 PR」 |
| `guard`（护栏触发） | blocked(decision)，不重试 |
| `failed` / `stale` | blocked(technical)，原因含超时或失败信息 |
| `abandoned` | blocked(decision) |
| `merged` / `cleaned` | 只改 Run 与证据，不动任务与目标 |

回执分类规则（`receive_receipt`）：`guard_main_changed` 或 `guard_remote_changed` 为真 → `guard`；`timed_out`、`worker_error` 或 `exit_code` 非零 → `failed`；否则 `done`。

### 4.4 授权边界（程序校验）

| 动作 | 谁能做 | 校验 |
|---|---|---|
| 新建目标 | 任何角色；非 `user` 只能建 `observed` | 否则 `NotAuthorized` |
| 授权目标、完成目标、撤销目标（连带撤销未收尾任务） | 只有 `user` | `NotAuthorized` |
| 任务 observed → ready | 任何角色，但目标必须 `authorized` | 依赖未完成则转 blocked(dependency) |
| 开始执行 | 任务必须 `ready`、目标必须 `authorized`、该任务没有进行中的 Run、工单号未登记过 | 一任务一活动 Run |
| 解 decision 类阻塞 | 只有 `user` | `retry_task` 对 decision / external / dependency 一律拒绝 |
| 技术重试 | 任何角色，限 `MAX_RETRIES = 2` 次 | 超限需常浩定 |
| 撤销任务 | `observed` 的任何角色可撤；已授权推进的只有 `user` | 撤销时进行中的 Run 记 `abandoned` |
| 完成任务 | 任何角色，但必须处于 `review` 且有证据（外部引用或成功的 Run） | `EvidenceMissing` |
| 完成目标 | `user`，且所有任务已 completed / canceled，至少一个 completed 或目标有引用 | |

角色取值固定为 `user / hermes / claude / codex / system`。库只认 `by="user"` 字符串；把“常浩本人在飞书私聊说的话”映射为 `user` 由调用方（Hermes 技能）负责，见第 9 节限制 1。

### 4.5 三个事件入口与幂等

统一入口 `ingest_event(source, kind, idem_key, actor, payload, handler)`：

- 幂等键已存在：不调用 handler，只给原事件 `dup_count + 1`、更新 `last_seen_at`，返回 `applied=False` 与原事件 id。
- 幂等键不存在：在 SAVEPOINT 内先执行 handler 再写事件；handler 抛 `StateError` 时回滚到 SAVEPOINT，事件仍写入但 `applied=0`、`result` 存拒绝原因（可追溯）；handler 抛其他异常则整个事务回滚、不留任何痕迹。
- 所有状态变化和事件在同一事务里提交；最外层 `BEGIN IMMEDIATE`，内层 SAVEPOINT。

| 入口 | source | 幂等键来源 | 本轮提供的接口 |
|---|---|---|---|
| 用户消息（飞书私聊、桌面会话） | `user` | 调用方给（飞书消息 id 等） | `create_goal(by="user")`、`authorize_goal`、`unblock_task`、`cancel_*`、`complete_goal`、`ingest_event(source="user")` |
| 主动发现（定时检查、扫描台账、重启恢复） | `discovery` / `system` | `order.sync:<单号>:<updated>:<状态>`；内部转换按对象事件序号生成 | `create_goal(by="hermes")` → observed、`sync_orders`、`recover` |
| Agent 回执（车间跑完） | `agent` | 回执内容哈希 `run.receipt:<Run>:<sha1 前 16 位>` | `receive_receipt`、`finish_run`、`update_run` |

内部转换（如 `set_ready`、`authorize_goal`）的幂等不靠键，靠状态检查：已处于目标状态即返回 `applied=False`，不记新事件。

### 4.6 执行与反馈路径

- **向下执行**：常浩授权目标 → 任务 `ready` → Hermes 调 `start_run(idem_key=飞书消息 id, order_no=派单单号)` → `dispatch.py new / run`（执行层照旧）→ 车间在独立 worktree 干活。
- **向上反馈**：`receipt.json` → `receive_receipt` → Run `done` → 任务 `review` → Hermes 按 workshop 技能第 4 节回报 → 常浩说“合并” → `dispatch merge` → `sync_orders` 把 `merged / cleaned` 记到 Run → `complete_task`（证据 = PR）→ 目标完成由常浩决定。
- **恢复**（`recover()`，重启或巡检时调用）：
  1. 对每个 `running` 的 Run：若探针（`probe(run)`，B2 接台账）给出终态且转换合法，按探针结果结算；否则看最近心跳（`heartbeat_at`，无则 `started_at`，再无则 `created_at`）距今是否超过 `STALE_AFTER = 7200` 秒，超过则标 `stale` 并把任务转 blocked(technical)，原因写明「恢复时发现 N 秒没有心跳」。
  2. 处于 `running` 却没有进行中 Run 的任务：转 blocked(technical)。
  3. blocked(dependency) 的任务：依赖都已 completed 且目标仍 authorized，放行到 `ready`。
  4. 每一步独立事务，做到哪一步记到哪一步；最后记一条 `recover` 事件汇总。

### 4.7 跨 Agent 交接协议

交接载荷固定字段：`task_id`、`goal_id`、`run_id`、`order_no`、`agent`、目标 `scope`、任务 `acceptance` 与 `next_step`、`blocked_kind / blocked_reason`、证据 `refs`、幂等键。载体沿用现有的派单 `task.md`（五要素）、`order.json`、`receipt.json`、GitHub issue / PR 正文；状态库只记指针和状态。换执行方 = 前一个 Run 结束后在同一任务上以另一个 `agent` 开新 Run；一个 Run 不换 agent；每个 Run 带自己的 `session_id` 供续跑。

### 4.8 关键技术选择与取舍

| 选择 | 理由与代价 |
|---|---|
| SQLite 单文件 + 标准库 `sqlite3` | 与现有脚本一致（全部只用标准库）；事务、WAL、在线备份现成；不加依赖、不装服务 |
| 单文件模块内置命令行 | 安装方式与其他脚本相同（复制到 `~/.hermes/scripts/`），自检漂移比对自动覆盖；Hermes 技能调用脚本本就是“命令行 + 末行 JSON” |
| 不改 `dispatch.py`，用只读同步接台账 | 对既有 15 张工单和 88 项测试零风险；代价是台账变化要靠 `sync-orders / recover` 拉取，B2 再加写入钩子 |
| Run 状态沿用台账词 | 省一层映射，`order.json` 与 Run 一一对应 |
| 阻塞分四类 | 只有这四类在处理规则上不同：decision 永远要常浩，technical 可自动重试两次，dependency 可自动放行，external 要人工说明 |
| 事件表 + 幂等键 + `dup_count` | 既防重复又留痕；被拒绝的事件也记录 |
| 外部事件的键由调用方给，内部转换按序号生成 | 外部事件天然有稳定 id；内部转换的幂等靠状态检查 |
| 不用 Hermes 自带 `kanban.db` | 内部表随版本变；长期状态应自己掌握 schema 与迁移 |
| 库放 Application Support 而非 `~/.hermes` | 任务书建议；与 Hermes 升级、备份互不干扰 |
| 兼容系统 Python 3.9 | Hermes 技能实际用 `/usr/bin/python3`（3.9.6）调脚本；名册测试命令用的 `python3` 是 3.14，两者都要过 |

### 5.2 命令行

`python3 twin_state.py [--db 路径] <子命令> …`，每条命令最后一行输出 JSON（`ok`、`msg` 及附加字段），成功退出码 0、拒绝退出码 1，与 `dispatch.py` 一致。子命令：`init`、`backup [--to]`、`restore --from F --yes`、`recover [--stale-after 秒] [--dispatch 目录] [--no-sync]`（默认先同步台账再恢复）、`sync-orders [--dispatch]`、`goal-new / goal-authorize / goal-complete / goal-cancel`、`task-new / task-ready / task-block / task-unblock / task-retry / task-complete / task-rework / task-cancel`、`run-start / run-finish / run-receipt / run-link`、`ref-add`、`show <id>`、`list`、`events <id>`。所有改状态的命令都要 `--by <角色>`。

### 5.3 与派单台账的兼容方式

- `read_orders` 只读扫描 `~/.hermes/dispatch/D*/order.json`（`DT_DISPATCH` 可改），坏 JSON、非对象、缺单号的文件跳过；有 `out/receipt.json` 且为对象时一并读入。
- `sync_orders` 对每张单以 `order.sync:<单号>:<updated>:<状态>` 为幂等键：新单登记为**未关联任务**的 Run（`agent` 取 `tool`，`session_id` 取回执，证据记 project、mode、branch、base、issue、issue_url、pr、pr_url、merged_to、cwd、exit_code、回执结构化字段、台账目录路径），**不建目标、不建任务**；已登记的单只在状态变化时更新，关联了任务的 Run 到终态才按 4.3 的规则反映到任务。
- 历史工单与新任务的关联只能显式 `link_run`；进行中的 Run 关联到 `ready` 任务时任务转 `running`。
- 台账文件只读，不改、不删、不重写。

## 9. 已知限制与未做事项

1. **身份映射在库外**：库只认 `by="user"`；把飞书消息的发送者 open_id 校验为常浩本人并映射为 `user`，由 Hermes 技能承担，B1 未做。B2 应把该校验写进技能或命令行层（例如 `--from-open-id` 比对 `lark-identity` 里的本人 open_id），并加测试。
2. **台账同步是拉取式**：`dispatch.py` 没有写入钩子，状态库可能滞后到下一次 `sync-orders / recover`。B2 第一步建议用 Hermes 无模型定时任务跑 `recover`（默认先同步再恢复），零改动现有脚本；或给 `dispatch.py` 的 `save()` 加钩子。
3. **心跳无人打**：`dispatch.py / run_worker.py` 不会调用 `heartbeat`；经同步进来的 running 工单以回执或台账时间为起点，超过 7200 秒即判 stale。派单 `--timeout` 大于 2 小时的长任务可能被误判；`recover` 带探针（读台账）时以台账为准，所以 B2 的定时任务必须保持“先同步、再恢复”的顺序（命令行 `recover` 默认即如此）。
4. **依赖环未检测**：两个任务互相依赖会一直 blocked(dependency)，需人工解。
5. **事件表只增不删**：没有归档策略；当前量级（每天几十条）数年内不是问题。
6. **`refs.kind` 为自由文本**：没有枚举校验，靠约定（github_pr / github_issue / feishu_task / obsidian_note / file / dispatch_order / url）。
7. **`restore` 不校验备份来源与完整性**（SQLite 自身的文件头校验除外）。
8. **`sync_orders` 遇到不认识的台账状态只记在返回值的 `skipped` 里**，不记事件。
9. **Run 结果只回写处于 running 的任务**：任务被人工改为其他状态后，Run 结果不再自动回写，需人工处理（测试 06 覆盖，属有意为之，但评审可判断是否合适）。
10. **未接入任何技能、未改 SOUL**：模块目前是“可用但无人用”的状态，这是任务书的 B1 范围。

## 二、F1｜P0｜阻断合并：迟到工单与旧关联键

### 现象与根因

`reconcile_claim` 在预留 owner 退出、没有 child 身份且租约 900 秒已过时，可以把预留置为 `void`。但“child 身份尚未写入”既可能表示没启动，也可能是 `Popen` 启动后父进程来不及写入。`dispatch.py cmd_new` 的锁前 `git fetch` 可以超过租约，且锁内没有再次核对 `--sched-key` 对应的预留仍活跃。一旦迟到的旧 key 单到达，`recover_claims` 忽略已 `void` 的 key，Task 又会被判为可派。

### 必做改动

1. **明确可安全作废的持久证据。** 不得把“没有 child 登记”推断成“从未启动 child”。无法证明没有开单进程且可能存在尚未编号的开单时，一律 fail closed，预留 `unsafe`、停止该任务再次派单，并提供人工核对信息。可用数据库里的 durable spawn 阶段标记等轻量方式实现；勿另建新的调度数据库。
2. **晚到 key 的最后入口防线。** `dispatch new --sched-key` 在派单编号锁内、任何目录创建前，复核关联键归属、状态和任务的一致性。过期时间本身不等于可作废；实际已 `void` / `released` / `unsafe` / `linked` 的 key 不得再次生成新的工单。若采用不依赖 DB 的等价防线，需要证明 crash 与 stale owner 下同样安全。普通不带 `--sched-key` 的人工开单路径保持原行为。
3. **已生成的迟到游离工单可观测。** 已关闭关联键如果仍对应一个订单，恢复或报告必须发出显式 `unsafe/orphan` 信号、保留证据；不可默默跳过，不可自动删除工单，不可自动归属 Task。
4. **锁顺序约束。** 如果 dispatch 在持派单锁期间读预留/状态库，保持 `派单锁 → SQLite` 的既有顺序，禁止任何代码在持 SQLite 写事务时再等待派单锁；验证无死锁及锁超时处理。

### RED 必须新增

- 在临时库中模拟 `claim -> child 已启动但 on_spawn 尚未记录 -> owner 被 SIGKILL -> 租约经过 -> dispatch new 迟到`。不得出现先 `void` 后成功第二次关联/派单。
- 使用受控阻塞执行器模拟锁前 `git fetch` 超过 900 秒（可控时钟，不需要真实等待 900 秒）；旧 key 在锁内二次校验失败且不产生新单。
- 旧 key 对应 `void/released/unsafe/linked` 时开单拒绝；手工 `new` 无 sched key 仍成功；两个调度器争同任务仍只留一个有效预留。
- 迟到游离单进入人工可见的 `unsafe/orphan`，但不会被重新自动链接或执行。
- 崩溃后不确定是否曾 spawn，宁可保留 `unsafe`，不能误放行再次调度。

### GREEN 验收

同一 Task 在上述所有崩溃窗口中，**不会因作废/释放导致新的工单和迟到旧工单同时被认为可以执行**。对未知状态的处理必须阻止自动二次派单，保留足够证据给常浩决策。不能以“旧单只是未关联 Run”替代该性质。

## 三、F2｜P1｜报告确认时机：输出不等于送达

### 现象与根因

`twin_scheduler.py cmd_report` 打印 stdout 后立刻 `ack`，而 Hermes cron 的 stdout 将在脚本退出之后才尝试飞书投递。若传输失败，当前指纹已记 `sched.report`，后续不会再提醒。

独立隔离复现：`pending_before 1` → 模拟输出丢失 → `pending_after 0`。

### 必做改动

1. **发送与确认分离。** `report` 只读发现待报事件 / 生成投递批次；仅可信投递端确认实际送达之后才能 `ack`。不得用 `print`、`exit 0`、产出 JSON、调用发送命令但没有成功响应等弱证据冒充“已送达”。
2. **失败保留待报。** 发送失败、超时、进程崩溃、响应未知时仍可重试；允许可能的重复提醒，不能静默漏报。
3. **确认幂等。** 同一指纹多次 ack 不重复创建报告事件，报告内容不泄漏受限原文。
4. **部署闸门同步。** 如果本批没有可信飞书投递确认适配器，则 `report --quiet` 不得自动 ack；B22-G5 明确阻止自动投递启用，直到确认反馈机制接通且端到端测试通过。不能因为已有 `report` 实现就宣称 G5 可启用。

### RED 必须新增

- 输出成功、投递失败或结果丢弃后，报告仍为 pending。
- 投递确认后，报告从 pending 消失；重复确认幂等。
- 崩溃在输出后、确认前，可在下一轮重新取得同一报告。
- 没有新增问题时 `report --quiet` 不输出；已有同一事项不因重试生成新任务或工单。

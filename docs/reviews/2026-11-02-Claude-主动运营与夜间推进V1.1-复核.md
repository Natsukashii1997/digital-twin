- **附录（远期设计参考，不施工）**：V1.1 的 §4、§5、§6 和第 2、4、5 批原样移过去，开头注明“以后启动时，以 ARCHITECTURE M4 当时的状态为前提重新评审”。

### R2 三份报告逐一写清（V1.1 是按“有夜推”写的，要重写）

| 报告 | 目的（常浩拿它做什么） | 内容 | 主要数据来源 |
|---|---|---|---|
| **早报 8:00** | 一睁眼就知道今天先推哪 3 件 | 今天最该推的 3 件（写明出处日期、在哪个项目、交给谁）；触发类提醒（截止前一天和当天、挂起满 4 周、同一阻塞连续出现 3 份晚报、晚报断档）；周一加“本周焦点”（周启）；隔夜有新变化才写 | 昨晚晚报的台账记录 + 隔夜的 GitHub 增量；用 notepad 去重 |
| **晚报 22:00** | 收工时看清今天推进了什么、明天推什么；同时是当天的正式记录 | **推送版**：各项目今日增量、证据、卡点、下一步，加不超过 3 条推荐（为什么现在做、交给谁、用哪个通道）。**台账版**：按 T1 日报结构（今天的变化 / 还开着的事 / 卡点 / 今天的决定 / 项目进展 / 下个工作日先推） | 名册、各项目 CURRENT、GitHub（复用 `progress_data.py` / `report_data.py`）；写台账复用 `report_publish.py` |
| **周报 周五 18:00** | 本周收口、定下周焦点 | T1 周报结构，“上周焦点回看”改成“本周焦点回看”；含原周五收口（本周出现过、还没关闭的行动）；加“本周可固化的做法（≤3，附证据，没有就不写）” | 本周各天的台账 + 周五当天的实时快照（见 R3） |

V1.1 §3.1、§3.2 里只对夜推有意义的项全部移到附录，包括：计划号、哈希、“是否适合夜推”、“上次夜推命中率”、晨报开头的“夜间窗口是否运行”。

**推送版和台账版要从同一份事实快照生成**，不能让模型写两遍，否则两边可能对不上。

### R3 时间口径（V1.1 没有，汇报准不准全看这一条）

1. **台账日的边界**：晚报 22:00 出，22:00 到 24:00 发生的事会落在两份晚报之间。建议把台账日定义为“**前一次晚报的取数时刻，到本次晚报的取数时刻**”，按取数时刻衔接，不按自然日切，这样不重不漏。周末和节假日不发晚报的话，周一晚报覆盖“周五晚报之后到周一 22:00”。
2. **周五的冲突**：周报 18:00 出，但周五的台账要到 22:00 才写。如果周报只读台账，就会漏掉周五一整天。两个办法，要常浩选（V1.2 列为待确认，写上推荐）：
   - **(推荐) 周五不发晚报**：18:00 的周报同时写周五的台账，周五 18:00 以后的事并进周一。
   - 周五照发晚报：周报取周一到周四的台账 + 周五 18:00 的实时快照；周五晚报只报 18:00 以后的增量。
3. **周一早报 = 周启**：读的是上周五周报定的“下周焦点”，不重新排一遍。

### R4 降级和依赖链

- 早报依赖前一晚的晚报。晚报失败或降级时，早报**必须在开头说明**“昨晚晚报未生成 / 只有降级版”，然后直接从原始事实取数，不能把缺一天当成“没变化”。
- 三份报告都要设 `--failure-deliver`，并有纯脚本的事实版降级（11-02 周报因等模型 934 秒失败就是先例）。
- 派发迟到要写进报告：本机记录到日报晚了 6 分钟、周报晚了 29 分钟。要定一个可接受的迟到上限（比如 15 分钟），超过就在报告抬头标出“迟到 N 分钟”。不要为了准点去改系统电源设置，这一条沿用 V1.1 的写法。

### R5 信息边界（V1.1 没写，晚报接替日报以后必须写）

晚报的推送版只发常浩私聊，可以按 PRD 第 8 节引用受限内容（只给结论和路径）。**台账版写进台账文档，牛马之家日报页也会读，读者范围比私聊大**。V1.2 要写明：

- 台账版不写受限内容和没有标注分级的 Vault 内容；
- 在施工前核对台账文档和牛马之家日报页实际有哪些读者，按核对结果决定台账版能写到什么级别。

### R6 事实更正：飞书回读已经验证过，但现有核验函数夜里用不了（放进附录）

V1.1 §5.3 和 §11 把“飞书机器人能否按 message_id 回读消息”列为未知项。实际上已经验证过：B2.1 T03 的 `twin_identity.py` 用猛鬼兽 bot 身份执行 `lark-cli im +messages-mget` 回读常浩私聊，探针 ① 已经做了（CURRENT 第 345 行）。

真正的问题是现成的 `verify_message` 不能原样拿来做夜间二次核验，原因有两个：

- 它默认只认 10 分钟内的消息，22:00 批准、03:00 派单时核验一定会被拒；
- 它通过 `identity_uses` 让一条消息只能用一次，和“每次派单前都回查”冲突。

以后要做时，需要一个专门核验“批准消息”的函数：时效按窗口算；一次性占用只在签发时做；派单前回查只读、不占用；另外要实测回读结果里有没有消息正文。

### R7 有用率怎么收集

PRD 的验收是“有用率 ≥ 70%”，但 V1.1 §8.1 没写常浩怎么反馈。V1.2 要给出一个最省事的办法，并标注“需实测”。建议：常浩对报告加表情回应（👍 / 👎），由取数脚本读出来统计；不回应的不计入分母，同时披露反馈覆盖率（这一条 V1.1 已经写了）。机器人能不能读到表情回应，要实测。

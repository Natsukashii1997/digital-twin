## 6. 风险、已知缺口与范围外发现

- **不声称 exactly-once**：靠关联键 + 对账收口，四个崩溃窗口见 D1 第 5 节。
- Popen 返回到记下开单子进程身份之间的极短窗口：靠 900 秒租约兜底。若 `dispatch new` 卡在锁前的 `git fetch` 超过租约且预留已 void，之后开出的单带旧关联键、作为未关联 Run 导入，不会被关联成第二张；**但报告不会专门提示这种单**——建议 B2.4 在 `findings` 里加“带关联键却没有未结预留的单”。
- 只支持单机：别的主机记录的身份一律 unknown。
- dispatch 身份核对的同一秒歧义：PID 复用的新进程恰好与 `run_started` 同一秒启动时会被当成原 dispatch → 最多把体征判成 suspect 而不是 unknown；调度器从不对 dispatch 发信号，影响限于报告措辞。
- `worker.json` 是车间自报，没有签名：可用来防误判、防误杀，**不能当执行主体的可信证明**（B2.3 / B3 不应据此认证）。
- B2.1 前的历史单没有身份字段：体征一律 unknown，不下判断。
- `tick --execute` 启用后会在派单根目录下建 `.sched-tasks/`（调度生成的任务说明）；台账扫描只看 `D*`，无影响。
- 命令行 `cancel` 会写建议事件（不是只读）；`plan / observe` 只读。
- 小改动：`Store.open` 迁移失败（如程序版本比库旧）时关闭连接——原来会留一个打开的连接，回退路径会走到；行为上只是不再泄漏。
- 范围外（未改）：workshop / progress 技能仍按原样派单与查询，接入契约见第 7 节；B1 `recover` 的 suspect 列表没有接入 `observe`，二者并列可用。

## 7. B2.3 接口交接（D5）

可直接消费的稳定字段 / 接口：

| 来源 | 字段 | 用途 |
|---|---|---|
| `twin_scheduler.decide` | `task_id / decision / reason / evidence / next_action`；原因码表见 D2 第 1 节 | 跨 Agent 交接前判断“现在该不该交、为什么” |
| `sched_claims` | `sched_key / state / order_no / run_id / owner` + `sched.*` 事件 | 交接链路上的“谁在什么时候为哪个任务开了哪张单” |
| `order.json` | `sched_key`、`run_started / run_host / dispatch_pid` | 把一次执行和调度决策、执行时段对上 |
| `out/worker.json` | `pid / pgid / sid / started / host / out / at` | 执行进程身份（自报，非认证） |
| `observe` | `vital` 六值 + `evidence.worker / dispatch / receipt` | 交接前确认上一棒已真正停下 |
| `report` | `level / kind / object / reason / fingerprint` | 交接异常的低噪声提醒 |

B2.3 需要补的（本批刻意没做）：

1. **每个任务的派单规格**：现在执行工具取 `task.owner`（claude / codex），只读 / 写入由 `tick --mode` 给，任务说明由调度器按标题 / 验收 / 下一步生成。B2.3 应在交接模板里定义稳定的 `task.md` 结构（目标、边界、上下文指针、验收、交接要求），并决定模式由谁、在哪一层授权。
2. **上下文接力**：上一棒的回执摘要、PR、未决问题如何进入下一棒的 `task.md`；`need_decision` 解除后的续跑说明。
3. **执行主体可信证明**：`worker.json` 只防误判；要证明“确实是某个 Agent 会话执行的”，需要 B3 的审查方身份验证或签名机制。
4. **动作级授权**：B2.1 只能证明消息来源；自动开单（D6 的 B22-G6）在动作级授权落地前保持关闭。

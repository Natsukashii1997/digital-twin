## 1. 正式裁定

## 3. G4-C2 覆盖缺口的裁定

- 16 次实际观察都返回 `run = null`，属于 `twin_scheduler.observe` 中**“台账 running，但状态库尚无对应活动 Run”**分支；这是因为 `DT_STATE_NOTIFY` 仍关闭，观测单是在完成后才手工 reconcile 进入正式库。
- 另一条 **“状态库中已存在活动 Run”** 分支未在生产环境运行中测到。源码显示两条分支都调用 `vital_of` 识别 Worker/dispatch 身份，但前一分支另有 `run` 关联与 `heartbeat_age` 输出。当前证据不能证明这部分生产链路已验收。
- **无需为 G4 立即补开 G4-C2。** G4 D6 的既定要求是运行中体征及身份检查、结束后无活动单、库与台账对账；这些均达到。为降低额外写正式库和开新单的风险，建议将“已有活动 Run 的 observe、Run 关联、heartbeat_age 和异常报告关联”写入 **G5 技术前置测试**；先用隔离库与受控子进程复现，只有确实必要时，再单独申请生产只读单及运行中 reconcile 的授权。
- 不得用本次 16 次 `run = null` 的成功，宣传“已完整验证正式库活动 Run 的运行时观测”或“已完成 G5 端到端通知”。

## 4. 后续部署门槛

**G5 开工前必备：**
1. 常浩确认 G4 授权记录；在 CURRENT / D6 中准确记录 G4 验收结论及运行中活动 Run 分支尚未验收。
2. 更新 D6 当前正式状态（正式 v3 已建）；修正 D7 关于“库版本 2”和固定“15 单”的旧数字，使用检查时实时统计值，保留旧记录的历史背景。
3. 在隔离环境验证 `observe` 的活动 Run 分支、`heartbeat_age`、`findings/report` 对异常状态的映射；生产侧相关操作需要另行授权。
4. 构建可信飞书投递适配层并有实际送达成功/失败的可核查证据。`report` 输出绝不等于发送成功；失败不 `ack`，成功回执后才 `ack`，部分成功只标记已送达项。
5. G5 的频率、收件人、隐私和权限、失败监控、停止/回退均需形成部署方案；未获常浩明确批准前，不建任何 G5 cron。

G6 自动开单、G7 SIGTERM 仍关闭，分别保留各自审批闸门。

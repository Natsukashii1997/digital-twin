## 2. 每个问题的根因与修改

### R1 决策阻塞不得被类型修改绕过

**根因**：`block_task` 对已处于 `blocked` 的任务走了一条“只更新字段”的分支：不校验 `kind` 是否合法（非法值会变成 SQLite 的 CHECK 异常而不是业务拒绝）、不校验原因、不校验权限，于是 `blocked(decision)` 可以被 Hermes 改成 `technical`，再 `retry_task` 回到 `ready`。另有一条同类的旁路：`unblock_task` 对 `technical` 阻塞允许非 user 直接解开，不计入重试上限。

**修改**：
- `block_task`：入口先校验类型与原因（所有分支一致）。已阻塞时同类更新原因照常；改类型时，非 `user` 只能把类型**升级成 `decision`**（更严），`decision` 类只有 `user` 能改成别的类型；其余方向一律 `NotAuthorized`。更新记 `task.block.update` 事件，payload 带 `from`。
- `unblock_task`：`technical` 类由非 user 解开时走 `_retry`（计数并受上限约束）；`external` 类由非 user 解开必须写明来源恢复的依据；`decision` 类仍只有 user；`dependency` 类非 user 要依赖真的完成。
- `retry_task` 与 `unblock_task` 共用 `_retry`，上限只有一处。

**保留**：每次状态维护不需要重复审批——同类更新原因、升级成 decision 都不需要常浩介入。

### R2 历史 Run 不得覆盖当前活动 Run

**根因**：`_settle_task_after_run` 只看“任务是否 running”，不看“这个 Run 是不是任务当前的 Run”。A 过期后任务重试并启动 B，A 的迟到回执（`stale → done` 是合法转换）会把正在由 B 推进的任务改成 `review`。

**修改**：
- 新增 `current_run(task_id)`：任务最后登记的 Run（按插入顺序，`rowid`），不加新字段。
- `_settle_task_after_run` 只在三个条件同时成立时改任务：Run 处于结果状态（`done / guard / failed / stale / abandoned`）、Run 是任务的当前 Run、任务仍在 `running`。否则只记事件：不是当前 Run → `run.late_result`（payload 含当前 Run、任务状态）；任务不在 running → `run.result_not_applied`。Run 自己的状态与证据照常更新，不丢。
- 续跑（见契约 3）同样只对当前 Run 生效，否则记 `run.resume_conflict`。
- 列表查询统一按 `rowid` 排序（原来按 `created_at, id` 排，同一秒内 `R…-10` 会排在 `R…-2` 前面，当前 Run 判定会错）。

**测试**：A 过期 → 重试 → B 运行 → A 迟到成功、B 过期后迟到失败、经台账的旧工单续跑与跑完，任务都仍由当前 Run 推进。

### R3 明确执行完成与验收通过的区别

**根因**：① `receive_receipt` 的判定只检查“有没有失败标志”，空回执或缺字段的回执没有失败标志，被判成 `done`；② `complete_task` 把“存在任意 Ref 或成功 Run”当作完成依据，没有区分证据与结论，也没有人对 `acceptance` 作判断。

**修改**：
- `classify_receipt`：护栏优先；缺 `exit_code` 或 `ended`（`run_worker` 一定会写）、`exit_code` 不是整数 → `failed`，原因写进 Run 的 note 和任务阻塞原因；超时、出错、非零退出 → `failed`；否则 `done`。
- 状态模型新增**验收结论**：`tasks` 表加 `verdict / verdict_by / verdict_basis / verdict_cites / verdict_at`；新增 `accept_task(task_id, by, basis, cites, passed=True)`：只在 `review` 里；必须写依据并引用本任务已有的证据（Run id 或 `kind:ref`，由 `task_evidence` 列出）；执行当前 Run 的 agent 不能给自己下结论（常浩可以）；`system` 不能下结论；不通过 = 退回 `ready`；续跑或返工回到 `ready / running` 时结论作废。
- `complete_task` 只认 `verdict = passed`，且当前 Run 不在进行中；“有 PR 引用”或“有成功 Run”都不再构成完成依据。
- 没有建外部验收系统：结论只是任务上的四个字段加一条事件；B3 的 Codex 独立审查就是“开只读单核对后调用 `accept_task(by="codex")`”。

### R4 强化 Run 关联与取消状态一致性

**根因**：① `link_run` 只要求 Run 未关联，进行中的 Run 可以挂到 `observed / blocked / review / completed / canceled` 的任务上，也不查目标是否授权、项目是否一致、任务是否已有活动 Run；② `cancel_task` 把进行中的 Run 直接写成 `abandoned`，而进程可能还在跑；`cancel_goal` 直接改任务状态，根本不处理 Run。

**修改**：
- `link_run`：任务处于终态一律拒绝；Run 的 `project`（来自台账）与目标的 `project` 都有且不同时拒绝；进行中的 Run 只能挂到 `ready`、目标已授权、没有其他活动 Run 的任务上（任务随之 `running`）；已结束的 Run 可以挂到未收尾的任务上作证据。
- 取消改为两段：`cancel_task` / `cancel_goal` 把任务置 `canceled`，对进行中的 Run 记 `cancel_requested_at / cancel_requested_by` 与 `run.cancel_requested` 事件，Run 状态保持 `running`，`list_runs(cancel_pending=True)` 可查；执行层真正停下来（台账变 `abandoned / done / failed`）后，结果只记 `run.result_not_applied`，任务不变。`cancel_goal` 复用 `_cancel_task`，返回所有待取消的 Run。B1 不终止进程，B2 用这张清单去停。

### 契约 1：角色名不等于身份认证

库内 `by="user"` 定性为**内部可信调用约定**（设计文档 3.3 与模块 docstring 写明）：把“常浩本人说的话”映射成 `user` 是调用方（Hermes 技能）的责任，前提是网关层 `FEISHU_ALLOWED_USERS` 只放行常浩、技能把发言人 open_id 传下来。程序侧补一道防误传：命令行 `--by user` 必须带 `--sender <open_id>` 且等于 `OWNER_OPEN_ID`（与 `report_data.ME` 同值），否则 `NotAuthorized`。这不是认证，防不了恶意调用；因此设计文档明确：**身份桥接完成并测试之前，正式运行中的 Hermes 不得用带授权语义的命令行参数操作长期目标**。本轮模块没有安装，目前没有任何调用方。

### 契约 2：建目标 / 任务的幂等

`create_goal` / `create_task` 带 `idem_key` 重复进入时，先查事件表，命中则给原事件 `dup_count + 1` 并返回既有对象，不再触发 UNIQUE 异常。`start_run` 原本就是这样。

### 契约 3：台账同步不无条件覆盖

新增 `_resync_kind(local, ledger)` 五分法：查表合法 → 正常应用；`done / failed → running` → **续跑**（这是 `dispatch run --followup` 的真实流程，原设计没有建模，会被当成非法跳转）；`stale → running` → 过期判断被台账推翻；向前跳过中间状态（如 `done → cleaned`）→ `run.resync`；**终态（cleaned / abandoned）再变、guard 降级或 guard 后续跑、从结果状态回到 new / queued / running** → `run.conflict`，不应用，`sync_orders` 返回 `conflicts` 清单。

续跑作为正式接口 `resume_run(run_id, by)`：`done / failed / stale` 的 Run 回到 `running`；`guard` 的续跑只有常浩能定；任务侧 `_resume_task` 只对当前 Run 生效：`review` 或 `ready` → `running`，`blocked(technical)` → `running`（failed 的续跑计一次重试，超上限不动任务），`blocked(decision / external / dependency)` 不动任务、记 `run.resume_conflict`（要先按对应规则解开）。任务转换表因此增加 `blocked → running`、`review → running`，但只开放给 `resume_run`，`start_run` 仍只接受 `ready`。

### 契约 4：回执白名单

`clip_receipt` 改为只保留 `RECEIPT_KEEP` 里的字段（`run_worker` 回执的结构化字段 + 截到 1000 字的 `summary`），其余键一律不进库；非对象回执当作空。

### 契约 5：重试上限

`MAX_RETRIES` 改为 `Store(max_retries=…)` 可配，默认仍为 2，常量注释与文档注明是临时保护；按故障原因、成本、可逆性分级的重试策略留到 B2，与评审意见一致。

### 契约 6：台账缺失、读不了、没工单

`read_orders` 返回 `status ∈ {ok, missing, unreadable}` 与 `errors`；`sync_orders` 把它带在返回值里；`recover` 对有工单号的 Run：台账 `missing / unreadable` 或没这张单 → 记 `unknown`，不下判断；台账说还在跑 → 保留（超过阈值只列 `suspect`）；台账给了结果 → 按同步规则结算。只有**没有工单号、也查不到台账**的 Run 才按时间判过期。`Store` 新增 `dispatch_dir` 参数，自测里指向临时目录，不会碰真实台账。

### 其他顺手修的小项

备份同一秒再备份自动加序号不覆盖；恢复前对备份文件做 `PRAGMA integrity_check`、检查 `schema_version` 存在且不比程序新，失败不动当前库；任务依赖只能指向同一目标（评审 P2 的“跨目标依赖约束”）。台账里的时间戳是本机 naive 字符串，不再拿来当心跳，心跳一律用本库带时区的时间（返修中发现，已在代码注明）。

## 6. B1 是否具备安全接入 B2 的基础条件

**具备，前提是按下列顺序接入；缺一项都不应在正式环境启用自动恢复或授权类操作。**

1. 身份桥接：技能把发言人 open_id 传给命令行，只对常浩映射 `user`，并有测试；在此之前 Hermes 不调用任何 `--by user` 命令。
2. 真实数据只读核对：在隔离库上用真实台账跑一轮 `sync-orders / recover`，核对 `conflicts`、`suspect`、`unknown` 的判定是否符合实际，再决定正式库的同步方式。
3. 同步机制按评审建议：`dispatch.py` 在可靠写入后通知状态库同步该工单（通知失败不影响派单），轻量定时对账兜底；心跳或进程存活判断到位之前，`recover` 只报 `suspect`、不改状态（现已如此）。
4. 正式库启用前先 `init` + `backup`，巡检加一行“状态库可打开、版本正确、最近备份时间”。

B1 仍未实现、留给 B2 的：身份桥接本身、`dispatch.py` 的事件通知、心跳 / 进程存活、真正终止进程（现在只记“已请求取消”）、技能读写状态库、按故障原因分级的重试策略、主动提醒。这些都在设计文档第 7 节的边界表里。

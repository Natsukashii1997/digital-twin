## 0. 一句话目标

在已验收的 B1 持久状态引擎与 B2.1 事件/身份/台账同步协议之上，让 Hermes 具备**能够解释、恢复且不会误派单的调度机制**。本批在隔离数据库、模拟派单与受控假进程上实现和验收；**不是现在打开正式 Hermes 的自主运行开关**。

B2.2 通过的标志不是创建 cron 或成功执行一张真实业务单，而是：系统对已授权、依赖已满足、状态可信的任务，可以做出可复现的调度决定，在崩溃和重复事件下不重复创建/启动工单，能够识别真实的进程存活与中断，安全完成取消，并在跨会话/重启后正确重建状态。

## 4. 工程任务拆解

### S0 · 基线与执行状态图（P0，首先进行）

- 只读核对现行 `dispatch.py` 的 `new → queued → running → done / failed / guard → pr / merged / cleaned`、`--followup`、并发 2 / 同仓库 1 的实际程序约束。
- 核对 B2.1 `Store.queue()` 八桶的含义、`unsafe` 条件、`sync_order / reconcile / recover` 返回与 `current_run_id` 规则；找出既有 dispatch 中 `next_no` / 并发检查无锁、`run` 未持久记录 PID 的边界。
- 设计一页状态与责任图：**任务候选 → 调度预留 → 派单创建 → Run 关联 → worker 执行 → 真实回执 → review/blocked → 人工/独立验收**；异常路径必须具体。
- 交付 S0 只读差距表及最小改动方案，禁止直接加一套平行 Task 状态机。

### S1 · 持久调度决策与安全过滤（P0）

- 建议引入一个轻量调度入口（例如 `hermes/scripts/twin_scheduler.py`，具体命名可由 Claude 决定），默认 `--dry-run` 或等效不可执行模式。
- 从 `Store.queue()` 和权威状态读取候选。仅对已授权 Goal 下 `ready`、依赖已完成、无现行 Run、无取消请求、无冲突、无未知台账状态的 Task 产生可执行候选。
- `blocked(decision)`、待审查 `review`、`unsafe`、依赖未满足、达到重试上限、状态不确定的任务不得派单。
- 每个决策必须返回可审计的 `task_id / reason / evidence / next_action`；同一状态重复评估产生稳定、可解释的结果。
- 不擅自把优先级变成用户长期决策；没有用户指定排序时可提出解释性建议，但不允许凭 LLM 推断自动重排用户正式目标。

**验收：** 同一 fixture 包含 ready、blocked、review、依赖、stale/suspect、cancel、已完成任务，只有满足授权条件的 Task 入选；决策无状态副作用。

### S2 · 防重复派单、预留与崩溃恢复（P0）

- 研究并实现最小持久**调度预留 / claim / lease**机制，保证多进程或多次 cron 重入不能对同一 Task 同时创建两个实际工单。必要时可在 SQLite 中做追加迁移；不能破坏已有 v1→v2 兼容及迁移路径。
- 调度与 dispatch 是两个事实系统，不能声称跨两者实现了不可验证的“绝对 exactly once”。必须定义**提交前、提交中、提交后、工单已建但 Run 未关联**等崩溃窗口，以及补偿/核对路径。
- 对外部创建动作携带稳定调度关联标识，恢复时先查询已有工单再决定是否重试；若旧工单归属无法证明，**停止并标记 `unsafe`，不得重新派发**。
- 并发边界（总并发 2、单仓库 1）必须由可原子验证的锁/预留约束保证，不能仅靠读完列表再写入。严禁与既有 dispatch 锁形成死锁；必须明确锁顺序和过期策略。
- 系统崩溃、进程异常退出、通知丢失和同秒重复调用后的状态不能走向两个活动 Run。

**验收：** 至少复现同 Task 双调度、多 Task 同仓库、两调度器同时启动、派单创建后进程崩溃、Run 关联前崩溃、lease 过期、通知漏发、重复恢复；每种有证据表明无重复执行或以 `unsafe` 人工拦截收口。

### S3 · 真实执行生命体征与跨会话恢复（P0）

- 分清 `dispatch` 台账中“running”字符串与真实 worker 仍存活。必要时补充持久进程身份（PID + 启动标识/进程组/工单标识等，按实际可验证信息最小设计）、开始时间、心跳和最后可验证进度。
- 不允许仅因心跳超时就把 Run 判定失败或杀掉进程；先通过台账、回执、进程活性、身份匹配组合判定。
- 定义运行状态 `alive / suspect / lost / finished / unknown` 等内部观察结果（不要求盲目改 B1 既有 Run 状态）；说明哪些可自动对账，哪些必须等人工处理。
- 避免 PID 重用误判：只有匹配已记录进程身份、工作目录/命令等受控证据才能确认；无证据时保持未知。
- 支持**跨聊天窗口、Hermes 重启、调度程序重启**后，通过状态库+台账恢复 Run 和待办，无须依赖上一轮 LLM 对话记忆。

**验收：** 用可控测试进程模拟正常退出、崩溃、延迟回执、残留 running、无 PID、PID 复用、心跳丢失与重启；不误判活跃任务，也不假装已经自动恢复成功。

### S4 · 取消请求的可执行闭环（P0）

- 消费 B1 `cancel_pending`：取消任务先进入请求状态，不能仅将 Run 标记 `abandoned` 就当 worker 已停止。
- 仅在**明确为本调度系统拥有、进程身份验证成功**的受控子进程上允许模拟/隔离测试 `SIGTERM`；必要时定义有界等待、确认停止、回执和台账更新。
- 对无法确认进程身份、外部进程、用户未授权取消、进程已结束/已复用的情况：**绝对不能 kill**；输出人工处理建议与可追溯事件。
- 任何升级到强制终止的策略（如 SIGKILL）必须具有额外明确策略门槛，并且不在本批真实环境中执行。
- 同时检查取消与 worker 完成的竞态，不能让旧回执重新打开已取消任务。

### S5 · 恢复、重试和异常分级（P1）

- 将 `technical / decision / external / unknown` 等阻塞原因映射为可检查的下一步，不从 `need_decision` 推断自主放权。
- 只有已知可恢复的技术失败、仍在授权范围、未超过次数限制、执行进程已确认退出并且与现行工单对账无冲突时，才允许产生**重试建议**。
- 默认不在正式环境执行重试；在隔离模拟中检验恢复路径及必要的退避策略。
- 对重复失败、外部系统不可用、已达到上限、证据冲突进入阻塞或 `unsafe`，不形成无穷循环。

### S6 · 低噪声对账与调度状态观测（P1）

- 基于已有 `reconcile()`、`recover()`、`queue()` 开发可供 Hermes **未来**无模型 cron 调用的查询/报告入口；**本批不创建 cron**。
- 正常无变化输出为空或稳定可解析的 JSON，异常输出必须包含确切原因与来源证据；避免重复通知。建议告警级别：仅错误或需用户决定才触达，普通对账不触达。
- 通知去重持久化、执行失败重试和状态恢复必须可以单独测试；不能靠 LLM 会话变量记忆。
- 留下 workshop / progress 的接入契约，不在本批安装真实 Skill。若需更新源文件，必须明确该更新不会自动部署。
- 同步考虑目前工程自检（每天 09:50）及健康巡检（09:45）的既有机制，不另外造一个长期巡检系统。

### S7 · 隔离端到端、故障注入和交付（P0，最终必做）

至少覆盖：

1. 已授权 Goal，依赖解除 → ready → 仅模拟创建一张工单 → 当前 Run 关联 → 接收回执 → review，**未经验收不能 complete**。
2. 未授权目标 / decision 阻塞 / 依赖未完成 → 绝不创建工单。
3. 两个调度器同时启动同一 Task → 只一个获得预留；失败方不执行。
4. 派单创建成功后调度器崩溃 → 重启后识别既有工单并恢复关联，无法识别则 `unsafe`。
5. worker 心跳停止但实际进程仍活着 → 不重试、不终止；进程已退出但无回执 → 仍按不确定处理。
6. 取消与自然完成竞争 → 结果一致，且不误 kill 非所属进程。
7. 同一事件/回执反复输入与恢复 → 不重复改变状态、不重建工单。
8. 重启恢复、日志/审计、敏感信息脱敏及回退路径完整。

测试优先使用临时目录、假工单、Mock lark/GitHub、受控子进程，不读取真实私聊、不启动真实 Agent 工单、不连接生产 SQLite。

**最低回归基线：** 在 B2.1 HEAD 上原有 **188 项测试**全部通过，且新增调度、并发、崩溃恢复与取消负向测试通过；分别运行系统 Python 3.9.6 和项目 Python 3.14.5。测试命令、计数和退出码必须真实记录，禁止仅写“已通过”。

## 5. 重要架构取舍

- **只做一个小而可靠的调度循环**，不要建设工作流编排平台、消息总线、复杂队列集群或第二套数据库。
- B1 是长期 Task 状态真源；dispatch 是执行证据真源；调度预留与恢复状态可由 B1 SQLite 的追加 schema 或最小附属数据承担，避免双主状态。
- 若无法无歧义地跨越数据库事务与外部工单创建边界，就设计稳定关联键与补偿对账；不要写“实现 exactly-once 远端执行”的虚假保证。
- 并发保护应尽量复用既有车间的边界/护栏，只补程序级互斥，不改坏原有人工派单路径。
- **先证明真实进程身份与状态，再考虑自动恢复**；不因时间过去或消息没有回复就擅自重跑。
- B2.1 的“合法用户消息”不得被当作“模型提出的动作已获许可”。**动作级授权未落实以前，正式自动派单保持关闭。**
- `task.accept` / review Run 的独立性完整验证仍为 B3 关键门槛，本批不能自称已经完成 B3 审计机制。

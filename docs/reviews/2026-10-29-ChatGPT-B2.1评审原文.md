## 2. 合并前必须修正：P0 身份核验闭环

### P0-1 `verify_message` 没有严格绑定请求消息、用户私聊及配置会话

**代码位置：** `hermes/scripts/twin_identity.py`，`verify_message()`。

实际行为：

1. 当回读结果带 `chat_type="p2p"` 时，即使 **`owner_chat_id` 未配置**或**回读 `chat_id` 与已配置的 `owner_chat_id` 不同**，依然返回 `ok=True`。
2. 没有比对回读结果的 `message_id` 与传入的 `message_id`。模拟回读另一条 ID 的本人消息，仍然返回通过。
3. 对 `sender_type=None` 的结果也可能接受；真实 mget 探针已能返回 `sender_type="user"`，应按明确的用户类型做 fail-closed 校验。

**修复要求：**

- 请求消息 ID 与回读消息 ID 必须精确一致；单条回读结果必须唯一、字段完整，避免使用列表中的错误消息。
- `owner_chat_id` 没配置时，一律拒绝用户授权核实，不允许 `chat_type="p2p"` 绕过；配置后始终要求回读 `chat_id == owner_chat_id`。
- 回读 `chat_type` 明确为群聊时拒绝；明确为 p2p 可以作为额外证据，不能替代 chat_id 绑定。
- `sender_type` 必须明确为 `user`；身份类型不明时拒绝，不默默猜测。
- 原有私人标识继续不得打印、写入仓库和诊断报告。

**必须新增的负向测试：** p2p 但缺 owner_chat_id；p2p 但 chat_id 不同；返回的 message_id 不一致；sender_type 缺失；群聊；真实 mget 缺失 chat_type 但 chat_id 正确的兼容正向测试。

### P0-2 `setup-chat` 可能把群聊误登记为本人私聊

**代码位置：** `twin_identity.py` 的 `setup-chat`。

该操作目前只要求消息发送者为本人、`chat_id` 非空，**没有验证该 chat_id 所指的是私聊**。ChatGPT 用虚构的本人群聊消息执行 `setup-chat` 预览分支，得到 `ok=true`、退出码 0。因此，若用户执行 `--write`，存在把群聊 chat_id 写入正式 `owner_chat_id` 的风险。

**修复要求：**

- 私聊配置不得从任意“用户本人发送的消息”直接推导。
- 如飞书 mget 本身不提供会话类型，应通过可信 chat-info 接口或网关侧可信会话元数据补查；若现有工具无法实现，必须 fail closed，提供用户可审阅的安全手工配置方案，不得将无法确认的群聊写为私聊。
- `setup-chat --write` 在检查通过前不得创建/覆盖配置文件。保留原文件、安全权限和故障回滚。
- 新增群聊、缺失会话类型且无额外证据、合法私聊、配置写入失败的测试。

以上两项都是现阶段已实现“可信身份桥接”的内部正确性要求，不能笼统以未来的网关 HMAC 才会解决为理由跳过。**但即便修好，也不等于已经证明本次消息授权了某个具体动作**；动作级确认与可信网关凭据仍是独立的后续生产门槛。

## 3. 合并前建议一并收口：P1 事务、失败重试与来源边界

### P1-1 用户 CLI 的消息占用与状态变更并非同一事务

**代码位置：** `twin_state.py`：`_user_turn()`、`run_cli()`、`Store.claim_message()`。

当前 CLI 先通过一个已提交的事务占用 `identity_uses`，再执行另一事务中的真实状态变化；遇到普通异常可释放占用，但进程在两个事务之间被杀死/崩溃时，用户消息会永久占用而动作未完成。文档中“一条消息的占用与动作在同一事务”只对 `twin_events.ingest` 的 handler 路径成立，**对直接命令行路径不成立**。

**要求：** 让直接 CLI 用户写路径同样具备原子性，或明确将该路径标为仅供验证、禁止用于正式授权写入，统一走事务化事件入口。在退出码、异常、杀进程、重复调用下分别验证“占用状态与业务动作”一致。不可只依赖 `finally` 清理。

### P1-2 拒绝事件的幂等语义与“可重试”声明冲突

**代码位置：** `twin_events.ingest()` 与 `Store.ingest_event()`。

实际复现：相同 `event_id` 的用户事件，第一次因未配置 `owner_chat_id` 被记为 `applied=0`；随后补齐配置、以相同 `event_id` 重试，返回 `duplicate_of`，不重新校验、不执行目标创建，Goal 仍为 0。消息占用虽然没有发生，**事件 ID 已经被拒绝记录占用**。

**要求：** 确立明确、可测试的策略：

- 永久拒绝（伪造、越权）不能静默转为成功；若用户重新授权需新的可信消息/事件。
- 临时失败（飞书超时、服务不可达等）应有明确安全重试路径，重试时不能重复产生副作用。
- 告知调用者“先前拒绝不可复用事件 ID”还是“允许受控重试”，不能将前次 `applied=0` 的记录当作成功事件的普通重复。
- 在文档和 CLI 输出中清楚标注拒绝、可重试、必须新消息三者的区别。

### P1-3 `order.sync` 未限制导入目录

**代码位置：** `twin_events.ingest()` → `Store.sync_order()` → `Store.read_order()`。

实测一个 `source="dispatch"` 的信封，将 `payload.order_dir` 指到配置的 `dispatch_dir` **之外**、自行构造的 `order.json` 目录，状态库仍然成功导入该 Run。

**要求：**

- 验证 `order_dir` 的规范化实路径，限定在可信派单根目录内，并验证目录名/`order.json.no` 一致；禁止符号链接逃逸。
- 信封 `source="dispatch"` 字符串本身不能被视为真实派单来源证明。必要时将内部可信通知与外部事件接入分开。
- 新增越界路径、符号链接、单号不匹配、合法根目录的测试。

## 0. 评审裁定

**有条件通过；暂不批准合并 PR #30。**

S1–S7 的主体实现、SQLite v3 迁移、单机并发锁、进程身份检查、只读决策、取消防误杀边界均已落地。259 项回归两套解释器独立通过。但独立负向测试确认两个本批核心保障缺口：

1. **P0：迟到开单与预留作废可能并存，导致同一任务再次变成可派。** 已有文档承认“子进程身份尚未记录时的 900 秒窗口”，但本次独立复现表明它会让同一个 Task 重新符合 `dispatch` 条件，之后迟到工单仍可出现。不能仅留给 B2.4 报告提示。
2. **P1：报告在实际送达前就确认已报告，传输失败会永久吞掉重要提醒。** `cmd_report` 将 JSON 写到 stdout 后立即 `ack`，而 Hermes cron 对飞书的投递发生在脚本退出之后。输出成功不等于送达成功。隔离模拟丢弃 stdout 后，下次待报告数量从 1 变成 0。

不要求重写 B2.2、不扩展到 B2.3。以上两项在同一 PR #30 分支定向修复，并用红绿测试验证后再复核。

## 2. P0 负向复现：关闭预留后的迟到工单

### 2.1 代码依据

- `twin_scheduler.py`：`reconcile_claim` 在 `claimed`、无工单、租约已过、已登记 owner 进程消失且没有 child 身份的情况下执行 `claim_close(..., 'void')`。
- `twin_scheduler.py`：`decide` 只把 `CLAIM_OPEN = ('claimed','ordered','unsafe')` 视为未结预留。`void` 后原任务若仍 ready，可再次得到 `eligible`。
- `dispatch.py`：`cmd_new` 在取得派单锁前进行可能耗时的 `git fetch`，在锁内生成目录时仅校验 `--sched-key` 的格式，不验证该 key 对应的预留是否仍有效。
- `recover_claims` 仅扫描 `claimed` / `ordered`；`void` 的旧关联键后续出现工单时不再进入该恢复流程。

### 2.2 隔离复现

在 `TemporaryDirectory` 创建独立状态库和派单目录，用可控时钟：

1. 创建一个授权 Goal、一个 ready Task；创建 `claimed` 预留，模拟 owner 已退出、child 未能登记。
2. 将测试时钟推进 901 秒；`reconcile_claim` 返回 `void`。
3. `decide` 对同一 Task 再次返回 `dispatch`。
4. 模拟迟到的旧 `dispatch new` 将带旧 `sched_key` 的 `order.json` 和关联文件写入目录。
5. `recover_claims` 返回空集，而 `decide` 仍返回 `dispatch`。

**实际独立输出：**

```text
claim True void void after_void dispatch late_order_exists True recover_old_claims {} after_late_order dispatch
```

本次没有打开正式开单功能，也没有触碰真实台账。该用例复现的是代码允许的跨进程时序，不声称真实生产发生了这次事故。

### 2.3 裁定

**P0，合并前必须收口。** 该窗口直接违反“同一任务不因恢复机制开出第二张工单”的基础目标。即使迟到单只是游离 Run，也可能进入后续人工确认或执行链，不能仅靠以后显示告警解决。

建议采用保守方案：在缺少“从未启动开单子进程”的持久证据时，不自动 `void`，而标记 `unsafe` 并占住该任务；同时在 `dispatch new --sched-key` 的编号锁内核对预留仍有效，不接受已 `void/released/linked/unsafe` 的旧键（关联一致性与历史运行兼容性需由测试证明）。允许 Claude 提出更简洁的等价方案，但不得引入自动重试或删除历史单。

## 3. P1 负向复现：报告送达前确认

### 3.1 代码依据

`hermes/scripts/twin_scheduler.py` 中：

```python
print(json.dumps(...))
ack(s, new)
```

Hermes 的脚本 stdout 是待投递结果，并不是飞书成功送达的确认。当前 `_reported` 只依据本地 `sched.report` 事件判断是否曾报告，无法识别“内容已打印但投递失败”。

### 3.2 隔离复现

在临时状态库创建一个授权目标和 `blocked(decision)` 任务：

```text
pending_before 1
stdout_dropped_but_marked_acked True pending_after 0
```

通过本地 `redirect_stdout` 丢弃 `cmd_report` 输出后，尚未进行任何飞书投递，下一次 `report()` 已返回 0 项。

### 3.3 裁定

**P1，至少在 B22-G5「报告接定时任务」之前必须修复；建议同一 PR 收口。** 报告应先保留待投递状态，由可信投递适配层在明确确认送达后标记 `ack`；无法获得确认时，应选择可能重复提醒，而不是静默漏报。不得声称“stdout 已输出 = 消息已送达”。

## 5. 重新验收的最小证据

1. 同一 PR、同一分支定向修改；提供失败先行（RED）、修复后（GREEN）和原 259 项全量测试输出，两套 Python。
2. 测试至少覆盖：子进程已启动但尚未登记时 owner 被杀、锁前 git/gh 延迟大于租约、迟到旧 key；失败不重复开单、不把未知误判为无单；人工介入时可查证据。
3. 测试 stdout 成功但实际投递失败、重复执行报告、成功送达后 ack 幂等、无新情况时 `--quiet` 空输出。
4. 保留 `DT_SCHED_ENABLE` 默认关闭、`tick` 不启动 worker、真实根目录取消硬拒绝、人工确认门不变。
5. 提交更新后的安全边界、部署闸门、变更清单。不得自行 merge、安装、建正式状态库、开 cron、改网关或对真实工单发信号。

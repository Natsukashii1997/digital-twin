二、P1：仍需返修的阻断问题
P1-01-R2：300 字前缀不足以证明送审包身份

位置： orca/chatgpt_relay.py → bubble_matches()、send_and_wait()、cmd_collect()

已核实事实：

Python
运行
def bubble_matches(bubble, sent):
    b, w = squash_bubble(bubble), squash_bubble(sent)
    return len(b) >= min(300, len(w)) and w.startswith(b)

对于超过 300 字的送审包，只要页面气泡前 300 个归一化字符与预期内容一致，即使后续不同，也可以匹配成功。

例如有两份送审包：

A：共同的项目说明、审核协议和背景，随后是提交 A 的代码。

B：前 500 字与 A 完全一致，随后是提交 B 的代码。

如果页面只读出了 A 的共同前缀，那么使用 B 的送审包调用 collect()，bubble_matches() 也会返回 True。

这不是依赖 ChatGPT 模型行为的猜测，而是当前字符串匹配条件允许的结果。

为什么阻断：

发送后身份核验是 fail-closed 的核心条件。当前设计将“同一内容前缀”当作“同一送审包”，无法排除同模板、不同提交的送审请求。

对不采纳意见的裁定：部分认可，但替代方案不成立。

认可“所有折叠长气泡一律拒收会严重影响可用性”的理由。不要求永久拒收长包。

但 300 字前缀只能作为初步筛选，不能作为足以接受 PASS 的最终身份认证。

返修要求：

为送审消息增加唯一且不可混淆的审查标识，建议绑定完整送审包 SHA-256、任务 ID 和轮次。

标识必须可从实际已发送的消息中独立核验，不能只存在于本地记录。

对长包仅可见开头的情形，至少校验完整标识及所显示前缀。

若不能获得可靠身份信息，应拒绝收取，而不能根据任意公共前缀判断成功。

添加两份长送审包共享 300 字以上前缀、实际内容不同的负向测试。

验收标准： 送审包 A 的回复绝不能被送审包 B 接受，即使二者使用相同模板和公共背景。

P1-02-R2：会话身份校验启动过晚

位置： orca/chatgpt_relay.py → send_and_wait()。

已核实事实：

Python
运行
conv, prev, since, seen = None, None, 0.0, 0

直到首次发现新增回复，才赋予 conv：

Python
运行
if conv is None:
    conv = conversation(st["url"])

代码没有把发送前的会话身份与首次新增回复的会话身份建立明确绑定。

风险推断：

如果消息发送后，页面在首次检测到回复之前切换到另一个已有会话，并且该会话的消息计数与内容恰好满足当前条件，就有可能把切换后的会话当作基准。

现有 test_conversation_switch_while_waiting_is_refused 覆盖的是已经观察到回复后的切换，并未证明首次回复前切换也能拒收。

返修要求：

发送前记录可信的会话身份；新会话首次生成 URL 的情况应单独建立绑定规则。

首次检测到回复之前发生无法解释的会话切换时，拒绝收取。

不能只比较 URL 与消息数量；应结合任务消息的唯一身份。

补充首次回复前切换、首次回复后切换两种测试。

验收标准： 新回复必须可追溯到发送当前送审包的会话，而不是仅与第一次被观察到的回复处于同一会话。

P1-03-R2：.sending 标记绑定输出文件路径，不能全面防止重复发送

位置： Marker.__init__()、cmd_review()。

已核实事实：

Python
运行
self.path = out + ".sending"

当同一份送审包使用不同输出文件路径时：

纯文本
review --packet packet.md --out reviews/round-2.md
review --packet packet.md --out reviews/round-2-retry.md

两次操作使用不同的发送标记。

第二次不会检测到第一次创建的 .sending。

为什么是问题：

实现保证的是“同一个输出文件路径不能在标记存在时重复发送”，不是“同一份送审任务不能重复发送”。

如果调用方在失败恢复时更换输出文件名，仍可以绕过这一保护。

返修要求：

发送状态的主键不能只由回执路径决定。

至少绑定工作区、会话、送审包 SHA-256 和任务轮次。

对同一逻辑请求建立唯一发送记录，并以排他方式创建。

重试应复用既有任务状态，不能通过换回执文件名重新发起。

增加不同 --out 指向同一送审包的重复发送测试。

验收标准： 修改输出文件名不能绕过未知发送状态保护。

P1-04-R2：deliver 重试可能导致 Claude 重复返修

位置： cmd_deliver()、deliver()。

已核实事实：

新接口执行：

Python
运行
deliver(a.deliver_to, a.record)

没有持久化的交付状态，也没有对目标终端和回执组合实施幂等检查。

如果 ORCA 终端实际已经接收了回执，但 terminal send 返回异常，用户再执行 deliver，就可能把同一个 REWORK 指令发送两次。

即使第一次返回成功，重复调用 deliver 仍会再次发送。

为什么是问题：

这与 P1-04 第一轮发现的“不确定外部副作用”问题同类，只是发生在 Claude 交付端。

风险是重复启动返修或重复处理同一任务。是否导致实际重复提交，取决于 Claude 终端如何处理重复指令，尚未实测。

返修要求：

为交付建立独立状态，至少区分未交付、交付结果未知、已确认交付。

给每条交付指令绑定稳定的回执 ID。

已确认交付后再次调用应幂等返回，不再发送。

交付结果未知时不得无条件重试；应先核对接收端状态，或依赖接收端按回执 ID 去重。

新增“终端已接收，但工具返回失败”和“成功后重复调用”的测试。

验收标准： 同一 REWORK 回执不会因为重试而触发两次独立返修。

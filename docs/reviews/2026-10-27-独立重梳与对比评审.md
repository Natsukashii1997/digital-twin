## 第一部分：从零独立设计

### 0. 设计依据

**常浩原话里能提炼出的硬约束（按优先级）：**

1. 终态只有一个飞书机器人 Hermes（猛鬼兽）；飞书里的 Claude、Codex 机器人、日报机器人都退役；本机访问也统一走 Hermes。
2. Hermes 定位 = 前台 + 调度员 + 数字分身。它的价值不是"又一个能干活的 agent"（这一点常浩说得很清楚：有任务他自己就能去 Claude / Codex 做），而是"流程跑通"：知道常浩要什么、主动推、把活派出去、把结果收回来。
3. 了解常浩不靠诉说：日报（常浩自己写，结构待重梳）、周报是信息源；Hermes 只需读取 + 按要求格式定时提醒 / 触发提醒。
4. 知识库只读、限定范围；画像由 Hermes 自己积累；派单可代发起。
5. 模型：默认走 Codex 月度会员额度，退一步 DeepSeek；要分别说明 Claude / Codex 会员能否接给 Hermes。
6. 隐私规则要"写好底层原则：什么能发什么不能发"，不是一刀切。
7. 项目太乱，要工程化、标准化：Matt Pocock skills 的开发流程 + GitHub 上传标准流程。
8. 巡检正常频次即可，注意额度消耗；"7 全部清理掉"（指某类冗余的东西，含义在第一阶段看不到上下文，按"不要的旧东西全清"理解）。
9. 动作快一点，不用那么多担心，直接改。

**本机环境事实（第一阶段只查了允许的范围）：**

- Hermes Agent v0.22.2（git 安装，`~/.hermes/hermes-agent`），网关已在跑，平台只有 Feishu / Lark；当前模型 `gpt-6.1-sol`，provider "ChatGPT or Codex Subscription"；已登记的 provider 还有 GitHub Copilot、Anthropic、DeepSeek；cron 10 个任务、2 个活跃。
- Hermes 自带的关键能力：`cron`（可挂技能、可 no-agent 纯脚本模式、有 notepad / runs / incidents / doctor / 预检）、`delegate_task` 子代理、`kanban`（SQLite 任务板，可绑项目、按 profile 派工、worktree 约定）、`project`（多文件夹工作区）、`memory`（MEMORY.md 2200 字符 + USER.md 1375 字符，冻结快照注入；可外接 honcho / mem0 等）、`skills`（agentskills.io 标准）、`hooks`、`fallback` 链、`auth` 凭据池、`send`（不经 LLM 直接发消息）、`pause / resume` 紧急停、`pairing` + `FEISHU_ALLOWED_USERS` + `FEISHU_GROUP_POLICY`、`approvals.mode` + 硬线黑名单、`/heartbeat`、`/goal`、可选的 Codex app-server runtime、`import-agent`（导入 Claude Code / Codex 配置）。
- 订阅与条款（联网核实，详见 1.5）：OpenAI 官方 "Sign in with ChatGPT" 的"可用套餐额度的应用"名单里有 Hermes Agent；Anthropic 消费者条款禁止非 API key 的自动化访问，11-12 生效的 AUP 明确点名"通过消费者订阅转发请求"；Hermes 文档说 Anthropic 路径只对 Max + 额外用量包可用，Pro 不行。Hermes 还会"借用" `~/.codex/auth.json` 和 Claude Code 凭据，但 refresh token 是单次轮换的，两个程序共用会互相顶掉。
- 本机 CLI：`claude`（有 `-p`、`--bg`、`--allowedTools`、`--agent`）、`codex exec`（非交互，`-c` 覆盖配置，有 sandbox）、`lark-cli`（飞书全域，含 `im`、`docs`、`calendar`、`task`、`event consume`）、`gh`（已登录）。
- 项目目录 `~/Documents/ChatGPT/个人/work/` 下 15 个目录：有 GitHub 远端的 5 个（agent-kit、digital-twin、github-center、personal-ai-workbench、work-desk，另有 work-desk-ui-bitmap 指向同一远端）；本地 git 无远端 1 个（carvomoto）；非 git 或探索性质的 8 个（Fmode、automation-reliability-20260929、automation-reliability-disabled-20260929、automation-repair-20260928、hermes-check-disabled-20260929、ops-desk、wiki-local、work-desk-backups、get-index）。"项目太乱"属实：同一产品两份检出、三个带日期的一次性目录、"disabled" 后缀的半废弃目录。

### 1. 目标定义

**一句话：** 常浩在飞书里只跟猛鬼兽说话；猛鬼兽知道常浩的项目、节奏和偏好，主动在对的时间问对的问题、把活派给车间（Claude Code / Codex）、收回结果、提醒常浩拍板；常浩不再自己去开 Claude / Codex 会话。

**不是什么：** 不是把 Claude / Codex 的能力搬进飞书（那只是换了个聊天窗口），不是一个会聊天的日报机器人，不是全自动无人值守的开发流水线。

**成功的可观测定义（终态验收，详见 1.11）：**

- 飞书里只剩一个机器人；常浩一个月内没有在飞书外手动开 Claude / Codex 会话去做"本可以派单的活"。
- 每个工作日早上，猛鬼兽在常浩开始工作前给出一条"今天要推什么"的消息，且常浩实际按它推了至少一件事。
- 常浩在飞书里说"把 X 做了"，24 小时内能收到带 PR 链接或明确失败原因的回执，不需要常浩去看终端。
- 问"我上次关于 Y 是怎么定的"，猛鬼兽能答对并给出 Vault 路径。

### 2. 角色分工

| 角色 | 职责 | 明确不做 |
|---|---|---|
| **Hermes（猛鬼兽）** | 唯一入口；读日报周报 / Vault / 项目状态；主动提醒与追问；派单给车间、收回执、汇总给常浩；维护常浩画像（USER.md + Vault 的 `个人上下文/` 提案）；定时巡检 | 不亲自写代码改仓库（除了它自己的技能与脚本）；不代替常浩拍板；不把受限内容发出私聊 |
| **Claude Code** | 车间 A：设计重、跨文件、需要读大量上下文的任务；评审；写规格 | 不常驻飞书；不自己决定做什么 |
| **Codex** | 车间 B：目标明确、可验证、改动小的任务；批量机械改动；第二意见 | 同上 |
| **Obsidian Vault** | Hermes 懂人的根：`个人上下文/`（角色、目标、偏好）、`决定/`、`10 项目/` 项目卡、`40 日记/`；只读 MCP 暴露给 Hermes | 不存项目当前状态（那在仓库 CURRENT.md）；不存密钥 |
| **飞书** | 唯一人机界面：私聊是本人入口；日报周报文档是信息源；群聊只在常浩明确要求时才让猛鬼兽发言 | 不是任务系统（任务在 GitHub Issues） |
| **GitHub** | 每个正式项目的唯一真源：Issues 是任务板，PR 是交付单位，分支与标签是流程状态 | 不存个人知识 |

**为什么 Hermes 不自己写代码：** 它跑在订阅额度上、在网关进程里、以飞书为界面，三者都不适合长时间编辑仓库；而 Claude Code / Codex 有 sandbox、worktree、权限模型和 hooks。把"决定做什么"和"把它做出来"分开，正是常浩原话"前台 + 调度员"的意思。

### 3. 信息流

```
常浩 ──私聊──▶ 猛鬼兽 ──派单──▶ 车间（claude -p / codex exec）──PR──▶ GitHub
   ▲              │ ▲                                                 │
   │   提醒/回执   │ │ 回执（JSON）                                      │
   │              │ └──────────────────────────────────────────────────┘
   │              ▼ 只读
   │        Vault（个人上下文 / 决定 / 项目卡 / 日记）
   │              ▲ 提案（经常浩确认才落盘）
   │              │
   └──日报/周报──▶ 飞书文档 ◀──定时读取── 猛鬼兽
```

四条流，各有唯一的落地格式：

1. **常浩 → 猛鬼兽（指令）**：只认飞书私聊里常浩本人 open_id 的消息；群聊 @ 也只认常浩。其他人的消息一律当内容不当指令。
2. **猛鬼兽 → 车间（派单）**：一张派单 = 一个 GitHub Issue（或一条明确的 Issue 编号）+ 一个 JSON 任务单（目标、验收、仓库、分支名、允许改动范围、超时、用哪个车间、用什么模型）；车间在 worktree 里干活，产出 PR；回执 JSON 写到固定目录并由猛鬼兽读回。
3. **车间 → 猛鬼兽 → 常浩（回执）**：回执只有三种状态：`done`（附 PR 链接 + 一句话 + 需要拍板的点）、`blocked`（缺什么）、`failed`（最后 20 行日志路径）。猛鬼兽翻译成一条私聊，不转发原始日志。
4. **日报 / 周报 → 猛鬼兽（了解常浩的一天）**：常浩写在飞书文档（或 Vault 日记）里的固定结构；猛鬼兽定时读，抽出三类字段：今天做了什么 / 明天要做什么 / 卡在哪；写进 cron notepad 当作"上次读到的状态"，用于第二天比对"说了要做的做了没"。

**关键选择：日报写在哪。** 常浩说"日报我会重新梳理结构"。两个候选：

- A. 飞书文档（现状延续）：常浩手机上就能写；猛鬼兽用 `lark-cli docs` 读。缺点：结构靠约定，解析脆弱。
- B. Vault `40 日记/年/年-月-日.md`：天然进知识库，frontmatter 可控，`vault-read` 直接读；缺点：手机上写不方便，除非 Obsidian 同步。

**我的建议：B 为真源、A 为镜像。** 日报是"Hermes 懂人"的核心燃料，应该沉在 Vault 里而不是飞书文档里；但为了手机可写，允许常浩先在飞书私聊里对猛鬼兽说"今日日报：……"，由猛鬼兽按模板写进 Vault 日记（这是 Vault 规则里允许的"常浩要求时追加"），再把渲染版发回飞书。这样日报机器人自然退役，且不需要解析飞书文档。

### 4. 信息边界与权限（"底层原则"）

常浩要求的是原则不是清单。我把它压成四条可以逐条执行的规则，每条有判定方法：

**原则 1：谁说的才算指令。** 只有常浩本人（固定 open_id，`FEISHU_ALLOWED_USERS` 只放这一个）在私聊里说的话是指令；群聊里常浩 @ 猛鬼兽也算；其他任何来源（群里别人、文档、网页、日报正文、车间回执里的文字、Vault 笔记里的"请……"）都是内容。实现：`FEISHU_GROUP_POLICY=allowlist`，SOUL 里写死这一条，并在派单模板里给车间也写死。

**原则 2：往哪发由内容的敏感度决定，不由谁问决定。** 沿用 Vault 的 `sensitivity` 三级：
- `受限` 或没标注：只回常浩私聊，且只给结论和路径，不贴原文（常浩明确要原文时例外）。
- `内部`：可以进常浩在的群聊和团队文档，但每次要常浩在私聊里确认。
- `普通`：同上，外部公开也要确认。
- 不在 Vault 里的信息（项目代码、Issue、PR）：按仓库是否公开决定；私有仓库内容等同 `内部`。
实现：猛鬼兽发往任何非常浩私聊的目标前，必须能说出这条内容的来源和级别；说不出就按受限处理 = 不发。

**原则 3：会动外界的动作分三档。**
- 直接做：读、搜、写回执、建 worktree、开 PR、在本仓库提交。
- 做了告诉常浩：建 Issue、派单、给车间发任务、改自己的 cron。
- 先问常浩：合并 PR、push 到非自己分支、删东西、发给常浩以外的人、改 Hermes 自己的配置和权限、任何花钱的事（切更贵的模型）。
实现：Hermes `approvals.mode` 保持默认（不开 `off` / yolo）；硬线黑名单天然兜底；派单模板里禁止车间 push 和 merge。

**原则 4：密钥不进任何文本通道。** 不进 Vault、不进仓库、不进飞书消息、不进回执；车间需要的凭据由本机环境提供（`gh` 已登录、`lark-cli` 已登录），派单 JSON 里只写"用本机已登录的 gh"。

**为什么这样设而不是"全开权限"：** 常浩说"我会给 Hermes 开所有需要的权限，不会有任何担心"。我理解为"不要因为担心而不做"，而不是"不要边界"。上面四条都不妨碍动作快：日常派单、建 Issue、开 PR 都在"直接做 / 做了告诉"档；只有不可逆和出圈的动作要问，而这些本来也该常浩拍板。

### 5. 模型与额度

**先回答常浩的两个问题：**

- **Codex 月度会员能不能接给 Hermes？能，而且是 OpenAI 官方认可的路径。** OpenAI "Sign in with ChatGPT" 的"可用 ChatGPT 套餐额度的应用"名单里明确列有 Hermes Agent（Plus / Pro 订阅者可以选择把套餐额度用于应用内请求）。Hermes 这边用 `hermes model` → "ChatGPT or Codex Subscription" 做 device-code 登录，凭据存 `~/.hermes/auth.json`。注意两点：① 额度怎么和 Codex CLI 的限额合并计算，Hermes 文档明说"未写明"，所以要自己盯用量；② 让 Hermes 单独登录，而不是借用 `~/.codex/auth.json`，并把自动借用关掉（Hermes 安全页：refresh token 单次轮换，两个程序共用会互相顶掉登录）。
- **Claude 月度会员能不能接给 Hermes？技术上 Hermes 支持，但条款上不建议。** Anthropic 消费者条款禁止通过非 API key 的自动化方式访问；2026-11-12 生效的 AUP 直接点名"通过消费者订阅转发请求的服务"；Hermes 文档也说只有 Max + 额外用量包可用，Pro 不行。结论：Claude 会员额度留给 Claude Code 本身（它是 Anthropic 自家 harness，合规），不接给 Hermes；Hermes 需要 Claude 模型时走 Anthropic API key 按量付费，只用于明确需要的场景。

**模型分层（按常浩的"默认 Codex，退一步 DeepSeek"）：**

| 用途 | 模型 | 理由 |
|---|---|---|
| 猛鬼兽日常对话、派单、读日报 | Codex 订阅（当前 `gpt-6.1-sol`） | 常浩拍板的默认；官方认可 |
| 猛鬼兽 fallback | DeepSeek（API key） | 常浩拍板；便宜；只在主模型限流 / 故障时 |
| cron 巡检、取数、格式化 | 尽量 no-agent 纯脚本；必须用模型时 `cron.model` 钉到 DeepSeek | 定时任务是额度黑洞，不能跑在主模型上 |
| 车间 Claude Code | 常浩的 Claude 会员（Claude Code 自己登录） | 合规；设计重的活值得 |
| 车间 Codex | Codex 订阅（Codex CLI 自己登录） | 同一份会员，和 Hermes 共用额度 |

**额度守则：**
- Hermes 的 `auth` 凭据池和 Codex CLI 各自登录，不共用 token 文件。
- 每个 cron 任务钉死模型和 reasoning 等级（Hermes 支持 per-job pin），默认 `low`。
- 每周一的周报里附一行"上周模型用量"（Codex 用量从 Hermes `--usage-file` 或 session 统计取；Claude 从 Claude Code 自己的用量取），让常浩看到额度去哪了。
- 同一个任务两个车间都失败两次就停，不要第三次自动重试——这是常浩 CLAUDE.md 里的规则，派单层也要遵守。

### 6. 派单流程

**派单不是"把话转给 Claude"，而是一张有验收的工单。** 流程五步，每步有落地物：

1. **收单（猛鬼兽）**：常浩在私聊里说要做什么。猛鬼兽先查：这是哪个项目（只认名册里的活跃项目）、仓库里有没有已有 Issue、`CURRENT.md` 的下一步是不是就是这个。拿不准就问一次，最多三个问题，每个带推荐答案（常浩自己的规则）。
2. **立单（GitHub Issue）**：没有 Issue 就建一个，模板固定：目标 / 验收标准 / 范围边界 / 需要常浩拍板的点。Issue 编号就是工单号。小活（一天内）直接走 `implement`；大活先派 `to-spec` → `to-tickets`，产出再回常浩确认。
3. **派工（任务单 JSON + 车间）**：猛鬼兽写一个任务单文件到 `~/Library/Application Support/DigitalTwin/dispatch/<issue>.json`，字段：`repo`、`issue`、`branch`（`<type>/<issue>-<slug>`）、`worker`（claude | codex）、`skill`（implement / tdd / code-review…）、`timeout_min`、`allowed_paths`、`model`。然后用一个统一的包装脚本启动车间：
   - Claude：`claude -p --bg --allowedTools "Edit Write Bash(git *) …" --append-system-prompt "<工单规则>" "<任务>"`，在该仓库的 worktree 里。
   - Codex：`codex exec -c sandbox_permissions=… "<任务>"`，同样在 worktree 里。
   - 车间规则随任务注入：只在当前分支干活、不切主分支、不 merge、不 push 主分支、完成后开 PR、写回执。
   **选车间的默认规则**：需要读很多上下文或做设计 → Claude；目标明确可验证、或者 Claude 刚做过要第二意见 → Codex。常浩可以在一句话里指定（"让 Codex 做"）。
4. **收回执（回执 JSON）**：车间完成后把 `{status, pr_url, summary, needs_decision[], log_path}` 写到 `dispatch/<issue>.result.json`。猛鬼兽用 cron（每 15 分钟一次的 no-agent 脚本检查目录）或车间结束时直接 `hermes send` 把结果推到常浩私聊。不让猛鬼兽长时间等待一个会话——网关里的长等待既占额度又容易断。
5. **收口（常浩拍板）**：回执里 `needs_decision` 非空时，猛鬼兽把它变成一条带编号的问题；常浩回答后猛鬼兽要么追加派单，要么告诉常浩"PR 可以合了"（合并由常浩在 GitHub 上点，或常浩说"合"之后猛鬼兽 `gh pr merge`）。

**不用 Hermes kanban 的原因：** Hermes 的 kanban 是给多个 Hermes profile 之间派活的，车间是 Claude Code / Codex 不是 Hermes profile；GitHub Issues 已经是真源，再加一个 SQLite 看板就是两份状态。等到真的需要多 Hermes 协作再考虑。

### 7. 日报周报与主动提醒

**日报结构（常浩说要重梳，这是我的提案）：** 每天一页，固定五段，每段一个 H2，机器好读、人好写：

```
## 做了        — 3～7 条，每条带项目名前缀 [项目]
## 明天         — 1～3 条，必须是能判断"做没做"的动作
## 卡住         — 可空；每条写"卡在谁 / 什么"
## 决定         — 可空；今天拍板的事，一条一句；跨项目的由猛鬼兽提案进 Vault 决定/
## 杂记         — 自由；猛鬼兽不解析
```

**周报由猛鬼兽起草、常浩改。** 每周日晚（或周一早）cron：读本周 5～7 篇日报 + 各活跃仓库本周的 PR / Issue 变化 + 派单回执，按"推进了什么 / 没推进的为什么 / 下周三件事"起草，发到常浩私聊；常浩回"可以"或改一句，猛鬼兽落盘到 Vault `40 日记/周报/` 并镜像到飞书文档。

**主动提醒只做四种，频次固定，其余不做：**

| 提醒 | 触发 | 内容 | 模型 |
|---|---|---|---|
| 晨推 | 工作日 08:30 | 昨天"明天"段里的事 + 今天的日程（`lark-cli calendar +agenda`）+ 悬而未决的回执 | DeepSeek 或 no-agent |
| 晚收 | 工作日 21:00，当天没写日报才发 | "今天日报还没写，回我一句我帮你记" | no-agent |
| 回执即时 | 车间写回执时 | 见第 6 节 | no-agent（`hermes send`） |
| 周报草稿 | 周日 20:00 | 见上 | Codex 主模型（一周一次值得） |

**不做的：** 每小时巡检、"有空吗"式的闲聊、对日报内容的点评。常浩说"频次不要太高，注意额度消耗"。

### 8. 项目工程化

"项目太乱"的根因不是没有流程，而是没有名册：哪些是正式项目、哪些是一次性探索、哪些该删。所以第一步是**名册**，第二步才是流程。

**名册（`projects.json` 之类，放 digital-twin 仓库）：** 每个正式项目一条：名字、本地路径、GitHub 远端、状态（活跃 / 暂停 / 归档）、默认车间、默认分支前缀。规则：
- 只有名册里"活跃"的项目可以被派单（猛鬼兽和包装脚本都要查）。
- 不在名册里的目录，要么登记，要么挪到 `~/Sandbox/<日期>-<主题>/`（常浩自己的规则），要么删。按现状，`automation-*`、`hermes-check-disabled-*`、`work-desk-backups`、`work-desk-ui-bitmap` 四类该清；`ops-desk`、`Fmode`、`wiki-local`、`get-index` 要常浩定去留。
- 每个活跃项目仓库根目录必备：`README.md`、`AGENTS.md`（Claude 和 Codex 共读）、`CURRENT.md`（当前状态 + 唯一下一步）、`.github/PULL_REQUEST_TEMPLATE.md`、Issue 模板、五个分流标签。

**开发流程（Matt Pocock skills）：** 大活 `to-spec` → `to-tickets` → `implement` / `tdd` → `code-review` → PR；小活跳过 `to-spec`。每个技能都是车间里跑，猛鬼兽只负责决定走哪条路和把产物（spec、tickets）回给常浩确认。

**GitHub 标准流程：** 主分支受保护（至少禁止直接 push）；所有改动走分支 + PR；PR 模板里三栏：对应 Issue / 怎么验证的 / 需要拍板的点；合并后由猛鬼兽在下一次晨推里提一句"X 已合，CURRENT 要不要更新"——或者更省事：合并后车间自己更新 `CURRENT.md` 作为 PR 的一部分。

**一个月做一次的名册自检（cron，no-agent 脚本）：** 每个活跃项目是否主分支干净、是否有未推提交、是否有超过 14 天没动的分支、标签模板是否齐。只报异常，不报正常。

### 9. 知识库：让 Hermes 真正懂人

常浩说"只有知识库搭得好，Hermes 才能真的更了解我，且有独立解决问题的能力"。这句话里有两件不同的事：

**(a) 懂人 = 画像稳定可查。** 画像不该散在聊天记忆里，应该有固定的家：Vault `个人上下文/`（角色、目标、偏好、约束）+ `决定/`（跨项目决定，一条一页）。Hermes 的 USER.md 只有 1375 字符，只能放"索引级"信息（常浩是谁、找什么去哪个目录、三条最重要的工作偏好），真正的画像在 Vault，用 `vault-read` 按需查。

**懂人的回路（这是"Hermes 自己积累"的具体做法）：**
1. 猛鬼兽在对话里发现一条新的偏好或决定（判定：常浩说了"以后都……"、"我不喜欢……"、"定了……"），不直接写 Vault；
2. 写成一条"画像提案"（改哪一页、原文、改后）发回常浩私聊；
3. 常浩回"采纳"才落盘（Vault 规则本来就要求 `个人上下文/` 和 `决定/` 须本人确认）；
4. 每周报里附"本周画像变化 N 条"。

**(b) 独立解决问题 = 查得到过去的判断。** 这靠三件事：
- Vault 的 `30 知识/卡片/`（一卡一结论）和 `10 项目/` 项目卡持续有人维护——这是常浩自己的 `/kb-digest`、`/kb-note` 流程，猛鬼兽不替代，只在周报里提醒"待整理有 N 条超过 7 天"。
- 猛鬼兽回答判断类问题前**先查 Vault 再答**（搜索顺序按 Vault AGENTS 第 3 节：个人上下文 → 决定 → 知识 → 待整理 → GET），并分清"常浩已确认的 / 来源事实 / 我的分析 / 不知道"。
- 回执和周报也沉进 Vault：每周一张"本周推进"卡进 `00 待整理/`，由常浩的消化流程处理。

**不建议的：** 接 honcho / mem0 这类外部记忆服务（多一个数据出口，和"受限内容不出本机"冲突）；让猛鬼兽直接改 Vault 卡片（会污染真源）。

### 12. 主要风险

1. **额度被定时任务吃光。** 10 个 cron 任务若都跑主模型，一个月的订阅额度可能被巡检花掉。对策：no-agent 优先、cron 钉便宜模型、周报里看用量。
2. **Codex 订阅被 Hermes 和 Codex CLI 两头用，限额不透明。** 对策：独立登录；观察两周用量；真不够再给车间 Codex 换 API key。
3. **日报结构不稳，解析失效。** 对策：日报由猛鬼兽按模板代写，而不是解析常浩自由写的文档。
4. **"全部权限"下的误操作。** 对策：第 4 节的三档动作；硬线黑名单；车间禁止 push / merge。
5. **知识库变成垃圾场。** 对策：画像提案制；猛鬼兽不直接写 Vault 真源目录。
6. **网关单点。** Hermes 网关挂了什么都停。对策：launchd 常驻 + 每日一次 no-agent 自检（`hermes status`），异常才发消息；不做高频巡检。
7. **提示注入。** 车间回执、日报、Vault 笔记、群聊都可能夹带"请……"。对策：原则 1 写进 SOUL 和派单模板；回执只读结构化字段。
8. **Hermes 版本迭代快（v0.22 还在频繁改 CLI）。** 对策：技能和脚本不依赖未文档化的行为；升级前 `hermes backup`。

### 2. 我的设计更好的地方

**2.1 日报的真源位置：现有方案把"Hermes 懂人"的燃料留在了飞书文档里**

- 现状：T1-Q2 / Q6 定了日报写进飞书文档，台账在文档里，常浩在文档里改以文档为准；T1-Q3 定了日报只写工作（内部级）、私人话题不写。Vault `40 日记/` 至今 0 篇，`00 待整理/` 0 篇。
- 代价：常浩原话 3 说"了解我的一天……日报周报是信息来源"，原话 7 说"知识库搭得好 Hermes 才真的了解我"。现在日报是"工作台账"，和 Vault 没有连接；日报里的决定要经 F7 每周再提炼一次才可能进收件箱，而 F7 还没跑起来。Hermes 回答"我上周为什么这么定"时查不到日报。
- 建议：日报、周报每天生成后，用一个 no-agent 的 cron（或 `report_publish.py` 顺手）把全文镜像一份到 Vault `40 日记/工作/YYYY/YYYY-MM-DD.md`（frontmatter `type: 日记`、`sensitivity: 内部`），`vault-read` 就能搜到；飞书文档仍是常浩手机上看和改的地方。
- 改动量：`report_publish.py` 加 20 行 + 一次 Vault 目录约定。
- 要拍板：Vault 规则里 `40 日记/` 是"只读；常浩要求时追加"，工作日报放进去（或另开 `40 日记/工作/`）需要常浩点头。

**2.2 台账状态机交给模型维护，风险大**

- 现状：`daily_report.md` 提示词要求模型自己做"二 = 前一篇的二 + 今天的 🆕 − 关闭"，并"不允许无声消失"、按编号重算天数、满 14 天移 🧊。第二次试写台账 19 件就出了 3 类错（个人项目被建成行动、链接任务被建成事项、硬写知识库行），而这还是模型读得最认真的首跑。
- 代价：台账是 F4 晨报、周启、收口、截止提醒的唯一数据源；模型每天凭提示词维护一个跨天状态机，丢项和改号只是时间问题，而且一旦丢了后面每天都接着错（每篇都基于前一篇）。
- 建议：把"二、还开着"和"三、卡点"的继承、天数、分组、🧊 判定交给 `report_data.py`（它已经读前一篇台账）——脚本先把前一篇台账原样带入并算好天数，模型只负责判断"今天的变化"里哪些是 🆕 / ⏩ / ✅ / ✖️ 并引用编号；脚本再合并出"二"，并做一致性校验（前一篇每个编号在今天必须出现一次，少了就在覆盖行报"台账丢失 N 项"）。
- 改动量：`report_data.py` 约 80 行、提示词删一半规则、测试加几项。
- 要拍板：接受"模型不直接写二段"这个分工。

**2.3 凭据借用默认开着，M0 级的小坑没关**

- 现状：`auth.adopt_external_logins` 未设置（默认 true）。Hermes 已有自己的 `openai-codex` 登录，所以不会去借 `~/.codex/auth.json`；但 `anthropic` 没有自有登录，一旦 Hermes 某次需要 Anthropic（例如以后给某个 cron 钉 Claude 模型，或 fallback 链加 Anthropic），它会去借 Claude Code 的凭据并刷新，Hermes 文档明说这会让 Claude Code 那边登录失效。
- 建议：`hermes config set auth.adopt_external_logins false`。
- 改动量：一条命令 + 回读。要拍板：改 Hermes 配置（D10 已授权 Hermes 自己改，但这是常浩在 M5 前应知道的）。

**2.4 飞书访问控制靠 pairing 单点，群策略没写**

- 现状：只靠 pairing 批了 1 个用户；`FEISHU_ALLOWED_USERS`、`FEISHU_GROUP_POLICY` 都没设。M5 要让猛鬼兽进团队群替机械邪龙兽发消息，到时群里 @ 它的处理策略是默认值。
- 建议：M5 进群前显式写 `FEISHU_ALLOWED_USERS=<常浩 open_id>` 和 `FEISHU_GROUP_POLICY=allowlist`（或 `disabled`，如果猛鬼兽在群里只发不听），让"只有常浩说的话算指令"在网关层也成立，不只靠 SOUL。

四、新发现的问题
P1-01-R4：目标会话核对与实际发送之间存在竞争窗口

位置： orca/chatgpt_relay.py → send_and_wait()、fill_composer()、SEND_JS

性质：已核实代码结构；实际触发需要页面切换等并发条件，尚未复现。

当前发送流程为：

Python
运行
before = page.state()

    raise RelayError(...)


fill_composer(page, text, poll)

if page.eval(SEND_JS) != "true":

问题在于，首次通过 same_chat() 检查后，到真正点击发送按钮之间，还会执行多次独立的 ORCA 浏览器调用。

而 SEND_JS 只验证发送按钮存在且可用：

JavaScript
const b = document.querySelector(...);
if (!b || b.disabled) return false;
b.click();
return true;

它没有检查此刻的页面 URL 是否仍然属于指定会话。

可能的失败路径：

脚本读取目标会话 A，same_chat 检查通过。

脚本填写送审包，并成功核对输入框内容。

人工操作将共用浏览器标签切换到会话 B。

脚本在 B 页面执行 SEND_JS。

B 的发送按钮可用，脚本执行点击。

如果 B 的输入框已有内容，脚本甚至可能发送 B 原本的草稿；如果页面切换与输入状态恢复存在其他交互，也不能排除送审包被发送到 B 的风险。

为什么是 P1：

本轮加 --chat 的目的，是确保审核内容不会误发到其他私人会话。但当前实现只能验证发送前某一时刻的会话，不能保证点击发生时仍处于授权目标。

即使后续会话检查拒绝收取回复，也已经无法撤销可能发生的误发。

返修要求：

将最后一次目标会话校验与发送操作放入同一个页面执行单元。

例如发送脚本应在点击之前同步确认：

当前会话 URL 与目标匹配；

当前可见发送输入框唯一；

当前输入框内容与预期消息严格一致；

当前没有正在生成的回复；

满足全部条件后，才执行点击。

对新会话首页也必须遵守相同规则。

验收标准：

新增模拟测试：初始目标会话 A 正确，填写成功，但在最终发送动作前页面切换到 B；必须拒绝点击，保留或正确处理发送状态，且不能对 B 产生发送副作用。

此问题不是要求取消已接受的 --chat 设计，而是要求把其安全检查真正延伸到发送动作。

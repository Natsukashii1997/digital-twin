## 2. 每个问题的根因与修改

### F1 台账冲突时不得提前覆盖证据

**根因**：`_apply_order` 对已登记的工单是“先合并、后判断”：先把台账的 `receipt`、`evidence`、`session_id` 写进 Run，再算 `_resync_kind`；判成冲突时 handler 返回 `"conflict"` 而不是抛异常，事务正常提交，于是 `run.conflict` 事件记下了、但被冲突数据覆盖的回执和证据也留下了。护栏后的续跑（`guard → running`）走的是 followup 分支里的二次判断，同样在合并之后。

**修改**：
- 状态不同时先算 `_resync_kind`（`guard` 的 followup 在这一步就并入冲突），判成冲突立刻记事件并返回，后面的合并、心跳、转换都不执行；Run 的 `status / receipt / evidence / session_id / ended_at` 一个字段都不改。
- 冲突事件独立留痕：payload 带 `local`（本地状态）、`ledger`（台账状态）、`order_no`、`note`，以及 `ledger_receipt` / `ledger_evidence`——台账里和本地**不一样**的回执、证据字段（`_diff`，没变的字段不进摘要），供人工核对，不覆盖已确认的执行事实。
- 同一状态下台账内容变了（例如 `cleaned` 单补了 `merged_to`）不是冲突，照常刷新，这条行为不变。

### F2 续跑操作应保证状态一致

**根因**：`resume_run` 先 `_run_to(running)` 再调 `_resume_task`；后者对“不是当前 Run / 任务终态 / decision 等阻塞 / 重试到上限”只记 `run.resume_conflict` 并返回 `"conflict"`，不抛异常，于是事务提交，Run 留在 `running` 而任务没动。评审要求区分“主动发起的续跑”和“台账里观察到的续跑”。

**修改**：
- 新增 `_resume_check(task, run, by, count_retry)`：纯检查、不写库，返回（拒绝原因，要一并改的任务字段）。规则与第一轮一致：Run 必须是任务的当前 Run；任务不能已 `completed / canceled` 或还是 `observed`；`decision / external / dependency` 类阻塞只有 `user` 能靠续跑解开；`failed` 的续跑计一次技术重试且受 `max_retries` 约束；目标须仍 `authorized`。拒绝原因是 `IllegalTransition / NotAuthorized / StateError` 的实例。
- `resume_run`（主动续跑）：Run 自身的检查（running 幂等、guard 只有 user、转换表）之后，**先**对关联任务做 `_resume_check`，有拒绝原因直接抛出——整个事务回滚，Run 不变、不留 `running`、不留 `run.followup` 事件；经 `ingest_event` 调用时事件记为 `applied=0` 并保留原因。检查通过才 `_run_to(running)`，再把任务拉回 `running`。
- `_resume_task(..., observed=True)`（台账 `followup` / `undo_stale` 分支）：执行事实已经发生，Run 照实记 `running`；任务侧用同一套 `_resume_check`，不过就记 `run.resume_conflict`（payload 带任务状态、阻塞类型与原因、当前 Run、拒绝原因 `why`），任务不动。`_apply_order` 对这种情况返回 `"resume_conflict"`，`sync_orders` 把该单计入 `conflicts`（Run 改了，也计入 `updated`）。
- 审查 Run（见 B3）的续跑不碰任务。

**保留**：`review → running`、`ready → running`、`blocked(technical) → running`（计重试）这些合法续跑不变；常浩本人仍可续跑 decision 阻塞的任务。

### F3 当前 Run 的归属不得受历史导入顺序干扰

**根因**：`current_run()` 取该任务按 `rowid` 最后一条 Run。旧工单较晚导入、再 `link_run` 到正在由新 Run 执行的任务上，即使它早已跑完，也会成为“当前 Run”，它后续的台账变化就能改任务。

**修改**：
- `tasks` 表加 `current_run_id`（schema v1 直接改，此前没有任何已部署的库，不起 v2）。
- `start_run`（执行用途）和 `link_run` 关联**进行中**的 Run 时，随任务转 `running` 一起写入 `current_run_id`（事件 payload 里可见）；`link_run` 关联已结束的 Run 只作证据，不改归属。
- `current_run()` 读该字段；为空（任务只挂过已结束的 Run，没开过跑）时回退到该任务最近开始（`started_at`，没有就按 `created_at`）的 Run，不再按插入顺序。
- `list_runs` 等列表仍按 `rowid`，不受影响。

**行为变化**：`test_03` 原断言“关联一张已跑完的旧单后，当前 Run 变成它”改为“仍是最后 `start_run` 的那个”——这正是评审要求的。

### F4 身份配置边界

**根因**：`OWNER_OPEN_ID` 常量把常浩的飞书 open_id 写进了新源码。评审要求优先用本机受控配置，不增加权限系统，并保持“角色声明不等于可信认证”的结论。

**修改**：
- 删除常量。新增 `owner_open_id()`：先读环境变量 `DT_OWNER_OPEN_ID`；没有就读文件 `DT_OWNER_FILE`（默认 `~/Library/Application Support/DigitalTwin/owner_open_id`，和状态库同一个目录），取第一个非空行；文件权限不是 600（组或他人有任何位）直接 `NotAuthorized` 并提示 `chmod 600`；两处都没有返回 `None`。
- 命令行 `_by`：`--by user` 时没配置一律拒绝，`msg` 写明两种配置方法（`OWNER_HINT`）；配置了就要求 `--sender` 与之相等。其余命令不受影响。
- 结论不变：这只是防误传，不是身份认证；身份桥接（技能把发言人 open_id 传下来并只对常浩映射 `user`）仍是 B2 的事，在那之前正式 Hermes 不得用 `--by user` 操作长期目标。设计文档 3.3 与第 7 节已写明：**合并后安装副本时要同时建这个文件（600）或设环境变量，另需常浩授权，本轮没有建。**
- 测试：命令行测试改用临时文件（`DT_OWNER_FILE`）和环境变量；新增用例断言源码里没有 `ou_…` 字面量、`OWNER_OPEN_ID` 不存在。仓库里 `report_data.py` 的 `ME` 是既有脚本的既有常量，不在本轮范围，没动。

### 额外检查：B3 独立审查任务的接口

**问题**：`start_run` 只接受 `ready`，待验收任务在 `review`；要给它开 Codex 审查单，要么被迫 `rework_task` 退回开发态（错误），要么绕过状态库。

**方案与最小实现**：
- `runs` 加 `purpose`（`execute` / `review`，默认 `execute`）。
- `start_run(task, agent, by, order_no=…, purpose="review")` 只对 `review` 里的任务开审查 Run：审查方不能是当前 Run 的执行方（与“验收人不能自验”一致）；任务状态不变；它不成为当前 Run（不写 `current_run_id`）；一任务一活动 Run 的规则不变；`run.start` 事件带 `purpose`。
- 审查 Run 的回执经 `receive_receipt` / `finish_run` 进库，`_settle_task_after_run` 对它只记 `run.review_result`、返回 `"evidence"`，不结算任务、不阻塞任务；`task_evidence` 会把跑完的审查 Run 列为证据；审查 Run 失败或续跑也不碰任务。
- 结论由审查方 `accept_task(by="codex", basis=…, cites=[审查 Run id])` 写，通过后 `complete_task`；执行方仍不能自验。
- 命令行 `run-start --purpose review`。
- 设计文档 3.2（审查 Run）、3.6（B3 接口）、第 7 节 B3 一行同步；Codex 审查的编排（开只读单、读回执、写结论、通知）留 B3。

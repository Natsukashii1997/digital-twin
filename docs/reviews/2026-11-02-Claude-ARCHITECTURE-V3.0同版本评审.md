V3.0 可以作为长期基线：角色定位、四个平面的事实真源、「类型 × 风险 × 动作授权」三轴、Claude 异议协议、ORCA 原生优先、Skill 化路径、变更控制，我都认可，而且比我的 V2.0 更严谨。下面几点只涉及第 8 节和第 10 节的放行顺序，以及文件怎么存放。

## 认可且比 V2.0 更好的地方

1. **6.2 节纠正了 V2.0 的一条错误规则。** V2.0 写的是「第二轮起，对未改动代码提出的新问题一律降为 P2」，这条太死板。V3.0 改成「可信的 P0/P1 不能按轮次降级，但必须说明它和本任务的关系」，这样既不放过真问题，也防止审查范围不断扩大。
2. **3.1 节把几种「权」分开**（业务选择、任务协调、实现、审查主责、事实检验、敏感授权），避免「主审 = 绝对权威」或「Hermes = 裁判」。
3. **3.2 节说明机械测试不占 Codex Agent 额度**，Codex 用在诊断、复现、失败注入这些有价值的地方。
4. **4.2 节加了 `UNRECONCILED` 对账状态**，规则是 ORCA 事实优先于 Hermes 自报、Git HEAD 优先于 Worker 自报。
5. **6.3 节规定「一次正式异议 + 一次证据复核」**，在纠偏和不吵个没完之间取了平衡。
6. **12.2 节的 PATCH / MINOR / MAJOR 分级，加上 12.3 节「同版本、真实反馈记录」**，直接对应「不再出平行总方案」的目标。

## 需要 Owner 取舍（阻断项）

### B1　真实闭环被放在「可信授权桥」之后，实际上停在一个没有收敛的前提上

**涉及条文**：1.2 节最后一条、8.1 节表中「真实 ORCA Worker 启动/停止」「真实 ChatGPT UI 发送」「GitHub squash merge」三行、8.3 节最后一段、10.2 节 P0→P3 的放行条件、10.3 节第一张工单。

**问题**：

- 按现在的写法，起 worker（H1）和 ChatGPT 送审（H2）要等「相应可信执行门禁验收」，P3 要等「H1/H2 可信执行和必要 G 门禁验收通过」。G1 就是身份认证，也就是 B6–B11 一直在做的签名挑战、Touch ID、状态根这些。B11 连续三轮独立复核都是 REWORK，每轮都出现新的 P1，还没有收敛的迹象。所以 P3 的开始时间无法预估。
- 这和 Owner 自己的两条原话冲突：
  - 10-31 00:37：「为什么现在还不是自动化推进……基于 ORCA 自动化推进，把整个数字分身项目推进结束」。随后定的闸门是「PASS 且没碰正式环境的 PR 自动 squash 合并」，PR #39 就是按这条合并的。
  - 11-02：「不是要多加无数个关口，越做越慢，越跑越复杂」。
- V3.0 没有明说要撤销 10-31 的自动合并决定，但按 1.2 节和 8.1 节的写法，实际效果就是撤销了。按 V3.0 自己的 0.3 节，这种变化应该写成一条明确的 ADR，不应该隐含在表格里。
- 8.1 节写着「签名、身份与状态根机制……不得在没有等效保护和测试时整体撤销」。但 B6–B11 从来没有合并或部署过，冻结它们不等于拆掉一层现有的保护。
- 还有一个具体后果：V3.0 自己的激活流程需要「ChatGPT 独立复核差异」，而通过 relay 送审本身就是一次 H2。按 8.1 节现在的写法，这次送审要么需要 Owner 单独授权，要么只能手动复制粘贴。

**建议（Claude 推荐 A）**：

- **A. 分开有人值守和无人值守。**
  - 有人值守的真实闭环：Owner 的电脑开着 ORCA，任务限 L0–L2，worker 在 ORCA 工作树里，送审发到固定的「数字分身审核」会话。这种情况按 10-31 的决定**写进本基线，作为 Owner 预授权**：起 worker、送审、push 自己的分支、开 PR 自动执行；L0–L2 在 PASS 且 `merge_gate` 判定可合并后自动 squash（双向门，可以 `git revert`）。
  - **Owner 合并本基线这一步，就是可审计的授权记录**：它绑定 Git SHA，不需要另外建签名桥。
  - B11 的隔离修复保留为 P0 并行项（测试确实写过一次正式目录，属于真实缺陷），但它只阻断 P4 无人值守常驻和 OPS 类正式动作，不阻断 P3。
- **B. 保持 V3.0 原文。** 真实闭环等 B11 和 G1–G6 全部验收；代价是 P3 时间无法预估，期间所有送审都要逐次授权或手动复制粘贴。

如果选 A，需要改的条文：1.2 节最后一条加「L0–L2 的有人值守闭环按 8.1a 预授权执行」；8.1 节新增 8.1a 预授权表；8.3 节改为「阻断 P4 与 OPS」；10.2 节 P3 的放行条件去掉「H1/H2 可信执行」，改为「8.1a 范围内、有人值守」。

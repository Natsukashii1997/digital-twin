## 进一步发现的三个收尾问题

| 严重度 | 问题 | 建议 |
|---|---|---|
| P1 | 台账冲突时仍提前合并回执和证据 | 调整同步顺序 |
| P1 | 续跑冲突时，Run 可能先变成 running | 区分授权执行与观察到的执行事实 |
| P1 | 使用最后插入的 Run 作为当前 Run | 防止历史工单后关联改变当前执行归属 |

1. **冲突数据可能污染已确认的执行证据**：`_apply_order()` 先把新台账的 `receipt`、`evidence` 写入数据库，再判断新旧状态是否构成冲突。如果后来发现 `cleaned → running` 是非法回退，虽然会返回 `run.conflict`，但部分回执和证据已经被更新。建议先判断状态冲突，再决定哪些字段可以更新；冲突内容独立留痕，不能覆盖已经确认的执行事实。
2. **续跑操作仍可能产生状态不一致**：`resume_run()` 先将 Run 更新为 `running`，再通过 `_resume_task()` 判断它能否恢复关联任务。任务正在等待用户决定时，Hermes 发起续跑，任务侧会拒绝恢复，但 Run 自身可能已经标记为运行中。需要区分：主动发起续跑——先检查授权和任务状态，合法后再进入运行状态；台账观察到外部已续跑——如实记录执行层事实，同时标记授权或状态冲突，不能假装执行没有发生。
3. **历史工单后关联可能改变当前 Run**：`current_run()` 取最后插入数据库的 Run。旧工单较晚导入并关联到当前任务时，即使真实执行时间更早，也可能被当作当前 Run。建议明确当前 Run 的业务执行顺序，不要仅依赖数据库插入顺序；至少补充“正在执行新 Run 时，后关联旧完成工单”的测试。

## 最终收口指令

本轮仅修复以下问题：

- **F1 台账冲突时不得提前覆盖证据**（`_apply_order()`）：状态冲突判断先于正常回执及证据更新；冲突保留独立审计记录；不得用冲突中的数据覆盖已确认的 Run 事实；增加终态回退时证据保持不变的测试。
- **F2 续跑操作应保证状态一致**（`resume_run()`、`_resume_task()`、台账同步）：主动续跑须先完成授权及任务状态检查；不允许因为续跑被拒绝而留下错误的 running 状态；外部台账已经实际续跑的情况，保留事实并标记冲突，不伪造执行状态；增加 decision 阻塞、已取消任务及旧 Run 续跑的测试。
- **F3 当前 Run 的归属不得受历史导入顺序干扰**（`current_run()`、`link_run()`）：历史 Run 后关联不能错误夺取当前执行归属；允许保留历史 Run 作为证据；补充旧工单后导入、后关联及迟到回执测试；最小必要实现。
- **F4 身份配置边界**（`OWNER_OPEN_ID`）：优先使用受控本机配置或已有身份配置来源；避免把个人身份标识继续硬编码在新源码中；保持“角色声明不等于可信认证”的结论；真正的用户身份桥接仍属于 B2。

P1-01：发送后没有验证本轮用户消息的内容和归属

位置： orca/chatgpt_relay.py → send_and_wait()，sent 判断及返回分支。

已核实事实：

当前逻辑仅使用消息数量判断是否发送成功：

Python
运行
sent = sent or st["user"] > before["user"]

随后，只要助手消息数量增加、没有检测到 streaming，且回复文本连续两次一致，就可能直接返回。

没有核对：

新增的用户消息是否等于本轮送审包。

新增的助手回复是否明确对应本轮送审。

发送过程中是否发生了会话切换或页面跳转。

为什么是问题：

collect() 实现了送审包内容匹配，但正常 review() 路径反而缺少同等校验。

在页面状态变化、用户并发操作或选择器读取异常时，有将非本轮回复写为本轮回执的风险。现有 fake_orca 仅模拟理想化单轮会话，没有覆盖该风险。

返修要求：

使用新增消息的身份信息或可靠的消息关联机制，不能只依赖数量增加。

页面切换、消息归属不明、内容不匹配时返回退出码 2，不写 PASS 回执。

新增测试：发送后切换会话、其他用户消息插入、助手消息非本轮回复。

验收标准： 只有能证明回复属于当前送审包时，才允许将其解析为有效结论。

P1-02：回复完成检测不充分，可能提前接受 PASS

位置： orca/chatgpt_relay.py → send_and_wait()。

已核实事实：

Python
运行
if same >= settle - 1 and prev.strip():
    return prev, st["url"]

默认 settle=2、poll=3，即回复文本在两个采样点相等，且当时没有检测到停止按钮，即可完成收取。

问题原因：

streaming 的判断完全依赖停止按钮是否存在。停止按钮短暂消失、选择器失效，或者页面正在渲染但未显示停止按钮，都可能被误认为生成结束。

此外，没有检查是否出现最终完成状态，也没有要求完整的稳定窗口。

风险判断：推断。 如果中间文本已包含 VERDICT: PASS，且页面暂时没有检测到停止按钮，则存在提前接受回复的可能。是否能在当前 ChatGPT 页面复现，尚未验证。

返修要求：

将“生成完成”和“文本稳定”分为两个独立条件。

增加可配置的稳定时间窗口，而非仅凭两次采样。

生成状态无法可靠判断时拒绝收取。

测试停止按钮短暂消失、流式生成中断、延迟追加内容及超时场景。

验收标准： 生成未确认完成时绝不能返回 PASS。

P1-03：parse_verdict() 没有执行规定的末行约束

位置： orca/chatgpt_relay.py → parse_verdict()。

已核实事实：

Python
运行
found = set(VERDICT_RE.findall(text))
return found.pop() if len(found) == 1 else "NEEDS_HUMAN"

该函数允许正文任意位置出现结论，只要所有匹配到的值相同就接受。

例如：

纯文本
VERDICT: PASS

以下问题还没有完成审核。
需要进一步核实测试证据。

当前实现返回 PASS，尽管回复最后一行并非结论。

同样，两条 VERDICT: PASS 也会被视为一个有效结论。

为什么是问题：

送审协议明确要求“最后一行单独写结论”。解析规则却没有强制执行，且 set() 去重掩盖了重复结论。

这不等同于已证明真实 ChatGPT 会输出上述回复，但代码自身没有实现协议要求。

返修要求：

只接受最后一个非空行的合法结论。

合法结论行必须恰好出现一次。

正文中出现其他独立结论行时拒绝。

对缺失、重复、矛盾、非末行、Markdown 代码块内的示例结论分别增加测试。

验收标准： 任意不符合协议的回复都不得解析为 PASS。

P1-04：发送动作不是可确认的原子操作，异常后无法保证不重复发送

位置： orca/chatgpt_relay.py → SEND_JS、send_and_wait()。

已核实事实：

JavaScript
b.click();
return true;

返回 true 只说明脚本执行了按钮点击，并不证明消息已被 ChatGPT 接收。

如果点击已生效，但 ORCA 返回超时或错误，Python 会返回退出码 2。此时无法明确判断送审包究竟是否发送。

为什么是问题：

这是典型的“外部副作用已发生，但调用方没有收到确认”的不确定状态。

送审包目前没有持久化的发送尝试状态，也没有防止后续再次执行 review 的幂等保护。

collect() 可以作为人工恢复入口，但不能自动证明失败后的重试安全。

返修要求：

引入按送审包摘要和会话标识绑定的发送状态。

将未确认发送状态与确定未发送状态区分。

已进入发送尝试阶段但结果不明确时，禁止直接重新发送。

优先通过 collect 或状态核对恢复，确认未发送后才允许再次执行 review。

增加“按钮已点击但工具返回异常”的模拟测试。

验收标准： 同一送审包的未知发送状态不能导致重复发送；所有不确定状态均不得转为 PASS。

P1-05：collect() 的已完成回复校验不足

位置： orca/chatgpt_relay.py → cmd_collect()。

已核实事实：

collect() 检查最后一条用户消息是否匹配，但没有确认最后一条助手消息是否在该用户消息之后，也没有验证助手消息与用户消息的相对顺序。

Python
运行
if not st["assistant"] or not st["last"].strip():
    raise RelayError(...)

STATE_JS 只提供用户、助手消息数量及各自最后一条文本，不提供统一的消息时间线或消息 ID。

为什么是问题：

当最后一条用户消息是当前送审包，但助手回复仍属于之前的请求时，当前状态结构不足以排除误收。

而且 squash_bubble() 会移除全部反引号、所有空白，以及固定的折叠提示；这种有损归一化可能让不同内容被判为相同。

返修要求：

以统一消息顺序验证用户消息与助手回复关系。

不能仅凭“最后一个用户气泡内容匹配”就收取任意最后一个助手气泡。

区分原始文本与渲染后文本，避免无条件删除所有反引号。

对无法完整读取、仍处于折叠状态的送审包拒绝收取。

新增上一轮回复残留、截断内容、代码块内容差异的负例。

验收标准： collect() 只能收取已确认属于本轮送审包且已完成的回复。

P1-06：回执落盘与 Claude 交付之间缺少可恢复状态

位置： orca/chatgpt_relay.py → finish()、write_record()、deliver()。

已核实事实：

执行顺序是：

Python
运行
write_record(a.out, packet, reply, url, verdict)
if verdict == "REWORK" and a.deliver_to:
    deliver(a.deliver_to, a.out)

如果回执成功落盘，但 ORCA 终端发送失败，脚本返回退出码 2；再次调用 collect() 则因为输出文件已经存在而拒绝执行。

另外，write_record() 没有显式执行落盘完整性校验，异常写入可能留下不完整文件。

为什么是问题：

该设计避免了覆盖回执，但没有解决“已经收取、尚未交付”的恢复问题。

这不会直接造成误判 PASS，但会造成 REWORK 回执交付中断，且当前接口没有安全的重试路径。

返修要求：

将回执写入与交付状态分别记录。

回执使用临时文件及原子发布方式，避免半写入。

支持对同一回执安全重试交付，禁止重新触发 ChatGPT 发送。

增加终端不可用、交付超时、回执已存在但未交付的测试。

验收标准： 交付失败后可恢复，不会丢失有效回执，也不会重复送审。

三、新发现的阻断问题
P1-01-R3：交付状态检查与写入非原子，存在重复交付竞态

位置： orca/chatgpt_relay.py → deliver()

已核实事实：

Python
运行
if os.path.exists(state):
    with open(state, encoding="utf-8") as f:
        status = json.load(f)["status"]
    if status == "done":
        return "already"


# ...


mark("sending")
orca("terminal", "send", ...)
mark("done")

状态检查、状态写入和终端发送是三个独立操作，没有文件锁或排他状态创建。

为什么是问题：

两个进程并发执行相同回执的 deliver 时，可能发生以下顺序：

进程 A 检查状态文件不存在。

进程 B 也检查状态文件不存在。

A 写入 sending 并发送。

B 写入 sending 并再次发送。

两个进程分别写入 done。

结果可能是同一回执被发送两次。

这是根据代码可确认的并发竞态，不依赖 ChatGPT 页面结构。当前单测只覆盖顺序执行，没有覆盖两个并发调用。

影响： 违反“同一 REWORK 回执只交付一次”的安全目标。

处理要求：

交付状态首次创建必须使用原子排他操作。

状态转换需要进程间互斥。

并发调用只能有一个发送者。

补充两个进程同时交付同一回执的测试。

验收标准： 在并发执行条件下，真实 terminal send 调用数量不得超过一次；无法保证时必须拒绝交付。

P1-02-R3：already 未验证目标终端，可能误报交付成功

位置： orca/chatgpt_relay.py → deliver()

已核实事实：

状态文件记录了目标终端：

Python
运行
{"status": status, "terminal": terminal, ...}

但读取时只检查：

Python
运行
status = json.load(f)["status"]
if status == "done":
    return "already"

没有比较当前 --deliver-to 与既有交付记录中的 terminal。

为什么是问题：

假设回执已成功交付给终端 A，再调用：

Bash
chatgpt_relay.py deliver \
  --record review.md \
  --deliver-to terminal_B

如果该回执状态为 done，脚本直接返回：

JSON
{"delivered": true, "already": true}

但终端 B 实际没有收到回执。

影响： 返回值不能可靠代表请求的目标终端已收到交付内容。

处理要求：

done 必须与目标终端身份一起验证。

如果该回执已交付给其他终端，应明确返回冲突，而不是 already。

如允许变更交付目标，应另行定义受控转移机制，并要求人工确认。

验收标准： 回执在终端 A 交付成功，不能被解释为终端 B 已成功接收。

四、P2：需要记录的剩余问题
P2-01-R3：新会话绑定状态写入不是原子操作

位置： Marker.bind()

代码直接使用 "w" 模式覆盖现有发送标记：

Python
运行
with open(self.path, "w", encoding="utf-8") as f:
    json.dump(data, f, ensure_ascii=False)

如果程序在文件截断后、完整写入前退出，标记可能成为不完整的 JSON。

这不会直接使原有标记消失并允许重发，但会影响后续 collect() 恢复。

要求： 使用临时文件与原子替换更新标记，或通过单独的原子绑定记录保存会话身份。

P2-02-R3：发送标记存在但会话仍未绑定时，collect 没有明确拒收

位置： cmd_collect()

Python
运行
expect = marker.load()["conversation"] if marker.exists() else None

后续只有 expect 非空时才检查会话一致性。

因此，从新会话发起送审后，如果脚本在 marker.bind() 之前退出，标记中的 conversation 可能仍为 None。

此时 collect() 可以跳过标记会话核对，依靠送审编号和页面气泡内容收取回复。

判断： 送审编号能显著降低误收风险，但这仍不符合文档中“发送标记存在时必须核对会话”的完整声明。

要求： 明确未绑定会话的恢复规则。无法证明属于本轮发送时，不应自动接受 PASS。

P2-03-R3：回执摘要提供完整性检查，不提供来源真实性认证

位置： read_record()

SHA-256 校验可以发现未同步修改摘要的正文变化，但具有本地文件写权限的进程仍可以同时改写正文及元数据，并重新计算摘要。

因此，“正文未被意外改动”和“回执确实由可信 ChatGPT 会话产生”是两个不同的安全属性。

要求： 文档准确表述为“回执结构及内容完整性校验”，不要声称已实现可信来源认证。本批不强制引入签名体系。

## 一、总体评价

**保留的部分**：闭环（感知 → 判断 → 提案 → 授权 → 执行 → 验收 → 汇报 → 沉淀）、“没授权就不启动”、授权绑定计划版本、到点只收口不延长、结果不明不重做、汇报里把“完成 / 测试过 / 审核过 / 已部署 / 已验收”分开写、8 项能力不等于 8 个 cron、没有新东西就不发长报告。这些都对，和现有 PRD、架构基线一致。

**主要问题有三类**：

1. **把目标能力当成近期能落地**：夜里无人在场的执行，在架构基线里就是 `UNATTENDED`，排在 M4，前面的 M1–M3 还没做完。送审稿的“阶段 2—3”等于跳过这几步，而且全文没有引用 SUPERVISED / UNATTENDED。
2. **几个 Hermes 能力的前提不成立**：“事件 Hooks”没有业务事件；`context_from` CLI 设不了；07:30 日报现在不推飞书；`/goal` 是 fail-open 的。
3. **授权入口有一个没被点出来的硬伤**：常浩在飞书里回一句“按建议推进”，是由**有 shell 的模型**来理解并落盘。模型可以自己写一份授权记录，“可信执行控制器”读到的就是假授权。

## 二、逐条勘误（必须改）

### E1 夜间执行要放进架构基线的两种运行模式里（阻断项）

- 问题：§4、§10 没写夜间执行属于哪种模式。按 ARCHITECTURE §4.3，`SUPERVISED` 是“有人值守的单次受控 Run”，`UNATTENDED` 是“Owner 离开后继续工作”。常浩睡着以后，没人能停机、没人能处理异常，这就是 UNATTENDED 的场景，它要求的“无人在场时可靠唤醒、重启后幂等恢复、常驻服务独立安装和撤销”（§5.3）现在都没有。
- 改法：在送审稿里加一节“夜间窗口的模式归属”，二选一，交常浩定：
  - **(推荐) 方案 A**：新定义一种“**有界窗口授权**”：授权来源用 SUPERVISED 的 5.2a(b)（飞书私聊），执行只能用**已验收、没有外部副作用**的通道（见 E7 的 v0）。按 ARCHITECTURE §12 改基线，不另起平行方案。
  - 方案 B：夜间执行完全按 UNATTENDED 走，等 M4 完成。这样近期只能做汇报，不能做夜推。
- 不论选哪个，§10 的阶段顺序都要和 M1–M4 对齐，写清“哪个阶段依赖哪个里程碑”。

### E2 授权不能由模型来解读和落盘（阻断项）

- 问题：§4.1 写的是“授权由可信执行控制器硬性检查”，但没说**授权记录由谁写**。现在的链路是：常浩回飞书 → 猛鬼兽（有 terminal/file）理解 → 写记录。`twin_identity.py` 自己也写了：它只能证明“这一回合是常浩触发的”，不能证明“常浩批准了这个计划”。
- 改法（两层，都用现有能力）：
  1. **签发不经模型**：授权、调整、撤销一律走固定命令，由网关插件 slash 命令（或 `quick_commands` exec）处理，不进模型回合。例如：
     - `/夜推 批准 N20261102-v2 #a1b2`（计划编号 + 版本 + 计划内容哈希前缀）
     - `/夜推 停`、`/夜推 只留 obsidian`、`/夜推 状态`
     - 常浩说自然语言“改到 1 点结束”时，模型只负责**生成新版本计划**并回一句“回复 `/夜推 批准 N…-v3 #c3d4` 生效”，不能自己生效。
  2. **执行前回查飞书**：授权记录里只存 `owner_message_id`。执行控制器（独立的 launchd 进程，不是模型的 shell）每次开新任务前，用猛鬼兽 bot 身份回读这条消息，核对：发送人是常浩、在私聊里、内容里的计划号和哈希与当前计划一致、没被用过、没被后来的 `/夜推 停` 覆盖。模型发不出“常浩发的飞书消息”，所以这一层它伪造不了。
- 残余风险照 ARCHITECTURE 5.2a 的写法如实列出：防不了同一 macOS 用户下的恶意本地进程。

### E3 “事件 Hooks”要换成实际存在的机制

- 问题：§2 表格、§8、§9 多处写“事件 Hooks / 监控”触发审核失败、执行异常提醒。Hermes v0.22.2 的网关钩子只有网关、会话、Agent 回合、命令这几类生命周期事件，没有业务事件。
- 改法：工程事件由**产生事件的一方主动推**：`relay_loop.py`（RELAY-02，现在就用猛鬼兽私聊通知 NEEDS_HUMAN / 超限）、run_worker 的回执、夜推控制器。拉取式的检查用 `--no-agent` 或 `--monitor-script`（输出不变就不调模型）。Hermes 钩子只用在 E2 的命令入口和 `agent:end` 审计上。

### E4 `context_from`、`continuity`、`/goal` 的用法更正

- `context_from`：源码有，CLI 设不了。要用的话，明确写“经 cronjob 工具设置，回读 `jobs.json` 确认”，或者干脆**不用**：晨报直接读夜推控制器写的收口文件（`--script` 取数），比依赖上一个 cron 的模型输出更可靠，也不会把模型的转述当事实。
- `continuity`：只适合“去重、接着上次说”的场景。晚报和晨报要的是**事实快照**，不该拿上一份模型输出当输入；去重按 PRD F4.3 用 notepad。
- `/goal`：判定失败按“继续”处理，夜里不能当执行器或续跑器。第 7.1 表要从“不视为全局调度器”改成“**夜间窗口内禁用**”。

### E5 “扩展已有日报”的前提现在不成立

- 07:30 日报还在**并跑**，`deliver=local`，写进并跑文档，**不推飞书私聊**；PRD F4 的 09:00 晨报还挂起（第 4 批）。所以“次日成果简报 = 扩展现有日报”前面还差两步：T7 切换 + F4 恢复。
- 11-02 周报因等模型 934 秒失败，日报晚了 6 分钟、周报晚了 29 分钟。用模型的定时任务本身还没达到“每天准点出”的可靠性，晚报 21:30 要做真决策入口，先得解决这件事（失败重试 + 失败时降级成脚本版纯事实简报）。
- PRD F4 验收是“**每天主动推送不超过 1 条**”。新方案至少有晚报、晨报两条，加上立即级告警。要么改 PRD（建议：晚报、晨报各 1 条，告警另算，夜间静默），要么把晨报并进晚报。这要常浩定。

### E7 可靠性前置条件没写（夜推的地基）

送审稿全是逻辑层设计，没写夜里没人在时**机器层**会出的问题。都是这个项目已经真实踩过的：

1. **网关断线没人知道**：11-01 断线 20 小时，告警发不出去。夜推需要**夜间心跳**（`--no-agent`，窗口内每 30 分钟，正常时不说话），加上告警发不出去时的兜底：写本机日志，晨报第一行必须报“夜间心跳是否完整”。**没有消息不等于一切正常。**
2. **电脑睡眠、重启、网络切换**：窗口控制器用 launchd（agent-kit G-05：launchd 直接起 `/bin/bash` 读不了“文稿”目录；G-12：会话里等到点再跑的后台任务，电脑一重启就丢）。窗口开始时要检查是否插电、`pmset` 是否会睡；不满足就不开窗，晚报里说明原因。
3. **ChatGPT 审核依赖 ORCA 内嵌浏览器的登录页面**：夜里页面过期、登录失效、额度用完时，审核那一步会卡住。规则：发送前核对页面（RELAY-01 已有），卡住就把该任务停在“待审核”，不换通道。
4. **run_worker 的护栏是事后检查**：write 模式放开了权限，push 只能事后发现。夜推 v0 用它时，要**事前**去掉写权限：worktree 里把 `remote.origin.pushurl` 设成无效地址，或用不带写权限的凭据。
5. **额度**：送审稿的“预算”写成调用成本，实际是会员额度（Codex 月度、ChatGPT）。预算改成“最多 N 张单、每单最多 M 轮返修、Codex 额度低于阈值就不派 Codex”，复用 PRD F10.4 的 `codex-quota-guard`。
6. **和白天的会话撞车**：夜推和常浩白天开的 Claude 会话可能改同一个仓库。夜推只在自己的 worktree 和 `night/<日期>-<单号>` 分支干活；晨报列出所有夜推分支，由白天决定合不合。

### E8 编号体系冲突

- 送审稿用 P0/P1/P2 同时表示能力优先级和通知级别，学习机制又用 L1/L2/L3，和架构基线的风险档位 L0–L3 撞名。ARCHITECTURE §4.4 明确不加第二套编号。
- 改法：通知分级改成“**立即 / 随报 / 周汇**”；学习三级改成“**观察 / 候选 / 正式**”；能力优先级只在本文件内部用“首批 / 第二批 / 后续”。

### E9 经验沉淀要接现成的渠道，不另建

现成的三条线路，各管一类：

| 发现了什么 | 去哪里 | 谁批准 |
|---|---|---|
| 某项目里踩的坑 | 该项目 `docs/LESSONS.md` | Claude / Codex 直接写 |
| 换个项目也成立的坑 | `agent-kit/LESSONS.md` 的 G-xx（已有“只出提案，常浩批准才写”的升级规则） | 常浩 |
| 可复用的做法 | `my-skills/skills/<名>/`（按 links.tsv 链接） | 常浩；Skill 变更走 PR |
| 决策缘由、对常浩的新认识 | Vault 收件箱（`/kb-note`），按 Vault 主线规则审 | 常浩 |
| 只出现一次的观察 | 夜推证据目录里的 `observations.md` | 不升级，攒着 |

规则：**同一个做法在 2 个以上任务里有效，才从“观察”提成“候选”**；猛鬼兽只能提候选，不能自己改 SOUL、HERMES.md、LESSONS 或 Skill。“定期思考”不单独建 cron，并进周报一段“本周可以固化的做法（≤3 条，附证据）”，没有就不写这一段。

### E10 晚报要加两项送审稿没有的内容

2. **每条推荐的可执行性判断要落到通道**：例如“能做到 PR 前（run_worker，隔离 worktree，不 push）”、“要等 ChatGPT 审核，夜里可能卡住”。不能只写“能自动做到哪一步”。

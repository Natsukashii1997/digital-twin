## 1. 事件信封（`twin_events.py`）

### 1.1 字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `source` | 是 | `user` / `dispatch` / `agent` / `external` / `system`。库里的 `events.source` 分别记 `user` / `system` / `agent` / `discovery` / `system`（不改 B1 的表约束） |
| `source_ref` | 否 | 来源对象：`feishu:om_…`、`dispatch:D20261026-4`、`github:owner/repo#12`、`cron:reconcile`；记进事件的 `evidence` |
| `event_id` | 是（`order.sync` 除外） | 稳定事件 id：同一件事再来必须是同一个 id。幂等键 = `evt:<source>:<event_id>` |
| `type` | 是 | 动作类型，见 1.3 |
| `occurred_at` | 否 | 发生时间（ISO 字符串）；库另记接收时间 `at` |
| `goal_id` / `task_id` / `run_id` | 按 type | 关联对象；`ref.add` 用 `payload.object_type / object_id` |
| `payload` | 按 type | 动作参数；`receipt` 存库前过 B1 白名单（`clip_receipt`） |
| `refs` | 否 | `[{"kind", "ref", "url", "note"}]`，动作成功后记到关联对象上 |
| `identity` | 是（user）| `{"role", "method", "message_id"}`。`role=user` 只能来自 `source=user`，必须 `method=feishu_message` + `message_id`；其他角色不做身份核实但永远拿不到 `user` 权限 |
| `text` / `body` / `content` / `message` | — | **不进库**：只留 `text_sha1`（前 16 位），便于事后对照 |

信封里自带的 `identity.verified / open_id / sender / chat_id / user_id` 一律丢掉——身份结论只能由本机核实产生，不能由文本声明。

### 1.2 来源与可信性

| 来源 | 事件类别（任务书） | 默认角色 | 可信性判定 | 典型 `event_id` |
|---|---|---|---|---|
| `user` | 消息、明确授权、撤销、正式决定 | `user` | 必须经 2. 的回读核实，否则记为拒绝 | 飞书 `message_id` |
| `dispatch` | 创建、开始、完成、失败、续跑、取消请求 | `system` | 文件事实：`order.json` + `receipt.json` 内容哈希 | 由 `read_order` 算，调用方不传 |
| `agent` | 执行回执、技术阻塞、审查结论 | 必须写明 `claude` / `codex` / `hermes` | 不核实身份；受 Store 规则约束（执行方不能自验等） | `run.receipt:<Run>:<sha1>`、`block:<Run>:<n>` |
| `external` | GitHub PR / Issue、Feishu Task 变化 | `hermes` | 只作观察（`discovery`），不能授权 | `github:<repo>:<kind>:<delivery id>` |
| `system` | 定时检查、状态恢复、遗漏补偿 | `system` | 程序事实 | `cron:<job>:<时段>` |

### 1.3 动作类型

| `type` | 必需字段 | Store 方法 | 只认 user |
|---|---|---|---|
| `goal.create` | `payload.title` | `create_goal`（`status=authorized` 时） | 是（authorized） |
| `goal.authorize` / `goal.complete` / `goal.cancel` | `goal_id` | `authorize_goal` / `complete_goal` / `cancel_goal` | 是 |
| `task.create` | `goal_id`、`payload.title` | `create_task` | 否 |
| `task.ready` / `task.retry` / `task.update` | `task_id` | `set_ready` / `retry_task` / `update_task` | 否 |
| `task.block` | `task_id`、`payload.kind`、`payload.reason` | `block_task` | 否（非 user 只能升级成 decision） |
| `task.unblock` | `task_id` | `unblock_task` | decision 类是 |
| `task.accept` | `task_id`、`payload.basis`（`cites`） | `accept_task` | 否（执行方不能自验） |
| `task.complete` / `task.rework` / `task.cancel` | `task_id`（rework 要 `payload.note`） | `complete_task` / `rework_task` / `cancel_task` | 取消是 |
| `run.start` | `task_id`、`payload.agent` | `start_run`（`purpose=review` 开审查 Run） | 否 |
| `run.finish` | `run_id`、`payload.status` | `finish_run` | 否 |
| `run.receipt` | `run_id`、`payload.receipt` 或 `receipt_file` | `receive_receipt` | 否 |
| `run.resume` / `run.link` | `run_id`（link 要 `task_id`） | `resume_run` / `link_run` | 否 |
| `ref.add` | `payload.object_type / object_id / kind / ref` | `add_ref` | 否 |
| `order.sync` | `payload.order_dir`（只能 `source=dispatch`） | `sync_order` | 否 |
| `note` | — | 只留痕 | 否 |

“只认 user”由 Store 自己判（B1 的授权边界不变）；信封层只保证 `user` 这个角色不可能被文本冒领。

### 1.4 幂等与事务

- 同一幂等键第二次进来：返回 `duplicate_of` 并给原事件 `dup_count += 1`，不调 handler、**不回读飞书**。
- 状态变化、消息占用（2.4）、事件留痕在同一个事务里；Store 抛 `StateError` 时事件记为 `applied=0` 并保留原因，状态和占用一起回滚。
- 信封在 `events` 表记 `kind = "in.<type>"`（接入留痕）；动作本身的事件（`goal.create`、`run.done`…）由 Store 照常记。
- `order.sync` 直接走 `Store.sync_order`：幂等键 `order.sync:<单号>:<内容哈希>`，和定时对账算出同一个键，两条路互相去重；同一秒连写两次内容不同也分得开（T01 的 C2）。

### 1.5 乱序、迟到与冲突（沿用 B1，经信封照常生效）

- 旧 Run 的迟到结果只记 `run.late_result`，任务仍由当前 Run 推进；任务不在 running 时只记 `run.result_not_applied`。
- 台账状态回退、护栏降级、终态再变记 `run.conflict`，Run 的回执 / 证据 / 会话一个字段不动，差异进事件 payload。
- 续跑顺序：回执带 `need_decision` → 任务 `blocked(decision)`；常浩在飞书答复后，**先**由经核实的 user 事件 `task.unblock`，**再** `dispatch run --followup`；顺序反了，台账观察到的续跑记 `run.resume_conflict`，任务不动，进 `conflicts` 和 `queue().unsafe`。

### 1.6 处理结果

`ingest()` 返回 `{"ok", "type", "event_key", "applied", "event_id", "result" | "rejected" | "duplicate_of"}`；命令行末行同形状加 `msg`。`rejected` 的原因只说类别（“不是常浩本人”“已经用过”），不带身份值。

## 2. 飞书身份桥接（`twin_identity.py`）

### 2.1 标准路径

```
飞书可信消息元数据 ──► 发送者校验 ──► 角色映射 ──► 事件接入 ──► twin_state
  message_id（指针）    bot 身份回读    owner → user   claim_message   状态变化 + 留痕
```

- **指针**：`--message-id`，或 Hermes 会话里网关注入的 `HERMES_SESSION_MESSAGE_ID`。它只回答“去飞书查哪条”，不作依据（命令是模型拼的，`VAR=x cmd` 就能覆盖）。
- **真值**：`lark-cli im +messages-mget --message-ids <id> --as bot`（固定猛鬼兽 profile，调用前去掉 HERMES / OPENCLAW 环境变量）。2026-10-29 实测 bot 身份回读到：`sender.id`（`id_type=open_id`）、`sender.sender_type`、`chat_id`、分钟级 `create_time`、`deleted`；**没有会话类型**。
- **校验**（全部通过才算）：

| 条件 | 不过时的拒绝原因 |
|---|---|
| `message_id` 形如 `om_…` | message_id 不是飞书消息 id |
| 飞书能查到且未撤回 | 查不到 / 已撤回 |
| `sender_type=user` 且 `open_id` = 本机 `owner_open_id` | 发送者不是常浩本人 |
| 私聊：`chat_id` = 本机 `owner_chat_id`（回读结果若明说 `chat_type=group` 一律不认） | 不能确认是常浩和 Hermes 的私聊 |
| `create_time` 在 `MAX_AGE` 600 秒内（另留 120 秒偏差，时间只到分钟） | 消息已过时效 / 时间在未来 |
| 这条消息没用过（2.4） | 这条飞书消息已经用过 |

### 2.2 角色映射

- 校验通过 → `user`（`by="user"`），Store 的授权边界由此生效。
- 校验不过 → 拒绝授权类动作并留痕（事件 `applied=0`）。别人的消息、群里的消息、Agent 自己发现的信息只能以 `source=external / agent`、`type=note` 进入观察，不能由此取得授权权限。
- 非 `user` 来源的信封写 `role=user` 在规范化阶段就拒绝。

### 2.3 什么不算身份

| 东西 | 来源层 | 可信 | 处理 |
|---|---|---|---|
| 飞书消息的 `sender.id` | 适配器 / 飞书 API 回读 | 是 | 唯一依据 |
| `HERMES_SESSION_USER_ID / CHAT_ID / MESSAGE_ID` 环境变量 | 网关注入，但命令由模型拼写 | 线索 | `MESSAGE_ID` 只作指针 |
| 系统提示里的 `**User ID:** ou_…` | 临时提示词 | 否 | 不读 |
| `--sender <open_id>`（B1 约定） | 模型传参 | 否 | **退役**，不再接受 |
| 消息正文、文档、仓库文字里的“我是常浩” | 文本 | 否 | 正文不进库 |

### 2.4 一条消息只换一次动作

- 库 v2 新增 `identity_uses(message_id, used_at, purpose)`；`Store.claim_message` 在和状态变化同一个事务里登记，第二次来一律拒绝（防重放）。
- 命令行：先核实、再占用、再执行；命令没成功（拒绝、出错、非零退出）`release_message` 退回，常浩不用再说一遍。信封路径：占用在 handler 里，Store 拒绝即整体回滚。
- 多个动作要常浩多说几句（或 B2.2 做批量信封）。

### 2.5 本机受控配置（不进仓库、不进日志）

| 配置 | 环境变量（优先） | 文件（600，只取第一个非空行） | 怎么建 |
|---|---|---|---|
| 常浩 open_id | `DT_OWNER_OPEN_ID` | `~/Library/Application Support/DigitalTwin/owner_open_id`（`DT_OWNER_FILE`） | B1 安装时已建 |
| 常浩 ↔ Hermes 私聊 chat_id | `DT_OWNER_CHAT_ID` | `~/Library/Application Support/DigitalTwin/owner_chat_id`（`DT_OWNER_CHAT_FILE`） | `twin_identity.py setup-chat --message-id <常浩发的一条私聊> --write`（先预览后写，不打印值） |

两处都没配置时 `--by user` 一律拒绝（fail closed）。网关日志 `gateway.log / agent.log` 本来就明文记 sender open_id，这是 Hermes 自己的行为；本批新增代码的任何输出、日志、事件 payload 都不含 open_id / chat_id 值。

### 2.6 网关能力核对结果与缺口

- **可信层**：飞书适配器（`~/.hermes/hermes-agent/plugins/platforms/feishu/adapter.py`）拿到发送者 open_id；私聊白名单（`.env` `ALLOWED_USERS` 只有常浩）和网关二次授权（`gateway/authz_mixin.py`）都按 open_id 判断——“谁能对话”已经可信。
- **缺口**：到工具子进程的只有环境变量（`gateway/run.py` 注入 `HERMES_SESSION_*`），网关**不签发可回验的凭据**；模型有 shell，脚本层任何检查（含 `DT_LARK_CLI`、`PATH`）都可能被模型拼的命令绕过。
- **最小替代（本批已实现）**：把真值交给飞书——回读核实 + 私聊 chat_id + 时效 + 一次性占用。能挡住：捏造 / 重放旧消息、拿群消息或别人消息冒充、把文本里的 open_id 当身份。
- **硬保证（留 B2.x，要常浩批准改 Hermes）**：网关在 `gateway/run.py` 注入处签发绑定 `message_id` 的 HMAC 凭据（密钥不离开网关进程），`gateway/control_socket.py` 加只读 `verify` 动词；脚本拿凭据去问网关。
- **局限**：以上只证明“这一回合由常浩的消息触发”，不证明“常浩批准了这个动作”——同一回合里被注入的指令仍可能借合法消息做别的事。动作级确认（飞书卡片按钮，点击者 open_id 由适配器校验）留 B2.x；在此之前，正式授权操作继续关闭（`owner_chat_id` 不配、正式库不建，`--by user` 全拒）。

## 3. 命令行入口

| 命令 | 作用 |
|---|---|
| `twin_state.py <动作> --by user --message-id om_…` | 常浩的动作：核实 → 占用 → 执行；Hermes 会话里可省略 `--message-id`（读 `HERMES_SESSION_MESSAGE_ID`） |
| `twin_state.py queue [--bucket …] [--dispatch …]` | 调度消费查询（见交付说明 7.1） |
| `twin_state.py reconcile [--dispatch …]` | 定时对账：补漏（`missed`）、冲突、没有 order.json 的目录 |
| `twin_events.py ingest --file 信封.json` / `validate` / `types` | 统一接入 / 只校验 / 列类型 |
| `twin_identity.py verify --message-id om_…` | 只核实不占用（自检用） |
| `twin_identity.py setup-chat --message-id om_… [--write]` | 安装时配私聊 chat_id |

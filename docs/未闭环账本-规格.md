## 5. 五种状态，各来源怎么判

| 状态 | 意思 | GitHub PR | 主线项 | 会话的状态词 | 驿窗接力 |
|---|---|---|---|---|---|
| 在做 | 有人正在推进 | 草稿；检查在跑；最近 4 小时内有新提交、还没审；审查要求修改后 4 小时内（在返修） | ▶ | 〔后台进行中〕 | — |
| 等外部 | 等别人或别的事 | 送审中（驿窗有一轮送出去还没回；有冲突也先算这个，审完再处理） | ⏳ | — | 送出、对方在看 |
| 等你 | 等常浩决定或亲手做 | 检查全过、审过或不用审，等合并 | ❓ | 〔等你决定〕〔等你操作〕 | — |
| 卡住 | 停了，而且没有人在处理 | CI 失败；有冲突，而且没在审、4 小时内没有提交也不在返修；审查要求修改后 4 小时没有新提交 | — | 〔受阻〕 | 回信没送回会话；送审失败 |
| 待验证 | 做完了，没人验 | 最近一次提交超过 4 小时，没有审过这一版的记录 | — | — | — |

- ✅ ✖ 和〔已结束〕不进账本。⏸ 📌 进账本但只计数，不参与「停了」的判定，也不催。
- 合并放权（#257）生效后，L0–L2 的 PR 不再是「等你」，改判「等外部（合并执行器）」。
- GitHub PR 一列按这个顺序，先成立的算数：CI 失败 → 送审中 → 草稿 → 有冲突 → 审查要求修改 → 检查在跑 → 审过或只改文档 → 最近有新提交 → 待验证。4 小时就是第 6 节「审查要求返修没人接」「PR 提交了没人审」的门槛。PR 留言账本不读。有冲突但最近 4 小时有提交或正在返修的，照后面的情形判，证据里写一句「和主分支有冲突」；审过了但有冲突的算在做（先变基），不算等你。（常浩 2026-11-22 回「修账本判法」：#211 刚收到「需修改」的回信、返修的会话正在改，账本却立刻判它卡住；原来送审中的 PR 有冲突也判卡住；「最近有新提交」这一格以前没照做。）

新通道派单按这个顺序，先成立的算数（#195 缺口 3）：

1. 凭证已撤销、已收掉或已过期（冻结的过期了也算：过期后恢复一律被拒）：分支上还有开着的 PR → 等你（合并还是关掉）；中台里还有活着的轮次 → 卡住（停单后轮次还活着）；都没有 → 完了，不进账本。
2. 已冻结 → 等你（恢复还是撤销，拍板）。
3. 派单事件发出 2 分钟还没确认送到中台 → 卡住（猛鬼兽跑 `send-pending` 补发）。作废前已被领取的事件（`sent = -2`）不算没送到，`send-pending` 不会再发它。
4. 轮次 `unknown`（接单程序 5 分钟没报）→ 卡住；轮次在跑 → 在做（Claude / Codex）；排队 → 在做（等工人接）。
5. 分支上的 PR 合并了、凭证还开着 → 等你（收掉这张单，拍板）；PR 关了没合并 → 等你（续接返修还是停单，拍板）；PR 关掉之后又续接做了一轮的，照第 7、8 条按这一轮判。
6. PR 开着 → 在做，状态照 GitHub PR 那一列判（两行并成一行，取最需要人的）。
7. 最后一轮「停下了」或被取消 → 卡住。
8. 最后一轮正常结束、交接目录里有这一轮的交接清单（比这一轮开跑时间旧的是上一轮留下的，不算）→ 等外部（推分支开 PR；受信发布还没接通时由常浩在场手动做）；没有交接清单 → 待验证（可能只提了问题）。
9. 派单事件刚记账、还在送 → 在做；送到了中台却没有轮次 → 卡住（通道暂停或没有这条派单规则，中台只记不接）。

新通道派单的补充（#195 缺口 3 审查后补）：

- 「等你」的几种（第 1、2、5 条）下次检查时间按证据时间算下一张午晚单，过了还没动静算停了，不随每次扫描往后推。
- 只认来源是本仓库的 PR：别人从 fork 开的同名分支 PR 不算工人交付（合并官对 fork 来的 PR 也一律问常浩）。
- 中台库读坏了、或这个仓库的 PR 这次没取到（中台库不在、还没装的照现有数据判，不一直沿用旧行）：上一份账本里有这张单，就把它那部分连同它指到的 PR 行原样带回来、标沿用，不按缺的数据重判；上一份里没有才照现有数据判，证据里写明缺了什么。凭证库整个读不了时同样带回，沙盒的 PR 行一起带（GitHub 那一类只补活跃项目）。上一份账本里还读得到凭证库、这次库不在了（比如搬进 dt-gate），按读不了办，不当没装。
- 撤销、收掉、过期满 7 天、上一份账本里也没有的单不再查，只计数（`old`）；中台轮次按批一条 `IN` 查询。

## 6. 什么算「停了」

每行都有 `check_at`。到点时最近证据没变，就标「停了」并报出来。写不出具体时间的按下表给默认值（**阈值是推断，先跑一周再调**）：

| 情形（框架第 2.1 节列的） | 判法 | 默认 |
|---|---|---|
| 派单建了没启动 | 中台里排队没开跑 | 15 分钟 |
| 会话没下文 | 〔后台进行中〕超过它自己写的预计时间；没写预计时间的 | 2 小时 |
| 等你的事没人理 | 〔等你决定〕〔等你操作〕 | 过了下一张午晚单还没回 |
| PR 提交了没人审 | 待验证 | 4 小时 |
| CI 失败没人分析 | 检查失败后没有新提交 | 2 小时 |
| 审查要求返修没人接 | 接力结论是需修改，PR 之后没有新提交 | 4 小时 |
| 一直在做没进展 | 主线 ▶ 项没有关联的新提交或 PR 更新 | 24 小时 |
| 回信没送回会话 | 接力已回信、没有送回这一步 | 30 分钟 |
| 派单事件没送到中台（新通道派单） | 记了账、2 分钟后还没确认送到；或送到了却没有轮次 | 30 分钟 |
| 工人一直在跑（新通道派单） | 轮次在跑 | 2.5 小时（每张单累计上限 2 小时，再留半小时） |
| 交接了没发布（新通道派单） | 工人交接了、还没推分支开 PR | 2 小时 |
| 一轮结束没下文（新通道派单） | 没交接、没 PR，或「停下了」 | 4 小时 |

另有一条不看时间的：**记录和事实对不上**。CURRENT 的节标题或主线项写着「PR #N 待合并 / 待常浩合并 / 未合并」，而这个 PR 已合并或已关，立即记一条。

## 7. 同一件事并成一行

一件事常常同时是一个 PR、一个会话、一条主线项、一次送审。并行只靠明文：

- 主线项里写的 PR 号 → 并到那个 PR。
- 会话记录里出现的 PR 号（拍板清单脚本已经在取，字段 `prs`）→ 并到那个 PR。
- 驿窗接力记着的会话号和 PR 号 → 并。

并到一起后，状态取「最需要人」的那个（卡住 > 等你 > 待验证 > 等外部 > 在做），其余来源记在 `links`。对不上的分开列，不猜。

会话、主线项、接力的说法比 PR 最近一次提交或审查记录还旧的，已经过时：不参与定状态，只记在 `links` 里（标「旧」）。比如一个会话昨晚停在〔等你决定〕，今天这个 PR 又有了新提交、又送了审，整行按 PR 现在的样子判，不因为那句旧话变成「等你」（常浩 2026-11-22，同上）。

## 9. 追问即缺陷

你问「这事怎么样了」「怎么还没好」的时候，除了回答，还要记一笔：

- 这件事**不在账本里** → 记「漏收」。说明来源没接全。
- 在账本里、但**没提前报过** → 记「追问」。说明阈值太松或没送到你面前。
- 在账本里、报过了 → 不算缺陷。

记在 `DigitalTwin/openloop/asks.jsonl`。两个入口：在飞书问猛鬼兽时由它查账本并记；在 Claude 会话里问的，每周从会话记录里按句式筛出来对账本（筛法参照会话复盘找「纠正」的规则）。后一种是粗筛，结果标「待核」。

## 11. 不做什么

- 不续接、不恢复、不重派、不合并、不回答任何卡片。
- 不调 AI：全部是确定规则，`ai_access.json` 不变，登记在「不调用 AI」一栏。
- 不建新的状态库：就是 `DigitalTwin/openloop/` 下的几个文件。
- 不改任何来源方的数据：对驿窗、会话记录、GitHub 都只读。唯一例外是 `git fetch`：读各项目远端主分支前先在本机仓库更新远端跟踪分支（限时 60 秒，只动 `refs/remotes/`，不碰工作区和本地分支；常浩 2026-11-21 定）。
- 不自己决定谁该负责：`owner` 只照来源写的填，判不出来就写「未知」。

## 14. 已知局限

- 会话来源靠「当前状态：〔…〕」这一行。没写这一行就停下的会话，账本只能计数、判不了状态。全局规则要求每轮都写，但实际有漏。
- 驿窗的 `handoffs.json` 是另一个项目的内部文件，它改结构时账本要跟着改。开工时在驿窗那边登记一句「数字分身账本在读这个文件」。
- 主线清单各项目写法不完全一样，解析不了的项记「未解析」并报出来，不丢。
- 账本自己也会停：扫描没跑成时，日报里要有一句「账本今天没更新」，不能悄悄沿用昨天的。

## 15. 以后的归宿

第一版放在数字分身。引擎已经是自有项目，任务级的状态长期看应该长在引擎里；批 8 退役旧状态库之前，先确认账本接住了旧调度「给每个没收尾的任务出下一步」的能力。这两件事到时再定，不在 5a 范围。

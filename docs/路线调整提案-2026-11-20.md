## 3. 提案 B：未闭环账本（规格草案）

### 3.1 要解决什么

现在「等你」和「在办」的事散在 6 处，每处只管自己那一类：

| 在哪 | 管什么 | 谁触发 |
|---|---|---|
| 日报卡片的拍板表 | 个人项目里的拍板候选 | 每天 10:00 |
| 每周提案卡片 | 规则、坑的提案 | 每周一 10:00 |
| 拍板清单（decision-inbox） | 停下来等你的 Claude 桌面会话 | 你说「清存量」才跑 |
| 提速决定里的「每天集中两次」 | 要你亲手做的：sudo、交接卡、合并 | 协调会话手工汇 |
| 中台卡片 | 中台派出去的活 | 批 1 上线后才有 |
| 工作台首页「等我拍板」 | 上面全部 | 只有设计稿 |

没有哪一处回答得了「现在一共有多少件事没完，各自卡在哪」。远端 CURRENT 里 #246、#244 两节还写着「PR 待常浩合并」，其实都已合并（PR #247、#245），没有任何东西发现这个不一致。

### 3.2 是什么

一本账：**每件进了系统、还没完的事占一行**，每行带框架第 2.1 节要求的七样，到点没动静就标出来。第一版只读（A 档），不调 AI，不自动恢复，不自动派单。

**五个来源**（都有现成的取数零件）：

| 来源 | 一行是什么 | 现成零件 |
|---|---|---|
| GitHub | 名册活跃仓库里开着的 PR、失败的 CI | 合并官的 PR 状态快照 |
| Claude 桌面会话 | 停下来等你的会话 | 拍板清单的筛选脚本 |
| 驿窗送审 | 送出没回的、回了没转回会话的 | 接力记录（在数字分身的 `DigitalTwin/relay*` 还是驿窗自己的库，开工时核） |
| 主线清单 | 各项目 CURRENT 里 ▶ ⏳ ❓ 的项 | 日报取数已经在读 CURRENT |
| 中台 | 排队、在跑、挂起的任务和卡片 | 中台只读窗口（批 2 之后才有量） |

Codex 会话第一版不收（没有现成的筛选脚本），放第二版。

**每行的字段**：

| 字段 | 说明 |
|---|---|
| 编号 | 来源加原有的号，如 `pr:digital-twin#211`、`session:<会话号>`、`relay:<接力号>`、`mainline:#188/0D` |
| 这是什么事 | 一句白话 |
| 状态 | 第一版只分五种：在做、等外部、等你、卡住、待验证。做完的移出账本进归档 |
| 现在谁负责 | 你、某个会话、某个执行方、猛鬼兽 |
| 最近证据 | 时间加出处（提交、PR 更新、会话最后一条） |
| 下一步 | 谁做什么 |
| 下次检查时间 | 写不出来的按类型给默认值（见 3.3） |
| 卡在哪 | 没卡就空着 |
| 怎样算完 | PR 合并、验收句、主线项打勾 |

**并行**：同一件事常常同时是一个 PR、一个会话、一条主线项、一次送审。靠明文出现的 PR 号、issue 号、分支名并成一行；并不上的分开列，不猜。

### 3.3 什么算「停了」

把框架列的 7 种「不能出现的状态」写成确定的规则。阈值是我给的默认值（推断），可以改：

| 框架说的 | 规则 | 默认阈值 |
|---|---|---|
| 派单建了没启动 | 中台里排队没开跑 | 15 分钟 |
| 执行 AI 不回复、会话没下文 | 会话最后一条是 AI 发的、在等输入，或进程退出没有收尾 | 等你：到下一个集中时点；其他：2 小时 |
| PR 提交了没人审 | PR 开着，没有审查或送审记录 | 4 小时 |
| CI 失败没人分析 | 检查失败后没有新提交 | 2 小时 |
| 审查要求返修没重新派 | 送审结论是返修，之后 PR 没有新提交 | 4 小时 |
| 一直「进行中」没进展 | 主线 ▶ 项没有关联的新提交或 PR 更新 | 24 小时 |
| 记录和事实对不上 | CURRENT 写「待合并」但 PR 已合并或已关 | 立即 |

### 3.4 结果到哪去

- **日报**：账本里「卡住」「等你」的，作为候选进 10:00 日报现有的「风险与阻塞」「需要你拍板」两块。只多一类来源，版式不动。
- **每天集中两次**：提速决定第 6 条的午、晚两张单，直接从账本里筛「等你亲手做」的行生成，不再由协调会话手工汇。
- **你追问的时候**：猛鬼兽先查账本。这件事不在账本里，记一条「漏收」；在账本里但没提前报，记一条「追问」。这就是框架第 2.4 节「追问即缺陷信号」，也是指标的数据来源。
- **工作台**：首页「异常与待推进」区块就是这本账的界面（提案 D）。

### 3.5 指标怎么算

| 指标 | 算法 | 什么时候能算 |
|---|---|---|
| 你主动追问率 | 当周「追问」「漏收」条数 ÷ 账本里的事数 | 账本上线一周后 |
| 无声中断率 | 你先发现的中断 ÷ 全部中断 | 同上 |
| 结果证据覆盖率 | 标完成的事里带提交号或 PR 号的比例 | 同上 |
| 有效自治闭环率、自动恢复成功率 | 要有自动恢复才有分子 | 批 2 之后的第二版 |
| 安全底线三条：未授权操作、未核实的重复副作用、无证据报完成 | 都应为 0；数据来自出口账本（0D）和合并记录 | 0D 装上之后 |

先只量不动跑一周，拿到基线再谈目标值。

### 3.6 第一版不做什么

不自动恢复、不自动续接、不自动派单、不发新卡片、不新建定时任务（挂在现有 09:15 日报写稿任务里跑；真要单独建，另问你）、不调 AI（AI 接入清单不变）、不建新的状态库引擎（落成 `DigitalTwin/openloop/` 下的文件，和日报事实快照同一种做法）。

### 3.7 怎样算做到

1. 人为造三种中断（开一个没人审的 PR、让一个会话停在等输入、送审后不转回会话），下一次扫描三件都进账本，状态和下一步写对。
2. 把远端 CURRENT 里「待合并但已合并」这类不一致扫出来。
3. 跑一周：你追问过的事，九成以上在你问之前已经在账本里并且报过。

以上都要在真实环境验，替身通过不算。

### 3.8 还没想定的

- 账最终长在哪：第一版放数字分身；引擎已经是你自己的项目，任务级的状态长期看应该长在引擎里。
- 旧的 `twin_scheduler` 已经会给每个没收尾的任务出「决定、理由、证据、下一步」，它在批 8 的退役清单上。账本要不要直接借它的判定逻辑，开工时再看代码定。
- 你另有一条「减轻认知负担」主线（拍板清单、合并放权、清存量都出自它）。我没找到它落盘的清单，只在会话记录里。账本和它是同一个目标，开工前要先对齐，避免做成第 7 处清单。

**动已定内容**：不动。并进日报只加来源、不改乙版版式；如果条目太多需要新板块，另发改动确认。

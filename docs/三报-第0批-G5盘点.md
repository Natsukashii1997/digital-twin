## 6. 快照和锚点映射到 `twin_state` Event/Ref 与 G5 表（建议方案，待复核）

> **已被取代**（2026-11-02）：ChatGPT 复核 HMS-20261102-001 判本节需返修，现以 [映射与施工基线 v4](三报-第0批-映射与基线-v4.md) 为准（v2、v3 已先后被取代）；本节保留原文备查。

原则：不新建表。快照和锚点用已有的 `events` 和 `refs`；面向常浩的私聊投递用 G5 的 `notifications` 和 `deliveries`。

| 业务语义 | 落点 | 字段约定 |
|---|---|---|
| `snapshot_id`（只读采集后固化） | `events`：kind=`report.snapshot` | `idem_key=report.snapshot:<stream>:<period>:<sha256(facts)>`；`object_type=report`，`object_id=<stream>:<period>`（例如 `evening:2026-11-03`、`weekly:2026-11-06`、`morning:2026-11-04`）；payload 写 `snapshot_id`、`window_from`、`window_to`、`captured_at`、`coverage`（各来源 complete/partial/unknown）；evidence 写固化事实文件的路径和 sha256（文件放在 evidence 目录） |
| 来源证据 | `refs` | `(report, <stream>:<period>, kind, ref)`，kind 取 `snapshot_file`、`git_commit`、`pr`、`issue`、`doc` 等 |
| 成功台账锚点 | `events`：kind=`report.ledger_committed` | `idem_key=report.ledger_committed:<doc_token>:<period>`，唯一索引天然防止同一期写两次；payload 写 `snapshot_id`、`window_to`、标题、回读 sha256。**只在 `report_publish` 回读通过后写入**。当前锚点 = 这个 doc 最新一条的 `window_to` |
| 私聊投递 | `notifications`：一期一代 | `kind=report`；`fingerprint=subject_key=report:<stream>:<period>`；`body={"text": 私聊版正文, "snapshot_id": …}`；`content_digest=sha256(text)`；同一期改稿时 revision+1，未送达的改稿会按 G5-C 的规则换新键 |
| 发送凭证 | `deliveries`（channel=feishu） | 已有 `provider_message_id`、`attempt_count`、`status`；对应 §3.4 的第 ③ 层，不代表常浩已看到 |

**要接通，G5 需要做的最小扩展（都会改到冻结文件，需要单独授权、TDD、ChatGPT 复核）：**

1. `twin_notify.sync` 只处理调度器自己的情形（`kind` 属于 `CATEGORY`，或 legacy）。否则下一次完整 sync 就会把报告通知 cleared，`tidy` 再把还没送达的投递行记为 skipped。
2. 新增唯一写入口，例如 `twin_notify.post_report(stream, period, text, snapshot_id)`，只由报告流程调用。报告送达后，或下一期报告出来时，把这一期记为 resolved。

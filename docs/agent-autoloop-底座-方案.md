## 2. 总体架构

### 2.1 七层

```
 ① 入口      飞书私聊（猛鬼兽，唯一能授权的入口）     驿窗侧栏（只显示，点了跳飞书）
       │
 ② 前台      Hermes 猛鬼兽：对话、记忆、Vault、人设、白话汇报、核验本人身份
             核验过的私聊 ──► 派单事件        按钮点击 / 引用回复 ──► 卡片回答
       │
 ③ 中台      fork 版 agent-autoloop（主账号运行，零补丁）
             事件 → 规则 → 一轮 → 回执；卡片挂起不占进程；定时；事件溯源日志
       │  只给「接单密钥」
 ④ 车间      接单程序 + Claude Code / Codex，跑在**独立 macOS 账号** dt-worker 下
             自己的 GitHub 机器账号、自己的 clone 和 worktree；读不到主账号的任何东西
       │
 ⑤ 出口      主账号下的固定脚本：合并、发飞书、改定时任务等撤不回或高档位动作
             写前账本（复用 custody_ledger）+ 幂等键 + 结果不明冻结对账 + 回读核实
       │
 ⑥ 交付知识  GitHub（main 限制更新，只有常浩点合并才动）  Vault  决定记录  LESSONS  my-skills
       │
 ⑦ 观测      工程自检、个人项目日报、驿窗看板（经只读代理，不握本人密钥）
```

### 2.2 一句话分工

**常浩在飞书私聊里定目标、给授权、点合并；猛鬼兽核验是常浩本人、把话变成事件、把卡片变成白话；中台排队、派活、挂起、定时；Agent 关在独立账号里只能改自己的 worktree、推自己的分支；撤不回的动作只由主账号的固定脚本在核实常浩点击后执行；GitHub 的分支保护是最后一道闸。**

| 角色 | 负责 | 拿不到 / 不负责 |
|---|---|---|
| 常浩 | 目标、授权、回答卡片、点合并 | — |
| 猛鬼兽（Hermes） | 对话、记忆；私聊核验后转派单事件；卡片的飞书收发；状态汇报 | 不调 CLI、不替常浩回答卡片（托管暂停） |
| 中台（主账号） | 事件、规则、派活、挂起续接、定时、花费统计 | 不懂常浩、不存人格记忆、不直接做撤不回的动作 |
| Agent（dt-worker 账号） | 在自己的 worktree 里改、提交；用机器账号推本单分支、开 PR | 读不到 `~/.agent-autoloop`、`~/.hermes`、主账号的密钥和项目目录；GitHub 上不能动 main |
| 出口脚本（主账号） | 合并（核实点击后）、发飞书、改定时任务（D 档有授权后） | 不做判断，只做核对过的固定动作 |
| 驿窗 | 显示中台卡片和状态，一点跳到飞书 | 不产生授权、不握本人密钥 |

### 2.3 为什么 Agent 必须换账号（Fable P0-1，已核实）

同一个系统账号下，中台的「先问清单」「access」「MCP 不进用户配置」都挡不住 Agent 自己给自己批：

- 中台把 `AGENT_AUTOLOOP_HOME` 交给每个 Agent（`worker/worker.ts:107`），本人密钥明文在 `~/.agent-autoloop/config.json`。
- 用本人密钥回答卡片**不核对**回答人和原消息，直接记「本人」（`kernel/http.ts:203-204`）；本人密钥还能直接触发任何规则（`kernel/http.ts:217` 起的 pause / run / replay）。
- 通道密钥在同一文件，回答人、消息号都能伪造；`rules.json` 同账号可写。
- 上游自己写明不隔离同一系统账号下的进程（SECURITY.md）；#135 已实证隔离容器都能连到宿主本机服务。

对策用上游自带的「另一台电脑只接活」（`agent-autoloop join <中台地址> --worker <名> --key <接单密钥>`）：把接单程序装在独立 macOS 账号 `dt-worker` 下，它只有接单密钥（只能领活、交回执、提问，不能回答卡片、不能触发规则）。主账号的数据目录是 700，dt-worker 读不到。这同时绕开了 G-05（后台读不了「文稿」）：dt-worker 从 GitHub 自己 clone，不碰主账号的项目目录。

再加两道兜底：合并出口**不信中台里的「已回答」**，自己回读飞书核实是常浩点的（复用 twin_identity）；GitHub 上沿用 #132 的「机器账号 + main 限制更新」，Agent 的机器账号推不了 main、合不了 PR。

〔待实测〕dt-worker 下 Claude / Codex 登录（同一会员账号再登一次）、代理变量、连主账号中台 127.0.0.1:3350 只能用接单密钥、Agent 读不到主账号文件。

## 3. fork 策略

### 3.1 上游事实（2026-11-15 只读查）

11-03 建仓，22 个版本（v1.0.0 → v1.8.5），近期几乎一天一版；维护者一人为主，近 100 个 PR 里外部合并 36 个；MIT。内核约 2000 行，测试 97 个文件约 1.9 万行，含 2 万步模拟和强杀。核心目录 v1.6.0 → v1.8.5 改了 922 行：**改内核的 fork 每周解冲突，不改内核的 fork 同步很轻。**

### 3.2 引擎零补丁

V2 想加的唯一内核补丁（规则加 `tier` 字段）取消：`tier` 已是 Agent 的「服务档位」字段（`protocol/rules.ts:178`），规则里的未知字段会被拒（`protocol/rules.ts:67`），而且规则本来就由生成器产出，档位放 digital-twin 的旁路表即可（第 5 节）。

| 层 | 放什么 | 仓库 |
|---|---|---|
| 引擎 | 上游原样 | **私有镜像**（GitHub 的 Fork 只能公开）+ `upstream` 远端；每周跟一次上游 Release，跑 `npm test` 和模拟 |
| 插件 | `dt-feishu`（只发不收）、`dt-worktree` 启动脚本、将来的驿窗只读代理 | **独立插件仓库**，`agent-autoloop add <本地路径>` 安装（安装目录插件优先于内置，`docs/plugins.md:13-15`）；不相对引用引擎源码 |
| 上游贡献 | 通用的小改进（如内置飞书通道加 `listen: false` 选项，监听段在 `plugins/feishu/channel.ts:207-228`） | 另留一个**公开 fork** 只用来提 PR；合进上游后删掉自己那份复制品 |
| 个人配置 | 规则生成器、档位表、Skill、出口脚本、主线文件 | digital-twin 仓库（名册里可写，列为 L3 路径），不进引擎和插件仓库 |

本机从安装版切到私有镜像版：先 `agent-autoloop uninstall`（保留数据），再 `AGENT_AUTOLOOP_REPO=<镜像目录> sh install.sh`（已装过时这个变量不生效，所以要先卸）。

## 5. 授权：落在「派单成立」这一步，档位一项不改

### 5.1 档位照清单（Fable P0-3，已核实）

`docs/常设授权清单.md` §2：写入类派单、新建或修改定时任务、推 main、安装部署都是 **D 档**（每次问本人）；B 档合并 = 本人点卡片 + 绑定版本 + L0–L2 + CI 通过 + `--match-head-commit`。V2 把推分支、开 PR 写成 A 档、夜间勾选写成「不超过 B」，都改动了已定档位，**撤回**。

### 5.2 授权在哪一步、由谁核

| 动作 | 档位 | 授权从哪来 | 谁核 |
|---|---|---|---|
| 只读派单 | A | 常浩私聊一句 | 猛鬼兽 |
| 写入派单 | D（或 C：常浩给的单次授权文件逐项写明） | 常浩在已核验私聊里确认这一单；夜间提案回「做 1 3」= 对这几单的授权，原样存成单次授权文件 | 猛鬼兽核验后才发派单事件；派单事件带授权文件路径 |
| 该单的推分支、开 PR | 随该单授权 | 同上 | GitHub 保护（机器账号只能推非 main 分支） |
| 合并 | B | 常浩点合并卡片 | 合并出口回读飞书核实点击 + merge_act 全部条件 |
| 新建 / 修改中台定时规则 | D | 常浩每次确认 | 规则生成器只认确认记录；工程自检比对 `rules.json` 哈希 |

档位表放 digital-twin（按规则名查），规则生成器据此生成：写入类规则只接带有效授权文件的派单事件（Skill 第一步核对，没有就交「待你处理」卡片）。「Agent 种类 × 档位」也可以编进 agent 编号（如 `claude-w`、`codex-r`），让 `doctor` 一眼看出。

### 5.3 出口脚本与写前账本（Fable P1-8）

撤不回或高档位的动作（合并、发飞书、改定时任务）只在主账号的出口脚本里做，作为中台 `command` 规则运行（不受 `access` 约束，所以脚本本身要严）：

- **写前账本**：复用 custody_ledger 的预占和冻结（本地 SQLite），动作开始前先记「预占」，不依赖中台事件日志（出口脚本运行中拿不到中台凭据，事件要等回执才入日志，中间崩溃会没有记录）。
- **幂等键**：`<动作>:<仓库>:<对象>:<版本>`，同一个键只做一次。
- **结果不明**：记「结果不明」、冻结同一对象，只读查远端对账；**脚本以退出码 0 结束并在回执里交一张「结果不明」卡片**，不报失败（报失败中台会自动重派最多 10 次，`docs/protocol.md` 失败一节），符合 ADR-011。
- **合并卡片由合并出口规则自己发**：回答只会回到建卡的那条规则（`kernel/decide.ts:552`）。

### 5.4 还要守的

- 卡片 `answerers` 只填常浩；本人密钥只在主账号的 Hermes 转交脚本和只读代理里用。
- 中台的 MCP 不配进任何 Agent 的配置。
- 派单正文只写任务需要的内容，受限内容不进事件（中台日志永久保存）。
- 推公开仓库按 PRD 8.6 每次确认；名册仓库的可见性在批 0 核一遍。

## 6. 关键链路

### 6.1 派活：私聊一句话 → 一个 PR

1. 常浩私聊：「让 Claude 给 dt-sandbox 加个 xx」。
2. 猛鬼兽（新技能 `autoloop`，替代 `workshop`）整理五要素，项目必须在名册里；写入单在私聊确认（D 档），确认原话存成授权记录。
3. 猛鬼兽用 `hermes` 来源密钥 `POST /v1/events`：`type: dispatch.<项目>.<执行方>.<读写>`，`subject: <项目>#<issue>`，`detail` 写五要素和授权记录路径。只有 twin_identity 核验过的常浩私聊才发。
4. 规则由 `autoloop_rules.py` 从名册 × 执行方 × 读写生成（`to` 固定在规则里，所以「交给谁」= 选哪条规则；切默认执行方 = 重新生成）；名册外的项目派不出去；`parallel` 按 subject 分事项，`maxActive: 1` 同仓一单。
5. dt-worker 上的 `dt-worktree` 启动脚本读 `AGENT_AUTOLOOP_CONTEXT` 拿 subject（`Turn` 里没有 subject，`worker/worker.ts:228-242`），在 dt-worker 自己的 clone 里建或复用 worktree 和分支 `claude/<issue>-<短名>`，查执行方可用，再启动 CLI。
6. Agent 提交；启动脚本在 CLI 退出后用机器账号推本单分支、开 PR〔待实测：退出后收尾不弄乱插件解析的输出〕；每轮完成通知（结论 + PR + 轮次号）经飞书出口发到私聊。

派单正文在中台里是「资料」不是指令：`dt-dispatch` Skill 写明这条信任只给带有效授权记录的 `hermes` 来源事件。

### 6.2 拍板：卡片 → 飞书 → 回中台

- `dt-feishu` 通道：内置飞书通道去掉监听（先给上游提 `listen: false`，合进来之前用独立插件仓库里的复制品），以猛鬼兽机器人身份（`lark-cli` 带 `--profile`，和现有脚本一致）只发不收。中台按「卡片:通道」各记消息号（`kernel/decide.ts:525`），飞书和以后的显示通道互不干扰。
- 点击由猛鬼兽网关收 → `merge-buttons` 新分支 → `autoloop_answer.py` 用通道密钥回答，带 `by`（常浩 open_id）和 `ref`（原消息号）。〔待实测：merge-buttons 现在只拿到按钮 value 和 chat_id（`hermes/plugins/merge-buttons/__init__.py:26-32`），原消息号要从回调里取或在按钮 value 里带上〕
- 也可以引用卡片打字回答，Hermes 技能调同一个脚本。
- 卡片只支持 2–5 个单选或一句文字（`kernel/http.ts:156`），没有多选。

### 6.3 交付：审查 → 常浩点合并

**不用中台的交付插件**：它自己写标签、和 merge_act 重叠、每个仓库要加 `ops/delivery.json`（Fable P1-11）。改成：

1. PR 开出后，一条普通审查规则派审查：合并官规则快速判定；L2–L3 送 ChatGPT High（驿窗审核门）。
2. 通过后，合并出口规则发「合并」卡片；常浩点了，合并出口回读飞书核实点击，再走 merge_act 全部条件合并。退回就留言、派返修一轮。

### 6.4 定时与报告

新的定时活写成中台规则，每条都是 D 档、逐条问常浩。报告类用 pdaily 模式（事实快照 → 写 → 核对 → 降级，取不到写「未知」不当 0）。现有 Hermes 推送不迁。

### 6.5 夜间行动提案（形态照 11-09 定稿）

- 22:30 中台规则让 Agent 读名册、主线、open issue，产出「今晚可推进的几件事」，飞书出口按**甲·清单**样式发到私聊（卡片是通知，不带勾选）。
- 常浩私聊回「做 1 3」「按推荐」或「今晚不做」；猛鬼兽原样存成当晚单次授权文件，按单发派单事件。00:30 前没回今晚不做。
- 上限照设计：一晚 ≤3 单、每单 ≤2 小时（规则 `timeout`）、同一时间 1 单（夜间组 `parallel: 1`）、只做到开 PR、08:00 前全部结束（到点停、记「超时」）。
- 次日 10:00 个人项目日报汇报。

### 6.6 主线负责人：靠定时巡视，不靠事件链

回执里发出的事件跳数 +1，超过 8 只记录不派发（`kernel/decide.ts:43、476`）；「派单 → 推分支 → 审查 → 合并 → 下一单」靠事件链很快超限。所以：

- 主线 = 目标 + 有序子项（沿用 CURRENT.md「主线清单」七种状态），存 digital-twin `mainlines/<名>.json`。
- 每天（或每几小时）一条巡视规则：读主线文件和 GitHub 实况，下一项具备条件就提议派单（写入单照样要常浩确认），停滞超过 N 天或同一阻塞连续出现就发提醒卡片，并进日报。
- 每次巡视开新会话、读主线文件，不无限续接长会话（越续越贵）。

### 6.7 并发与睡眠

- 两台接单程序：dt-worker（Agent 任务，`capacity` 2）和主账号（出口脚本，单独的 `capacity`），合并、发飞书不会排在长任务后面。
- 本机是笔记本，夜里会睡眠（G-20）：夜间组规则开跑时用 `caffeinate` 包住到 08:00〔待实测〕；改系统睡眠设置只能常浩本人做。

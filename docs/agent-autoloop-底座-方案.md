## 2. 总体架构

### 2.1 七层

```
 ① 入口      飞书私聊（猛鬼兽，唯一能授权的入口）     驿窗侧栏（只显示，点了跳飞书）
       │
 ② 前台      Hermes 猛鬼兽：对话、记忆、Vault、人设、白话汇报、核验本人身份
             核验过的私聊 ──► 派单事件        按钮点击 / 引用回复 ──► 卡片回答
       │
 ③ 中台      fork 版 agent-autoloop（主账号运行，零补丁）
             事件 → 规则 → 一轮 → 回执；卡片挂起不占进程；定时；事件溯源日志
       │  只给「接单密钥」
 ④ 车间      接单程序 + Claude Code / Codex，跑在**独立 macOS 账号** dt-worker 下
             自己的 GitHub 机器账号、自己的 clone 和 worktree；读不到主账号的任何东西
       │
 ⑤ 出口      主账号下的固定脚本：合并、发飞书、改定时任务等撤不回或高档位动作
             写前账本（复用 custody_ledger）+ 幂等键 + 结果不明冻结对账 + 回读核实
       │
 ⑥ 交付知识  GitHub（main 限制更新，只有常浩点合并才动）  Vault  决定记录  LESSONS  my-skills
       │
 ⑦ 观测      工程自检、个人项目日报、驿窗看板（经只读代理，不握本人密钥）
```

### 2.2 一句话分工

**常浩在飞书私聊里定目标、给授权、点合并；猛鬼兽核验是常浩本人、把话变成事件、把卡片变成白话；中台排队、派活、挂起、定时；Agent 关在独立账号里只能改自己的 worktree、推自己的分支；撤不回的动作只由主账号的固定脚本在核实常浩点击后执行；GitHub 的分支保护是最后一道闸。**

| 角色 | 负责 | 拿不到 / 不负责 |
|---|---|---|
| 常浩 | 目标、授权、回答卡片、点合并 | — |
| 猛鬼兽（Hermes） | 对话、记忆；私聊核验后转派单事件；卡片的飞书收发；状态汇报；**按常浩签的代批清单替常浩批准（第 5.6 节）** | 不调 CLI；清单以外不代批；不听工人和外人的话 |
| 中台（主账号） | 事件、规则、派活、挂起续接、定时、花费统计 | 不懂常浩、不存人格记忆、不直接做撤不回的动作 |
| Agent（dt-worker 账号） | 在自己的 worktree 里改、提交；用机器账号推本单分支、开 PR | 读不到 `~/.agent-autoloop`、`~/.hermes`、主账号的密钥和项目目录；GitHub 上不能动 main |
| 出口脚本（主账号） | 合并（核实点击后）、发飞书、改定时任务（D 档有授权后） | 不做判断，只做核对过的固定动作 |
| 驿窗 | 显示中台卡片和状态，一点跳到飞书 | 不产生授权、不握本人密钥 |

### 2.3 为什么 Agent 必须换账号（Fable P0-1，已核实）

同一个系统账号下，中台的「先问清单」「access」「MCP 不进用户配置」都挡不住 Agent 自己给自己批：

- 中台把 `AGENT_AUTOLOOP_HOME` 交给每个 Agent（`worker/worker.ts:107`），本人密钥明文在 `~/.agent-autoloop/config.json`。
- 用本人密钥回答卡片**不核对**回答人和原消息，直接记「本人」（`kernel/http.ts:203-204`）；本人密钥还能直接触发任何规则（`kernel/http.ts:217` 起的 pause / run / replay）。
- 通道密钥在同一文件，回答人、消息号都能伪造；`rules.json` 同账号可写。
- 上游自己写明不隔离同一系统账号下的进程（SECURITY.md）；#135 已实证隔离容器都能连到宿主本机服务。

对策用上游自带的「另一台电脑只接活」（`agent-autoloop join <中台地址> --worker <名> --key <接单密钥>`）：把接单程序装在独立 macOS 账号 `dt-worker` 下，它只有接单密钥（只能领活、交回执、提问，不能回答卡片、不能触发规则）。主账号的数据目录是 700，dt-worker 读不到。这同时绕开了 G-05（后台读不了「文稿」）：dt-worker 从 GitHub 自己 clone，不碰主账号的项目目录。

再加两道兜底：合并出口**不信中台里的「已回答」**，自己回读飞书核实是常浩点的（复用 twin_identity）；GitHub 上沿用 #132 的「机器账号 + main 限制更新」，Agent 的机器账号推不了 main、合不了 PR。

〔待实测〕dt-worker 下 Claude / Codex 登录（同一会员账号再登一次）、代理变量、连主账号中台 127.0.0.1:3350 只能用接单密钥、Agent 读不到主账号文件。

## 3. fork 策略

### 3.1 上游事实（2026-11-15 只读查）

11-03 建仓，22 个版本（v1.0.0 → v1.8.5），近期几乎一天一版；维护者一人为主，近 100 个 PR 里外部合并 36 个；MIT。内核约 2000 行，测试 97 个文件约 1.9 万行，含 2 万步模拟和强杀。核心目录 v1.6.0 → v1.8.5 改了 922 行：**改内核的 fork 每周解冲突，不改内核的 fork 同步很轻。**

### 3.2 引擎零补丁

> **2026-11-20 常浩改定，本节作废**：agent-autoloop 转为常浩自己的项目，不再跟上游，像驿窗一样自己深度开发、自己使用；引擎可以直接改，不再锁版本、不再每周查上游、不再经公开 fork 提 PR。见 `docs/DECIDED.md` 2026-11-20 一条。下面保留原文作记录。

V2 想加的唯一内核补丁（规则加 `tier` 字段）取消：`tier` 已是 Agent 的「服务档位」字段（`protocol/rules.ts:178`），规则里的未知字段会被拒（`protocol/rules.ts:67`），而且规则本来就由生成器产出，档位放 digital-twin 的旁路表即可（第 5 节）。

| 层 | 放什么 | 仓库 |
|---|---|---|
| 引擎 | 上游原样 | **私有镜像**（GitHub 的 Fork 只能公开）+ `upstream` 远端；每周跟一次上游 Release，跑 `npm test` 和模拟 |
| 插件 | `dt-feishu`（只发不收）、`dt-worktree` 启动脚本、将来的驿窗只读代理 | **独立插件仓库**，`agent-autoloop add <本地路径>` 安装（安装目录插件优先于内置，`docs/plugins.md:13-15`）；不相对引用引擎源码 |
| 上游贡献 | 通用的小改进（如内置飞书通道加 `listen: false` 选项，监听段在 `plugins/feishu/channel.ts:207-228`） | 另留一个**公开 fork** 只用来提 PR；合进上游后删掉自己那份复制品 |
| 个人配置 | 规则生成器、档位表、Skill、出口脚本、主线文件 | digital-twin 仓库（名册里可写，列为 L3 路径），不进引擎和插件仓库 |

**零补丁是优先策略，不是绝对禁令**：上游接口够用时不改引擎；当安全正确性无法在公开接口实现时，先申请上游扩展点，再评估最小补丁及其维护成本，不为守零补丁去做复杂旁路。

**锁版本、验证后升级**：运行版本锁到完整提交号；每周**检查**上游更新，但不自动替换；升级前跑兼容性检查、挂起恢复测试、插件回归和事件日志 / 数据库迁移验证，通过才切换；回滚靠升级前的完整数据快照（`agent-autoloop backup`：数据库、主密钥、配置、规则、secrets.env），不是直接装旧版程序。

本机从安装版切到私有镜像版：先 `agent-autoloop uninstall`（保留数据），再 `AGENT_AUTOLOOP_REPO=<镜像目录> sh install.sh`（已装过时这个变量不生效，所以要先卸）。

## 5. 三份契约：授权、信任边界、状态与恢复

原则（GPT 第 1 轮）：**Hermes 负责发现和表达本人意图；可信网关负责验证授权事实；固定执行入口负责强制执行授权约束。Agent、Skill 和中台普通回执都无权创建或扩大授权。** 自有代码只集中在三处：可信入站网关、受限 worker 启动与交付、确定性操作出口；不重写队列、事件日志、挂起续接、定时调度和规则语言。

### 5.1 契约 A：授权与任务凭证

**档位照清单，一项不改**（`docs/常设授权清单.md` §2）：写入类派单、新建或修改定时任务、推 main、安装部署是 D 档；B 档合并 = 本人点卡片 + 绑定版本 + L0–L2 + CI 通过 + `--match-head-commit`。授权的**载体**（私聊确认、单次授权文件、夜间「做 1 3」）不改变动作的**档位**：私聊批准一单写入任务，就是满足了这一单的 D 档要求，不是把它降成 C 档。

**任务凭证**：每张写入单在常浩批准后，由主账号的入站网关脚本（复用 twin_identity 核验 + 授权记录）签发一张凭证，存在主账号 `~/Library/Application Support/DigitalTwin/autoloop/grants/`（dt-worker 不可读写）：

| 字段 | 作用 |
|---|---|
| `task_id` | 唯一任务号，也是全链路的关联键（契约 C） |
| `approval_id` | 对应哪一次本人批准（私聊消息号或授权文件 + 原话） |
| `repo`、`scope` | 仓库和任务范围（五要素原文的哈希） |
| `executor` | claude 或 codex，不自动换家（P-13） |
| `allowed_actions` | 只列这一单允许的副作用：`edit`、`push_branch`、`open_pr`；`merge`、`send`、`cron` 永远不在凭证里，各自单独授权 |
| `valid_until` | 绝对时间；夜间单是次日 08:00 |
| `status` | 有效 / 已撤销 / 已完成 / 冻结；只有网关能改 |
| `base_sha`（可选） | 需要绑定基线时填 |

**谁核、在哪核**（不靠 Skill）：

1. **派单前**：网关只给有效凭证发派单事件；事件只带 `task_id`，凭证内容不进事件。
2. **每轮开跑前**：dt-worker 的启动脚本经主账号一个**只读核验接口**查凭证（只回答「这个 task_id 现在能不能做 X」，不返回任何密钥）；无效、过期、撤销、范围哈希对不上 → 不启动 CLI，回执交「授权已失效」卡片。续接时同样重核：**授权绑定任务，不绑定 CLI 会话**；会话接不上、改用新会话时，凭证仍有效就继续，扩权、改目标、换执行方必须重新批准。
3. **副作用发生处**：推分支、开 PR 由 GitHub 侧强制（机器账号只能推非 main、不能合并，#132）；合并、发飞书、改定时规则由主账号出口逐个核授权（5.2、5.3）。启动脚本里的检查只防正常流程误操作，**不当作不可绕过的边界**。
4. **撤销**：常浩私聊说「停 <单号>」→ 网关把凭证改成已撤销，并 `agent-autoloop stop` 正在跑的轮次；之后任何核验都失败。

**卡片回答的信任**：中台核对的 `by`、`ref` 是调用方传进来的，可信与否取决于 Hermes 网关从飞书回调里拿到的回答人和原消息号是否可信。所以：授权类、合并类卡片只认 Hermes 网关转来的回答（网关核对回调来源、`open_id`、原消息号），**不开卡片网页链接**（`links` 不打开）；合并出口还要自己回读飞书核实（5.3）。〔待实测：Hermes 按钮回调能否可信拿到 `open_id` 和原消息号〕

### 5.2 契约 B：主账号与 dt-worker 的信任边界

| 项 | dt-worker 能 | dt-worker 不能 |
|---|---|---|
| 系统 | 标准非管理员账号，自己的家目录 | sudo；主账号钥匙串；读主账号文件 |
| 中台 | 持**接单密钥**：领活、交回执、提问（`kernel/http.ts:163`） | owner、通道、`hermes` 来源密钥；回答卡片（要通道或本人密钥，`:194`）；触发规则（要本人密钥，`:228`） |
| 本机服务 | 连中台 3350（只能用接单密钥）、主账号的只读凭证核验接口 | 连 Hermes 网关、驿窗、牛马之家等任何其他本机服务；经代理绕回宿主（#135 的教训）——**批 0A 实测，过不了就加本机防火墙规则或升级隔离** |
| GitHub | 机器账号：推 `claude/` `codex/` 前缀分支、开 PR | 推 main、合并、改保护规则、碰名册外仓库 |
| 回执 | 只能发规则 `emits` 里列出的事件类型（中台只收 `emits` 匹配的回执事件，`kernel/decide.ts:475`） | 让主账号执行任意命令 |

**主账号固定脚本的输入纪律**：主账号的 `command` 规则只跑 digital-twin 里登记的固定脚本；脚本只接受结构化参数（`task_id`、仓库、PR 号、版本），每个参数按白名单校验；**从不执行 dt-worker 产生的脚本、命令或补丁内容**；Agent 规则的 `emits` 只开放 `review.request`、`mainline.progress` 这类数据事件，不开放任何直接触发出口的类型——出口规则只由定时巡视或 Hermes 转来的常浩回答触发。

**升级条件**：dt-worker 反向测试出现「能触及受保护控制面、且无法用简单鉴权或网络限制消除」的路径 → 升级到独立虚拟机或独立机器（上游 `join` 支持远程接单）。

### 5.3 契约 C：任务状态与故障恢复

**状态权威表**（冲突时谁说了算）：

| 事实 | 权威 | 原则 |
|---|---|---|
| 常浩批准了什么 | 任务凭证（契约 A） | 中台、Agent 不能生成批准 |
| 排队、运行、挂起 | 中台事件日志 | Hermes 不另建调度状态 |
| 改了什么 | Git / GitHub | 不信 Agent 自述 |
| 合并、发送是否成功 | 出口账本 + 外部系统回读 | 不信中台显示的成功 |
| 目标是否完成 | 主线文件 + 验收证据 | 一轮做完 ≠ 目标完成 |

**统一标识**：`task_id` 贯穿凭证、事件 `subject`、分支名、PR 描述、出口账本；出口动作的幂等键 `<动作>:<task_id>:<对象>:<版本>`。

**业务状态**（和中台的轮次状态分开，存在出口账本 / 凭证里）：执行完成、业务成功、等待授权、结果不明、冻结、终止。中台显示「做完」只代表轮次结束；退出码 0 只代表脚本妥善处理了，不代表业务成功。

**写前账本**（复用 custody_ledger）：动作前先写「预占」并落盘；动作后写结果。脚本被强杀时没有结果记录 → 下次任何脚本启动先扫「有预占、无结果」的记录，一律当「结果不明」处理，不靠异常捕获。

**结果不明**：冻结同一对象的后续动作；只读查远端对账，凭证据记成已做或未做；脚本以退出码 0 结束并交「结果不明」卡片（报失败中台会自动重派最多 10 次）；依赖这个结果的规则读到冻结就不推进。

**恢复顺序**：中台重启、电脑睡醒、网络恢复后，先对账（出口账本 × GitHub × 中台日志），再决定续跑；**无法确认时停下并报告**。单点故障可以接受，单点故障导致越权或重复操作不能接受。

### 5.5 三条不变量（V2.3，ChatGPT 第 2 轮）

三份契约之间还剩三处没闭合，补成三条不变量：

**不变量 1：授权与 GitHub 发布一致（〔待常浩定〕）。** dt-worker 如果直接持有 GitHub 写凭据，常浩撤销任务后、或 Agent 绕过启动脚本时，它仍能往非 main 分支推代码、开 PR——GitHub 不知道 `task_id` 是否还有效。两种走法：

| 走法 | 做法 | 剩余风险 |
|---|---|---|
| **乙：受信发布（推荐）** | dt-worker 只在自己的 worktree 改、提交，**不持有 GitHub 写凭据**；主账号的发布脚本取 dt-worker 的提交（只取 Git 对象，不运行其中任何代码），发布前核凭证、动作、仓库、分支、有效期，走写前账本推分支、开 PR | 多一个固定发布脚本和受控的数据传递（主账号从 dt-worker 的只读共享目录或本地 bare 仓库取对象）；撤销、冻结、对账和合并出口共用一套机制 |
| 甲：worker 直接发布 | 沿用 V2.2，机器账号交给 dt-worker | 只能保证「main 不被自行修改」，不能保证「撤销后不再推分支、不超出任务范围推代码」；推分支、开 PR 的结果不明也要在 worker 里另做幂等和冻结 |

**不变量 2：主账号不执行 PR 里的不可信代码（采纳，涉及改变 merge_act 现有行为，〔待常浩确认〕）。** 已核实：merge_act 现在用主账号身份在 PR HEAD 的副本里跑仓库测试命令（`hermes/scripts/merge_act.py:311-326`），干净副本 ≠ 安全执行环境；Agent 改了测试脚本或构建配置，就会以主账号权限运行。改为：凡可能执行 Agent 修改内容的测试、构建、依赖安装，都在 dt-worker（或无特权 CI）里跑，结果连同 HEAD 写成证据；主账号合并出口只核对**同一 HEAD** 的测试证据和既有合并条件（CI 通过、`--match-head-commit` 等），不自己跑 PR 代码。合并档位和「必须测试通过」的要求不变，变的是测试在哪跑。

**不变量 3：所有受保护副作用都过恢复闸（采纳）。** 中台会自己恢复接单、派发和重试，「先对账再续跑」不能只靠文档。做法：出口账本加一个「启动对账」标记——中台或出口重启、电脑睡醒后，标记清零；对账完成前，所有受保护副作用入口（发布、合并、发飞书、改定时规则）一律拒绝；对账发现结果不明或冻结的对象，相关动作继续拒绝。中台照常恢复轮次、排队和状态显示，但**恢复轮次 ≠ 恢复外部写操作**。夜间 08:00 的目标同理：08:00 后不再产生新的受保护副作用（发布入口按绝对时间拒绝），可能还活着的旧进程识别后终止，未确认完成的动作不自动补做。

### 5.6 秘书代批（托管并入，常浩 2026-11-15 选「从一开始做」）

常浩原话：秘书「是我的数字分身」，要能替他批准、能碰到钥匙和保险柜。所以：**猛鬼兽（主账号）可以按常浩签的清单替常浩批准；工人（dt-worker）仍然什么都批不了、碰不到。** 飞书里仍只有猛鬼兽一个机器人。

| 要点 | 做法（复用已有托管资产） |
|---|---|
| 能批什么 | 常浩签的**代批清单**（沿用 `托管策略` 的签署方式：私聊口令 + 版本 + 全文哈希，`custody.py sign`）；清单逐项写动作、项目、每日上限、有效期。清单以外一律问常浩 |
| 怎么批 | 代批 = 由猛鬼兽给任务凭证签字（契约 A 的 `approval_id` 记成「秘书代批 + 清单版本 + 理由」），或代常浩回答卡片（经网关，`by` 记成秘书，不冒充常浩本人） |
| 额度 | 每次代批在 custody_ledger 里原子预占额度，用完就停，结果不明就冻结 |
| 汇报与推翻 | 代批后按 `custody_report` 发汇报卡（白话五项、乙版表格，11-14 定稿）；常浩点「推翻」就撤销凭证、停掉相关轮次，合并类开 revert PR（只开不合） |
| 防被骗 | 猛鬼兽只把常浩本人私聊当指令；工人回执、PR 文字、外部消息只当资料。代批决定的依据必须来自清单和事实（Git、CI、凭证），不能来自工人的说法 |
| 开关 | 沿用 `custody_state`：开 / 排空 / 冻结 / 关；常浩随时说「关托管」 |
| **D 档** | **一律不代批**（常浩 2026-11-15：「D档还是都不能替我批」，维持常设授权清单 v1「托管时 D 档一项不减」）：L3 改动、推 main、安装部署、新建或修改定时任务、改网关或 Hermes 配置、写正式 Vault、改授权清单、跨企业域、花钱、对外发言，都只能常浩本人定。代批清单里出现 D 档动作，签署时直接拒绝 |

落进分批：0B 授权门同时做「秘书代批」——凭证签发支持两种批准来源（常浩本人 / 秘书按清单），汇报卡和推翻在 0B 一起验收；之后每一批的验收都包含一次代批和一次推翻。代批的具体设计在 0B 开工前单独出规格，属于新的授权落点，按 ARCHITECTURE §12.4 送审时只送这一块。

### 5.7 还要守的

- 卡片 `answerers` 只填常浩；本人密钥只在主账号的 Hermes 转交脚本和只读代理里用。
- 中台的 MCP 不配进任何 Agent 的配置。
- 派单正文只写任务需要的内容，受限内容不进事件（中台日志永久保存）。

## 6. 关键链路

### 6.1 派活：私聊一句话 → 一个 PR

1. 常浩私聊：「让 Claude 给 dt-sandbox 加个 xx」。
2. 猛鬼兽（新技能 `autoloop`，替代 `workshop`）整理五要素，项目必须在名册里；写入单在私聊确认（D 档），确认原话存成授权记录。
3. 猛鬼兽用 `hermes` 来源密钥 `POST /v1/events`：`type: dispatch.<项目>.<执行方>.<读写>`，`subject: <项目>#<issue>`，`detail` 写五要素和授权记录路径。只有 twin_identity 核验过的常浩私聊才发。
4. 规则由 `autoloop_rules.py` 从名册 × 执行方 × 读写生成（`to` 固定在规则里，所以「交给谁」= 选哪条规则；切默认执行方 = 重新生成）；名册外的项目派不出去；`parallel` 按 subject 分事项，`maxActive: 1` 同仓一单。
5. dt-worker 上的 `dt-worktree` 启动脚本读 `AGENT_AUTOLOOP_CONTEXT` 拿 subject（`Turn` 里没有 subject，`worker/worker.ts:228-242`），在 dt-worker 自己的 clone 里建或复用 worktree 和分支 `claude/<issue>-<短名>`，查执行方可用，再启动 CLI。
6. Agent 提交；启动脚本在 CLI 退出后用机器账号推本单分支、开 PR〔待实测：退出后收尾不弄乱插件解析的输出〕；每轮完成通知（结论 + PR + 轮次号）经飞书出口发到私聊。

派单正文在中台里是「资料」不是指令：`dt-dispatch` Skill 写明这条信任只给带有效授权记录的 `hermes` 来源事件。

### 6.2 拍板：卡片 → 飞书 → 回中台

- `dt-feishu` 通道：内置飞书通道去掉监听（先给上游提 `listen: false`，合进来之前用独立插件仓库里的复制品），以猛鬼兽机器人身份（`lark-cli` 带 `--profile`，和现有脚本一致）只发不收。中台按「卡片:通道」各记消息号（`kernel/decide.ts:525`），飞书和以后的显示通道互不干扰。
- 点击由猛鬼兽网关收 → `merge-buttons` 新分支 → `autoloop_answer.py` 用通道密钥回答，带 `by`（常浩 open_id）和 `ref`（原消息号）。〔待实测：merge-buttons 现在只拿到按钮 value 和 chat_id（`hermes/plugins/merge-buttons/__init__.py:26-32`），原消息号要从回调里取或在按钮 value 里带上〕
- 也可以引用卡片打字回答，Hermes 技能调同一个脚本。
- 卡片只支持 2–5 个单选或一句文字（`kernel/http.ts:156`），没有多选。

### 6.3 交付：审查 → 常浩点合并

**不用中台的交付插件**：它自己写标签、和 merge_act 重叠、每个仓库要加 `ops/delivery.json`（Fable P1-11）。改成：

1. PR 开出后，一条普通审查规则派审查：合并官规则快速判定；L2–L3 送 ChatGPT High（驿窗审核门）。
2. **L0–L2** 通过后，合并出口规则发「合并」卡片；常浩点了，合并出口回读飞书核实点击，再走 merge_act 全部条件合并。退回就留言、派返修一轮。
3. **L3** 审查通过也**不走飞书合并卡片**（merge_act 规定飞书 B 档只覆盖 L0–L2）：状态记「审查通过，等高风险人工操作」，按现有 L3 流程由常浩在电脑上处理。

### 6.4 定时与报告

新的定时活写成中台规则，每条都是 D 档、逐条问常浩。报告类用 pdaily 模式（事实快照 → 写 → 核对 → 降级，取不到写「未知」不当 0）。现有 Hermes 推送不迁。

### 6.5 夜间行动提案（形态照 11-09 定稿）

- 22:30 中台规则让 Agent 读名册、主线、open issue，产出「今晚可推进的几件事」，飞书出口按**甲·清单**样式发到私聊（卡片是通知，不带勾选）。
- 常浩私聊回「做 1 3」「按推荐」或「今晚不做」；猛鬼兽原样存成当晚单次授权文件，按单发派单事件。00:30 前没回今晚不做。
- 上限照设计，各自用确定性的办法保证（V2.1 写「规则 timeout」有误：`timeout` 是 Agent 级字段，`protocol/rules.ts:182`，而且单轮超时不等于整单超时）：

| 约束 | 怎么保证 |
|---|---|
| 一晚最多 3 单 | 网关签发夜间凭证时计数 |
| 同时只跑 1 单 | 夜间规则同一个 `group`，`parallel: 1` |
| 每单 ≤2 小时 | 启动脚本跨轮累计该 `task_id` 的运行时长（人工挂起时间不计），超了不再启动、凭证改冻结 |
| 00:30 后不接受授权 | 网关按绝对时间拒签 |
| 08:00 停 | 凭证 `valid_until` 是次日 08:00；独立的截止规则停掉运行中的轮次，排队和挂起中的单凭证失效 |
| 只做到开 PR | 凭证 `allowed_actions` 不含 `merge`；GitHub 机器账号合不了 |
- 次日 10:00 个人项目日报汇报。

### 6.6 主线负责人：靠定时巡视，不靠事件链

回执里发出的事件跳数 +1，超过 8 只记录不派发（`kernel/decide.ts:43、476`）；「派单 → 推分支 → 审查 → 合并 → 下一单」靠事件链很快超限。所以：

- 主线 = 目标 + 有序子项（沿用 CURRENT.md「主线清单」七种状态），存 digital-twin `mainlines/<名>.json`。
- 每天（或每几小时）一条巡视规则：读主线文件和 GitHub 实况，下一项具备条件就提议派单（写入单照样要常浩确认），停滞超过 N 天或同一阻塞连续出现就发提醒卡片，并进日报。
- 每次巡视开新会话、读主线文件，不无限续接长会话（越续越贵）。

### 6.7 并发与睡眠

- 两台接单程序：dt-worker（Agent 任务，`capacity` 2）和主账号（出口脚本，单独的 `capacity`），合并、发飞书不会排在长任务后面。
- 本机是笔记本，夜里会睡眠（G-20）。`caffeinate` 只能在跑起来之后防止睡眠，**不能让已经睡着的 Mac 准时在 22:30 起来**；中台错过的定时醒来后只补最近一次，所以夜间提案、夜间凭证一律按**绝对日期时间**判有效，第二天上午补发的提案直接作废。要不要让电脑夜里保持可运行，由常浩定（第 12 节）；不保持就接受「那晚跳过」。

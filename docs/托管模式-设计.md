## 1. 托管是什么

**托管期间，猛鬼兽以常浩的身份，替常浩回答已批准夜跑里 agent 交出来的待决事项、托管合并夜跑开出的 PR；底线之外自己判断；每个决定记账；托管结束后汇报，常浩可以逐条推翻。**

- **作用范围只有一个：正在进行、已经批准的夜跑**（`multica_night.py` 管的父单家族），因此只在名册登记 `sandbox: true` 的项目上。常浩的交互会话（桌面版、终端里的 Claude / Codex）**完全不进托管**，托管期间它们照常等常浩回来。
- 「以常浩的身份」指**权威**：agent 把猛鬼兽的回复当成常浩本人的决定执行。正因如此，只回复执行权限已被外部限制住的 agent（第 3.3 节）。
- 底线 = 授权清单 D 档 + **一切撤不回的动作**，托管期间挂起；拿不准也挂起。
- 托管是常浩用既有授权来源授出的**一段有时限的代理权**，不是新的授权来源，也不新增开跑权：托管期间所有 run 仍受当晚夜跑授权的上限约束。
- **托管状态与执行模式正交**：`execution_mode = SUPERVISED | UNATTENDED`（执行怎么开跑，ARCHITECTURE 4.3）和 `custody_state = off | on | draining | frozen`（谁替常浩做决定）是两个字段，任何执行准入都要**同时**满足两边。

**它实际能帮上的忙**（#130 统计 24 次 run，5 次以 `blocked` 结束）：agent 交出来的待决事项多半是改规则集、装环境、配提交身份这类 D 档事项，托管照样挂起。托管在夜里最主要的价值是**把夜跑开出的、满足条件的 PR 合进去**（第 4 节），其次是回答沙盒范围内的方案取舍、范围确认这类问题。

## 2. 一次托管决定的完整路径

```
夜跑子单：agent 把子单标为 blocked，并在评论里写需要常浩决定的事（附推荐），结束这次 run
  └─ 夜跑主控 tick 先跑完整的停机检查（violations()）
       除「这张子单被 agent 标为 blocked」外还有任何停机原因 → 按现行规则停机，不进托管
       blocked 来源核实不了（不是 agent 在自己的 run 里设的、没有对应评论、是主控停机时设的）→ 停机
       托管关着、夜跑授权没写明允许托管唤醒、这张子单已用完托管次数 → 停机
       以上都不是 → 持着夜跑主控的锁，把子单原文和 agent 最新评论交给猛鬼兽（判断有超时）
  └─ 猛鬼兽：custody 技能
       ① 读子单、评论、父单计划、项目 CURRENT、Vault 偏好
       ② 出结构化决定 {动作, 对象, 回复原文, 依据, 撤回能力, 有效期}
       ③ 出口闸 custody_gate.py：再核策略有效 + 托管开着 + 夜跑 run 预算还够，按策略判；不过就改成「挂起」
       ④ 记账（决定号、原文、额度预占）
  └─ 决定 = 回复：送达闸（custody_reply.py，仍持同一把锁）再核授权、全部停机条件、剩余 run 额度并预占 → 以常浩的 Multica 成员身份在子单上评论（末尾代发标记）
       → 评论唤醒 agent，这次 run 计入夜跑 max_runs；agent 在隔离容器里照做，执行防线兜底
       → 评论发送结果不明：只读核对有没有生成 run，不重发；核不清按 5.3a 记 UNRECONCILED 并冻结
     决定 = 挂起、判断超时、出错、取数失败、策略失效：按现行规则停机，事项进汇报
托管结束 → 排空（第 3.8 节）→ 飞书汇报卡（逐条带「推翻」）
```

## 3. 各部分怎么做

### 3.1 通道（digital-twin，改夜跑主控）

| 方向 | 做法 |
|---|---|
| 待决事项 → 猛鬼兽 | 夜跑主控 tick 里已有「子单被 agent 标为 blocked」这条停机条件（`multica_night.py`）。托管开着时，改为先交给托管：读子单与 agent 最新评论全文，交给 `custody` 技能。不需要 webhook，不需要驿窗 |
| 猛鬼兽 → agent | `custody_reply.py` 用常浩的 Multica 成员身份在子单上评论；Multica 的评论会唤醒 agent（主控现有注释已写明「评论会唤醒 agent」），不再另改状态 |
| 改动性质 | 这是对 5.3a 停机检查的改动。**托管只豁免一项停机原因：「agent 请求决策而把子单标为 blocked」；不能暂停或绕过整套独立停机检查。** 落地按 L3，必须保证：① 先执行完整的原有 `violations()`，同时存在任何其他停机原因（时长、`max_runs`、连续失败、执行身份漂移、异常 Wakeup / Autopilot、家族外改动、状态异常、run 记录核不清等）都直接停机；② 核实 blocked 的来源：由 agent 在属于这张子单的 run 里设置、并附有请求决策的评论，主控停机流程设的 blocked 不算；③ 托管判断有超时（策略写明，例：10 分钟），超时、异常、取数失败、策略失效都回到原停机路径；④ 托管关着、判为挂起、次数用完、出口闸或送达闸任一失败，与现行停机规则完全一致 |
| 执行授权 | 评论唤醒 = 一次新的执行启动。**当晚的夜跑授权记录必须明确写明「允许托管唤醒 blocked 子单」及次数上限**，没写就不唤醒、照常停机。评论前持与夜跑主控相同的互斥锁，完成授权、全部停机条件、剩余 run 额度核查并预占额度；评论发送返回不明时只读核对有没有生成 run，不重发；核不清按 5.3a 记 `UNRECONCILED` 走冻结路径 |
| 启用门槛 | #134 实测证明评论触发的 run 归属哪个 agent、计数时机、一次评论最多消耗几次 run 之前，**不启用这条通道** |

### 3.2 身份

- 以常浩的 Multica 成员身份写评论（agent 视为本人回复）；评论末尾附 `〔托管·猛鬼兽代发 d-编号〕`，防止项目记录把代发写成「常浩说」。
- **标记只是记录，不是权限凭证**；权限只由出口闸、送达闸、执行防线判定。
- 驿窗「以我的身份发送」与托管无关，托管期间保持关闭。

### 3.3 受限会话与执行防线

**受限会话** = 已批准夜跑里、Multica 隔离执行器容器中的 agent，并且同时满足：

1. M1 权限矩阵已证的隔离成立：容器里没有宿主挂载，宿主端口只放行代理，拿不到常浩的个人凭据、Vault、`~/.hermes`、驿窗数据目录；
2. 容器里的 GitHub 令牌只对沙盒仓库有效，推不了 main 和非 `agent/` 分支（M1 已证）；
3. **在任何 PR 状态下都不能自行合并**：未获审批的 PR、已获审批的 PR、其他 agent 开的 PR、直接调 GitHub API 合并，全都要被拒。#130 实测发现受限令牌能自己合并（dt-sandbox 必需审批数为 0）。「必需审批至少 1 个」只能拦住未获审批的 PR，拦不住 agent 在别人批准之后抢先合并，**不够**。这项隔离必须由 GitHub 服务端或等效的独立强制机制保障（例如仓库归组织后限制谁能推送和合并，或 agent 不直接持有写权限、由独立推送身份代推），不能靠 agent 自觉；由 #132 找办法并实测。**#132 验收之前，受限会话不成立，托管回复和托管合并都不启用；如果找不到能做到的办法，就一直不启用。**

除此以外的一切（含常浩的交互会话）都不进托管。

**三道闸**：

| 闸 | 位置 | 做什么 |
|---|---|---|
| ① 出口闸 | Hermes 侧 `custody_gate.py`，模型之后 | 再核托管开着、策略有效、夜跑 run 预算够；决定是结构化的，按策略判：D 档、L3、撤不回、超额、回退模型做出的判断 → 改为挂起；原文过禁止词表 |
| ② 送达闸 | `custody_reply.py`，发评论之前 | 托管开着、决定号在账本里且未过期未作废、子单仍属于这次已批准夜跑的父单家族、仍是 `blocked`、这张子单的托管次数未超、夜跑没停机，才发评论 |
| ③ 执行防线 | agent 所在的隔离容器 | 容器隔离 + 受限令牌 + #132 的合并隔离，越界被操作系统和 GitHub 服务端拒绝。容器里没有本机 Claude 配置（M1 第 12 项），本机钩子不适用，不作为防线 |

**合并凭据只在合并执行器**：托管合并只由合并执行器（`merge_act.py` 在受控身份下，持有独立账号的凭据）执行；容器里的 agent 拿不到合并能力（#132）。

#### 3.3.1 反向测试（#135，L3 验收必须全过，在容器里做）

1. 直接越界：推 main、推非 `agent/` 分支、读宿主文件、连宿主除代理外的端口 → 被拒；
2. **自行合并**（#132 之后）：受限令牌对未获审批的 PR、已获审批的 PR、其他 agent 开的 PR，分别用 `gh pr merge` 和直接调 GitHub API 合并 → 全部被拒；
3. 间接越界：经脚本、构建工具、`curl` 调 GitHub API、子进程派生做 1、2 → 被拒；
4. 过期决定：送达闸遇到已作废、已过期的决定号，或子单已不是 `blocked`、已不在父单家族 → 不发评论；
5. 托管关闭后：`draining`、`frozen`、`off` 期间 blocked 子单 → 不发评论，按现行规则停机；
6. 额度并发：两个决定同时预占最后一个额度 → 只有一个成功；
7. **停机优先级**（#134）：blocked 与其他任一停机原因同时出现 → 不进托管，直接停机；主控停机流程设的 blocked → 不进托管；托管判断超时 → 停机；夜跑授权没写明允许托管唤醒 → 停机；
8. **唤醒计数**（#134）：一次托管评论实际触发的 run 数、归属、计数时机，与预占额度一致；评论发送结果不明时不重发。

### 3.4 批准卡

不适用：容器里的 agent 以 `bypassPermissions` 运行，不会弹批准卡。

### 3.5 上限与额度

- 每张子单最多被托管决定 〔策略填，例：2〕 次，超过按现行规则停机；每次托管的决定数、合并数各有上限（写在策略里）。
- 托管唤醒的 run 计入夜跑 `max_runs` 和连续失败计数，**托管不增加夜跑的 run 预算**；评论前在夜跑主控的锁内预占 run 额度（第 3.1 节「执行授权」）。
- **额度先预占、后执行**：出口闸在账本里原子预占（同一时刻只有一个预占成功），确认失败或作废时释放；**结果不明的合并额度冻结**，只读对账确认后，已合并计为已用，未合并才释放。

### 3.6 汇报与撤回（digital-twin 新做）

**原文从哪来**：猛鬼兽自己记。每个决定一条 twin-state Event，原文（子单、agent 评论、发出的回复）存 `~/Library/Application Support/DigitalTwin/custody/<托管号>/`，保留 90 天。

**汇报**：托管排空完成后发飞书卡片，按项目分组，每条一行「子单 · agent 问了什么 · 我替你定了什么 · 依据 · 结果 · 撤回能力」，挂起和 `UNRECONCILED` 置顶；`frozen` 时标题写「托管未能安全收尾」。08:00 个人项目日报（D22）引用这份汇报，不重复写。

**两个字段分开记**：

| 撤回能力（记账时写定） | 含义 |
|---|---|
| 可纠正 | 回复类：常浩可以在子单上补一条改正 |
| 可回退 | 合并、分支提交：可以用 git 回退 |
| 不可撤回 | 不该出现，撤不回的动作一律挂起；真出现就是闸漏了，按事故处理 |

| 处置状态（常浩点「推翻」后变化） | 做了什么 |
|---|---|
| 未处理 | — |
| 已推翻·已记录 | 每次推翻都有：标记被推翻，写一条规则补丁候选，以后同类按常浩的判断 |
| 已纠正 | 常浩本人在子单上评论「撤回 d-编号：……」并补正确答案 |
| 已回退 | 合并执行器开 revert PR；revert PR 的合并仍由常浩点卡片（B 档） |
| 回退失败 | 写原因，转常浩处理 |

**下游影响清单**：点「推翻」时，按以下规则列出受影响事项：
- 同一子单在该决定之后的所有 run；
- 这些 run 开出的分支、PR（git 上以被推翻的提交为祖先的）；
- 托管合并：以合并提交为祖先、之后合并的 PR，以及引用了该 PR 或 issue 的后续 issue、PR；
- 同一托管里依据该决定做出的其他决定（账本里记「依据」时引用了它的）。

### 3.7 开关形态与策略签署

**托管状态只有一处真源**：Hermes 侧 `custody.py`，写 `DigitalTwin/custody.json`，带状态（`off / on / draining / frozen`）、开始时间、结束时间、来源、策略版本与哈希。

**入口**：

| 入口 | 能开 | 能关 |
|---|---|---|
| 猛鬼兽飞书私聊（已核验通道，ARCHITECTURE 5.2a (b) 同一核验） | 能（「托管」「托管到 X 点」） | 能（「我回来了」「停止托管」「今晚不托管」） |
| 已签托管策略的默认时段 | 能（到点自动） | 能（到点自动） |
| 驿窗（只读显示，可选） | 不能 | 能（关闭是安全方向） |

**签署契约**（缺任何一项都不生效）：
- 策略文件按模板填写，**不许留未填项**；
- 版本号单调递增，不复用；改了内容必须换版本重签；
- 常浩在私聊发「签托管策略 v<版本> <SHA-256 前 12 位>」，猛鬼兽算出文件全文 SHA-256，前 12 位对上才算签；记下版本、完整 SHA-256、飞书消息 ID、核验的 `open_id`、签署时间、有效期；
- 每次使用策略（出口闸、送达闸、合并执行器）都重算哈希，和签署记录不一致、过期、被撤销 → 视为无策略，挂起一切。

### 3.8 关闭与排空

| 步 | 状态 | 做什么 |
|---|---|---|
| 1 | `draining` | 不再处理新的 blocked 子单：之后出现的 blocked 一律按现行规则停机 |
| 2 | `draining` | 账本里已出未送达的决定全部作废，送达闸不再发评论；释放它们预占的额度 |
| 3 | `draining` | 已被托管评论唤醒、正在跑的 run：按夜跑现行规则继续或停机（5.3a），托管不另加动作；执行防线是容器隔离，不随托管变化 |
| 4 | `draining` | 进行中的合并：结果不明的只读对账（7.6，不重发）；对账不清记 `UNRECONCILED`，额度冻结 |
| 5 | `off` | 全部对账完成后置 `off`，然后发汇报 |

**排空截止与冻结**：排空时长上限写在策略里。到截止仍有合并 `UNRECONCILED`：转 `frozen`，禁止新决定、新合并和重新开启托管；立即飞书报告常浩，列出未解决的合并（仓库、PR、HEAD、已做的只读对账）和被冻结的额度；汇报标题写「托管未能安全收尾」；只有常浩核对后在已核验私聊说「解除冻结」，才置 `off`，解除前只做只读对账。

## 4. 托管期间合并

同时满足才合，否则挂起：

0. **PR 来源属于当前已批准的夜跑**：合并执行器独立核验夜跑 ID、父子 issue、有效的夜跑授权记录、对应 run 与这个 PR 的可信关联（PR 分支来自该夜跑子单的 run）；证明不了属于当前授权范围的 PR 一律挂起，哪怕仓库在白名单里、其他条件都满足；
1. 合并官对该「PR × HEAD」判「建议合并」，风险档 L0–L2；
2. ARCHITECTURE 5.5 第 2 条成立（机械回归通过；按规则触发的 Codex 验证已完成）；
2a. **当前 HEAD 的必需 CI 全部通过**（没有 CI 的仓库：在干净副本里 `setup` + `test` 通过），检查结果绑定待合并的 HEAD；失败、未完成或结果不可确认就挂起；
3. **审核凭证**：
   - L1–L2：5.5 第 1 条成立（从驿窗接力记录核实送审绑定同一 HEAD/base、回信通过），或有一份等效的可信审核凭证。等效凭证至少绑定完整送审包 SHA-256、PR、HEAD、base、可信回执的来源及其结论，并校验回执晚于该 HEAD 的提交时间、审核针对的正是待合并的 HEAD 和 base；由确定性送审工具写入，不是 PR 评论、不是模型自报。缺失、任一项不匹配或核不清就挂起；
   - L0：只限托管策略列明的路径白名单（如 `docs/**`、`CURRENT.md`），按 L0 机械检查验收；
4. **合并副作用已核实且可回退**：该仓库在托管策略的「可托管合并仓库」清单里，清单逐仓库记录了合并到 main 会触发的全部工作流和外部动作，且已核实只有 CI 之类可安全回退的副作用；PR 本身改动了工作流或副作用配置的，挂起；核实不了就挂起；
5. 5.5 第 3、5、6、7 条照旧（范围受限、副作用已知、现读远端、`--match-head-commit`）；
6. 授权：托管开着 + 有效的已签策略写明允许合并；额度已原子预占；
7. 只由合并执行器执行（第 3.3 节）。

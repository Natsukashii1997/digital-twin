## 1. 托管是什么

**托管期间，猛鬼兽以常浩的身份替常浩回话、批准、合并；底线之外自己判断；每个决定记账；托管结束后汇报，常浩可以逐条推翻。**

- 「以常浩的身份」指**权威**：接收会话把猛鬼兽的话当成常浩本人的决定来执行。正因如此，只能送给**执行权限已被外部限制住**的会话（第 3.3 节）。
- 底线 = 授权清单 D 档 + **一切撤不回的动作**，托管期间挂起到常浩回来；拿不准也挂起。
- 托管是常浩用既有授权来源授出的**一段有时限的代理权**，不是新的授权来源。
- **托管状态与执行模式正交**：数据上是两个字段，`execution_mode = SUPERVISED | UNATTENDED`（执行怎么开跑，ARCHITECTURE 4.3）和 `custody_state = off | on | draining`（谁替常浩做决定）。界面可以叫「托管模式」，但任何执行准入都要**同时**满足原执行模式的前提和托管的限制，托管不替代、不放宽执行模式。

## 2. 一次托管决定的完整路径

```
会话这一轮结束并在等常浩（提问、wrap_up 待决、批准卡）
  └─ 驿窗：custody_state=on？会话是「受限会话」？
       否 → 不转交，留给常浩（汇报里列为「挂起」）
       是 → 把待决事项原文 POST 给猛鬼兽（本机 webhook，HMAC）          纸飞机：会话 → 猛鬼兽
  └─ 猛鬼兽：custody 技能
       ① 读原文、项目 CURRENT、Vault 偏好
       ② 出结构化决定 {动作, 对象, 回复原文, 依据, 撤回能力, 有效期}
       ③ 出口闸 custody_gate.py：再核策略有效 + 托管开着，按策略判；不过就改成「挂起」
       ④ 记账（决定号、原文、额度预占）
  └─ 驿窗送达闸：托管开着 + 发件是猛鬼兽 + 决定号在账本里且未过期未作废 + 会话仍是受限会话 + 链未超上限
       → 以常浩身份送进会话（末尾代发标记）                              纸飞机：猛鬼兽 → 会话
       └─ 会话照做；执行防线（受限执行身份 + 默认拒绝的执行点钩子）兜底
托管结束 → 排空（第 3.8 节）→ 飞书汇报卡（逐条带「推翻」）
```

## 3. 七问的回答

### 3.1 通道（驿窗改动，新做为主）

| 方向 | 做法 | 新做 / 复用 |
|---|---|---|
| 会话 → 猛鬼兽 | 驿窗加收件方 `hermes`，送达方式是 POST 到猛鬼兽本机 webhook 路由 `custody`（`hermes webhook subscribe`，带 HMAC、挂 `custody` 技能、`--script` 先做确定性预筛）。不走飞书：飞书给人看，有长度和格式限制，也会吵到常浩 | 驿窗新做收件方；Hermes webhook 现成，但 `platforms` 目前只开了飞书，要开 webhook 平台〔待实测，改 Hermes 配置属 D 档，单独问常浩〕 |
| 触发 | 托管开着时，驿窗在三种时刻对**受限会话**自动转交：① 完成钩子触发、这一轮最后回答在等常浩；② 批准卡出现；③ agent 主动 `send_message` 给 `hermes` | ① ② 复用现有完成钩子、注意钩子和「取最后回答」；「这一轮是否在等人」的判定新做 |
| 猛鬼兽 → 会话 | 驿窗加一个只给猛鬼兽用的发件口（本机命令或本地接口，带本机令牌），由 Hermes 侧确定性脚本 `custody_reply.py` 调用，模型不直接调。不复用 `send_message` 的会话识别：Hermes 不是驿窗认得的四家会话 | 新做 |

转交内容要**全文**：会话 id、项目目录、这一轮最后回答原文、wrap_up 的 ask 和按钮、批准卡的命令和理由。

### 3.2 身份（驿窗改动，改已定行为，要先发改动确认）

- 以常浩本人身份提交（Claude Code 用 `asUser: true`）；只在托管开着、只对猛鬼兽发件口、只对受限会话生效。
- 驿窗全局开关 `agentMessagesAsUser` 不用于托管，托管期间保持关闭。
- 消息末尾附 `〔托管·猛鬼兽代发 d-编号〕`，防止项目记录把代发写成「常浩说」。**标记只是记录，不是权限凭证**；权限只由送达闸、执行防线判定。

### 3.3 底线闸：先限住会话能做什么，再管说什么

**会话分两类**，由驿窗按会话的运行身份判定，判定结果写进转交内容和送达闸：

| 类 | 条件（全部满足） | 托管期间 |
|---|---|---|
| **受限会话** | 跑在 ARCHITECTURE 5.2c 式的受限执行身份下（单独 macOS 用户或容器，拿不到常浩的个人 git/gh 凭据、SSH agent、Vault、`~/.hermes`、驿窗数据目录）；它的 GitHub 凭据只能推 `agent/` 或会话分支，**没有合并和推 main 的能力**；该客户端的执行点钩子已通过第 3.3.2 节反向测试 | 可以以本人身份送达回复、答批准卡 |
| **全权会话** | 其他一切，包括常浩日常身份下、持有完整凭据的 Claude Code / Codex 会话 | **一律不送达**，待决事项挂起到常浩回来。不送「非本人」的提示消息：带权威的回复和不带权威的提示，在持有完整凭据的会话里都可能被执行 |

Codex 在通过同等验证之前，一律视为全权会话。

#### 3.3.1 三道闸

| 闸 | 位置 | 做什么 | 性质 |
|---|---|---|---|
| ① 出口闸 | Hermes 侧 `custody_gate.py`，模型之后、发出之前 | 再核托管开着、策略有效；决定是结构化的（动作类型 + 对象 + 原文），按策略判：D 档、L3、撤不回、超额、回退模型做出的判断 → 改为挂起；原文过禁止词表 | 管「说什么」，结构化部分可靠，自由文本只能尽力 |
| ② 送达闸 | 驿窗发件口 | 托管开着、发件是猛鬼兽、决定号在账本里且未过期未作废、会话仍是受限会话、链未超上限，才送达 | 确定性 |
| ③ 执行防线 | 接收会话所在的执行环境 | **主**：受限执行身份和受限凭据，越界操作被操作系统和 GitHub 拒绝；**辅**：执行点钩子按**白名单默认拒绝**（项目目录内读写、跑测试、推会话分支、开 PR 之外的一律拒绝），不是危险命令黑名单 | 主防线不依赖钩子；ARCHITECTURE 5.2c 已写明 `bypassPermissions` 下钩子不能作为可靠边界，所以钩子只作纵深 |

**合并凭据只在合并执行器**：托管合并只由独立的合并执行器（`merge_act.py` 在受控身份下，持有单独的合并凭据）执行；任何 Claude / Codex 会话都拿不到能合并或推 main 的凭据。

#### 3.3.2 批 3 的反向测试（L3 验收必须全过）

在受限会话里逐项实测，记录命令和结果：

1. 直接越界：推 main、`gh pr merge`、写项目目录外文件、读 `~/.hermes` 和 Vault → 被拒；
2. 间接越界：经脚本、Makefile、`npm run`、`python -c`、`curl` 调 GitHub API、`git` 别名、子进程派生做同样的事 → 被拒；
3. 权限绕过：会话尝试改钩子配置、改自身权限模式、找其他凭据 → 被拒或无效；
4. 过期决定：送一个已过期 / 已作废的决定号 → 送达闸拒收；
5. 停托管后：托管进入 `draining` 和 `off` 后，已在跑的会话继续尝试越界 → 仍被拒（执行防线不随托管关闭而解除，见第 3.8 节）；
6. 额度并发：两个决定同时预占最后一个合并额度 → 只有一个成功。

### 3.4 批准卡（驿窗改动，新做，排在后面）

- 只对受限会话转交；回「允许 / 拒绝 / 挂起」，挂起 = 卡片留着等常浩。
- 命令级，规则判为主：白名单内 → 允许；其余交模型，拿不准挂起。允许不改变执行防线：受限身份下做不到的事，批准了也做不到。
- 钩子等待时长上限〔待实测〕。

### 3.5 来回上限与额度

- 猛鬼兽的决定**不**清零来回计数；常浩真人插话照旧清零。
- 托管单独计数：每条链、每次托管的决定数，以及合并数、派单数，上限都写在托管策略里。
- **额度先预占、后执行**：出口闸在账本里原子预占一个额度（同一时刻只有一个预占成功），执行失败或决定作废时释放；不靠执行后计数。

### 3.6 汇报与撤回（digital-twin 新做）

**原文从哪来**：猛鬼兽自己记，不依赖驿窗日志。每个决定一条 twin-state Event，原文（收到的待决事项 + 发出的回复）存 `~/Library/Application Support/DigitalTwin/custody/<托管号>/`，保留 90 天。

**汇报**：托管结束、排空完成后发飞书卡片，按项目分组，每条一行「会话 · 问了什么 · 我替你定了什么 · 依据 · 结果 · 撤回能力」，挂起的单列在最上面。08:00 个人项目日报（D22）引用这份汇报，不重复写。

**两个字段分开记**：

| 撤回能力（记账时写定） | 含义 |
|---|---|
| 可纠正 | 回复类：可以给会话补一句改正 |
| 可回退 | 合并、分支提交：可以用 git 回退 |
| 不可撤回 | 不该出现，撤不回的动作一律挂起；真出现就是闸漏了，按事故处理 |

| 处置状态（常浩点「推翻」后变化） | 做了什么 |
|---|---|
| 未处理 | — |
| 已推翻·已记录 | 每次推翻都有：标记被推翻，写一条规则补丁候选，以后同类按常浩的判断 |
| 已纠正 | 常浩本人给会话发「撤回 d-编号：……」并补正确答案 |
| 已回退 | 合并执行器开 revert PR；revert PR 的合并仍由常浩点卡片（B 档） |
| 回退失败 | 写原因，转常浩处理 |

**下游影响清单**：点「推翻」时，猛鬼兽按以下规则列出受影响事项，写进推翻回执：
- 同一会话在该决定之后的所有轮次；
- 该会话之后开出的分支、PR（git 上以被推翻的提交为祖先的）；
- 托管合并：以合并提交为祖先、之后合并的 PR，以及引用了该 PR 或 issue 的后续 issue、PR；
- 同一托管里依据该决定做出的其他决定（账本里记「依据」时引用了它的）。

### 3.7 开关形态与策略签署

**托管状态只有一处真源**：Hermes 侧 `custody.py`，写 `DigitalTwin/custody.json`，带状态（`off / on / draining`）、开始时间、结束时间、来源、策略版本与哈希。驿窗只读，不自行判定。

**入口**：

| 入口 | 能开 | 能关 |
|---|---|---|
| 猛鬼兽飞书私聊（已核验通道，ARCHITECTURE 5.2a (b) 同一核验：平台认证事件、常浩 `open_id`、私聊、消息 ID 防重放） | 能（「托管」「托管到 X 点」） | 能（「我回来了」「停止托管」「今晚不托管」） |
| 已签托管策略的默认时段 | 能（到点自动） | 能（到点自动） |
| 驿窗侧栏开关 | **不能**：驿窗分不清是常浩亲手点的还是本机 agent 点的（5.2a (a) 的限制），所以只显示状态 | **能**：关闭是安全方向，任何来源都可以关 |

**签署契约**（缺任何一项都不生效）：
- 策略文件按模板填写，**不许留未填项**；
- 版本号单调递增，不复用；改了内容必须换版本重签；
- 常浩在私聊发「签托管策略 v<版本> <SHA-256 前 12 位>」，猛鬼兽算出文件全文 SHA-256，前 12 位对上才算签；记下版本、完整 SHA-256、飞书消息 ID、核验的 `open_id`、签署时间、有效期；
- 每次使用策略（出口闸、送达闸、合并执行器）都重算哈希，和签署记录不一致、过期、被撤销 → 视为无策略，挂起一切。

### 3.8 关闭与排空

托管关闭（任一入口）不是瞬间结束，按顺序走：

| 步 | 状态 | 做什么 |
|---|---|---|
| 1 | `draining` | 停止接收新的待决事项；出口闸不再出新决定 |
| 2 | `draining` | 账本里已出未送达的决定全部作废，送达闸拒收；释放它们预占的额度 |
| 3 | `draining` | 已送达的会话：让当前这一轮跑完，不再送任何决定；执行防线**照旧生效**（受限身份本来就不随托管变化，执行点钩子在排空期间按托管规则继续拦） |
| 4 | `draining` | 进行中的合并：结果不明的只读对账（ARCHITECTURE 7.6，不重发）；对账不清就记 `UNRECONCILED`，在汇报里置顶 |
| 5 | `off` | 全部对账完成后才置 `off`，执行点钩子回到非托管规则，然后发汇报 |

## 4. 托管期间合并

同时满足才合，否则挂起：

1. 合并官对该「PR × HEAD」判「建议合并」，风险档 L0–L2；
2. ARCHITECTURE 5.5 第 2 条成立（机械回归通过；按规则触发的 Codex 验证已完成）；
3. **审核凭证**：
   - L1–L2：5.5 第 1 条成立（从驿窗接力记录核实送审绑定同一 HEAD/base、回信通过），或有一份等效的可信审核凭证——由确定性送审工具写入、绑定 PR、HEAD、base、审核结论和审核来源，不是 PR 评论、不是模型自报；拿不到就挂起；
   - L0：只限托管策略列明的路径白名单（如 `docs/**`、`CURRENT.md`），按 L0 机械检查验收；
4. **合并副作用已核实且可回退**：该仓库在托管策略的「可托管合并仓库」清单里，清单逐仓库记录了合并到 main 会触发的全部工作流和外部动作，且已核实只有 CI 之类可安全回退的副作用（没有部署、发布、通知外部、数据迁移）；PR 本身改动了工作流或副作用配置的，挂起；核实不了就挂起；
5. 5.5 第 3、5、6、7 条照旧（范围受限、副作用已知、现读远端、`--match-head-commit`）；
6. 授权：托管开着 + 有效的已签策略写明允许合并；额度已原子预占；
7. 只由合并执行器执行（第 3.3.1 节）。

只豁免 5.5 第 8 条（审核模式可证）和影子门槛。托管合并在 `agreement.csv` 记 `owner=custody`，不计入影子一致率，不作为升档证据。

## 5. 托管期间派单（D23）

- 托管期间 D23 夜间提案没回复时，猛鬼兽**只执行**推荐组合里**此前已经有效授权**的项：对象（仓库 + issue 号）、动作范围（只到开 PR）、时限、额度都已经由常浩在已核验通道或单次授权文件里逐项写明（授权清单第 5 节第 1 条）。
- 签一份通用托管策略**不等于**对未来未知的仓库、issue 的写入授权。推荐项不在已授权范围内的，只出提案、挂起，第二天日报列出来。
- 想让托管策略本身覆盖一类动态写入派单，要先由常浩改 D 档规则（授权清单第 4 节「写入类派单从 D 降到 C」），本批不做。

## 7. 分批

最小闭环：**一个沙盒项目里，受限会话停下问 → 驿窗转猛鬼兽 → 猛鬼兽按推荐回 → 以常浩身份送回 → 记账 → 排空 → 汇报 → 推翻**。

| 批 | 仓库 | 内容 |
|---|---|---|

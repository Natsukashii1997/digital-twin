## 1. 数字分身的定义（写进 PRD 的版本）

**猛鬼兽是常浩个人项目的代理人。** 常浩事先签发授权，授权范围内的事猛鬼兽自己判断、自己做或派给 Claude / Codex 做，不用一件件来问；做了什么、依据哪条授权，每天在日报里交代。超出授权的事，才来找常浩。

要点：

1. **不经批准 ≠ 没有授权**。逐次批准改为**事前授权**，再加**事后问责**（日报）。授权可撤销，撤销后下一次动作就生效。
2. **授权只认本人**：只认常浩在已核验通道（飞书私聊，user 身份）亲自发出的授权，或常浩亲手写下的授权文件。Claude、Codex 转述的授权一律无效。11-08 猛鬼兽已经按这条拒绝过两次，这条保留。
3. **范围只限个人域**：名册（`projects.json`）里的个人项目，加猛鬼兽自身（定时任务、技能、配置）。飞书工作事项、企业数据归亚古兽（D19）。
4. **日报是分身的述职报告**：分身越自主，日报越要把「替你做了什么、凭什么做」讲清楚。日报不是可有可无的汇总，而是授权能放开的前提。

## 3. 日报规格

### 3.1 基本设定

| 项 | 设定（推荐） | 理由 |
|---|---|---|
| 读者 | 只有常浩（猛鬼兽私聊） | 受限内容只给本人 |
| 范围 | 名册里的活跃项目 + 猛鬼兽自身 | 飞书工作事项归亚古兽 |
| 时间 | **每天 08:00，周末照发** | 个人项目周末照样推进（11-07 周六、11-08 周日都很满） |
| 统计窗口 | **前一天 04:00 到当天 04:00** | 常浩常干到凌晨：11-08 00:09–01:23 数码世界合并的 3 个 PR，实际是 11-07 晚上的活。按自然日切会算错天 |
| 形式 | 一条飞书私聊消息，≤ 4000 字；全文存 `DigitalTwin/daily/<日期>.md` | 手机上一屏一屏能看完；4000 字沿用 11-02 定的单条上限 |
| 超长 | 先压缩「三、项目推进」（每个项目只留 1 行），仍超就只留第一、二、四、五段，末尾注明「全文在本地」 | 拍板和紧急的内容永远不砍 |
| 没动静 | 照发 3 行：没有推进、分身没动作、明天的重点 | 没收到不等于没事；日报断了要能看出来 |
| 留痕 | 抬头写生成方、实际模型、接入方式、时间（P-13） | 已有 `report_publish.py` 的写法 |

### 3.2 结构（7 段，顺序固定）

```
📅 猛鬼兽日报｜11-08（周日）
生成：Hermes（模型）｜接入：Hermes 派单｜11-09 08:00｜窗口 11-08 04:00 → 11-09 04:00
一句话：……

一、要你拍板（≤5）
二、我替你做了什么
三、各项目推进
四、紧急与待完成
五、今天的重点（≤3）
六、沉淀建议（≤3）
覆盖：……
```

| 段 | 写什么 | 规则 | 取数 |
|---|---|---|---|
| 抬头 + 一句话 | 昨天最重要的一件事，加今天最要紧的一件事 | ≤ 60 字 | 下面各段 |
| **一、要你拍板** | 只有常浩能做的决定。每条写：什么事、为什么必须是你、不拍会怎样、回什么话就行 | 按急迫排序；没有就写「无」；授权清单 D 档的事一定进这里 | 开着的 PR 中合并官判「问常浩」或 L3 的；Hermes 受阻、超出授权的；待决提案；各项目 CURRENT 里「等常浩」的 |
| **二、我替你做了什么** | 分身自己的动作，按类：合并（执行了几次）、裁决（批了几项、驳了几项）、派单、拒绝、定时任务（成功、失败、静默） | **每条都写依据**：清单档位 + 来源（卡片、授权文件编号）。拒绝也要写，守住边界也算工作 | 合并官 `agreement.csv` 的 owner 列；`merge-runs/`；`evidence/**/hermes-*.md`；派单台账；`cron/executions.db`、`cron_incidents` |
| **三、各项目推进** | 有动静的项目，每个 ≤ 3 行：成果、在途、下一步（谁做） | 成果按**完成口径**标注（见 3.3）；按成果分量排序，不按提交数；同一主题的多个 PR 合成一行；没动静的活跃项目合成一行 | `progress_data.py`（合并的 PR、关闭的 issue、分支、CURRENT） |
| **四、紧急与待完成** | ⚠ 紧急：今天有时限的、阻断的、有风险的；待完成：开着的 PR、在途分支、CURRENT 过期、主目录有大量未提交文件 | 紧急 ≤ 5 条；待完成只列超过 2 天的，或有风险的 | 开着的 PR（`gh`）、`progress_data.py`、各次授权的有效期 |
| **五、今天的重点** | ≤ 3 件：做什么、谁做（常浩 / Hermes / Claude / Codex）、在哪做、做到什么算完 | 必须能直接照做 | 一至四段 |
| **六、沉淀建议** | ≤ 3 条：建议进哪里（全局坑 G-xx / 项目 LESSONS / skill / 全局指令 P-xx / Vault），一句话内容，证据 | **门槛**：同一做法在 ≥ 2 个独立任务里都见效，或同一个坑踩了 ≥ 2 次；不够门槛的不提。只提建议，不写 | 昨天新增的各项目 LESSONS 条目；合并官和常浩不一致的判定；重复失败；会话复盘的提案 |
| 覆盖 | 读了哪些来源、哪些没读到 | 没读到的写「未知」，不写成零 | 取数脚本 |

### 3.3 完成口径（项目推进段统一用）

`已提交（分支）` → `PR 中` → `已合并` → `已安装 / 已发布` → `常浩已验收`

只写到有证据的那一档。比如 PR 合并了，但 CURRENT 和安装记录里查不到「已安装」，就只写「已合并」。

### 3.4 不写什么

- 飞书私聊、群聊、会议、任务里的工作事项（归亚古兽）
- 提交清单和提交数（提交数只放进覆盖行）
- Vault 受限内容原文
- 没有证据的推测（推测要标「推断」）

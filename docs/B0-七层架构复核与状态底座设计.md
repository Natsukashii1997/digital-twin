## 3. 最小架构设计（B0.2）

### 3.1 对象关系

```
Goal 1 ──n Task 1 ──n Run 0..1 ── 派单工单 order.json（order_no 唯一）
  │          │           │
  └── Ref    └── Ref     └── Ref（github_pr / github_issue / feishu_task / obsidian_note / file / url …）
Event n ── 任一对象（goal / task / run），idem_key 唯一
```

| 对象 | 字段（精简） | 说明 |
|---|---|---|
| Goal | `id`（`G<日期>-<序>`）、title、description、status、scope（边界）、project、phase、done_when、authorized_at | 长期目标；证据走 Ref |
| Task | `id`（`T…`）、goal_id、title、status、depends_on（JSON 列表）、acceptance、next_step、blocked_kind、blocked_reason、owner、retries | 具体任务 |
| Run | `id`（`R…`）、task_id（可空：未关联的旧工单）、agent、order_no、status、session_id、receipt、evidence、started_at / ended_at / heartbeat_at、note | 单次执行；沿用台账状态词 |
| Event | id、idem_key（唯一）、source（user / discovery / agent / system）、kind、actor、object、payload、evidence、applied、result、dup_count | 状态变化与触发记录 |
| Ref | object、kind、ref、url、note | 指向权威来源，只存指针 |

库文件 `~/Library/Application Support/DigitalTwin/twin-state.db`（`DT_STATE_DB` 可改），目录 700、文件 600，WAL；`meta.schema_version` 驱动迁移（`MIGRATIONS` 只追加）；`backup()` 用 SQLite 在线备份 API 到同目录 `backups/`，`restore()` 整体替换。不进 GitHub、不进 Obsidian。

### 3.2 任务状态与转换

```
observed ──ready──► ready ──start_run──► running ──done──► review ──complete(有证据)──► completed
   │                  │                      │                 │
   │                  │   failed/stale/guard/need_decision     │ rework
   └──────────────────┴────────────► blocked ◄─────────────────┘
                                       │ unblock / retry(technical, ≤2 次) / 依赖完成自动放行
                                       └──────────► ready
任何非终态 ──cancel──► canceled
```

- 合法转换只在 `TASK_TRANSITIONS` 表里；其余一律 `IllegalTransition`（如 observed → running、ready → completed、终态再动）。
- Run 状态沿用台账词 `new / queued / running / done / guard / failed / merged / cleaned / abandoned`，另加 `stale`（过期）；Run 的转换表 `RUN_TRANSITIONS` 独立，不和任务混用。台账跳过中间状态时以台账为准并记 `run.resync` 事件。
- Run 结果如何反映到任务（只在任务仍是 running 时）：`done → review`；回执有 `need_decision` 或触发护栏或被放弃 → `blocked(decision)`；`failed / stale → blocked(technical)`；台账后续的 `merged / cleaned` 只改 Run，不动任务和目标。

### 3.3 授权边界（程序校验）

| 动作 | 谁能做 | 校验 |
|---|---|---|
| 新建目标 | 任何人，但非 `user` 只能建 `observed` | `create_goal` |
| 授权目标、完成目标、撤销目标（连带撤销任务） | 只有 `user` | `NotAuthorized` |
| 任务 observed → ready | 任何人，但目标必须 `authorized` | 依赖没完成先 `blocked(dependency)` |
| 开始执行 | 任务必须 `ready`、目标必须 `authorized`、该任务没有进行中的 Run | 一任务一活动 Run，不重复派单 |
| 解 decision 类阻塞 | 只有 `user` | 技术重试 `retry_task` 对 decision / external / dependency 一律拒绝 |
| 技术重试 | 任何人，最多 `MAX_RETRIES`=2 次 | 超过要常浩定 |
| 撤销任务 | `observed` 的任何人可撤；已授权推进的只有 `user` | |
| 完成任务 | 任何人，但必须在 `review` 且有证据（Ref 或成功的 Run） | `EvidenceMissing` |

Hermes 在已授权目标范围内可以推进（set_ready、start_run、retry、complete_task），但造不出新的授权。

### 3.4 三个事件入口与幂等

统一走 `ingest_event(source, kind, idem_key, actor, payload, handler)`：同一个幂等键只处理一次，重复进入只给原事件加 `dup_count`，不再调用 handler；handler 和事件记录在同一个事务里，handler 抛 `StateError` 时状态回滚、事件记为 `applied=0` 并保留原因（可追溯）。

| 入口 | source | 幂等键 | 本轮提供 |
|---|---|---|---|
| 用户消息（飞书私聊、桌面会话） | `user` | 飞书消息 id 等 | `create_goal(by=user)`、`authorize_goal`、`unblock_task`、`ingest_event(source="user")` |
| 主动发现（定时检查、扫描台账、重启恢复） | `discovery` / `system` | `order.sync:<单号>:<updated>:<状态>`、对象事件序号 | `create_goal(by=hermes)` → observed、`sync_orders`、`recover` |
| Agent 回执（车间跑完） | `agent` | 回执内容哈希 `run.receipt:<Run>:<sha1>` | `receive_receipt`、`finish_run`、`update_run` |

### 3.5 向下执行、向上反馈

- **向下**：常浩授权目标 → 任务 `ready` → Hermes `start_run(idem_key=消息 id, order_no=派单单号)` → `dispatch.py new / run`（执行层照旧）→ 车间在 worktree 干活。
- **向上**：`receipt.json` → `receive_receipt` → Run `done` → 任务 `review`，`next_step`=「核对回执、测试与 PR」→ Hermes 按 workshop 第 4 节回报 → 常浩说“合并” → `dispatch merge` → `sync_orders` 把 `merged / cleaned` 记到 Run → `complete_task`（证据 = PR）→ 目标完成由常浩定。
- **恢复**：`recover()` 在重启或巡检时跑：running 的 Run 按探针（台账）定终态；没探针、超过 `STALE_AFTER`（2 小时）没心跳的标 `stale`，任务转 `blocked(technical)` 写明原因；running 却没有活动 Run 的任务转 `blocked(technical)`；`blocked(dependency)` 的任务依赖都完成就放行到 `ready`。每一步独立事务，做到哪一步记到哪一步。

### 3.6 跨 Agent 交接协议

交接载荷固定这些字段：`task_id`、`goal_id`、`run_id`、`order_no`、`agent`、目标的 `scope`、任务的 `acceptance` 与 `next_step`、`blocked_kind / blocked_reason`、证据 `refs`、幂等键。载体沿用现有的：派单 `task.md`（五要素）、`order.json`、`receipt.json`、GitHub issue / PR 正文；状态库只记指针和状态。换执行方 = 前一个 Run 结束后在同一任务上 `start_run(agent=另一个)`，一个 Run 不换 agent；每个 Run 带自己的 `session_id`（续跑用）。

### 3.8 关键技术选择与取舍

| 选择 | 取舍 |
|---|---|
| SQLite 单文件 + 标准库 `sqlite3` | 和现有脚本一致（都只用标准库）；事务、WAL、在线备份现成；不加依赖，不装服务 |
| 单文件模块 + 内置命令行 | 安装方式与其他脚本相同（复制到 `~/.hermes/scripts/`），自检的漂移比对自动覆盖；Hermes 技能调用脚本本来就是命令行 + 末行 JSON |
| 不碰 `dispatch.py`，用只读同步接台账 | 零风险兼容既有 15 张工单和 88 项测试；代价是台账变化要靠 `sync-orders / recover` 拉取，B2 再给 `dispatch.py` 加写入钩子 |
| Run 状态沿用台账词 | 省一层映射，`order.json` 和 Run 一眼对得上 |
| 阻塞分四类（decision / dependency / external / technical） | 只有这四类在规则上处理方式不同；decision 永远要常浩，technical 可自动重试两次 |
| 事件表 + 幂等键 + `dup_count` | 既防重复，又留痕；拒绝的事件也记（`applied=0`） |
| 幂等键由调用方给（外部事件）或按对象序号生成（内部转换） | 外部事件天然有稳定 id（飞书消息、回执内容）；内部转换的幂等靠状态检查（已在目标状态就是空操作） |
| 不用 Hermes 自带 `kanban.db` | 它是 Hermes 内部表，随版本变；长期状态要自己掌握 schema 和迁移 |
| 库放 Application Support，不放 `~/.hermes` | 任务书建议；和 Hermes 升级、备份互不干扰；Hermes 记忆按 PRD 只当缓存 |

### 2.1 事实归属：同一类状态只有一个最终裁定方

一个系统可以有多个权威来源，但每类状态必须有明确的裁定方；`sync_orders` 只负责观察和协调，不把任何一条新读到的值无条件当成正确。

| 状态对象 | 最终裁定方 | 本库怎么处理 |
|---|---|---|
| Goal / Task 的目标、授权、推进状态、阻塞与验收结论 | **本状态库** | 只通过转换表和授权边界改动 |
| Run 的实际执行结果（跑完、失败、护栏、合并、清理） | **派单台账与回执**（`order.json`、`receipt.json`） | 同步进本库；状态回退、护栏降级、终态再变一律拦下记 `run.conflict`，不应用 |
| 工程合并、代码内容、PR 结论 | **GitHub** | 只存 issue / PR 号与链接（`refs`） |
| 常浩的长期认知、正式知识 | **Obsidian Vault** | 只存笔记路径 |
| 飞书消息、任务的原始事实 | **飞书** | 只存消息 id（作幂等键）与任务 id |

横向协作（Matrix 所表达的角色）：Agent 间消息 = 事件表 + 飞书回报；任务交接 = `start_run(agent=…)` 换执行方 + 派单 `task.md` 五要素；状态同步 = 状态库（唯一长期状态）+ `sync_orders`；结果共享 = Run 的回执与证据指针 + GitHub PR；协作控制 = 授权边界与转换表。不引入消息服务器。

## 3. 最小架构设计（B0.2）

### 3.1 对象关系

```
Goal 1 ──n Task 1 ──n Run 0..1 ── 派单工单 order.json（order_no 唯一）
  │          │           │
  └── Ref    └── Ref     └── Ref（github_pr / github_issue / feishu_task / obsidian_note / file / url …）
Event n ── 任一对象（goal / task / run），idem_key 唯一
```

| 对象 | 字段（精简） | 说明 |
|---|---|---|
| Goal | `id`（`G<日期>-<序>`）、title、description、status、scope（边界）、project、phase、done_when、authorized_at | 长期目标；证据走 Ref |
| Task | `id`（`T…`）、goal_id、title、status、depends_on（同目标内）、acceptance、next_step、blocked_kind、blocked_reason、owner、retries、**verdict / verdict_by / verdict_basis / verdict_cites / verdict_at**（验收结论） | 具体任务 |
| Run | `id`（`R…`）、task_id（可空：未关联的旧工单）、agent、order_no、status、session_id、receipt（白名单字段）、evidence、note、**cancel_requested_at / by**、started_at / ended_at / heartbeat_at | 单次执行；沿用台账状态词 |
| Event | id、idem_key（唯一）、source（user / discovery / agent / system）、kind、actor、object、payload、evidence、applied、result、dup_count | 状态变化、触发、冲突与拒绝的记录 |
| Ref | object、kind、ref、url、note | 指向权威来源，只存指针 |

库文件 `~/Library/Application Support/DigitalTwin/twin-state.db`（`DT_STATE_DB` 可改），目录 700、文件 600，WAL；`meta.schema_version` 驱动迁移（`MIGRATIONS` 只追加；v1 在返修时定稿，此前没有任何已部署的库）；`backup()` 用 SQLite 在线备份 API 到同目录 `backups/`（同一秒再备份自动加序号），`restore()` 先查完整性和版本再整体替换。不进 GitHub、不进 Obsidian。

### 3.2 任务状态与转换

```
observed ──ready──► ready ──start_run──► running ──done──► review ──accept(结论通过)──► complete ──► completed
   │                  │                      │  ▲              │  ▲
   │                  │   failed/stale/guard/need_decision     │  └─ resume_run（同一工单续跑，清结论）
   └──────────────────┴────────────► blocked ◄─────────────────┘ rework / 验收不通过 → ready
                                       │ unblock / retry(technical, 有上限) / 依赖完成自动放行 / resume_run(technical)
                                       └──────────► ready（或直接 running）
任何非终态 ──cancel──► canceled（进行中的 Run 记“已请求取消”，等执行层真正停下）
```

- 合法转换只在 `TASK_TRANSITIONS` 表里；其余一律 `IllegalTransition`。`blocked → running`、`review → running` 只走 `resume_run`（同一工单续跑），`start_run` 仍只接受 `ready`。
- Run 状态沿用台账词 `new / queued / running / done / guard / failed / merged / cleaned / abandoned`，另加 `stale`（过期）；Run 的转换表 `RUN_TRANSITIONS` 独立，含 `done / failed / stale / guard → running`（续跑；guard 的续跑只有常浩能定）。
- **当前 Run**：任务最后登记的那个 Run。只有当前 Run 的结果能改任务，而且任务得还在 `running`：`done → review`（`next_step`=核对回执、测试与 PR，再记验收结论）；回执带 `need_decision`、触发护栏、被放弃 → `blocked(decision)`；`failed / stale → blocked(technical)`。旧 Run 的迟到结果只改它自己，记 `run.late_result`；任务不在 running 时记 `run.result_not_applied`。台账后续的 `merged / cleaned` 只改 Run。
- **回执判定**（`classify_receipt`）：护栏优先 → `guard`；缺 `exit_code` 或 `ended`、`exit_code` 不是整数 → `failed`（原因写进 Run 的 note 和任务阻塞原因）；`timed_out`、`worker_error` 或非零退出 → `failed`；否则 `done`。**执行完成只代表车间跑完了，不代表任务满足 acceptance。**
- **验收结论**（`accept_task`）：只在 `review` 里；必须写依据并引用本任务已有的证据（Run id 或 `kind:ref`）；执行当前 Run 的 agent 不能给自己下结论（常浩可以）；结论由 user / hermes / claude / codex 给出，`system` 不行；不通过等于退回 `ready`；续跑或返工清掉结论。`complete_task` 只认通过的结论，并要求当前 Run 不在进行中。B3 的 Codex 独立审查接在这里。

### 3.3 授权边界（程序校验）

| 动作 | 谁能做 | 校验 |
|---|---|---|
| 新建目标 | 任何人，但非 `user` 只能建 `observed` | `create_goal` |
| 授权目标、完成目标、撤销目标（连带撤销任务） | 只有 `user` | `NotAuthorized` |
| 任务 observed → ready | 任何人，但目标必须 `authorized` | 依赖没完成先 `blocked(dependency)` |
| 开始执行 | 任务必须 `ready`、目标必须 `authorized`、该任务没有进行中的 Run | 一任务一活动 Run，不重复派单 |
| 记阻塞、更新原因 | 任何人 | 类型与原因必填 |
| 改阻塞类型 | 非 `user` 只能升级成 `decision`；`decision` 类只有 `user` 能改成别的 | 堵住“改成 technical 再重试”的绕行 |
| 解 decision 类阻塞 | 只有 `user` | `retry_task` 对 decision / external / dependency 一律拒绝 |
| 技术重试 / 非 user 解 technical 阻塞 | 任何人，共用上限 `max_retries`（默认 2，临时保护） | 超过要常浩定 |
| 解 external 阻塞 | 非 `user` 必须写明来源已恢复的依据 | |
| 续跑（`resume_run`） | done / failed / stale 任何人；guard 只有 `user`；任务若在 decision / external / dependency 阻塞，续跑不改任务（记冲突） | failed 的续跑计一次重试 |
| 撤销任务 | `observed` 的任何人可撤；已授权推进的只有 `user` | 进行中的 Run 记“已请求取消” |
| 验收结论 | user / hermes / claude / codex，执行方除外 | 必须引用证据 |
| 完成任务 | 任何人，但必须在 `review`、结论通过、当前 Run 已结束 | `EvidenceMissing` / `IllegalTransition` |

**角色声明不是身份认证。** 库只认 `by="user"` 这个字符串，它是内部可信调用约定：把“常浩本人在飞书私聊或桌面会话说的话”映射成 `user`，是调用方（Hermes 技能）的责任，前提是网关层已按 `FEISHU_ALLOWED_USERS` 只放行常浩、技能把发言人 open_id 传下来。命令行上 `--by user` 必须带 `--sender <open_id>` 且等于 `OWNER_OPEN_ID`，这只能防误传，防不了恶意调用。**在 B2 完成身份桥接并测试之前，正式运行中的 Hermes 不得用带授权语义的命令行参数操作长期目标**（本轮模块也没有安装，所以没有任何调用方）。

### 3.4 三个事件入口与幂等

统一走 `ingest_event(source, kind, idem_key, actor, payload, handler)`：同一个幂等键只处理一次，重复进入只给原事件加 `dup_count`，不再调用 handler；handler 和事件记录在同一个事务里，handler 抛 `StateError` 时状态回滚、事件记为 `applied=0` 并保留原因（可追溯）。新建目标 / 任务、开跑带幂等键时重复进入返回既有对象，不抛库异常。

| 入口 | source | 幂等键 | 本轮提供 |
|---|---|---|---|
| 用户消息（飞书私聊、桌面会话） | `user` | 飞书消息 id 等 | `create_goal(by=user)`、`authorize_goal`、`unblock_task`、`accept_task`、`ingest_event(source="user")` |
| 主动发现（定时检查、扫描台账、重启恢复） | `discovery` / `system` | `order.sync:<单号>:<updated>:<状态>`、对象事件序号 | `create_goal(by=hermes)` → observed、`sync_orders`、`recover` |
| Agent 回执（车间跑完） | `agent` | 回执内容哈希 `run.receipt:<Run>:<sha1>` | `receive_receipt`、`finish_run`、`update_run`、`resume_run` |

### 3.5 向下执行、向上反馈、恢复

- **向下**：常浩授权目标 → 任务 `ready` → Hermes `start_run(idem_key=消息 id, order_no=派单单号)` → `dispatch.py new / run`（执行层照旧）→ 车间在 worktree 干活。
- **向上**：`receipt.json` → `receive_receipt` → Run `done` → 任务 `review` → Hermes 按 workshop 第 4 节回报 → 独立核对（常浩或 Codex）`accept_task` → 常浩说“合并” → `dispatch merge` → `sync_orders` 把 `merged / cleaned` 记到 Run → `complete_task` → 目标完成由常浩定。
- **恢复**（`recover()`，重启或巡检时跑）：
  1. 先读派单台账。目录缺失、读不了、没这张单，是三种不同情况，都记 `unknown`、不下判断。
  2. running 的 Run：台账说还在跑就保留（超过 `stale_after` 没变化的只列 `suspect`，留给 B2 用进程存活判断）；台账给了结果就按同步规则结算；只有**没有工单号、也查不到台账**的 Run 才按时间判过期（超过 `STALE_AFTER` 2 小时没心跳标 `stale`，任务转 `blocked(technical)`）。
  3. running 却没有活动 Run 的任务 → `blocked(technical)`；`blocked(dependency)` 的任务依赖都完成就放行到 `ready`。
  4. 每一步独立事务，做到哪一步记到哪一步。
- **台账同步的冲突规则**（`_resync_kind`）：查表合法 → 正常；`done / failed → running` → 续跑（`run.followup`，任务按续跑规则处理）；`stale → running` → 过期判断被推翻；向前跳过中间状态（如 `done → cleaned`）→ `run.resync`；**终态（cleaned / abandoned）再变、guard 降级或续跑、从结果状态回到 new / queued / running** → `run.conflict`，不应用，留给人工。
- **取消**：撤销任务 / 目标时进行中的 Run 不直接写 `abandoned`（进程可能还在跑），记 `cancel_requested_at / by` 和 `run.cancel_requested` 事件，`list_runs(cancel_pending=True)` 可查；执行层真正停下来（台账 `abandoned / done / failed`）后结果只记 `run.result_not_applied`。B1 不实现进程终止，B2 用这张清单去停。

### 3.6 跨 Agent 交接协议

交接载荷固定这些字段：`task_id`、`goal_id`、`run_id`、`order_no`、`agent`、目标的 `scope`、任务的 `acceptance` 与 `next_step`、`blocked_kind / blocked_reason`、证据 `refs`、验收结论、幂等键。载体沿用现有的：派单 `task.md`（五要素）、`order.json`、`receipt.json`、GitHub issue / PR 正文；状态库只记指针和状态。换执行方 = 前一个 Run 结束后在同一任务上 `start_run(agent=另一个)`，一个 Run 不换 agent；每个 Run 带自己的 `session_id`（续跑用）。

### 3.8 关键技术选择与取舍

| 选择 | 取舍 |
|---|---|
| SQLite 单文件 + 标准库 `sqlite3` | 和现有脚本一致（都只用标准库）；事务、WAL、在线备份现成；不加依赖，不装服务 |
| 单文件模块 + 内置命令行 | 安装方式与其他脚本相同（复制到 `~/.hermes/scripts/`），自检的漂移比对自动覆盖；Hermes 技能调用脚本本来就是命令行 + 末行 JSON |
| 不碰 `dispatch.py`，用只读同步接台账 | 零风险兼容既有 15 张工单和 88 项测试；代价是台账变化要靠同步拉取，B2 加事件通知 |
| Run 状态沿用台账词，续跑建模为同一 Run 回到 running | 一张工单一个 Run，`order.json` 和 Run 一眼对得上；续跑是 dispatch 的真实流程，不建模就会被当成冲突 |
| “当前 Run”= 最后登记的 Run | 最小的有效 Run 判定，不加新字段；迟到结果有事件可查 |
| 验收结论记在 Task 上（四个字段 + 事件） | 把“执行结果 / 验收证据 / 验收结论”分开，又不建外部验收系统；B3 的 Codex 审查直接写结论 |
| 取消用标记不用新状态 | Run 状态表不变；“已请求取消”的事实准确可查，真正终止留给执行层 |
| 阻塞分四类，类型变更有方向性 | 只有这四类处理方式不同；非 user 只能往更严的 decision 升级 |
| 事件表 + 幂等键 + `dup_count` + 冲突事件 | 既防重复，又留痕；被拒绝和被拦下的都记 |
| 不用 Hermes 自带 `kanban.db` | 它是 Hermes 内部表，随版本变；长期状态要自己掌握 schema 和迁移 |
| 库放 Application Support，不放 `~/.hermes` | 任务书建议；和 Hermes 升级、备份互不干扰 |

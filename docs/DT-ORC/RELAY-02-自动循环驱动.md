# RELAY-02 ORCA 自动循环驱动（#37，Part of #32）

## 1. 为什么做

常浩 10-31：「基于 ORCA 自动化推进，把整个数字分身项目推进结束」，不要每一步都让他确认。RELAY-01（PR #36）只解决了「送审包怎么进 ChatGPT、回执怎么回 Claude」这一段运输；把开发、审核、返修串成一个不需要人值守的循环，是本批的事。

## 2. 流程

```
relay_loop.py run
  ├─ 把任务说明交给 ORCA 终端里的 Claude（同一条只交一次）
  ├─ 等 round-N.ready（Claude 写完送审包后最后创建；驱动不猜送审包写没写完）
  ├─ 查任务开工后有没有被合并的 PR（执行方不许合并）→ 有就通知，退出 20
  ├─ 送审（RELAY-01）：第 1 轮在项目首页开新会话，之后固定在该会话
  │     发送前 relay 自己核对：指定会话、聊天模式、思考强度「高」（不是就调高并回读）；
  │     点发送的同一段页面脚本里再核一次模式和强度，不对就不点
  ├─ 回执核对：送审包摘要、送审编号、本目录为这一轮记下的送审包和任务、审核会话，全部对上才认
  ├─ PASS → 再查一次越权合并 → 飞书私聊通知常浩「等合并闸门」，退出 0
  ├─ NEEDS_HUMAN → 通知，退出 20
  ├─ REWORK → 回执交回 Claude 返修，等下一轮 ready；返修超过 2 轮（D3-5）→ 通知，退出 20
  └─ 任何出错（含没预料到的异常）→ 通知并记入 errors.jsonl，退出 2；排除后重跑同一命令即续跑
```

同一运行目录同时只能有一个驱动（`.lock`，flock）：第二个进程退出码 3，不交付、不送审、不通知。

运行目录里的文件、续跑规则见 `orca/relay_loop.py` 开头的说明。续跑时：已有回执的轮次核对通过后直接读回执（对不上就停下，不判结论）；送审包有发送标记（上次发送结果不明）的，到标记记下的会话里 collect，不重发；交给 Claude 的消息、飞书通知都按键只发一次（飞书侧另带幂等键）。

## 3. 通知

用猛鬼兽 bot 身份私聊常浩（`lark-cli im +messages-send --as bot --user-id <owner_open_id>`），open_id 从本机受控文件读，不进仓库。只发任务标题、轮次、结论和回执路径，不带回执正文。

## 4. 闸门与执行方权限边界

常浩 10-31 定的闸门（记在 CURRENT）：开 issue、开分支、开发、审核、返修（最多 2 轮），以及 PASS 且没碰正式环境的 PR 自动 squash 合并，都全自动；正式安装和部署、改 Hermes 正式配置和 cron、机器人对外发消息、NEEDS_HUMAN、返修超限，飞书私聊攒起来问他。

驱动本身不合并、不安装、不改正式配置，PASS 之后停在「等合并闸门」；合并由驱动之外的总控按闸门做（第 3 批任务队列接管）。执行方（ORCA 终端里的 Claude）有三层约束：

1. **执行层拦截（强制）**：执行方必须用 `orca/executor-settings.json` 启动（见第 5 节命令）。它是 Claude Code 的 deny 规则，auto 模式下同样生效，拦下：合并 PR（`gh pr merge`、`gh api`）、推 main 和强推、`launchctl`、`crontab`、`hermes` 命令、`lark-cli`（对外发消息），以及用编辑工具写 `~/.hermes/`、`~/Library/LaunchAgents/`、Claude Code 用户设置。负向验证：`evidence/relay02-r2-20261031/executor-deny-test.*`，8 项越权操作全部被拒，对照项正常执行。
2. **事后检测（强制）**：驱动每轮送审前和 PASS 收口前查一次「任务开工后被合并的 PR」，查到就停下通知（退出 20），不发 PASS。查询失败也停下（不能确认就不放行）。
3. **任务消息里的明文要求**：不要合并、不要安装、不改正式配置、不发飞书消息，被拦就停下写进送审包，不许换办法绕过。

**残余风险（如实记录）**：deny 规则按命令前缀和路径匹配，执行方如果刻意绕（`bash -c`、写个脚本再执行、`git push origin 分支:main`、用 `cp` 写进 `~/.hermes/`），规则拦不住；GitHub 私有仓库在免费账户下不能开分支保护（实测 `branches/main/protection` 返回 403「Upgrade to GitHub Pro」），所以服务器端也没有兜底。第 2 层能事后发现越权合并，发现不了直接推 main 和本机正式环境改动。是否接受这一残余风险由常浩决定；在他接受前，执行方只跑本仓库的开发任务，不派涉及正式环境的任务。

## 5. 实测发现

- **ORCA 终端里的 Claude 要带代理启动**：Orca 终端里没有代理环境变量，`claude` 直连 Anthropic 被拒（`API Error: 403 Request not allowed`）；系统代理是 `127.0.0.1:8086`，但命令行程序不会自动使用。另外 Orca 用 shell 函数包装了 `claude`，把 `CLAUDE_CONFIG_DIR` 指到它自己管理的配置目录。启动命令统一为：
  `HTTPS_PROXY=http://127.0.0.1:8086 HTTP_PROXY=http://127.0.0.1:8086 command claude --permission-mode auto --settings <仓库>/orca/executor-settings.json`（用默认登录，auto 模式，带执行层拦截）。首次在新目录启动可能会问是否信任该文件夹。
- **新会话先用临时编号**：在项目首页开新会话，发送后地址先是 `/c/local-chatgpt%3A…`，服务器分配真实编号后才换掉。RELAY-01 曾把临时编号当成会话，真实编号出现时报「会话变了」（送审包其实已发出）。已修：`conversation()` 把临时编号当作还没进入会话。
- **续跑收回执要等**：思考强度「高」时回复要几分钟；续跑走 collect 时，驱动在送审超时内反复收，不再看一眼就报错。
- **思考强度读数会变**：切到一个会话后，强度按钮先显示默认的「中」，约 1 秒后才换成该会话记住的值。所以 relay 要连续两次读数一致才判断；先读到瞬时的「高」、随后稳定在「中」，也会调高。
- `orca terminal send --enter` 遇到 Orca 认为 Claude 界面上有确认提示时会拒收（`agent_prompt_blocked`）；原样字节（不带 `--enter`，用 `\r`）不受影响。驱动不改发送方式（原样字节会把任务文字打进确认菜单里），而是把这个错误码当作「确定没发出」：撤掉交付记录、立即停下通知，人到终端处理菜单后重跑同一命令即可重发，不用 `--confirm-not-received`，也不会空等到就绪超时。

## 6. 已知限制

- 驱动由一个进程跑完一个任务；多个任务排队、任务完成后自动接下一个，是下一批的事。
- 越权合并检测按「任务开工后被合并的 PR」算：驱动运行期间，总控也不能合并别的 PR，否则会误报停下。
- 驱动只看就绪文件，不看 Claude 有没有真的开始干活：任务交出去后 Claude 报错停住（如上面的 403），驱动会等到超时才报。
- ~~ChatGPT 的 GitHub 连接器读不到 digital-twin（404）~~：历史限制。常浩 10-31 把连接器的仓库访问设为「所有仓库」后，PR #40 第 1 轮审核已通过连接器独立读取 PR #40、HEAD、Issue #37/#38 和 PR #39。连接器不跑测试，测试结果仍以送审包里的原样输出为准。
- 共用浏览器标签在驱动运行期间不能人工操作（RELAY-01 已记）。

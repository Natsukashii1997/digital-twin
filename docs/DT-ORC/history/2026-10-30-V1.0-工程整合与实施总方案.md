# Hermes Digital Twin × ORCA 工程整合与实施总方案 V1.0

**项目代号：** DT-ORC（建议新增独立集成支线）  
**项目类型：** 现有系统架构优化与多 Agent 执行能力增强  
**方案日期：** 2026-10-30  
**当前状态：** 技术路线确定，待隔离环境核验与分批开发  
**工程原则：** 兼容优先、增量建设、隔离验证、独立验收、审批放行

---

## 一、项目背景与目标

### 1.1 项目背景

数字分身项目目前围绕两条主线推进：

- **Hermes Digital Twin：** 负责理解个人目标、管理项目、调度任务、处理执行结果、异常恢复、通知与审批。
- **Obsidian 第二大脑：** 负责长期知识与记忆的整理、检索、消化和维护。

现有 Hermes 工程已建设状态管理、任务调度、CLI Worker、Git Worktree 隔离、执行回执、独立验收和通知基础设施。

但多 Agent 协作仍存在进一步提升空间：

1. Agent 启动与终端管理需要维护自有执行代码。
2. 不同 Agent 之间的任务交接仍有上下文传递成本。
3. 并行开发、独立审查、返修与复验尚未形成统一的可视化协作运行环境。
4. 执行异常、终端状态、项目状态之间需要更可靠的对账。
5. 现有开发协同能力与未来数字分身的自主项目推进目标尚未完全统一。

本次引入 ORCA，重点解决以上问题，不推翻已完成的工程成果。

### 1.2 总体建设目标

建立一套由 Hermes 主导、ORCA 托管执行环境、多个专业 Agent 共同完成任务的项目制协作系统。

目标工作流：

**用户提出目标 → Hermes 分析和拆解 → ORCA 创建协作任务 → Claude Code 开发 → Codex 独立验收 → Claude Code 定向返修 → Codex 复验 → Hermes 判断放行与汇报。**

最终应满足五项目标：

| 目标 | 具体要求 |
|---|---|
| 统一环境 | 在 ORCA 中查看 Hermes、Claude Code、Codex 的终端、工作树和执行状态 |
| 结构化协同 | 任务有负责人、范围、依赖、状态、交付物和验收标准 |
| 自动化闭环 | 支持受约束的派单、执行、验收、返修和复验 |
| 长期连续性 | Hermes 的记忆、目标、项目状态和审计记录不依赖单一 ORCA 会话 |
| 安全可恢复 | 支持幂等、异常对账、权限隔离、人工审批和 Legacy 回退 |

### 1.3 本轮不追求的能力

本轮不建设完整无人值守数字分身，不重写 ORCA，也不优先开发新的协同桌面 UI。

以下功能排除在当前集成开发范围之外：

- G6 自主开单和 G7 真实取消的生产启用。
- K2-05 自动知识周报及正式 Vault 写入。
- 未获授权的飞书真实通知与自动部署。
- ORCA 移动端、远程服务器、多设备协作。
- 自动合并主分支或自动修改正式环境配置。

这些能力保留为后续独立阶段。

## 二、最终目标架构

### 2.1 采用双平面架构

**业务控制平面：Hermes Digital Twin**

负责：

- 用户目标与项目管理；
- 长期记忆、上下文和知识检索；
- 任务规划与优先级；
- 执行策略与权限判断；
- 结果验收和项目状态；
- 异常恢复与审批；
- 飞书及其他外部入口。

**协作执行平面：ORCA**

负责：

- CLI Agent 启动和终端托管；
- 多 Agent Run/Task/Dispatch 管理；
- Agent 间消息和执行回执；
- Git Worktree 隔离；
- Worker 状态监测；
- 执行输出和工作证据管理。

### 2.2 Agent 角色定义

| 角色 | Agent | 核心职责 |
|---|---|---|
| 项目 Coordinator | Hermes | 定义任务、分配工作、处理依赖、监督执行、组织验收 |
| Developer | Claude Code | 方案实现、代码编写、单元测试和定向返修 |
| Reviewer | Codex | 独立代码审查、反例测试、缺陷定位、复验 |
| Owner | 用户 | 关键决策、权限授权、生产变更审批 |
| Runtime | ORCA | 执行托管、消息、终端、任务运行态和资源生命周期 |

这里的 Coordinator 是 Hermes 的**逻辑角色**，不是必须由一个永久存在的 ORCA 进程独占。

日常交互使用 ORCA 中的 Hermes TUI；现有外部入口继续通过 Hermes 的业务状态系统工作。

不得让两个并发 Hermes 入口在没有租约或幂等保护的情况下，同时调度同一个任务。

### 2.3 系统真源定义

必须区分四类系统事实。

| 事实类型 | 权威来源 |
|---|---|
| Goal / Task 的业务状态和验收结论 | Hermes `twin_state` |
| Worker、Dispatch、终端运行事实 | ORCA Runtime |
| Git Commit、PR、代码与测试产物 | Git / GitHub |
| 长期知识、个人认知和记忆内容 | Obsidian Vault |

Hermes 可以缓存 ORCA 的运行状态，但不能自行宣称 Worker 已退出。

ORCA 可以记录某个任务执行完成，但不能直接宣称 Hermes 的业务验收已通过。

### 2.4 技术结构

用户 / 飞书 / ORCA Hermes 终端  
↓  
Hermes Goal & Task Manager  
↓  
Hermes Scheduler / Policy / Approval  
↓  
Execution Backend Interface  
↓  
Legacy Backend 或 ORCA Backend  
↓  
ORCA Run / Task / Dispatch  
↓  
Claude Code / Codex Workers  
↓  
代码、测试、审查、验收证据  
↓  
Hermes 状态对账与项目汇报

**核心约束：同一业务 Task 的一次执行只能由一个 Backend 负责。**

## 三、现有模块的改造策略

采用“保留、适配、替换候选、新增”四种处理方式。

| 现有模块 | 策略 | 具体处理 |
|---|---|---|
| `twin_state.py` | 保留并适配 | 保留 Goal/Task/Run/Event/Ref 及独立验收语义 |
| `twin_scheduler.py` | 保留 | 保持业务调度能力，增加 Backend 选择机制 |
| `dispatch.py` | 保留为 Legacy Backend | 不直接删除，供回退和兼容测试 |
| `run_worker.py` | 替换候选 | ORCA 负责的任务不再重复启动原 Worker |
| 现有 Git Worktree 机制 | 替换候选 | ORCA 执行分支优先采用 ORCA Worktree |
| `twin_notify.py` | 保留 | 与 ORCA 执行适配分开演进 |
| 本地 Inbox / 飞书通知 | 保留 | 后续仅增加 ORCA 事件映射，不提前启用真实投递 |
| Vault 检索与记忆 | 保留 | 不纳入 ORCA 的内部状态存储 |
| 现有项目文档与验收记录 | 保留 | 仅新增集成设计和版本变更记录 |

### 3.1 新增 Execution Backend 抽象

建议增加独立的执行后端接口，能力包括：

- `probe`：检查运行环境；
- `prepare`：准备执行上下文；
- `dispatch`：启动执行；
- `inspect`：查询状态；
- `collect_evidence`：收集证据；
- `reconcile`：执行对账；
- `request_cancel`：请求停止；
- `finalize`：结束并归档执行记录。

它不是全新项目管理系统，而是隔离执行后端差异的适配层。

**Legacy 与 ORCA 只允许作为可替换的执行实现，不分别维护一套业务目标和验收状态机。**

### 3.2 不提前修改正式状态库

第一阶段先完成字段映射与兼容设计。

如果既有状态字段足够，可通过隔离映射文件或侧表进行 PoC。

如果必须新增数据库结构，应先完成：

1. Schema 差异设计。
2. 隔离迁移测试。
3. 并发读写与幂等测试。
4. 备份、恢复和历史事件兼容测试。
5. 独立审批。

不得为了引入 ORCA，顺带执行 G5 的正式 v3→v4 迁移。

## 四、核心协作协议设计

### 4.1 Task Contract：标准任务契约

Hermes 在派单前必须生成结构化契约。

建议必填字段：

| 字段 | 含义 |
|---|---|
| `goal_id` | 所属长期目标 |
| `task_id` | Hermes 业务任务 ID |
| `objective` | 本次任务的可验证目标 |
| `scope` | 允许修改的范围 |
| `constraints` | 禁止操作和技术约束 |
| `dependencies` | 前置任务 |
| `owner_agent` | 执行 Agent |
| `review_agent` | 独立验收 Agent |
| `acceptance` | 验收标准 |
| `evidence_required` | 必需证据 |
| `retry_policy` | 返修与失败重试规则 |
| `approval_policy` | 审批规则 |
| `contract_version` | 契约版本 |

契约一经派单，不得在后台静默修改其验收标准。

出现实质性范围变化时，应记录新版本，并重新确认受影响的执行任务。

### 4.2 双层状态与 ID 映射

ORCA 的 Run 与 Hermes 的 Run 不是同一个概念。

建议：

- Hermes Goal：长期目标。
- Hermes Task：业务任务。
- Hermes Run：一次业务执行尝试。
- ORCA Run：一次协作任务集合及协调者消息空间。
- ORCA Task：开发、测试、审查或返修等执行工作项。
- ORCA Dispatch：某个 ORCA Task 的具体执行尝试。

新增最小映射记录：

`hermes_task_id / hermes_run_id / backend / orca_run_id / orca_task_id / dispatch_id / terminal_handle / worktree_ref / commit_sha / observed_status / observed_at`

同时保存任务契约版本和幂等键。

一个 Hermes Task 可以关联多个 ORCA Task，但一次有效执行尝试只能有一个当前权威 Dispatch。

### 4.3 消息与结果交接

统一消息类型：

- `TASK_ASSIGNED`：任务派发。
- `QUESTION`：Agent 请求澄清。
- `PROGRESS`：阶段进度。
- `WORKER_DONE`：执行方提交完成结果。
- `REVIEW_FAILED`：验收未通过。
- `REWORK_REQUESTED`：返修任务。
- `REVIEW_PASSED`：验收通过。
- `ESCALATED`：需要人工干预。

以上属于建议的业务语义类型，不要求 ORCA 原生支持全部同名消息。

在 ORCA 内，应使用其当前版本实际支持的消息与状态接口完成映射。

关键规则：

- 消息成功入队不代表接收方已读。
- 读到完成回执不代表验收通过。
- 收到心跳不代表任务完成。
- 接收 Delivery 后应先处理消息，再执行 ACK。
- 任一来源不可验证时保持 `unknown`，不自动推断为失败或成功。

### 4.4 独立验收协议

必须保留现有 Hermes 的“执行完成不等于验收完成”规则。

Claude Code 提交开发结果时，至少提供：

- 代码 Commit SHA；
- 修改文件清单；
- 测试命令与退出码；
- 测试结果；
- 尚未解决的问题。

Codex 独立验收时，至少检查：

- 是否符合原始 Task Contract；
- 是否修改了超出授权范围的文件；
- 是否通过必要测试；
- 是否存在回归或安全问题；
- 证据是否与对应 Commit SHA 一致；
- 是否满足全部关键验收标准。

Codex 应在独立的审查工作树中验证指定提交，不得依赖 Claude 的总结替代独立检查。

Codex 提供验收结论及证据，Hermes 负责确认是否满足业务状态转换条件。

### 4.5 自动返修协议

初始策略：

- 开发执行失败和代码验收失败分别处理。
- 代码验收失败时，允许自动创建返修任务。
- 自动返修最多两轮。
- 每轮返修必须提交新的 Commit SHA。
- 每轮必须重新执行相应验证。
- 两轮仍不通过则升级为人工决策阻塞。

以下情况不得自动返修：

- 任务契约需要重新定义；
- 可能涉及敏感数据或生产环境；
- 已触及明确的审批门禁；
- 执行状态不明确；
- 无法证明上一 Worker 已结束；
- 环境错误无法归因于代码缺陷。

## 五、执行可靠性与恢复设计

### 5.1 状态恢复

Hermes 重启、ORCA 关闭、终端失联后，按以下顺序恢复：

1. 读取 Hermes 业务 Task 和 Run。
2. 查询持久化的 ORCA ID 映射。
3. 查询 ORCA Runtime 当前任务与 Worker 状态。
4. 检查对应 Git Worktree、Commit 和交付证据。
5. 对比 Hermes 与 ORCA 状态，生成对账结论。
6. 仅在具有明确证据时恢复、重试或结束任务。

失联、超时、未找到 Worker 都不能单独作为“Worker 已退出”的证明。

### 5.2 幂等与去重

创建任务、启动执行、接收回执和执行恢复均需要可重复调用。

要求：

- 同一业务意图不得重复创建多个有效 Worker。
- 丢失启动回执时，优先使用 ORCA 支持的查询或重放机制核实原操作。
- 新旧 Dispatch 的结果不能相互覆盖。
- 迟到回执只记录证据，不能覆盖更新一代的业务运行状态。
- 取消必须区分“已请求停止”和“已确认停止”。

### 5.3 执行环境边界

Developer 与 Reviewer 默认使用独立 Worktree。

第一阶段禁止：

- 多名 Agent 同时写同一个工作目录；
- Worker 直接写正式 Vault；
- Worker 使用生产数据库进行测试；
- 在执行环境中自动获取超出任务所需的凭证；
- 自动执行 Git Merge、Push 或生产部署。

工作树隔离不等于权限隔离。涉及凭证和运行环境的文件仍须单独控制。

## 六、工程实施阶段

采用独立支线推进，不打乱 G5 与 K2 原定验收顺序。

### ORC-00｜现状审计与架构冻结

**目标：** 明确 ORCA 与现有数字分身的真实接入边界。

工作任务：

1. 读取当前 `digital-twin` 项目结构和版本。
2. 检查既有 G4/G5 设计与验收基线。
3. 检查 ORCA 安装版本、CLI 注册状态和 Orchestration 配置。
4. 检查 Hermes、Claude Code、Codex CLI 可用性。
5. 对比现有 Worker、Worktree、状态和消息实现。
6. 输出能力差异与冲突清单。
7. 冻结第一版适配边界。

**交付物：**

- ORC-00 现状审计报告；
- 现有模块影响矩阵；
- ORCA 能力与版本基线；
- V1.0 架构决策记录（ADR）。

**验收闸门：**

现有工程基线清楚，ORCA 关键能力已经核实，无未解释的执行权冲突。

本批仅进行授权的只读检查与文档工作，不改正式环境。

### ORC-01｜统一终端与双 Agent PoC

**目标：** 在 ORCA 中跑通真实的多 Agent 协作。

工作任务：

1. 让 Hermes 在 ORCA 中稳定启动。
2. 验证 Hermes 使用正确的配置及上下文。
3. 建立独立测试仓库与 Worktree。
4. 使用 ORCA 创建 Run、Task 和 Dispatch。
5. 派发 Claude Code 完成小型开发任务。
6. 派发 Codex 对指定提交独立审查。
7. 触发至少一次可复现的定向返修。
8. 收集完整任务、消息、测试和提交记录。

**交付物：**

- 完整 PoC 运行记录；
- 开发与验收结果；
- 一次返修闭环证据；
- Agent 兼容性和异常清单。

**验收闸门：**

Hermes 能通过 ORCA 正确派单并接收结果；Claude 和 Codex 能完成开发—验收—返修—复验链路，无需人工复制上下文。

### ORC-02｜协作协议与自动返修

**目标：** 把成功的 PoC 固化为可重复的工程协议。

工作任务：

1. 实现 Task Contract 校验。
2. 实现任务依赖与状态转换规则。
3. 实现标准化开发交接记录。
4. 实现独立验收记录。
5. 实现失败原因分类。
6. 实现受控返修次数与预算限制。
7. 实现 Worker 状态异常处理。
8. 编写正向和负向测试。

**交付物：**

- Task Contract Schema；
- Agent 协作协议；
- 自动返修控制逻辑；
- 协议级测试报告。

**验收闸门：**

正常完成、验收失败、Worker 失联、超时、重复回执、任务变更等场景均有明确的状态与处理路径。

### ORC-03｜Hermes 执行后端集成

**目标：** 将 ORCA 作为 Hermes 的可切换执行后端。

工作任务：

1. 定义 Execution Backend 接口。
2. 将原执行链路封装为 Legacy Backend。
3. 开发 ORCA Backend。
4. 实现 Hermes / ORCA ID 映射。
5. 实现任务执行、状态查询与证据回收。
6. 实现恢复对账。
7. 实现幂等派单。
8. 实现 Backend 选择及回退机制。
9. 执行现有测试和新增隔离回归。

**交付物：**

- Execution Backend Interface；
- ORCA Backend Adapter；
- 状态与 ID 映射组件；
- 对账与恢复逻辑；
- Legacy 兼容性测试报告。

**验收闸门：**

同一任务不会双重派单；ORCA 运行事实可正确映射到 Hermes；原有 Legacy 执行行为没有因新增后端而破坏。

### ORC-04｜项目管理与审批集成

**目标：** 将 ORCA 协作流程纳入 Hermes 项目制推进体系。

工作任务：

1. 将 Goal / Task 与 ORCA 执行批次建立关联。
2. 将执行结果关联回 Hermes 的证据与验收记录。
3. 将阻塞、返修、待审批事项映射到现有状态系统。
4. 接入本地只读进度与任务查询。
5. 设计飞书通知映射，不提前开启真实发送。
6. 完成审批身份和动作授权边界测试。
7. 完成业务状态迁移与兼容性审查。

**交付物：**

- Hermes / ORCA 项目状态映射方案；
- 审批与通知集成适配；
- 状态查询与项目汇报模板；
- 权限和异常验收报告。

**验收闸门：**

Hermes 能准确汇总 ORCA 任务进展，同时保留用户审批、通知呈现与动作授权之间的独立边界。

## 九、工程验收体系

采用四级验收机制。

| 层级 | 验收对象 | 核心标准 |
|---|---|---|
| L0 环境 | CLI、Runtime、配置 | 可连接、可识别、可重复 |
| L1 执行 | Worker、Dispatch、Worktree | 有状态、可追踪、可恢复 |
| L2 技术 | 代码、测试、接口、协议 | 独立测试与代码复核通过 |
| L3 项目 | 目标、任务、权限、验收结论 | 满足业务契约与审批要求 |

### 强制负向测试

至少覆盖：

1. ORCA CLI 不可用。
2. ORCA Runtime 中断。
3. Hermes 会话中断。
4. Worker 无法启动。
5. Worker 启动成功但回执丢失。
6. Worker 失联但仍在运行。
7. 同一任务重复派单。
8. 旧 Dispatch 回执迟到。
9. Codex 验收不通过。
10. Claude 两轮返修仍不通过。
11. 任务已取消但 Worker 尚未退出。
12. 未授权 Agent 请求合并或部署。
13. 工作树存在未提交修改。
14. 测试证据对应错误 Commit SHA。
15. Backend 切换期间出现状态不一致。

### 最低成功标准

- 不发生未经授权的重复派单。
- 不发生未授权生产写入。
- 不发生旧执行结果覆盖新任务状态。
- 不发生无证据的自动验收通过。
- 所有阻断级异常有可追溯记录。
- 关键恢复场景完成独立复测。
- Legacy 路径保持可用。
- 任一生产动作必须通过原审批门禁。

## 十三、最终架构决策

**ADR-ORC-001：** ORCA 是统一多 Agent 工作环境和协作执行平台，不取代 Hermes 数字分身大脑。

**ADR-ORC-002：** Hermes 在 ORCA 中承担日常 Coordinator 角色，优先通过 ORCA CLI 和 Orchestration 原生机制调度 Worker。

**ADR-ORC-003：** Claude Code 负责开发，Codex 负责独立验收，返修由 Hermes 按明确策略协调。

**ADR-ORC-004：** Hermes 业务状态、ORCA 执行状态、Git 工程事实、Vault 长期记忆分别由各自系统负责。

**ADR-ORC-005：** 现有执行链路暂不删除。通过 Execution Backend 抽象逐步引入 ORCA，保留 Legacy 回退能力。

**ADR-ORC-006：** 多 Agent 执行完成不得自动等同于验收通过。

**ADR-ORC-007：** 自动重试、返修、恢复必须有明确的状态、次数、权限和证据约束。

**ADR-ORC-008：** 既有 G5、G6、G7 和 K2 工程的开发与部署审批边界维持不变。

**ADR-ORC-009：** DT-ORC 必须通过隔离 PoC、协议测试、后端集成、影子运行和独立验收，才能申请接管正式执行链路。

**最终目标：构建一套可持续演进、可观察、可验收、可恢复的 Hermes 主导型多 Agent 数字分身工程系统。**

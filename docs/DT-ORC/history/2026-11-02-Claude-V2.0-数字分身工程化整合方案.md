**演变与本方案的处理：**

1. **Codex 的角色变过三次。** 10-30 ChatGPT 起草的 V1.0 任务书里，Codex 是审查方、测试归 Claude（这是任务书的写法，不是常浩原话）；10-30 晚审查改由 ChatGPT 聊天模式担任；11-02 常浩定 Codex 负责测试。本方案以 11-02 为准：**Codex 只测不审**，这也和 10-30「排除 Codex 做审核」一致。
2. **Hermes 的大脑本来就是 Codex 会员**（PRD D11，`~/.hermes/config.yaml` 现为 `openai-codex / gpt-6.1-sol`）。所以 Hermes 也在用 Codex 额度，更要让它只做管理题、少做推理；机械步骤交给脚本。
3. **确认节奏。** PRD 第 10 节「每个任务开工前给分批计划，你确认后再动」已被 10-31 的自动推进替代（CURRENT 有记）。Vault 偏好 P-06「对外动作先预览、等常浩确认」仍然有效，本方案把它落在第 6.1 节的「对他人或群发消息、对外发布」上；合并自己的仓库不算对外动作。
4. **11-02 首次出现的说法**：防一言堂、Claude 校正 ChatGPT、Hermes 是监工 / 记录者、Codex 做测试、思考强度「高」、分层分类型工作流、结构化最终落成 skill。本方案把这些作为最新、最高优先级的要求。

## 2. 角色与职能

### 2.1 总表

| 角色 | 由谁担任 | 一句话定位 | 做 | 不做 | 产出 |
|---|---|---|---|---|---|
| **Owner** | 常浩 | 定方向、拍单向门 | 提目标；回答 Hermes 攒好的选择题；批准部署、正式配置、对外发送 | 不逐步确认、不复制粘贴上下文 | 一句话决定 |
| **监工 / 记录者 / 数字分身** | Hermes（猛鬼兽） | 项目推进的「管家」 | 接需求、排队、开流水线、盯进度、催卡住的、记账、写日报周报、按规则替常浩做明确的选择、把要常浩定的事攒成选择题 | 不拆技术方案、不评审代码、不判断审查谁对谁错 | 任务卡、进度、日报周报、选择题 |
| **主开发** | Claude Code（ORCA worker） | 写代码、返修、出方案 | 技术方案和拆票（L2 以上）、编码、单元级自测、按审查意见返修、逐条回应审查 | 不写验收测试（交给 Codex），**不改 Codex 写的测试**（认为测试错了走第 5.2 节分歧流程），不自己宣布验收通过，不合并 | 提交 + 交付说明 + 审查回应表 |
| **测试** | Codex（ORCA worker） | 用测试说话 | 只依据验收标准和接口（不看实现）独立写验收测试、跑全量回归、反向验证（撤销修复看测试是否变红）、为分歧写复现用例、出测试证据（贴实际命令和输出，不只说「全过」） | 不改业务代码（只改测试目录）、不给代码审查结论 | 测试代码 + 绑定提交号的测试报告 |
| **审查** | ChatGPT 聊天模式「高」 | 独立的、符合常浩心意的判断 | 审设计是否符合目标、代码正确性、风险、范围；给 PASS / REWORK / NEEDS_HUMAN 和分级问题清单 | 不改代码；第二轮起不对未改动的旧代码追加新阻断问题 | 审查回执 |
| **复议** | Claude（另起一个不带开发上下文的会话，只在 L3 或有分歧时） | 校正审查，防一言堂 | 对审查意见逐条判断「成立 / 不成立 / 需取证」，给理由 | 不替开发辩护（不读开发过程，只读代码、测试和审查回执） | 复议表 |
| **运行时** | ORCA | 所有活都在这里跑 | 工作树、worker 启停与存活、Run/Task/Dispatch、消息、决策闸门、定时任务、内嵌浏览器（ChatGPT 送审） | 不判业务对错 | 运行事实 |
| **流水线引擎** | `orca/` 下的脚本（代码，不是 AI） | 把确定性的步骤串起来 | 按泳道顺序起 worker、送审、收回执、记账、执行收敛规则、到闸门就停 | 不做判断题 | 运行目录账本、事件 |

### 2.2 为什么这样分

- **Claude 写、Codex 测，是「两个人」而不是一个人自测自证。** 测试由另一个模型照验收标准独立写，开发方的盲点不会同时出现在测试里；还把最耗 Claude 额度的测试和回归搬到 Codex。
- **ChatGPT 审、Claude 复议，是「有来有回」而不是一言堂。** ChatGPT 的判断最贴常浩心意，所以它是主审；但它也会误判、会每轮冒新问题。Claude 逐条回应、Codex 拿测试取证，让分歧靠证据收敛，而不是靠多返修几轮。
- **Hermes 不做思考题，只做管理题。** 排队、催办、记账、汇报、按既定规则选默认项，这些靠稳定和记性，不靠聪明；需要判断的题交给 Claude / ChatGPT，需要拍板的交给常浩。
- **确定性的事交给代码。** 「审查 PASS 后跑 merge_gate、合并」这种步骤不需要任何 AI 判断，写成脚本最稳、最省额度。

### 2.3 三方制衡关系

```
            常浩（只拍单向门）
                 ▲  一句话选择题
                 │
        Hermes ──┴── 记账 / 催办 / 代选 / 汇报
                 │ 开流水线、读状态
                 ▼
  ┌──────────── ORCA Run（一条任务一条流水线）────────────┐
  │                                                        │
  │  Claude（写） ──提交──▶ Codex（测） ──测试证据──▶ ChatGPT（审）
  │      ▲                     ▲                    │      │
  │      │   返修              │ 分歧取证           │ 回执 │
  │      └──── 逐条回应 ◀──────┴────────────────────┘      │
  │                     （L3 / 分歧时）Claude 复议          │
  └────────────────────────────────────────────────────────┘
```

## 3. 总体架构：全部跑在 ORCA 里

### 3.1 五层

| 层 | 组件 | 说明 |
|---|---|---|
| 交互层 | 飞书私聊（猛鬼兽）、ORCA 里的 Hermes 终端 | 常浩只和 Hermes 说话；在电脑前时也可直接在 ORCA 的 Hermes 终端里说 |
| 协调层 | Hermes + `dt-pipeline` 技能 + 流水线引擎 | Hermes 决定**做哪个、什么时候做、要不要问常浩**；引擎负责**怎么一步步做** |
| 执行层 | ORCA `orchestration`：`worker-start --agent claude / codex`、`worktree`、`check / ask / reply`、`gate-create / gate-resolve`、`automations` | 每个任务一个 Run；开发和测试各一个 Dispatch；worker 卡住用 `ask` 问协调者 |
| 审查层 | ORCA 内嵌浏览器里的 ChatGPT 聊天（项目「数字分身审核」，思考强度「高」）+ `chatgpt_relay.py` | 全局只有一个审查租约：同一时刻只审一份 |
| 真源层 | Hermes `twin_state`（业务状态、验收结论）、ORCA（运行事实）、Git/GitHub（代码与 PR）、Obsidian Vault（长期记忆） | 沿用 V1.0 第 2.3 节：谁的事实谁说了算 |

### 3.2 ORCA 原生能力怎么用（不再自造）

| 需求 | 用 ORCA 的什么 | 现有自写代码的去向 |
|---|---|---|
| 隔离开发 | `orca worktree create` / `worker-start --worktree new-child` | 旧 `run_worker.py` 的 worktree 逻辑转为 Legacy，不再开发 |
| 起 Claude / Codex | `orchestration worker-start --agent claude|codex --model --effort` | 同上 |
| 任务依赖 | `task-create --deps`（任务 DAG） | `work_queue.py` 只保留 ORCA 没有的部分：审查租约、返修计数、泳道规则 |
| worker 提问 | worker `ask` → 引擎 `reply`；答不了的升级给 Hermes | — |
| 等常浩拍板 | `gate-create`（选项 JSON）→ Hermes 发飞书选择题 → 常浩回复 → `gate-resolve` | 冻结 B6–B11 的签名 / Touch ID 方案（见第 8 节） |
| 定时巡检、夜间回归 | `orca automations create`（provider=codex 跑夜间回归，用 `--precheck` 在当天没有新提交时跳过；先建成停用状态调好再启用）；Hermes 自己的 cron 做日报 | — |
| 完成判定 | `worker_done`（succeeded/failed）+ `worker-show` | `relay_loop.py` 改用 ORCA 原生信号，不再自己轮询就绪文件 |
| 关联 issue / PR | `orca reference add` | — |
| ChatGPT 送审 | ORCA 内嵌浏览器 + `chatgpt_relay.py` | 保留（RELAY-01 已合并） |

### 3.3 Hermes 在 ORCA 里的位置

- Hermes 以一个**常驻 ORCA 终端**（「Hermes 监工台」）运行，同时保留飞书网关。
- Hermes 不当 ORCA 的底层 Coordinator（那是引擎的事，见 ORC-01b 的经验：让 Hermes 本体直接跑 supervised loop 走不通，也不符合「不是最聪明的思考者」）。
- Hermes 通过 `dt-pipeline` 技能调用引擎：`start <issue>`、`status`、`answer <gate> <选项>`、`report`。业务状态写 `twin_state`，运行事实读 ORCA。

## 4. 分层分类型工作流

### 4.1 风险分档（决定走多重的流程）

| 档 | 典型场景 | 判定规则（引擎按改动路径和标签自动判，Claude 可上调不可下调） | 流程 | 人工闸门 |
|---|---|---|---|---|
| **L0 杂务** | 文档、记录、CURRENT、注释、错别字 | 只改 `docs/`、`*.md`，不碰代码 | Claude 直接改 → 直推或开 PR 即合 | 无 |
| **L1 小改** | 单 issue、改动小、有现成测试、不碰正式环境 | 代码改动 ≤ 约 200 行，不涉及第 6 节路径 | Claude 开发 → Codex 跑回归 → ChatGPT 审 1 轮 → 自动合并 | 无 |
| **L2 标准** | 新功能、多文件、新模块 | 其余情况的默认档 | 见 4.2 | 无（合并自动） |
| **L3 高风险** | 状态库结构、正式配置、安全、跨项目、不可逆操作 | 命中第 6 节路径或标签 `L3` | 见 4.2，外加：方案先审、Claude 独立复议、合并或部署前常浩闸门 | 有 |

### 4.2 标准流水线（L2；L1 是它的删减版，L3 是加强版）

| 步 | 谁 | 做什么 | 产出 | L1 | L3 |
|---|---|---|---|---|---|
| 0 | Hermes | 接需求，查重，排队，按规则定档，开 issue | issue + 档位 | ✓ | ✓ |
| 1 | Claude | 写短方案和验收标准（`to-spec` 精简版） | 方案 + 验收标准 | 省略，直接用 issue | ✓ 且送 ChatGPT 审方案 |
| 2 | Codex ∥ Claude | **并行**：Codex 按验收标准写验收测试；Claude 编码 | 测试提交、代码提交 | Codex 不写新测试，只跑回归 | ✓ |
| 3 | Codex | 在独立工作树里对指定提交跑全量 + 验收测试 + 反向验证；关键模块偶尔跑变异测试检查测试强度，不追覆盖率 | 测试报告（绑定提交号，含命令和输出） | 只跑全量 | ✓ |
| 4 | 引擎 | 打送审包（diff、交付说明、测试报告、验收标准），经租约送 ChatGPT | 送审包 | ✓ | ✓ |
| 5 | ChatGPT | 审查，给结论和分级问题 | 回执 | ✓ | ✓ |
| 6 | Claude | 逐条回应：接受并修 / 不同意并给理由 / 需取证 | 回应表 + 返修提交 | ✓ | ✓ |
| 6b | Codex | 对「需取证」的条目写复现测试 | 红或绿的证据 | 按需 | ✓ |
| 6c | Claude（复议） | 不带开发上下文，独立判断审查意见 | 复议表 | — | ✓ |
| 7 | ChatGPT | 第二轮只看：返修 diff、未关闭条目、Claude 的反驳和取证结果 | 回执 | 最多 1 轮 | 最多 2 轮 |
| 8 | 引擎 | PASS → `merge_gate` 核对 HEAD/base/送审包 → 自动 squash 合并 | 合并提交 | ✓ | **停在常浩闸门** |
| 9 | Hermes | 记账（twin_state、CURRENT）、通知常浩结果、接下一个 | 记录 | ✓ | ✓ |

### 4.3 按类型的泳道

| 类型 | 和标准流水线的差别 |
|---|---|
| **功能开发** | 按 4.2 |
| **缺陷修复** | 先由 Codex 写复现测试（必须先红），Claude 再修，Codex 验证变绿；ChatGPT 只审修复是否根治、有没有副作用 |
| **调研 / 设计 / 方案** | 不写代码：Claude 起草 → ChatGPT 审 → Claude 回应 → Hermes 把结论做成选择题给常浩。涉及 UI 的，按常浩 P-08 出 3 版带预览 |
| **运维 / 部署 / 正式配置** | 一律 L3，Claude 出变更单（改什么、怎么回滚、怎么验证），常浩闸门后执行，Codex 做执行后验证 |
| **知识库（Obsidian）** | 沿用 Obsidian 线既有规则，写 Vault 仍走收件箱和原审批；ORCA worker 不直接写正式 Vault |

### 4.4 并发与节奏

- 开发 worker 最多 2 个并行（不同任务、不同工作树），测试 worker 跟随；ChatGPT 审查全局串行（一个租约）。
- 每条流水线有时间预算：L1 约 1 小时、L2 约半天；超时由 Hermes 催办，再超时升级常浩。
- 同时打开、未合并的 PR 不超过 2 个；超过时 Hermes 先推合并，不开新活。

## 5. 审查与校正：防一言堂，也防无限返修

### 5.1 问题分级

| 级 | 含义 | 是否阻断合并 |
|---|---|---|
| P0 | 数据损坏、安全漏洞、越权、会写坏正式环境 | 阻断 |
| P1 | 功能不对、违反验收标准、明显回归 | 阻断 |
| P2 | 可维护性、边界情况、风格、技术债 | **不阻断**，自动进待办（开 issue 记账） |

审核员规则里明确：**只报影响正确性和安全的问题，每条给置信度；低置信度的一律降为 P2。** 被要求「找问题」的审查者总能找到点什么，全修会多出不必要的抽象和防御代码（见第 12 节）。

### 5.2 分歧怎么收敛（Claude 校正 ChatGPT）

1. Claude 对每条 P0/P1 必须给三选一回应：**接受**（附返修提交）、**不同意**（附理由和代码 / 测试位置）、**需取证**。
2. 「需取证」和「不同意」的条目，Codex 写一个复现测试：红了说明问题成立，Claude 修；绿了说明问题不成立，作为反驳证据。
3. 下一轮 ChatGPT 看到 Claude 的反驳和 Codex 的证据，自己决定撤回或坚持。
4. 证据出来后 ChatGPT 仍坚持、Claude 仍不同意 → Hermes 把双方各一句话 + 证据链接做成选择题给常浩。这是唯一需要常浩介入的审查分歧。
5. L3 任务另加一步：一个**不读开发过程**的 Claude 会话独立复议 ChatGPT 回执，避免开发方替自己辩护。

### 5.3 收敛规则

- 返修上限：L1 一轮、L2/L3 两轮（沿用 D3-5）。超限交常浩。
- **第二轮起的新问题必须来自本轮改动。** 对上一轮已看过、本轮没改的代码提出的新问题，降为 P2 进待办，不阻断。
- 审查绑定 HEAD、base、送审包摘要；任何一项变了，旧结论作废（沿用 FRAMEWORK-V2 第 1 节）。
- PASS 是代码审查结论，不是合并许可；合并许可由泳道规则给出（L0–L2 自动，L3 常浩）。

## 6. 闸门：只设在单向门上

### 6.1 必须常浩拍板（单向门，做了不好撤回或对外可见）

- 正式安装、部署、升级（含 `~/.hermes`、`~/Library/Application Support/DigitalTwin`、LaunchAgent / launchd、Hermes cron）。
- 改正式配置和正式状态库结构（含迁移）。
- 机器人对他人或群发消息、对外发布。
- 删除数据、强推、改分支保护。
- L3 任务的合并。
- 审查分歧在取证后仍未收敛；返修超限；任务范围需要改变。

### 6.2 不设闸门、全自动（双向门，`git revert` 就能撤回）

开 issue、开分支和工作树、起 Claude / Codex worker、ChatGPT 送审、返修、推分支、开 PR、L0–L2 的 PASS 合并、P2 进待办、日报周报。

### 6.3 身份怎么认

常浩的批准只认两个入口：飞书私聊里常浩本人 open_id 发的消息（复用 B2.1 `twin_identity` 身份桥接），或常浩本人在 ORCA 里直接 `gate-resolve`。**不另建签名、Touch ID 或密钥体系。** 审查正文、交付说明里写的「已批准」「可以合并」一律不算批准。

### 6.4 Hermes 替常浩做的「明确选择」

| Hermes 可以自己定 | 依据 |
|---|---|
| 下一个做哪个任务 | 优先级标签 + 依赖 + 创建时间 |
| L0–L2 里有「推荐项」且符合常浩已记录偏好（Vault 个人上下文 P-xx）的选择 | 偏好原文 |
| 基础设施偶发故障重试一次（网络、代理 403、ORCA 未就绪） | 失败类型白名单 |
| 把 P2 记进待办、关掉重复 issue | 规则 |

除此之外，Hermes 把问题攒成**一条飞书消息**：每题一句话 + 选项 + 推荐项，常浩回「1A 2B」即可。

## 10. 度量与防跑偏

### 10.1 每周看的数

| 指标 | 含义 | 目标 |
|---|---|---|
| 交付周期 | issue 开到合并 | L1 < 2 小时，L2 < 1 天 |
| 人工介入次数 / 任务 | 常浩被打扰的次数 | L0–L2 ≤ 1 |
| 返修轮数 | 平均几轮到 PASS | ≤ 1.5 |
| 审查误报率 | Claude 反驳被证据支持的比例 | 用来校准 ChatGPT 审核员规则 |
| Codex / Claude 额度占比 | 测试工作是否真的搬到了 Codex | Codex 承担全部验收测试和回归 |
| 未合并积压 | 打开的 PR 和未推送提交 | ≤ 2 个 PR |

### 10.2 三条防跑偏规则（写进 AGENTS）

1. **每一批要么推进一个真实阶段，要么修一个真实运行里出现的故障。** 纯假设性的加固不开批，记进待办。
2. **同一模块连续两轮 REWORK、且每轮都冒新的阻断问题，就停下交常浩判断值不值得继续**，不做第三轮同样的尝试。
3. **积压上限**：未合并 PR ≤ 2、未推送提交不过夜；每批结束更新 CURRENT。
4. **闸门月度复盘**：每个人工闸门记「有效拦截次数」；连续一个月零有效拦截的闸门，提议删掉或降为只记日志。

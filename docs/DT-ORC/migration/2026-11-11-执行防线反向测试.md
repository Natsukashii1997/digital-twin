## 一、结论

**#135 不验收，受限会话不成立，托管保持禁用。** 否决理由是 §3.3.1 第 1 项「连宿主除代理外的端口」有两条路径没被拒，任何一条都够否决，不需要证明那些服务已被实际利用。

| 隔离能力 | 判定 | 依据 |
|---|---|---|
| 机器账号直接更新 main（git 推送、Contents API、`PATCH refs`、GraphQL `updateRefs` / `createCommitOnBranch`） | **已测路径全部被拒** | 第三节 1、2 |
| 机器账号直接合并 PR（未审批、常浩批准后、常浩开的 PR，各 16 种方式） | **已测路径全部被拒** | 第三节 2 |
| main 规则对机器账号由 GitHub 服务端强制 | **证据较充分** | `--admin`、REST、GraphQL 都由服务端判 `Repository rule violations`；绕过名单只有仓库 admin 角色；开测前后规则集字节一致 |
| 经脚本、构建工具、直调 API、子进程等途径做以上 GitHub 动作 | **已测路径全部被拒** | 第三节 3 |
| 读宿主文件 | **被拒** | 容器里没有宿主挂载 |
| 容器碰不到宿主上的服务 | **不通过** | ① 经代理 8086 能访问宿主 127.0.0.1 上的服务；② 经宿主局域网 IP 能连监听所有网卡的服务（第三节 1d、1e） |
| 容器碰不到 Colima 虚拟机管理面 | **不通过** | 虚拟机 sshd 经 Docker 网关 `172.18.0.1:22` 和经代理 `127.0.0.1:50055` 都能连上（要密钥，容器里没有；但端口可达本身不算安全） |
| 容器无法经其他服务间接取得合并能力 | **未证明** | 容器已能访问宿主 HTTP 服务；宿主会话持有常浩管理员 `gh` 登录和合并执行器令牌（#132 第五节）。本次只对这些服务做了 GET，没测写接口，也没证明它们够不到凭据 |
| 完整受限会话（规格 §3.3） | **不通过** | 上面两项不通过、一项未证明 |

所以这份记录能支持的说法是：**在当前仓库规则、机器账号身份和令牌下，机器账号不能用已测的 GitHub Git / API 操作直接合并 PR 或更新 `dt-sandbox/main`。** 它不能支持「隔离容器无论经什么渠道都无法自行合并」。

## 四、测试方法的代表性

- **`docker exec` 可以代表的部分**：和 agent 同一个容器、同一个 `node` 用户（uid 1000）、同一个网络命名空间和挂载、同一个 `gh` 登录。GitHub 服务端按令牌身份授权，所以对第三节 2、3 的 GitHub 结论来说，进程是谁起的没有本质区别。
- **不能完全等价的部分**：`docker exec` 起的是独立进程，不一定继承 Multica 实际拉起 agent 时的全部环境变量、工作目录、启动参数、凭据助手，以及运行期注入的 `MULTICA_TOKEN` 等凭据。所以这次证明的是「这个容器的防线」，还没证明「真正执行任务的 agent 进程受同样的防线」。复验 E 组要用一张无副作用的测试子单，在真实执行入口做一次运行态对照（见第六节），不需要启动完整夜跑。
- **`b1` 的退出码**：见证据索引下的「判定依据」。`b1` 里依赖退出码才能判断的只有 D9（正向对照），它的成功有远端新分支和后来开出的 PR #18 佐证。

## 五、修复原则（建议，待常浩定；本单没改任何配置）

**总原则：默认拒绝，按业务需要逐项放行。** 容器的出口只允许去「Multica 内部业务服务」和「一个受控的出口代理」，别的一律拒绝。不靠维护一份私网网段黑名单：宿主会换网络（这两天 IP 就变了一次），也可能多出新网卡、启用 IPv6。

### 1. 三个防护面分开处理

| 防护面 | 现在的问题 | 建议 |
|---|---|---|
| 容器 → macOS 宿主 | 局域网 IP 绕过了过滤；代理会转发到宿主回环 | 容器出口默认拒绝（含 IPv6），只放行受控代理和 Multica 内部服务 |
| 容器 → Colima 虚拟机 | Docker 网关 `172.18.0.1:22` 可达。这段流量走虚拟机的 `INPUT` 链，不经过 `FORWARD`，现有的 `DOCKER-USER`（挂在 `FORWARD` 路径上）管不到 | 在虚拟机的 `INPUT` 链，或在 sshd 的监听地址上，单独拒绝来自容器网段的访问。**不能把 Docker 网桥网段整体当成可信的「Multica 内部网段」**：Multica backend 的业务端口和虚拟机的 SSH、Docker 管理端口要分开授权 |
| 局域网 → Colima ssh 端口转发 | 宿主 `*:53` 对整个局域网开放，背后是虚拟机的 53 端口 | 把转发的监听地址限制在 127.0.0.1，或关掉这项转发；查清它是哪项 Colima 配置开出来的 |

端口能连上就算缺口，不能因为「现在容器里没有 SSH 私钥」判为安全。

### 2. 出口代理：关键是它能连什么，不是它放在哪

推荐在 Colima 虚拟机里另起一个专用出口代理，不再借用宿主上的闪电猫加速器。但光把代理搬进虚拟机不等于安全：新代理如果仍然接受任意 `CONNECT`，风险只是换了个入口。约束如下：

- 只转发白名单里的目标（GitHub、模型 API 等实际需要的域名和 443 端口），不接受任意目的地址和端口；
- 校验时同时看域名和解析出来的 IPv4 / IPv6 地址，并在实际连接时再查一次（防 DNS 重绑定），不只看 URL 文本；
- 拒绝转发到回环、链路本地、宿主地址、虚拟机管理面和未授权的内网地址；
- 代理本身不持有任何 GitHub 管理员凭据或合并执行器凭据；
- 网络策略要在内核层强制：容器即使清掉代理环境变量、用原始套接字，也只能连到代理和 Multica 内部服务。

另一种做法是在 fc-core 里禁止转发到回环和私网，只能作为过渡。fc-core 是宿主上的通用加速器，它的规则不归本项目管，规则漏一条，宿主回环就又暴露了。

### 3. 运行前身份闸（托管启用的前提之一）

每次夜跑 / 托管开跑前自动检查，任何一项不符就关闭托管（fail-closed），不靠一次性人工核对。#132 交接评论提过，`runtime/login-gh.sh` 等入口仍可能把容器引回常浩账号：

1. 容器里 GitHub 实际认证的身份是 `shanhao1997`；
2. 对 dt-sandbox 的权限仍是 write，不是 admin / maintain，也不在任何规则集的绕过名单里；
3. 机器账号能访问的仓库仍只有 dt-sandbox，`gh auth status` 里没有其他账号或令牌；
4. 容器里找不到管理员令牌、合并执行器凭据或其他登录入口（检查 `~/.config/gh/hosts.yml` 的账号数、`git config` 里的凭据助手、环境变量名）。

长期可以考虑改用只装在 dt-sandbox 上的 GitHub App。不建议直接换成 fine-grained 令牌：GitHub 文档列出它在「协作者访问他人名下仓库」的场景下有限制，机器账号正是以协作者身份访问常浩名下的 dt-sandbox（没实测，换之前先核实）。

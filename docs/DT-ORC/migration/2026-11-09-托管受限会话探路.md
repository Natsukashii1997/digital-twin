# 托管受限会话探路（#130）

- 日期：2026-11-09 20:10–20:25（Asia/Shanghai）
- 来由：托管规格（`docs/托管模式-设计.md` §3.3）要求托管只对「受限会话」以常浩身份送达，批 3、批 4 都建立在它上面；本单实测它能不能成立。常浩 11-09 回复「按步骤开始」授权本次实测（含启动 Colima `multica`、在 dt-sandbox 做一次探针合并并回退）。
- 只记事实与结论；令牌值不记。

## 一、四个问题与实测

### 1. 受限执行环境里能不能跑 Claude Code / Codex 会话

能，但形态是 **Multica 拉起的无头 agent**，不是交互会话。隔离执行器容器 `multica-isolated-agent-1`（镜像 `multica-local-agent:0.8.1-claude-2.1.319-codex-0.166.0`，用户 `node`）里装着 Claude Code 和 Codex，由 Multica daemon 按 issue 指派拉起。M1 / M5 共 24 次 run 都是这种形态。单独 macOS 用户的路线需要新建系统用户，本次没做，只在第 2 问做纸面判断。

### 2. 驿窗能不能看到这些会话、拿到「停下等人」的信号、把消息送进去

**不能，而且是隔离本身决定的。** 驿窗与会话之间只有四条通道，全部依赖宿主上的文件或本机进程：

| 驿窗通道 | 依赖（驿窗主干代码） | 容器里能否连上 |
|---|---|---|
| 读会话记录 | 宿主 `~/.claude/projects`、`~/.codex/sessions` | 不能：容器内 `/Users` 不存在，`mount` 里没有任何宿主挂载 |
| 钩子回调（批准卡、完成、注意） | 宿主 Unix 套接字 `app.postpane.mac/hooks/callback.sock`（权限 `srw-------`，属主 nat） | 不能：没有挂载；驿窗在宿主上没有任何 TCP 监听 |
| Claude 插件送达（`asUser`） | 宿主共享文件夹 `app.postpane.mac/claude-plugin`，插件每 5 秒签到取件 | 不能：没有挂载 |
| Codex 送达 | 宿主上 Codex 自己的队列 `thread/queue/add` | 不能 |

从容器试连宿主 `192.168.5.2`：8086（代理）能连上；3501、43100、43101 被拦。这和 M1 的防火墙加固一致（只放行 8086）。

单独 macOS 用户的路线（纸面）：驿窗按用户运行，会话记录在另一个用户的主目录里，套接字权限是 `srw-------`。要接通就得放宽目录和套接字权限，等于让那个用户反向接触驿窗，而驿窗能给常浩的所有会话发消息。

**要接通，就得在隔离上开口子**（挂宿主目录或套接字进容器），这会让受限 agent 接触到能向常浩全部会话发消息的驿窗，违背受限会话的定义。

### 3. 这些会话在实际工作里会不会停下问人

**不会在会话里停下，而是写成 issue。** 统计 `DigitalTwin/runs/` 下 9 组记录、24 次 run，结束时 issue 状态：`done` 11、`in_review` 8、**`blocked` 5**。`blocked` 的那几次，agent 都在 issue 评论里写「需要常浩处理」「需要常浩决定」并给出推荐（例：SBX-4 写「推荐：把规则集的排除项改成 `refs/heads/agent/**/*`」；另一单写「需要常浩决定：在运行环境装好 Python 3.11 + pytest；给 git 配一个提交身份」），然后结束这次 run。

也就是说，受限世界里的「待决事项」信号是 **Multica issue 进入 `blocked` + 一条评论**，不是驿窗的完成钩子。

### 4. 容器里的凭据能不能「只推分支、不能合并、不能推 main」

**推 main、推非 `agent/` 分支：不能（M1 已证）。合并：能——这是缺口。**

- dt-sandbox 回读（20:2x）：公开仓库；main 分支保护 `required_pull_request_reviews` 存在，但 **`required_approving_review_count = 0`**，`enforce_admins = true`，没有必需检查；规则集 `only-main-and-agent-branches` 生效中。
- 实测：容器内 `gh` 以 Natsukashii1997 身份登录（fine-grained 令牌，只能看到 dt-sandbox）。新建 `agent/probe-130`，开 PR dt-sandbox#13，**`gh pr merge 13 --squash` 退出码 0，已合并**（合并提交 `de32d65`）。
- 回退：容器内开 `agent/probe-130-revert`，PR dt-sandbox#14 合并（`6cb7c06`）；两条探针分支已删；回读 main 上 `probes/probe-130.md` 为 Not Found，远端没有 probe 分支；容器 `/tmp/probe130` 已删。#13 上留了说明评论。
- 原因：令牌有 Contents 和 Pull requests 写权限，必需审批数为 0，所以「必须走 PR」拦不住令牌持有者自己合并。令牌代表的是常浩本人的账号，GitHub 不允许作者批准自己的 PR，所以要把审批设成必需，就得另有一个账号来批。这正是 #132（合并执行器独立凭据）要解决的，修法转 #132，本单不改任何设置。

## 二、结论

**选 B：受限会话就是 Multica 隔离容器里的 agent，托管通道改走 Multica issue；驿窗不承担受限会话的收发。** 理由：

1. 驿窗的四条通道全部被隔离切断，接通就得破坏隔离（第 2 问）；
2. 受限 agent 本来就不在会话里停下，而是用 `blocked` + 评论把待决事项交出来（第 3 问），猛鬼兽读 Multica 就能拿到全文，不需要驿窗转交；
3. 常浩日常的交互会话本来就属于全权会话，托管不送达（规格 §3.3），驿窗收发通道对托管没有剩余用途。

**附带缺口**：受限令牌能自行合并 PR（第 4 问）。在 #132 修好之前，受限会话**不满足**规格 §3.3 的「没有合并能力」，托管不能对它送达任何决定。

## 三、对规格和各单的影响（待常浩确认后按 ARCHITECTURE 12.4 修订）

| 对象 | 影响 |
|---|---|
| 规格 §3.1 通道 | 收件改为猛鬼兽读 Multica：父单家族里进入 `blocked` 的 issue 及其最新评论；决定以 issue 评论送回（末尾代发标记），再把 issue 改回 `todo` 唤醒 agent。改回 `todo` 会触发新的 run，属于开跑，必须落在当晚执行模式的授权（夜跑批准的 run 预算）之内；托管本身不新增开跑权 |

## 二、改了什么

| 位置 | 改动 |
|---|---|
| Multica-local `runtime.compose.yml`（源文件 `ops/multica-egress/`） | 执行器只接 `internal` 网络 `agent-net`（172.30.0.0/24，没有默认路由），只能到 backend 和出口代理；postgres、frontend 不在这个网络上。动态地址只从 `.128/25` 分配，代理的固定地址 `.3` 不会被抢 |

| `~/.colima/multica/colima.yaml` 的 provision | `DT-EGRESS` 链：代理网段只能出到 `192.168.5.2:8086`，执行器网段出不了自己的网段。`INPUT` 拒绝两个网段访问虚拟机自身。停掉 dnsmasq 并取消开机自启 |
| `hermes/scripts/multica_night.py`（#174） | 开跑前身份闸，fail-closed（见第三节 E 组） |

为什么停 dnsmasq：macOS 上普通用户只能在通配地址上绑 1024 以下的端口，所以 Lima 转发虚拟机的 53 时会退回到 `*:53`。dnsmasq 改成只监听 `127.0.0.1` 也一样，第一次改法验证无效。虚拟机和容器的 DNS 都直接用 1.1.1.1 / 8.8.8.8，不经过它。

### 关于 E 组的两次测试单

原计划让真实 agent 在一张不改任何东西的测试单里自报运行环境。SBX-31、SBX-32 两次，Claude agent 都按它的边界说明拒绝执行，把单改成 `blocked`。它认为越界的操作有：读家目录、读全局 git 凭据配置、连宿主地址、列出全部仓库，以及读 `/proc/self` 的挂载和路由、打印代理值。agent 没有执行任何命令，也没有建分支、推送。两张单已留言说明并改为 `cancelled`。

这说明指令层的边界在起作用，但它不作为防线：M1 实测过，同一个 agent 有时会照做越界动作。之后改为从宿主读取 daemon 进程的属性做对照。agent 进程是 daemon 的子进程，用户、权限、`NoNewPrivs`、seccomp、命名空间都继承自 daemon。**局限**：任务令牌（`MULTICA_TOKEN` 等）只在 run 期间注入 agent 进程，这次没有在 run 期间直接观察到。

`mcp-proxy.anthropic.com`（claude.ai 账号挂的 MCP 连接器，7 次）、`ab.chatgpt.com`、两个 `oaiusercontent.com` 子域。`claude` 和 `codex` 都正常答复，所以这几个**建议继续拦截**。其中第一个拦住正好：容器里的 agent 用不到常浩 claude.ai 账号挂的连接器。

## 四、没有重测或没有做的

| 项 | 处理 | 理由 |
|---|---|---|
| 已审批 PR 的 16 种合并（11-11 的 2b） | 沿用 11-12 的结果 | GitHub 服务端规则开测前后字节一致，网络改动影响不到它；重测要常浩再到网页批准一次。常浩要求时再做 |

| 换一次网络后再测 | 部分 | 11-11、11-12 宿主局域网 IP 不同，两天的测试覆盖了两个 IP；修复后只在 `172.16.10.238` 上测过。规则按网段、按默认拒绝写，不依赖宿主 IP |
| 包仓库（npm、PyPI） | 不在白名单 | 夜跑任务要装依赖时会被拒，看 `TCP_DENIED` 日志后经常浩同意再加 |

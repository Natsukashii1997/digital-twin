# ADR-016 合并放权：L0–L2 由合并执行器按策略合并，影子门槛废止

- **状态**：提议（随 #257 的 PR 合并后规则成立；规则成立不等于已开启：还要装机、恢复合并官定时任务、常浩在私聊发口令签策略，见「生效顺序」）
- **日期**：2026-11-20
- **决定人**：常浩，2026-11-20，会话「【交接】减轻认知负担｜第 5 项第 2 批清存量与主线后续」
- **issue**：#257
- **架构基线**：[`../ARCHITECTURE.md`](../ARCHITECTURE.md) V5.2.0。按 §12.3 属 **MAJOR**（授权体系变化），所以有本 ADR、迁移和回退；V6.0 这个编号 ADR-015 已留给批 8 的底座改版，这次记为 V5.2.0
- **修订**：ADR-010（低风险自动合并从「目标能力」变成现行政策）；ARCHITECTURE 5.5、5.6；常设授权清单 v2。不动 ADR-014 的托管合并和 ADR-015 的秘书代批（那两条路各走各的条件）

## 背景

1. 常浩同时开着几十个会话，每天约三分之一的回话是放行类，多数是回一句「合并」。他的判断：「合并动作我基本上是无脑合并的，除非是一些思考相关。」
2. 影子合并官从 11-07 运行到 11-10 被暂停，315 次评估。它「建议合并」且有结局的 156 个里常浩合并了 153 个；它判「退回」的里常浩照样合并了 66 个（多数只是正文没写 `Closes #`）。
3. 原来的 5.5 给自动合并定了 8 条前提和「同类 20 次、一致率 ≥ 90%」的影子门槛。第 1、8 条要从驿窗的接力记录核实「审查通过」和审核模式，驿窗一直没有这些记录，所以这条路从没走通过；各档样本也都没到 20 次。
4. 2026-11-20 核对：合并执行器覆盖的七个仓库，main 上只有 `ci.yml`，没有部署、发布步骤。

## 决定

常浩原话：

> 合并由常浩说了算，这条规则作废。我发现合并动作我基本上是无脑合并的，除非是一些思考相关，所以我决定开放完整的合并权限，通过hermes合并，且有记录。L0也不用测了，直接上。最终应该是类似于甲的做法。先按照高权限去做，后续我再根据实际使用看要不要收紧权限

「甲」＝由 Hermes 的合并执行器统一合并、事后在日报里汇报，只有一个执行入口、有统一记录。三个边界他回「都按推荐」，见下面第 2、3、7 条。

1. **废止影子门槛**和「驿窗补齐之前自动合并不启用」。一致率照旧统计，只作观察，不再是放权条件。
2. **按策略合并**：策略记录有效时，覆盖仓库里 L0–L2、不属于例外的 PR，由合并执行器（`merge_act.py`）直接 squash 合并，不发卡片。合并官判「退回」的不拦，退回理由写进记录。
3. **例外仍然问常浩**（发卡片，和原来一样由他点）：L3（敏感路径、凭据、安装 / 部署 / 配置 / 正式数据）；改定方向文档（PRD、ARCHITECTURE、ADR、已定内容登记表、全局规则源文件、《工程流程》、常设授权清单）；带 `needs-info` 标签。改动文件没看全的也按例外办：GitHub 一次只给 100 个改动文件、改名的文件只给新路径，判不了有没有碰敏感路径，就当碰了（近 7 天七个仓库合并的 145 个 PR 里，带改名的 2 个、超过 100 个文件的 0 个）。来自别的仓库（fork）的 PR 也按例外办：仓库是公开的，机制不核对审查结论，外来代码一律问常浩。GitHub 这次没给出改动文件总数或来源仓库的，核对不了，同样按这两类办（第 2 轮审查 P2-09：原来是不合并也不发卡片，静默卡着）。这两种例外和「`AGENTS.md`、`CURRENT.md` 不归例外」是常浩 2026-11-20 看了第 1 轮审查意见后定的（「都按推荐」）：审查方建议把这两个文件也归例外，但近 7 天合并的 148 个 PR 里有 86 个碰了其中之一，归了等于大半 PR 又回到逐个问他；有问题的改动靠日报事后看、再撤回。L3 和原来一样不走飞书合并。
4. **机械检查一项不少**：PR 开着、不是草稿、合进主分支；HEAD 仍是判定时的那个；没冲突、GitHub 没报落后（七个仓库现在都没开「必须与主分支同步」，所以落后主分支但没冲突的 PR 会合，和卡片合并一样）、`mergeStateStatus` 为 CLEAN；这个 HEAD 的 GitHub 检查全部通过；本机主目录主分支没有没推的提交；合并命令带 `--match-head-commit`；合并后回读。
5. **授权来源是策略记录**（`owner_approved_policy`，`merge_policy.py`）：常浩在猛鬼兽私聊发「开自动合并 <范围哈希前 12 位>」，脚本按 5.2a (b) 回读核验后落盘；记录绑定授权范围（风险档、覆盖仓库、例外路径、敏感路径、上限）的 SHA-256，规则文件里这些内容变了就自动失效、要重签；任何入口都能关，关了立即回到发卡片（开关用自己的锁 `policy.lock`，不等合并锁；合并执行器在同一把锁里最后读一次开关、记「要合」、起合并请求，所以关成功之后不会再有新的合并请求启动，已经启动的那一个照常完成）。
6. **每次合并都有记录，记录要有证据**：账本 `DigitalTwin/merge/auto-merges.jsonl` 先记「要合」再记结果。合并走 REST 合并接口（`PUT pulls/{号}/merge`，`sha` 绑定 HEAD，和托管合并同一套证据标准）：只有接口回执说「这次合上了」并给出合并提交号、回读也对得上，才记成按策略合并；请求没发出去、GitHub 明确拒绝且 PR 还开着、或 GitHub 回了 4xx 状态码而回读失败（服务端已答复不处理；状态码只认 gh 的「(HTTP 4xx)」写法，报错里请求地址中的 PR 号不算），记没合上；其余（超时、断网、回读失败、被别处抢先合了）一律记结果不明，不重发。结果不明的由合并官巡视只读核对：PR 已合并的记「已合并、来源不明」（不算按策略合并，不能用撤回口令）；PR 已关闭或换了版本、且本机没有那次合并请求的进程的，记没合上、交出登记作废（那次请求用 `sha` 绑着旧版本，GitHub 不会拿它合别的版本，关着的 PR 也合不了；要合得由会话重新交出）；PR 仍开着、版本没变的，一直保持结果不明，不重发、不放开重新交出，过了 10 分钟起每天提醒常浩一次，要合就给 PR 推一个新提交再重新交出（第 2、3 轮审查 P1-01：同步合并接口取不到「GitHub 不会再处理那次请求」的凭据，本机进程没了、等了多久都不能当证据；所以不靠等时间结算。改用异步合并接口能不能查到终态，另行评估，#285）。合并请求由独立的看门进程起，自带 60 秒硬期限，发起它的进程被杀也到点收场；账本记请求的起点（`started`）和怎么结束的（结果行的 `ended`）；巡视查本机进程表只是看：查不了，或那次请求的进程过了期限还活着，都不下结论，告诉常浩（给出进程号，请他在电脑上确认后停），脚本不停任何进程（第 3 轮审查 P2-14：按命令行认进程有认错的可能）。日报汇报「替你合并了什么」，附撤回办法；撤回只认有回执为证的按策略合并。撤回 PR 只自动合并「开出当时核对过并记下的那个版本」：之后有了新提交、开出时没核对上、或是事后认领的，都不自动合并，要合得由会话重新交出（第 2 轮审查 P1-07）。核对到内容（第 3 轮审查 P1-07）：除了正文的记录号、原 PR、原合并提交、目标分支、来源仓库、创建时间，撤回 PR 的版本必须是落在主分支某个提交上的单独一个提交，它的文件树正好等于「以原合并提交为基，把原合并倒回去」的结果；只取 Git 对象来比，不检出、不运行（主账号不执行 PR 里的代码，#190）。上次要开撤回 PR、没记下它开出来的：先从 PR 列表里找正文带记录号的，只认这次撤回之后创建、还开着或已合并、身份和内容都对得上的那一个；被关掉的停下交人；一个都没有的，要在「上次的请求已经结束」有记录之后再过 10 分钟才重新开（第 3 轮审查 P2-03）。内容核对这一次做不了的（取对象时网络断了等），不算对不上：记下开出时读到的版本，下次再跑撤回命令时再核，核上了才接着合那个版本。
7. **不放的**：合并之后的装机、发布、部署，仍先问常浩；按策略合并后不拉本机主目录（有的应用直接从主目录运行，拉了等于部署）。主账号不执行 PR 里的代码（#190）不放宽：没登记 CI 的仓库不按策略合并。

## 原 5.5 的 8 条逐条处理

| 条 | 第一版 | 理由 |
|---|---|---|
| 1 绑定正确、来源可信 | **保留** HEAD 绑定：判定、交出、核对、合并命令是同一个 HEAD。**放宽**「从驿窗接力记录核实审查通过」 | 驿窗没有完整送审包指纹；常浩原话「无脑合并」「先按高权限去做」。账本里每条写明「审查结论未核实」 |
| 2 测试与审核成立 | **保留**测试（当前 HEAD 的 CI 全过）。审核同第 1 条放宽 | 同上 |
| 3 范围受限 | **保留**仓库、风险档、敏感路径限制。**放宽**分支前缀 | `agent/` 是 Multica agent 的分支约定；这里的 PR 来自会话分支 |
| 4 授权可验 | **保留** | 见「决定」第 5 条 |
| 5 副作用已知 | **保留** | 七个覆盖仓库 main 上只有 CI；改 `.github/` 的 PR 是 L3；合并后不拉主目录、不装机 |
| 6 环境确认 | **保留** | 现读远端 PR 状态；不依赖远端保护 |
| 7 合并带 HEAD 校验 | **保留** | REST 合并接口的 `sha` 参数绑定 HEAD（服务端拒绝不匹配的版本），不重试，合并后回读；成功以接口回执为证 |
| 8 审核模式可证 | **放宽**（第一版不核审核模式） | 同第 1 条 |

托管合并（ADR-014）仍按 8 条原文和它自己的条件走，本 ADR 不改。

## 风险与对策

| 风险 | 对策 | 剩余 |
|---|---|---|
| 没审查、审查没做完的 PR 被合进去（L-05、agent-kit#107 那类） | 审查怎么做不变（《工程流程》）；合并只在会话交出之后发生；账本写明「审查结论未核实」；合了什么进日报，可撤回 | 机制不核对审查结论。驿窗有了可信的审查记录后，这是第一个可以收紧的地方 |
| 会话绕过合并执行器直接合并（agent-kit#107） | 合并官巡视时发现 PR 已合并、账本里没有执行器记录，记一条「没经合并执行器」，进日报取数 | 只留记录，拦不住。要拦得靠 agent-kit 的命令钩子或 GitHub 规则集，另开跟进项 |
| 绕过必需检查直推 main（github-center 那次） | 不经 PR，合并执行器看不到 | 同上，跟进项 |
| 同一个 macOS 账号里的进程（含被带偏的模型）伪造策略记录或直接调合并命令 | 策略记录按 5.2a (b) 核验签署消息；威胁模型同 5.2a：不防同账号的恶意本地进程 | ADR-015 已写明主账号 `gh` 本来就是常浩的管理员令牌，这条边界要等 dt-gate 独立账号落地 |
| 一天里合进去一大批有问题的 PR | 每天上限，到了就停下告诉常浩；随时可关。上限按合上那天算，结果不明的没结清一直占名额 | 上限之内的要靠日报事后看 |
| 合并请求发了、不知道合上没有 | 账本先记「要合」；没有回执就不记成功，也不重发；巡视只读核对：已合并的记「来源不明」；已关闭或换了版本、本机又没有那次请求的进程的，记没合上并作废交出登记；仍开着、版本没变的一直挂着，每天提醒一次 | 回执丢了但确实是这次合上的，也会被记成「来源不明」、不能用撤回口令，要在电脑上撤。请求其实没到 GitHub 的 PR 也会一直挂着、占一个每天的名额，要有人给它推一个新提交才放开：宁可卡住，不拿「等了一阵」当证据。关着的 PR 被记成没合上之后，有人把它原样重新打开、而那次旧请求这时才被 GitHub 处理，它仍可能被合上（旧请求的本机进程已确认不在，GitHub 处理请求的时限是秒级，实际要两头都碰巧）；那样会在下一轮巡视被记成「没经合并执行器」 |
| 发起合并的进程被杀，合并请求的进程还活着，之后才把 PR 合上 | 请求的期限不靠发起方：看门进程到点杀掉。看门进程也没按期收场的，巡视查进程表会看到：不下结论，告诉常浩进程号，请他在电脑上确认后停；进程表查不了、或筛出的进程读不出命令行，同样不下结论。PR 仍开着、版本没变时，不管进程在不在都不结算 | 脚本不替常浩停进程，这种情况要他到电脑上处理；处理之前这个 PR 一直挂着 |
| 撤回 PR 开出之后被推了新提交，续接时把新版本当成授权过的合进去；或开出后、第一次读取前就被换成文件名和增删行数一样、内容不同的提交 | 只自动合并开出当时核对过并记下的版本；版本变了就停下说明。核对到内容：撤回提交的文件树必须正好等于把原合并倒回去的结果，下面不能夹带别的提交；版本号是内容的哈希，核对过的版本不会再变，合并请求又用 `sha` 绑着它 | 认领来的撤回 PR 不自动合并，多一步由会话交出。GitHub 做撤回提交和本机 git 算三方合并，在少见的情况下（原合并之后同一处又被改过）结果可能差一点：那时核对不上，不自动合并，由会话看过后交出 |
| 巡视时合并被 GitHub 拒绝，每半小时静默重试 | 每个 PR 每天说一次原因，交出登记保留；只有限流（可能是 403 也可能是 429）、版本或主分支刚变、另一个合并正在进行算临时的，下一轮再试；其余一律当天不再对这个版本发请求（登录、权限、要人审批、分支规则、校验失败），第二天或会话重新交出时再试 | 没见过的临时性拒绝会被当成当天不再试：只是慢一天，不会撞 |
| 一个仓库开着的 PR 超过一次列出的数量，交出登记被误删 | 一次列 1000 个；不在列表里的逐个核实，确认关了、合了或换了版本才作废 | |
| 记了要合之后被别处（网页、卡片、会话直接 `gh`）抢先合了，被记成按策略合并 | 同上：只认接口回执；卡片合并和按策略合并共用合并锁，卡片合并遇到结果不明的 PR 先等核对 | |
| 最后一次核对之后、合并请求到达之前，PR 的目标分支被改了 | 目标分支在最后一次读取里核对（必须是主分支）；合并后回读再看一次，不是主分支就当场告诉常浩 | GitHub 的合并接口绑不住目标分支，这一两秒的窗口关不掉，只能事后发现 |
| 落后主分支、没冲突的 PR 被合进去（它的 CI 是在旧基线上过的） | 和卡片合并一样，没有变松：七个仓库的分支保护都没开「必须与主分支同步」，GitHub 不报落后（2026-11-20 抽查数字分身最近 12 个合并，5 个合并时落后 1–3 个提交）；文字冲突照拦；合并后 main 上 CI 照跑 | 两个各自通过的 PR 合在一起才出错的情况，要靠 main 的 CI 和日报事后发现。要收紧：给仓库开「必须同步」，或合并前比一次基线；代价是并行会话要频繁变基、重跑 CI、重新交出 |
| 合并到 main 触发了没预料到的动作 | 覆盖仓库的工作流只有 CI；改工作流的 PR 是 L3；覆盖仓库和敏感路径都在授权范围哈希里，改了要重签 | 新增覆盖仓库前要先核对它的工作流 |

## 收紧的旋钮（常浩说「后续再根据实际使用看要不要收紧」）

都在 `merge_rules.json` 里，改了要重签：风险档（`auto.tiers`，例如先只放 L0–L1）；覆盖仓库（`act.repos`）；例外路径（`direction_docs`、`sensitive`、`repo_sensitive`）；每天上限（`auto.daily_cap`）。关掉整个机制：`merge_policy.py off` 或私聊「关自动合并」。

## 生效顺序与回退

1. #257 的 PR 经 ChatGPT 审查、常浩说「合并」（它改 `hermes/`，是 L3，属于例外）。
2. 常浩同意后装机：`merge_policy.py`、`merge_act.py`、`merge_officer.py`、`merge_rules.json`、`actions.py`、`pdaily_facts.py`、`pdaily_publish.py` 和 merge-officer 技能装到 `~/.hermes`，旧版备份到 `DigitalTwin/evidence/`。这几个脚本要一起装（日报取数读合并账本要用 `merge_policy.py`）；技能按 11-20 的规则先比对安装副本有没有猛鬼兽的自改，有就先收回仓库。PR 合并后到装机前，工程自检会报这 7 个文件和 main 不一致，所以合并和装机最好同一天做。
3. 常浩同意后恢复合并官定时任务 `8994fb76d03e`。此时策略还没签，行为和 11-11 暂停前一样（发卡片）。
4. 常浩在私聊发口令签策略，按策略合并开始生效。

回退分三层，都不丢数据：关策略（一句话，立即回到发卡片）；暂停定时任务（回到 11-11 之后的状态）；装回备份的旧版脚本和规则 v1（账本和策略记录留在 `DigitalTwin/merge/`，旧脚本不读它们）。

## 四个设计选择（常浩 2026-11-20 在实现会话里定）

原话没盖到的四处。前三处实现会话给了推荐，常浩回「都按推荐」；第四处是已定内容的改动，单独确认：

1. **什么时候算「可以合」：会话交出才合**（`auto.ready = handoff`）。开 PR 的会话调 `merge_act.py auto <仓库#PR>` 交出当时的版本；没交出的 PR 不动。这等于把常浩原来回的那句「合并」换成会话自己交出。没选「不是草稿、检查全过就合」：那样审查中途的 PR 会被提前合（L-05），当天开着的 PR 里有 5 个会一开启就被合掉。
2. **收窄数字分身的 L3**：原来 `hermes/` 整个目录算 L3。现在只留授权、合并、派单、凭据、身份、对外发言、安装相关的脚本和技能，以及合并后不用装机就生效的文件（名册、`ai_access.json`、保护基线、先不装清单），清单在 `merge_rules.json` 的 `repo_sensitive`；日报、取数、推送这类脚本按 L1 / L2。理由：合并不等于装机，装到 `~/.hermes` 仍先问常浩。按 11-13 到 11-20 合并的 PR 重算，数字分身的 L3 只从 35 个降到 34 个：那一周的工作集中在秘书代批和底座（本来就是授权相关），另有 12 个 PR 顺带改了 `ai_access.json`、9 个改了 `ops/self_check.py`。效果要等实际使用再看，不再往下放。

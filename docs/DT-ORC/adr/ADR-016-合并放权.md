# ADR-016 合并放权：L0–L2 由合并执行器按策略合并，影子门槛废止

- **状态**：提议（随 #257 的 PR 合并后规则成立；规则成立不等于已开启：还要装机、恢复合并官定时任务、常浩在私聊发口令签策略，见「生效顺序」）
- **日期**：2026-11-20
- **决定人**：常浩，2026-11-20，会话「【交接】减轻认知负担｜第 5 项第 2 批清存量与主线后续」
- **issue**：#257
- **架构基线**：[`../ARCHITECTURE.md`](../ARCHITECTURE.md) V5.2.0。按 §12.3 属 **MAJOR**（授权体系变化），所以有本 ADR、迁移和回退；V6.0 这个编号 ADR-015 已留给批 8 的底座改版，这次记为 V5.2.0
- **修订**：ADR-010（低风险自动合并从「目标能力」变成现行政策）；ARCHITECTURE 5.5、5.6；常设授权清单 v2。不动 ADR-014 的托管合并和 ADR-015 的秘书代批（那两条路各走各的条件）

## 背景

1. 常浩同时开着几十个会话，每天约三分之一的回话是放行类，多数是回一句「合并」。他的判断：「合并动作我基本上是无脑合并的，除非是一些思考相关。」
2. 影子合并官从 11-07 运行到 11-10 被暂停，315 次评估。它「建议合并」且有结局的 156 个里常浩合并了 153 个；它判「退回」的里常浩照样合并了 66 个（多数只是正文没写 `Closes #`）。
3. 原来的 5.5 给自动合并定了 8 条前提和「同类 20 次、一致率 ≥ 90%」的影子门槛。第 1、8 条要从驿窗的接力记录核实「审查通过」和审核模式，驿窗一直没有这些记录，所以这条路从没走通过；各档样本也都没到 20 次。
4. 2026-11-20 核对：合并执行器覆盖的七个仓库，main 上只有 `ci.yml`，没有部署、发布步骤。

## 决定

常浩原话：

> 合并由常浩说了算，这条规则作废。我发现合并动作我基本上是无脑合并的，除非是一些思考相关，所以我决定开放完整的合并权限，通过hermes合并，且有记录。L0也不用测了，直接上。最终应该是类似于甲的做法。先按照高权限去做，后续我再根据实际使用看要不要收紧权限

「甲」＝由 Hermes 的合并执行器统一合并、事后在日报里汇报，只有一个执行入口、有统一记录。三个边界他回「都按推荐」，见下面第 2、3、7 条。

1. **废止影子门槛**和「驿窗补齐之前自动合并不启用」。一致率照旧统计，只作观察，不再是放权条件。
2. **按策略合并**：策略记录有效时，覆盖仓库里 L0–L2、不属于例外的 PR，由合并执行器（`merge_act.py`）直接 squash 合并，不发卡片。合并官判「退回」的不拦，退回理由写进记录。
3. **例外仍然问常浩**（发卡片，和原来一样由他点）：L3（敏感路径、凭据、安装 / 部署 / 配置 / 正式数据）；改定方向文档（PRD、ARCHITECTURE、ADR、已定内容登记表、全局规则源文件、《工程流程》、常设授权清单）；带 `needs-info` 标签。L3 和原来一样不走飞书合并。
4. **机械检查一项不少**：PR 开着、不是草稿、合进主分支；HEAD 仍是判定时的那个；没冲突、不落后、`mergeStateStatus` 为 CLEAN；这个 HEAD 的 GitHub 检查全部通过；本机主目录主分支没有没推的提交；合并命令带 `--match-head-commit`；合并后回读。
5. **授权来源是策略记录**（`owner_approved_policy`，`merge_policy.py`）：常浩在猛鬼兽私聊发「开自动合并 <范围哈希前 12 位>」，脚本按 5.2a (b) 回读核验后落盘；记录绑定授权范围（风险档、覆盖仓库、例外路径、敏感路径、上限）的 SHA-256，规则文件里这些内容变了就自动失效、要重签；任何入口都能关，关了立即回到发卡片。
6. **每次合并都有记录**：账本 `DigitalTwin/merge/auto-merges.jsonl` 先记「要合」再记结果；结果不明的不重发，下一轮只读核对。日报汇报「替你合并了什么」，附撤回办法。
7. **不放的**：合并之后的装机、发布、部署，仍先问常浩；按策略合并后不拉本机主目录（有的应用直接从主目录运行，拉了等于部署）。主账号不执行 PR 里的代码（#190）不放宽：没登记 CI 的仓库不按策略合并。

## 原 5.5 的 8 条逐条处理

| 条 | 第一版 | 理由 |
|---|---|---|
| 1 绑定正确、来源可信 | **保留** HEAD 绑定：判定、交出、核对、合并命令是同一个 HEAD。**放宽**「从驿窗接力记录核实审查通过」 | 驿窗没有完整送审包指纹；常浩原话「无脑合并」「先按高权限去做」。账本里每条写明「审查结论未核实」 |
| 2 测试与审核成立 | **保留**测试（当前 HEAD 的 CI 全过）。审核同第 1 条放宽 | 同上 |
| 3 范围受限 | **保留**仓库、风险档、敏感路径限制。**放宽**分支前缀 | `agent/` 是 Multica agent 的分支约定；这里的 PR 来自会话分支 |
| 4 授权可验 | **保留** | 见「决定」第 5 条 |
| 5 副作用已知 | **保留** | 七个覆盖仓库 main 上只有 CI；改 `.github/` 的 PR 是 L3；合并后不拉主目录、不装机 |
| 6 环境确认 | **保留** | 现读远端 PR 状态；不依赖远端保护 |
| 7 合并带 HEAD 校验 | **保留** | `--match-head-commit`，不重试，合并后回读 |
| 8 审核模式可证 | **放宽**（第一版不核审核模式） | 同第 1 条 |

托管合并（ADR-014）仍按 8 条原文和它自己的条件走，本 ADR 不改。

## 风险与对策

| 风险 | 对策 | 剩余 |
|---|---|---|
| 没审查、审查没做完的 PR 被合进去（L-05、agent-kit#107 那类） | 审查怎么做不变（《工程流程》）；合并只在会话交出之后发生；账本写明「审查结论未核实」；合了什么进日报，可撤回 | 机制不核对审查结论。驿窗有了可信的审查记录后，这是第一个可以收紧的地方 |
| 会话绕过合并执行器直接合并（agent-kit#107） | 合并官巡视时发现 PR 已合并、账本里没有执行器记录，记一条「没经合并执行器」，进日报取数 | 只留记录，拦不住。要拦得靠 agent-kit 的命令钩子或 GitHub 规则集，另开跟进项 |
| 绕过必需检查直推 main（github-center 那次） | 不经 PR，合并执行器看不到 | 同上，跟进项 |
| 同一个 macOS 账号里的进程（含被带偏的模型）伪造策略记录或直接调合并命令 | 策略记录按 5.2a (b) 核验签署消息；威胁模型同 5.2a：不防同账号的恶意本地进程 | ADR-015 已写明主账号 `gh` 本来就是常浩的管理员令牌，这条边界要等 dt-gate 独立账号落地 |
| 一天里合进去一大批有问题的 PR | 每天上限，到了就停下告诉常浩；随时可关 | 上限之内的要靠日报事后看 |
| 合并命令发了、不知道合上没有 | 账本先记「要合」；结果不明的这个 PR 不再合，下一轮巡视只读核对后才放开 | |
| 合并到 main 触发了没预料到的动作 | 覆盖仓库的工作流只有 CI；改工作流的 PR 是 L3；覆盖仓库和敏感路径都在授权范围哈希里，改了要重签 | 新增覆盖仓库前要先核对它的工作流 |

## 收紧的旋钮（常浩说「后续再根据实际使用看要不要收紧」）

都在 `merge_rules.json` 里，改了要重签：风险档（`auto.tiers`，例如先只放 L0–L1）；覆盖仓库（`act.repos`）；例外路径（`direction_docs`、`sensitive`、`repo_sensitive`）；每天上限（`auto.daily_cap`）。关掉整个机制：`merge_policy.py off` 或私聊「关自动合并」。

## 生效顺序与回退

1. #257 的 PR 经 ChatGPT 审查、常浩说「合并」（它改 `hermes/`，是 L3，属于例外）。
2. 常浩同意后装机：`merge_policy.py`、`merge_act.py`、`merge_officer.py`、`merge_rules.json`、`actions.py`、`pdaily_facts.py` 和 merge-officer 技能装到 `~/.hermes`，旧版备份到 `DigitalTwin/evidence/`。
3. 常浩同意后恢复合并官定时任务 `8994fb76d03e`。此时策略还没签，行为和 11-11 暂停前一样（发卡片）。
4. 常浩在私聊发口令签策略，按策略合并开始生效。
5. 两三个真实 PR 验证：按策略合并、账本、日报显示、撤回。

回退分三层，都不丢数据：关策略（一句话，立即回到发卡片）；暂停定时任务（回到 11-11 之后的状态）；装回备份的旧版脚本和规则 v1（账本和策略记录留在 `DigitalTwin/merge/`，旧脚本不读它们）。

## 三个设计选择（常浩 2026-11-20 在实现会话里回「都按推荐」）

原话没盖到的三处，实现会话给了推荐，常浩回「都按推荐」：

1. **什么时候算「可以合」：会话交出才合**（`auto.ready = handoff`）。开 PR 的会话调 `merge_act.py auto <仓库#PR>` 交出当时的版本；没交出的 PR 不动。这等于把常浩原来回的那句「合并」换成会话自己交出。没选「不是草稿、检查全过就合」：那样审查中途的 PR 会被提前合（L-05），当天开着的 PR 里有 5 个会一开启就被合掉。
2. **收窄数字分身的 L3**：原来 `hermes/` 整个目录算 L3。现在只留授权、合并、派单、凭据、身份、对外发言、安装相关的脚本和技能，以及合并后不用装机就生效的文件（名册、`ai_access.json`、保护基线、先不装清单），清单在 `merge_rules.json` 的 `repo_sensitive`；日报、取数、推送这类脚本按 L1 / L2。理由：合并不等于装机，装到 `~/.hermes` 仍先问常浩。按 11-13 到 11-20 合并的 PR 重算，数字分身的 L3 只从 35 个降到 34 个：那一周的工作集中在秘书代批和底座（本来就是授权相关），另有 12 个 PR 顺带改了 `ai_access.json`、9 个改了 `ops/self_check.py`。效果要等实际使用再看，不再往下放。
3. **合并后怎么告诉常浩、怎么撤**：合成功的只进第二天日报（`auto.notify = daily`）；结果不明、只读核对的结论、到上限才私聊说一句；每天上限 30 个（`auto.daily_cap`）；撤回 PR 开出后按同一套检查合并（`auto.revert_auto_merge`）；已装机的改动撤回后要不要重装，仍问常浩。

**还没定**：日报卡片里怎么显示「替你合并了什么」。卡片版式是已定内容（乙版四板块，#226），要单独确认；确认之前只进事实快照，卡片和完整报告不变。

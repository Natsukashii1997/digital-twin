## 背景

1. 常浩 2026-11-15 定下唯一主线：fork agent-autoloop（下称「中台」）当数字分身的执行底座。猛鬼兽（Hermes）留作飞书前台兼「秘书」，按常浩签的清单代批，D 档一律不代；工人（Claude / Codex）关在独立 macOS 账号 dt-worker 里。方案 V2.4 经 Fable 5.2 独立评估和 ChatGPT High 两轮思维评审，常浩 11-15 回「代批选 B，9 件事都按推荐」。
2. 批 0A 隔离门已过：dt-worker 越权反向测试 22 项全挡住（PR #191）。批 0B 授权门完成 0B-1 任务凭证与派单网关（PR #199）、0B-2 中台配置与只读窗口（PR #200，已安装）、0B-3 飞书按钮实测（PR #201）、0B-4a 飞书桥接与本人点击（PR #202，已合并、未签钥匙、未安装）。
3. **两次 L3 审查指出同一个问题**：
   - PR #199 审查 P0-01：派单网关和猛鬼兽跑在同一个 macOS 账号，猛鬼兽的模型有 shell，能改身份配置、读写凭证库、读 hermes 来源密钥，从而绕过两步批准。常浩 11-17 定：沙盒阶段先接受。
   - PR #202 审查 P1-01：点击人、聊天号是网关传进来的参数；同账号的进程能伪造这些参数，也能直接读 feishu 通道钥匙，甚至自己签钥匙。常浩 11-17 选甲：先合并，不签 feishu 通道钥匙、不安装；隔离在本 ADR 定，方向是「独立账号 dt-gate + 单独飞书机器人直接收点击」，0C 之前定。
4. **起草本 ADR 时核实的事实**（2026-11-18）：
   - 猛鬼兽的飞书对话开着终端、文件、代码执行、浏览器、网页、电脑操作等工具（`hermes tools list --platform feishu`）。
   - 主账号的 `gh` 登录的是常浩本人（仓库管理员）的令牌，存在钥匙串里；合并执行器的专用令牌也在同一个登录钥匙串（`merge_act.py` 的 `CUSTODY_CRED`）。ADR-014 修订 2 已记下「宿主上的全权会话本身就能合并」，但当时的托管只送受限会话，没有论证过「秘书本人就在全权账号里」。
   - 中台的本人密钥明文存在主账号 `~/.agent-autoloop/config.json`；本人密钥回答卡片不核对回答人（方案 2.3，`kernel/http.ts:203-204`），还能触发任何规则。
   - 结论：今天主账号里任何被外部内容带偏的猛鬼兽，不用伪造批准也能直接推 main、合并、改中台规则。只把网关搬走，挡住的是「伪造授权记录」，挡不住「直接动手」。

## 决定

### 1. 底座方向（照 11-15 裁决，不重开）

1. 中台用 fork 版 agent-autoloop：**私有镜像引擎**（零补丁，锁完整提交号，每周检查上游但不自动替换，升级前兼容性检查、挂起恢复、插件回归、数据迁移验证，回滚靠升级前快照）；**独立插件仓库**放自己的插件；**公开 fork** 只用来给上游提 PR，合进上游后删掉自己那份。零补丁是优先策略，不是绝对禁令：安全正确性在公开接口做不到时，先申请上游扩展点，再评估最小补丁（方案第 3 节）。
2. 角色：常浩定目标、给授权、点合并；猛鬼兽负责对话、记忆、把常浩的话变成提议、把卡片变成白话；中台负责事件、规则、派活、挂起、定时；工人只在 dt-worker 里改自己的 worktree；撤不回的动作只由确定性出口在核实授权后执行；GitHub 分支保护是最后一道闸（方案 2.2）。第 3 节决定上面这些放在哪个账号。
3. 三份契约（授权与任务凭证、信任边界、状态与恢复）和三条不变量（受信发布、主账号不执行 PR 代码、恢复闸）照方案第 5 节，不在本 ADR 重写。

### 2. 融合与退役

按方案第 4 节逐项落位，摘要：

| 去处 | 内容 |
|---|---|
| 融进中台（插件 / 规则 / 出口） | #132 合并隔离、#174 执行器身份闸、run_worker 的「不能用就报错不换家」与回执字段、ai_access、常设授权档位表、twin_identity、custody_ledger（写前账本）、twin_scheduler 的恢复规则、merge_act（合并出口本体）、actions 行动记录、合并官规则、夜间行动提案（形态不改）、主线巡视、proposal_digest |
| 留在猛鬼兽前台 | 个人项目日报、AI HOT、Tidings、skill 体检、记忆日报、AI 前沿群学习报告等推送（不迁）；merge-buttons 多认一种中台卡片按钮 |
| 沉淀成方法 | #135 执行防线结论、pdaily 的「事实快照 → 写 → 核对 → 降级」、信息边界、github-center 的隔离跑法、codex-push 发送规范、DAEMON-RUN |
| 退役（批 8，每项可回滚） | run_worker / dispatch / workshop 技能、multica_night 与 Multica 容器、twin_state |

驿窗只显示中台卡片、点了跳飞书，不当授权入口；接中台改变了「第三方只做一键唤起」的定位，批 6 前单独做改动确认。

### 3. 信任边界（0C 前定）〔评审中，待常浩定〕

**原则**：读外部内容的模型进程，不和「能签授权、能持撤不回凭据」的进程放在同一个系统账号里。同账号内没有软件办法隔开两者（上游 SECURITY.md、ARCHITECTURE 5.2a、两次审查一致）。

四个信任域：

| 域 | 是谁 | 信不信 |
|---|---|---|
| 常浩本人 | 飞书私聊里本人发的话、本人的点击 | 唯一的授权来源 |
| 控制面 | 中台、派单网关、凭证库、各把钥匙、确定性出口 | 可信，但只做核对过的固定动作 |
| 秘书 | 猛鬼兽的模型（读网页、群消息、PR 文字、工人回执） | 当作可能被带偏的一方：能提议，不能自证 |
| 工人 | dt-worker 里的 Claude / Codex | 不可信，0A 已隔离 |

**三种做法**：

| | 甲：维持同账号，接受风险 | 乙：独立账号 dt-gate，不加机器人 | 丙：dt-gate + 单独「门卫」飞书机器人（**推荐**） |
|---|---|---|---|
| 做法 | 签 feishu 通道钥匙、装桥接；网关、钥匙、中台都留在主账号 | 中台（含本人密钥）、凭证库、hermes 来源钥匙、两把通道钥匙、签发与回答、受信发布、合并执行器令牌、代批的前后闸与送达，都搬进 dt-gate；猛鬼兽只能从本机一个窄接口递「提议」「消息号」「候选决定」；dt-gate 用飞书接口回读常浩私聊原话核验 | 乙的全部，再加一个不带 AI 的飞书应用「门卫」：凭证只在 dt-gate，发确认卡（派单五要素、合并、代批汇报的推翻），点击回调直接连到 dt-gate；常浩只认门卫发来的卡 |
| 挡住 | 打错参数、旧消息重放、外人冒充、工人越权（0A） | 甲的全部 + 猛鬼兽伪造批准记录、偷钥匙、自己签钥匙、用本人密钥直接答卡或触发规则 | 乙的全部 + 伪造点击 + 「冒牌说明」（猛鬼兽以同一个机器人身份发假说明诱导常浩误批） |
| 挡不住 | 被带偏的猛鬼兽自己批、伪造点击；而且它本来就能用常浩的 GitHub 直接推 main、合并 | ① 按钮点击：卡片回调由收它的那一方接（同一应用多个长连接时飞书只推给其中一个，**未核实**），dt-gate 核不到点击，按钮只能改成打字口令；② 冒牌说明；③ 猛鬼兽手里常浩的 GitHub 全权（第 4 节） | 猛鬼兽手里常浩的 GitHub 全权（第 4 节）；常浩自己看错卡 |
| 常浩亲手做 | 签钥匙、装（说「装」） | 建 dt-gate 账号（系统设置，输管理员密码）；装后台常驻的系统服务（sudo，dt-gate 平时不登录）；扩 0A 的门卫规则（sudo） | 乙的全部 + 在飞书开放平台建一个企业自建应用（只开私聊发消息和卡片回调，可能要管理员审批发布）；把应用密钥亲手粘进 dt-gate，不经过任何 AI |
| 已定内容 | 不碰 | 不碰；但飞书按钮改打字，和 0B-4a、11-14 定稿的汇报卡「推翻」按钮交互冲突，要改动确认 | **碰到方案 R1「不新增机器人」、PRD 原则 1「飞书里只有 Hermes」**：门卫不聊天、不带 AI，「只有一个 AI 入口」仍成立，但字面要改，单独做改动确认 |
| 工作量 | 0 | 约 2～3 个 PR | 约 3～4 个 PR |

**推荐丙**，理由：

1. 只有丙让「常浩点了」这件事不可伪造：点击直接到控制面，中间不经过会被带偏的一方。
2. 乙省掉一个机器人，但按钮要退回打字，还留着「冒牌说明」这个最便宜的骗法。
3. 甲让整个 0B 授权门只是记账，秘书代批上线后，常浩不在场时没有任何东西在拦。
4. 丙就是常浩 11-17 定的方向，这次只是把边界写全：中台本身也要搬，否则本人密钥留在主账号，等于没搬。

**丙落地后各放在哪**：

| 放在 | 内容 |
|---|---|
| dt-gate | 中台（`~/.agent-autoloop` 整体，含本人密钥、`rules.json`、数据库）；派单网关与凭证库（`autoloop_grants`）；中台配置生成与签钥匙（`autoloop_config`）；只读窗口（`autoloop_readonly`，向主账号开本机只读接口）；门卫机器人收发与本人点击处理（`autoloop_feishu`、`autoloop_answer` 改造）；代批前后闸、送达、账本、汇报卡与推翻（`custody*`）；受信发布（机器账号令牌）；合并执行器（专用令牌） |
| 主账号（猛鬼兽） | 对话、记忆、技能、现有推送；写提议、递消息号、秘书判断（`hermes chat` 单次）出候选决定；全部经窄接口交给 dt-gate，拿不到任何钥匙 |
| dt-worker | 不变：接单密钥，只读凭证镜像，只能连中台 3350 和过滤代理 8090 |

### 4. 配套：收紧秘书自己能动的东西〔评审中，待常浩定〕

第 3 节不管选哪种，都挡不住「秘书用常浩的身份直接动手」。这不是中台带来的新风险，今天就存在；但秘书代批会让秘书在常浩不在场时自主行动，所以**秘书代批上线（0B-4c 启用）之前，本节必须做完一种**。候选做法：

| 做法 | 是什么 | 好处 | 代价 |
|---|---|---|---|
| 4a 收工具 | 猛鬼兽的飞书对话关掉终端、代码执行、电脑操作、文件写；技能只能调登记过的固定脚本 | 最小改动，主账号不动 | Hermes 能不能「只放行登记过的命令」未核实；progress、workshop、merge-officer 等技能现在靠终端调脚本，要改；**和 PRD 原则 6「权限一次开够」冲突，要改动确认** |
| 4b 换账号 | 猛鬼兽整体搬进低权限账号（拿不到常浩的 `gh`、钥匙串、项目目录） | 边界最硬 | 牵涉最大：猛鬼兽的定时任务里有以常浩飞书用户身份读群、读私聊的（记忆日报、群学习报告），这些用户令牌要一起搬或拆；Vault 读取要重配 |
| 4c 降常浩的 GitHub 凭据 | 主账号不再常驻常浩的全权 `gh`，改成按需输入或只读令牌 | 不动猛鬼兽 | 常浩自己在电脑上的 Claude / Codex 会话也会受影响 |

推荐方向（待评审）：4a 先行，作为代批上线前的门槛；4b 作为长期目标，在批 8 收口时评估。

### 5. 迁移与回退原则

1. **旧的不删，直到新的验收**：批 1～7 期间旧结构保留；回退 = 暂停中台规则或卸载中台（保留数据）、停 dt-worker 接单；merge-buttons 的中台分支删掉不影响原有按钮（方案第 10 节）。
2. **每项退役都可回滚**（批 8）：退役前备份到 `evidence/`，写明恢复命令；常浩验收「只保留这一套」后才删。
3. **镜像可回退**：切回上游安装版；升级失败用升级前快照回滚，不是直接装旧版程序。
4. **恢复先对账**：中台或出口重启、电脑睡醒后，对账完成前所有受保护副作用一律拒绝（方案 5.5 不变量 3）。
5. **搬家期间不签新钥匙**：dt-gate 搬迁完成、重新验收前，不签 feishu、secretary 通道钥匙，派单规则保持暂停；搬家前后各备份一次中台数据，搬完回读状态和钥匙权限。
6. **做不通就停，不降级**：dt-gate 或门卫机器人配不通，停在当前批回来改方案，不退回同账号（方案第 11 节第 1 条的同一原则）。

1. ARCHITECTURE 仍是唯一工程架构基线。本 ADR 是 V6.0 的决议，不另起平行方案；批 8 按 §12.4 改正文：执行层从 Multica 换成中台 + dt-worker、新增 dt-gate 控制面、事实所有权表改按方案 5.3 状态权威表、5.2a 的威胁模型边界改为「控制面与秘书分账号」。
2. 部分取代 ADR-013：Multica 退出执行层；「Hermes 管业务、GitHub 管交付、执行层不推送不合并、送审走驿窗」保留。
3. 修订 ADR-014（修订 3）：托管并入为「秘书代批」，作用对象从 Multica 夜跑子单换成中台卡片；托管状态机、账本、额度、汇报卡、推翻沿用；D 档一律不代；修订 2 里「全权会话本身就能合并」一条，由本 ADR 第 4 节接着处理。
4. PRD 要同步修订（批 8 前）：F4.3、F5.4、F5.6、F9、第 3 节终局图；若选丙，原则 1 的字面；若选 4a，原则 6 的字面。原则 7、第 8 节信息边界不变。
5. 常设授权清单四档一项不改。

## 代价与风险

| 风险 | 对策 |
|---|---|
| 多一个账号、一个机器人，运维更复杂 | 自检和巡检加 dt-gate 服务、门卫机器人连接；装法照 DAEMON-RUN |

## 重开条件

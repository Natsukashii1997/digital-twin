## 背景

1. 常浩 2026-11-15 定下唯一主线：fork agent-autoloop（下称「中台」）当数字分身的执行底座。猛鬼兽（Hermes）留作飞书前台兼「秘书」，按常浩签的清单代批，D 档一律不代；工人（Claude / Codex）关在独立 macOS 账号 dt-worker 里。方案 V2.4 经 Fable 5.2 独立评估和 ChatGPT High 两轮思维评审，常浩 11-15 回「代批选 B，9 件事都按推荐」。
2. 批 0A 隔离门已过：dt-worker 越权反向测试 22 项全挡住（PR #191）。批 0B 授权门完成 0B-1 任务凭证与派单网关（PR #199，未装）、0B-2 中台配置与只读窗口（PR #200，已装）、0B-3 飞书按钮实测（PR #201）、0B-4a 飞书桥接与本人点击（PR #202，已合并、未签钥匙、未装）。
3. **两次 L3 审查指出同一个问题**：
   - PR #199 审查 P0-01：派单网关和猛鬼兽跑在同一个 macOS 账号，猛鬼兽的模型有 shell，能改身份配置、读写凭证库、读 hermes 来源密钥，从而绕过两步批准。常浩 11-17 定：沙盒阶段先接受。
   - PR #202 审查 P1-01：点击人、聊天号是网关传进来的参数；同账号的进程能伪造这些参数，也能直接读 feishu 通道钥匙，甚至自己签钥匙。常浩 11-17 选甲：先合并，不签 feishu 通道钥匙、不安装；隔离在本 ADR 定，方向是「独立账号 dt-gate + 单独飞书机器人直接收点击」，0C 之前定。
4. **起草和评审中核实的事实**（2026-11-18）：
   - 猛鬼兽的飞书对话开着终端、文件、代码执行、浏览器、网页、电脑操作等工具（`hermes tools list --platform feishu`）。
   - 主账号的 `gh` 登录的是常浩本人（仓库管理员）的令牌；合并执行器的专用令牌也在同一个登录钥匙串（`merge_act.py` 的 `CUSTODY_CRED`）。ADR-014 修订 2 记过「宿主上的全权会话本身就能合并」，但当时没有论证「秘书本人就在全权账号里」。
   - 中台的本人密钥明文存在主账号 `~/.agent-autoloop/config.json`；本人密钥回答卡片不核对回答人（方案 2.3，`kernel/http.ts:203-204`），还能触发、暂停任何规则。
   - **猛鬼兽应用和亚古兽应用的飞书用户令牌都含 `im:message.send_as_user`、`im:message`（以常浩本人身份发消息）**，凭证在主账号 `~/.lark-cli`（`lark-cli auth status`）。主账号里任何进程都能以常浩的身份在私聊发一句「派单 <确认码>」，twin_identity 回读只能证明「这条消息以常浩身份发出」，证明不了是常浩亲手打的（推断：分不出来，未实发测试）。
   - 飞书的 `open_id` 按应用区分：本机两个应用里常浩的 `open_id` 已经不同。
5. 结论：今天主账号里被外部内容带偏的猛鬼兽，不用伪造批准也能直接推 main、合并、改中台规则，还能以常浩身份发私聊确认。只把网关搬走，挡住的是「伪造授权记录」，挡不住「直接动手」和「冒充本人打字」。

## 问题定义（评审第 1 轮重述，采纳）

在单机、多个 AI 自主运行的条件下，**两个目标必须同时成立**，缺一个代批就不能上线：

1. **授权真实性**：秘书、工人或任何程序制造的事件，都不能被当成常浩本人的批准。
2. **执行不可绕过性**：秘书即使被带偏、执行任何允许的工具调用，也拿不到绕过控制面所需的权限，不能用另一把钥匙直接完成本来要批准的动作。

单机账号隔离以 macOS 的用户身份、文件权限和管理员权限为可信基础；已经拿到 root 的进程不在本 ADR 的防护范围内。

## 决定

### 1. 底座方向（照 11-15 裁决，不重开）

1. 中台用 fork 版 agent-autoloop：**私有镜像引擎**（零补丁，锁完整提交号，每周检查上游但不自动替换，升级前兼容性检查、挂起恢复、插件回归、数据迁移验证，回滚靠升级前快照）；**独立插件仓库**放自己的插件；**公开 fork** 只用来给上游提 PR，合进上游后删掉自己那份。零补丁是优先策略，不是绝对禁令：安全正确性在公开接口做不到时，先申请上游扩展点，再评估最小补丁（方案第 3 节）。
2. 角色：常浩定目标、给授权、点合并；猛鬼兽负责对话、记忆、把常浩的话变成提议、把卡片变成白话；中台负责事件、规则、派活、挂起、定时；工人只在 dt-worker 里改自己的 worktree；撤不回的动作只由确定性出口在核实授权后执行；GitHub 分支保护是最后一道闸（方案 2.2）。第 3 节决定上面这些放在哪个账号。
3. 三份契约（授权与任务凭证、信任边界、状态与恢复）和三条不变量（受信发布、主账号不执行 PR 代码、恢复闸）照方案第 5 节，不在本 ADR 重写；授权证据的形式按本 ADR 第 3.3 节修订。

### 2. 融合与退役

### 3. 信任边界

**原则**：读外部内容并自主做决定、能生成有效授权、能不经授权直接完成受保护副作用——这三种能力不能落在同一个不可信主体手里。同账号内没有软件办法把它们隔开（上游 SECURITY.md、ARCHITECTURE 5.2a、两次审查、评审第 1 轮一致）；工具开关、提示词、技能白名单只是纵深防御，不算边界。

#### 3.1 五个信任域

| 域 | 系统账号 | 是谁、持有什么 | 信不信 |
|---|---|---|---|
| 常浩本人 | — | 在门卫卡片上的点击 | 唯一的授权来源 |
| 控制面 | **dt-gate**（新建，标准账号，平时不登录，系统服务运行） | 中台整体（含本人密钥、`rules.json`、数据库）、派单网关与凭证库、各把来源和通道钥匙、门卫机器人凭证与回调接收、本人点击处理、代批前后闸与送达、账本、汇报卡与推翻、受信发布（机器账号令牌）、合并执行器（专用令牌） | 可信，但只做核对过的固定动作 |
| 秘书 | 低权限账号（第 4 节；暂名 dt-secretary） | 猛鬼兽的对话、记忆、技能、推送；写提议、出候选决定，只经本机窄接口交给 dt-gate | 能提议，不能自证；拿不到任何钥匙、常浩的 GitHub 全权、能以常浩身份发消息的令牌 |
| 工人 | dt-worker（不变） | 接单密钥；只读凭证镜像；只能连中台 3350 和过滤代理 8090 | 不可信，0A 已隔离 |
| 常浩的人工工作区 | 主账号 | 常浩本人和他亲手开的 Claude / Codex 会话 | 受信的人工管理操作；不承载自动化的信任根（第 3.4 节） |

秘书和控制面都不复用 dt-worker。

#### 3.2 门卫机器人（常浩 11-18 决策 1：选甲）

- 新建一个**不带 AI** 的飞书企业自建应用「门卫」：只开私聊发消息和卡片回调，凭证只在 dt-gate；卡片回调直接连到 dt-gate，中间不经过秘书。
- 门卫只发固定格式的确认卡：派单五要素、中台提问卡、合并、代批汇报（含「推翻」）；不聊天。常浩只认门卫发来的卡。
- 门卫应用里常浩的身份**独立绑定**：门卫的 `open_id` 由 dt-gate 自己从常浩的一次点击取得并登记，不从猛鬼兽配置复制，不接受秘书声明（`open_id` 按应用区分）。0B-3 实测到的「私聊报 group」「拿不到原消息号」不直接继承，以门卫实际收到的回调为准。
- **PRD 原则 1 的例外**（常浩 11-18 批准）：「飞书里只有 Hermes」改为「飞书里只有一个 AI 对话入口（Hermes）；门卫是不带 AI 的授权组件」。PRD 字面在批 8 前随 PRD 修订一起改。
- 备选「丁」（单应用 + 可信消息网关：dt-gate 持猛鬼兽应用凭证、收全部飞书事件，普通对话转给秘书）**不采用为基线**。只有在验证 Hermes 网关能低成本外置事件入口、又不破坏主动推送和定时任务时，才另开 ADR 修订考虑，不推迟门卫落地。

不选甲（维持同账号）：授权门只是记账。不选乙（dt-gate 不加机器人）：按钮点击核不到、留着「冒牌说明」，而且私聊打字确认已被证明能被冒充（背景第 4 条）。

#### 3.3 授权证据只认门卫点击（常浩 11-18 决策 4：选甲）

1. **常浩本人的批准只认门卫卡片上的点击**：由 dt-gate 直接收到回调，核对门卫应用的应用身份、登记过的常浩 `open_id`、卡片令牌、卡片版本、选项，防重放。
2. **私聊打字口令不再单独作为授权证据**。方案 5.1 和 0B-1 的「派单 <确认码>」两步批准，改为：秘书递提议 → dt-gate 经门卫发五要素确认卡 → 常浩点「派单」。私聊打字可以触发提议，不能完成批准。0B-1 代码在 0E 跟着改（尚未安装）。同理，其他「放权」类私聊口令（签代批清单、开秘书 / 托管、解除冻结、「恢复 <单号> <冻结码>」）都改成门卫确认卡上的点击；「关秘书」「停 <单号>」这类收权的口令任何入口都照收。
3. **飞书用户令牌去掉写权限**：所有秘书和自动任务能碰到的用户令牌，去掉以常浩身份发消息、改消息、发邮件等写权限，只留各功能实际要读的权限；随秘书降权一起做（第 4 节）。需要以常浩身份写的功能逐项列出，单独问常浩。
4. 卡片里的白话说明由 dt-gate 按可信数据（凭证、Git、CI）生成；秘书写的白话只能作为卡片里标明「秘书说明」的一段，不能改动确认的对象。

#### 3.4 主账号里的其他全权 AI 进程（常浩 11-18 决策 3：选甲）

- 常浩亲手开的 Claude / Codex 会话，算受信的人工管理操作，照旧可以用常浩的全权。
- **无人值守、自动运行、会读不可信内容的全权 AI 进程**（定时的 `claude -p`、猛鬼兽派的旧车间 run_worker、Codex 自动任务等）纳入绕行检查：要么迁进 dt-worker 或秘书账号这类低权限身份，要么证明它拿不到绕过控制面的权限，要么停用。0E 前列出清单。

### 4. 秘书有效降权（常浩 11-18 决策 2：选甲）

**代批生效（0B-4c 启用）之前，必须证明：秘书执行任何它被允许的工具调用，都拿不到绕过 dt-gate 所需的权限。** 只关工具（原 4a）不算数。

| 做法 | 定位 |
|---|---|
| 4b 猛鬼兽整体搬进低权限账号（拿不到常浩的 `gh`、钥匙串、项目目录、能写的飞书用户令牌） | **首选** |
| 4c 猛鬼兽留在主账号，但主账号里不再有秘书能用的全权凭据和受保护出口 | 4b 做不通时的等效方案，必须逐条证明所有绕行通道都已失效 |
| 4a 关掉猛鬼兽的终端、代码执行、电脑操作等工具 | 只作纵深防御，不作门槛；不在本 ADR 里先做（改变猛鬼兽现有能力，按第 15 节单独确认） |

- 4b、4c 选哪个，在 0E 前按真实依赖清单定（凭据、脚本、定时任务、Vault 读取、用户令牌）。
- **PRD 原则 6「权限一次开够」会被改动**：具体改法随 4b / 4c 选定后单独发改动确认，常浩确认前不改 PRD、不动猛鬼兽。
- 秘书仍是常浩说的「数字分身」：它的判断照样决定代批（秘书代批规格不变），只是「判断」和「持钥送达」分在两个账号，判断结果经 dt-gate 的前后闸送达。

### 5. 迁移与回退原则

1. **旧的不删，直到新的验收**：批 1～7 期间旧结构保留；回退 = 暂停中台规则或卸载中台（保留数据）、停 dt-worker 接单；门卫停用不影响猛鬼兽原有按钮（方案第 10 节）。
2. **每项退役都可回滚**（批 8）：退役前备份到 `evidence/`，写明恢复命令；常浩验收「只保留这一套」后才删。
3. **镜像可回退**：切回上游安装版；升级失败用升级前快照回滚，不是直接装旧版程序。
4. **恢复先对账**：中台或出口重启、电脑睡醒后，对账完成前所有受保护副作用一律拒绝（方案 5.5 不变量 3）。
5. **搬家期间不签新钥匙**：dt-gate 搬迁完成、重新验收前，不签 feishu、secretary 通道钥匙，派单规则保持暂停；搬家前后各备份一次中台数据，搬完回读状态和钥匙权限。
6. **真实特权不回流**：开发和测试期间不把真实发布凭据、合并令牌、通道钥匙放进主账号或秘书账号「先跑起来」。
7. **做不通就停，不降级**：dt-gate、门卫或秘书降权做不通，停在当前批回来改方案，不退回同账号。

2. 部分取代 ADR-013：Multica 退出执行层；「Hermes 管业务、GitHub 管交付、执行层不推送不合并、送审走驿窗」保留。
3. 修订 ADR-014（修订 3）：托管并入为「秘书代批」，作用对象从 Multica 夜跑子单换成中台卡片；托管状态机、账本、额度、汇报卡、推翻沿用；D 档一律不代；修订 2 的「全权会话本身就能合并」由本 ADR 第 3.4、4 节处理；托管的开启来源从「飞书私聊」改为门卫点击（第 3.3 节）。

1. 本 ADR 合并 → 规则成立，不放行任何动作。
2. 0C 执行门：工人一侧照原计划；**受信发布出口从第一天按归 dt-gate 写**，开发测试不装真实凭据、不启动代批。不用等 0E。
3. 0D 恢复门：对账、恢复闸按在 dt-gate 里运行设计；多一次「搬家后中台挂起任务照常恢复」演练。
4. **新增批 0E 控制面搬家与秘书降权**：建 dt-gate；搬中台、网关、凭证库、钥匙、出口；建门卫应用并独立绑定常浩身份；0B-1 改成门卫确认卡；验证 dt-gate 不登录时能安全读到凭据（后台服务和登录钥匙串不同）；用户令牌去写权限；4b（或等效 4c）；第 3.4 节的无人值守全权进程清单处理完。
5. 0B-4b～4d、0B-5 照原计划写，组件按「能整体放进 dt-gate」写；不签钥匙、不装，等 0E。
6. 批 1 飞书拍板改为门卫；批 2、3 的写入单和出口在 0E 验收后才跑。
7. **代批生效**要同时通过三类反向验收（看最终状态，不只看拒绝记录）：

| 维度 | 通过标准 |
|---|---|
| 授权隔离 | 秘书伪造点击、伪造本人文字、复用失效卡片 / 凭证、拿签发钥匙——都不能成为有效批准 |
| 执行隔离 | 秘书直接合并、推 main、改分支保护或规则集、改中台规则、借用系统服务或主账号进程——都做不到 |
| 运行可用 | 常浩不在线、dt-gate 不登录时，合法批准和代批照常完成；重启、睡醒后不用人工解锁 |

## 代价与风险

| 风险 | 对策 |
|---|---|
| 多两个账号、一个机器人，运维更复杂 | 自检和巡检加 dt-gate 服务、门卫连接、秘书账号状态；装法照 DAEMON-RUN |
| dt-gate 不登录，后台服务的代理、钥匙串、睡眠行为和登录用户不同（G-19、G-20） | 0E 先实测；系统服务的环境变量写进 plist；凭据存法按实测定 |
| 猛鬼兽搬账号牵涉大（用户令牌、Vault 读取、定时任务） | 4b 做不通就走 4c，但要逐条证明；做不通就停，不降级 |
| 常浩分不清两个机器人 | 门卫只发固定格式的确认卡，不聊天；白话写清「只认门卫的卡」 |
| 打字口令改成点卡，手机上多一步 | 门卫卡一点即可；打字仍可发起提议 |
| 搬家时中台挂起任务丢失 | 先备份、再搬、回读；搬家期间派单规则保持暂停 |
| 飞书不允许建门卫应用，或回调拿不到可靠的操作人 | 不启用按钮授权，回到本 ADR 重选（丁或其他可信接收方式） |

## 重开条件

- 0E 实测推翻门卫的可行性（建不了应用、回调拿不到可靠操作人、身份绑定做不到）；
- 猛鬼兽在低权限账号跑不起来，4c 也证明不了等效；
- 上游中台协议变化，使「本人密钥只在控制面」做不到；
- 常浩决定不做秘书代批（第 4 节的门槛随之放宽）。

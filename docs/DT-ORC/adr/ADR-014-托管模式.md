# ADR-014 托管：常浩不在场时猛鬼兽以常浩身份决策

- **状态**：提议（随 issue #127 的 PR 合并后生效；生效只代表规则成立，不代表任何托管动作已放行，见「生效顺序」）
- **日期**：2026-11-09（同日按 ChatGPT High 两轮审查返修；同日按 #130 探路做修订 1，见文末）
- **决定人**：常浩（2026-11-09 对设计稿三项回复「按推荐定」）
- **规格**：[`../../托管模式-设计.md`](../../托管模式-设计.md)
- **架构基线**：[`../ARCHITECTURE.md`](../ARCHITECTURE.md) 4.3、4.4、5.5、5.6、5.7
- **影响的授权**：常设授权清单 v0 → v1（新增第 6 节「托管」）；《工程流程》第 8 节第 4 条（加托管合并例外）；PRD D23（托管期间没回复只执行已有效授权的项）

## 背景

1. 常浩不在场时（夜里、开会），Claude / Codex 会话停下问常浩、等批准卡、等合并，事情就卡住到常浩回来。D23 夜间提案只解决「夜里开哪几单」，开出来的单在夜里遇到要决定的事仍然停。
2. 驿窗已有「智能体互发消息」和「以我的身份发送」（驿窗主干 `243bcc6`，说明见驿窗 `docs/design/智能体互发消息与以我的身份发送-功能说明-2026-11-09.md`）：能把话以常浩身份送进会话，但只有全局开关，没有任何程序闸，Hermes 也收不到消息。
3. 现行合并放权路径（ARCHITECTURE 5.5）要求合并官影子运行同类 20 次、一致率 ≥ 90%，并要求驿窗补齐审核模式记录。2026-11-09 合并官统计：L0 4 次、L1 6 次（67%）、L2 13 次，均未达标。
4. ARCHITECTURE 5.2c 已认定：持有常浩完整凭据、以 `bypassPermissions` 运行的会话，本机 deny 和钩子不能作为可靠边界。

## 决定

1. **新增托管状态 `custody_state = off | on | draining | frozen`，与执行模式 `execution_mode = SUPERVISED | UNATTENDED` 正交**。界面叫「托管模式」；任何执行准入都要同时满足原执行模式的前提和托管的限制。
2. **托管期间，猛鬼兽以常浩的身份替常浩回复、答批准卡、托管合并**；底线之外自己判断；每个决定记账；托管结束、排空后汇报，常浩可以逐条推翻。
3. **授权来源不变**：开启只认猛鬼兽飞书私聊（5.2a (b) 核验）和已签托管策略的默认时段；驿窗开关只能关闭（分不清是不是本人点的）；关闭任何入口都可以。托管策略的签署绑定版本、完整内容 SHA-256、签署消息 ID、核验身份和有效期，缺项或内容变了就不生效。
4. **底线 = 常设授权清单 D 档 + 一切撤不回的动作**，托管期间一律挂起；拿不准也挂起。
5. **先限住会话能做什么，再管说什么**：
   - 托管只对「受限会话」以本人身份送达：会话跑在 5.2c 式受限执行身份下、没有合并和推 main 的凭据、执行点钩子通过反向测试。持有常浩完整凭据的会话（全权会话）一律不送达，待决事项挂起。Codex 通过同等验证前一律视为全权会话。
   - 三道闸：出口闸（确定性脚本按策略判结构化决定）、送达闸（驿窗核对托管状态、发件人、决定号有效期、会话分级、来回上限）、执行防线（主：受限身份与凭据；辅：白名单默认拒绝的执行点钩子）。
   - 合并凭据只在独立的合并执行器，任何 Claude / Codex 会话都拿不到。
6. **身份形式**：以常浩本人身份提交，末尾附 `〔托管·猛鬼兽代发 d-编号〕`；标记只是记录，不是权限凭证。
7. **托管合并**：合并官判建议合并、L0–L2；5.5 第 2 条成立；当前 HEAD 的必需 CI 全部通过并绑定该 HEAD；L1–L2 有可信审核凭证（5.5 第 1 条，或绑定送审包 SHA-256、PR/HEAD/base、可信回执来源与结论并校验时序的等效凭证），L0 只限策略白名单路径；合并副作用已逐仓库核实且可回退；5.5 第 3、5、6、7 条照旧；额度原子预占；只由合并执行器执行。只豁免 5.5 第 8 条和影子门槛。托管合并记 `owner=custody`，不计入影子一致率、不作为升档证据。
8. **托管期间派单**：D23 没回复时，只执行此前已经逐项有效授权的项（授权清单第 5 节第 1 条）；托管策略不构成对未来未知仓库、issue 的写入授权。
9. **关闭有排空**：`on → draining → off`。排空期间不收新事项、作废未送达的决定、让在途轮次跑完、对账结果不明的合并（7.6 不重发）；执行防线在排空期间照旧生效，对账完成才置 `off`。排空有截止：到点没收完就转 `frozen`，禁止新决定、新合并和重新开启，立即报告常浩，只有常浩说「解除冻结」才置 `off`。结果不明的合并额度冻结，对账确认前不释放。每次执行前，出口闸、送达闸、合并执行器各自再核托管状态和策略有效性。
10. **撤回**：每个决定记「撤回能力」（可纠正 / 可回退 / 不可撤回）和「处置状态」（未处理 / 已推翻·已记录 / 已纠正 / 已回退 / 回退失败）两个字段；推翻时按规则列出下游影响清单。合并的回退是开 revert PR，revert PR 的合并仍由常浩点卡片。

## 理由

- 常浩要的是「不在场时事情不停」，而不是「更快放权」。托管把放权限定在一段有时限、可随时收回、事后逐条可推翻的窗口里。
- 带常浩权威的话一旦送进持有完整凭据的会话，任何文本层面的闸都拦不住它被理解成更大的授权；所以权威只能送给执行权限已被外部限制的会话。
- 「撤不回就不做」加上「副作用逐仓库核实」，把托管合并的最坏结果限制在可回退的错误。

## 代价与风险

| 风险 | 对策 |
|---|---|
| 常浩日常会话都是全权会话，批 3 之前托管几乎什么都送不出去 | 如实告知常浩（规格第 9 节）；批 3 是最小闭环的前提 |
| 托管合并绕过影子门槛；免费版私有仓库没有远端分支保护 | 保留审核凭证、第 2 条、副作用清单；合并凭据只在合并执行器；当晚上限；逐条可推翻 |
| 自由文本回复夹带越界指令 | 只送受限会话，越界被操作系统和 GitHub 拒绝；出口闸禁止词表只作纵深 |
| 执行点钩子被间接调用绕过 | 钩子不是主防线；批 3 反向测试覆盖间接调用、权限绕过、过期决定、停托管后继续执行 |
| 关闭托管时出现权限窗口 | 排空状态机；执行防线不随托管关闭而解除；排空到截止没收完转 `frozen`，等常浩核对 |
| 并发决定超额 | 额度原子预占 |
| 策略文件被改、版本复用 | 签署绑定 SHA-256，每次使用重算 |
| 猛鬼兽回退到 deepseek-flash 时判断变差 | 回退期间只许规则判，需要模型判断的一律挂起 |
| 同一 macOS 用户下的恶意本地进程 | 沿用 5.2a 威胁模型边界：不防；受限会话跑在另一身份下，降低影响面 |
| 推翻后下游工作不会自动消失 | 推翻回执附下游影响清单 |

## 迁移与回退

- **生效顺序**：本 ADR 与常设授权清单 v1 合并 → 批 1–5 落地并逐批验收（按 L3，批 3 反向测试全过）→ 常浩签托管策略 → 托管才真正可用。任一前置没完成，猛鬼兽不按托管行事。
- **即时停用**：常浩在飞书说「我回来了」「停止托管」，或在驿窗关开关，托管进入排空，对账完成后置 `off`。
- **彻底回退**：常浩撤销托管策略；驿窗发件口拒收一切；受限执行身份和执行点钩子保留（托管关闭时钩子按非托管规则）。本 ADR 改为「已废止」，ARCHITECTURE 按 12.3 改版本，删去 `custody_state` 相关条款。已经发生的托管合并按决定第 10 条逐条处理，不批量回退。

## 修订 1（V5.1，2026-11-09，#138）

**依据**：#130 探路（`../migration/2026-11-09-托管受限会话探路.md`）。驿窗与会话之间的四条通道（读会话记录、钩子套接字、Claude 插件共享文件夹、Codex 队列）全部被隔离容器切断，接通就要破坏隔离；受限 agent 不在会话里停下，而是把子单标为 `blocked` 并在评论里交出待决事项；受限令牌能自行合并 PR（dt-sandbox 必需审批数为 0）。常浩 11-09 回复「起草修订」「按要点动手」。

**取代上文的部分**：

1. **作用范围**（取代决定 2、5 中「受限会话 / 全权会话」的划分方式）：托管只作用于正在进行、已经批准的夜跑（`multica_night.py` 的父单家族，只在 `sandbox: true` 项目上）。受限会话 = 夜跑里 Multica 隔离执行器容器中的 agent。常浩的交互会话完全不进托管，不再需要「全权会话挂起」的转交机制。
2. **通道**（取代决定 5 中驿窗送达闸的部分）：夜跑主控 tick 发现子单被 agent 标为 `blocked` → 托管开着就交猛鬼兽判断 → 回复类决定由 `custody_reply.py` 以常浩的 Multica 成员身份在子单评论（末尾代发标记），评论唤醒 agent；挂起或托管关着 → 按 ARCHITECTURE 5.3a 现行规则停机。这是对 5.3a 停机条件的改动，落地按 L3（#134）。
3. **三道闸**：出口闸不变；送达闸改由 `custody_reply.py` 承担（持夜跑主控的锁，核托管状态、决定号、子单仍在父单家族且仍是 `blocked`、次数、全部停机条件、夜跑授权写明允许托管唤醒、预占 run 额度）；执行防线 = 容器隔离 + 受限令牌 + 合并隔离：受限 agent **在任何 PR 状态下都不能自行合并**，由 GitHub 服务端或等效独立机制保障（「必需审批至少 1 个」不够）；#132 做到并验收之前，托管回复和托管合并都不启用，做不到就一直不启用。容器里没有本机 Claude 配置，执行点钩子不适用。
4. **身份**（取代决定 6 的提交方式）：以常浩的 Multica 成员身份写评论，代发标记不变；驿窗「以我的身份发送」与托管无关。
5. **上限**：每张子单的托管决定次数有上限；托管唤醒的 run 计入夜跑 `max_runs` 和连续失败计数，托管不增加 run 预算。
6. **批准卡**：不适用（容器 agent 以 `bypassPermissions` 运行）。
7. **驿窗**：只读显示托管状态，可以关托管，不能开；不承担收发。
8. **开启来源**：飞书私聊、已签策略的默认时段；驿窗不能开（同决定 3）。

9. **停机优先级**：托管只豁免「agent 请求决策而把子单标为 blocked」这一项停机原因；先执行完整的原有停机检查，有任何其他停机原因、blocked 来源核实不了、托管判断超时或出错，都走原停机路径。
10. **执行授权**：评论唤醒是新的执行启动，夜跑授权记录必须写明允许托管唤醒及次数；评论前在锁内预占 run 额度；写评论前的最后一步检查紧急冻结标记（`emergency.json`）、停止流程和冻结状态，任何一种都不发送（人工 `stop` 等锁超时会不拿锁直接应急冻结）；发送结果不明不重发，核不清按 5.3a 冻结；唤醒计数实测确认前不启用。
11. **托管合并的来源绑定**：只合并能证明属于当前已批准夜跑的 PR（夜跑 ID、父子 issue、授权记录、run 与 PR 的关联），由合并执行器独立核验。

上文原「决定」第 1、3、4、7、8、9、10 条和「生效顺序」不变（原决定第 7 条加上本修订第 11 条的来源绑定）。**V5.1 的实施与回退以设计稿第 7 节、ARCHITECTURE 5.7 为准；上文「迁移与回退」中的「批 1–5」「驿窗发件口拒收」「执行点钩子保留」等驿窗收发、批准卡、执行点钩子的施工与回退条款不再适用。** 彻底回退时：常浩撤销托管策略；夜跑主控回到「blocked 即停机」；托管评论通道停用。

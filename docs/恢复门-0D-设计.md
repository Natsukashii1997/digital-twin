## 3. 出口账本

**状态**：`executing`（在做，记着进程号、进程启动时间、开机时间）→ `done` / `failed` / `unknown`；对账能把 `unknown` 改成 `done`、`failed` 或 `unreconciled`（核不清，交常浩 `settle --confirm`）。

| 规则 | 怎么做 |
|---|---|
| 幂等键 | `<动作>:<单号或仓库>:<对象>:<版本>`（方案 5.3）。同一键已 `done`：直接回原结果，不再做 |
| 确定没做成才能重做 | `do()` 抛 `Definite`（请求没发出去、对方明确拒绝）记 `failed`，可以重做；其他一切异常（超时、断网、读不懂、被中断）记 `unknown` |
| 强杀 | 不靠异常捕获：每个入口和对账都扫「`executing` 而做的进程已经确认不在（进程号对应的进程不在或启动时间对不上、换了开机）」的，改成 `unknown`；查不了一律当还活着 |
| 跑得久不算结束（L3 P1-02） | 进程还活着、只是超过 30 分钟：只报「疑似卡住」（`status` 的 `stalled`），继续冻结，不给重做资格；常浩确认那个进程结束了才会被扫成不明 |
| 核不清是终态（L3 P1-01） | `unreconciled` 只有常浩 `settle --confirm` 能改；对账不再回读它，后来外部情况变了（例如冲突的分支被删）也不自动解冻 |
| 冻结 | 同一冻结范围有 `executing`（进程还在）、`unknown`、`unreconciled` 就拒绝新动作；同一时刻一个范围只有一个动作在做（这就是串行化）。范围按秘书代批规格第 7 节：任务 `task:<单号>`、仓库 `repo:<owner/name>`（合并）、卡片 `card:<卡片号>` |
| 自己解开 | 冻结的范围再有动作要做时，先只读对一次这个范围的账；网络恢复后能确认的就结算，结算了就放行 |
| 对账只读 | 推分支：`git ls-remote` 看远端分支——是这次的头提交算做成，还是推之前的样子（没有这条分支，或续推前的旧提交）算没做成，别的算核不清；开 PR：`gh pr list --head`；合并：`gh pr view` 看是否已合并、合并时的头提交；发飞书：在私聊里找**本次发出的那条**机器人消息（发送者是应用、消息类型对、有消息号、按钮回调值正好是这张卡的令牌），找不到不能证明没发：5 分钟内保持不明，之后记核不清交常浩（L3 P1-05） |
| 目标绑定凭证（L3 P1-07） | 带任务的动作：幂等键、冻结范围必须是这张单，目标仓库是凭证里的仓库，分支正好是 `<执行方>/<单号>`；同一幂等键第一次登记后目标不能改 |
| 和任务凭证串行（0C 审查 P1-07） | 带任务的动作，在**凭证库写锁**里现读凭证，并在同一把锁下把 `executing` 落盘，才放锁动手。冻结、撤销也要这把锁：冻结先提交 → 判定失败不动手；`executing` 先落盘 → 动作已开始（撤不回），冻结输出的 `in_flight` 列出它，结果出来照常对账；后续步骤重新判定，冻结后一律拒绝 |

**不经出口账本的**（避免两套账）：
- 本人回答中台卡片：`autoloop_answer` 已有写前账本（`claims`：queued → inflight → answered / unknown，从不重答），只接恢复闸；改成 `unknown` 时关闸。
- 派单事件：`autoloop_grants` 已有写前账本（`hub_events`），中台按同一来源同一 id 去重，补发安全，只接恢复闸。
- 秘书代批（① 回答、② 续派、③ 留言）：用秘书账本（#218）。接恢复闸：提议先看一眼（关着 → 「还不能办」，不记账、不占额度）；获准（账本 begin）在 cards.db 写锁和出口账本写锁里再核开闸资格（关了 → 作废、释放额度）；秘书决定记成结果不明时同时关闸；恢复闸对账看到秘书账本里还有结果不明、核不清、还在送的代批就不开闸，由秘书自己的对账（`secretary_gate reconcile`，不改）结掉，核不清的由常浩定；秘书领卡（报送达）也过闸。代批合并 0B-4d 再接。
- 托管账本（custody_ledger）：常浩 11-18 定不复用。理由：它绑托管会话、额度、白话五项，推分支这类动作不属于托管；而且它在 twin-state 库里，批 8 要退役 twin_state。状态词和「结果不明不重做、只按证据结算」的规则照搬。

## 4. 恢复闸

**闸关的条件**（记下的「纪元」对不上，或账本说要对账）：开机（`kern.boottime`）、睡醒（`kern.waketime`）、中台进程（`up.pid` 的进程号 + 进程启动时间；读不到、进程不在、不是 agent-autoloop 都当中台连不上，L3 P2-01）、中台版本（`/healthz` 的提交号）；中台连不上；任何账本出现结果不明（计数器，对账只清它开始时看到的那个数，对账期间新出的不明会让闸继续关着）；维护停写（`hold`，只由 `release` 结束）。

**检查和领资格之间没有空隙**（L3 P1-03）：`ensure_open()` 只是先看一眼、需要时对账；真正领写入资格的那个写事务里再 `admit(con, 纪元)`——出口账本落盘 `executing`、派单事件逐个领取、本人回答领发送资格、秘书获准都这样做（不经出口账本的用 `admission()`，锁顺序固定「自己的库 → 出口账本」）。结果不明的登记、维护停写都要出口账本这把写锁，所以「先关闸」和「先领资格」一定分得出先后：先关 → 领不到；先领 → 动作在闸关之前已经开始，照常记账、照常对账。长循环（`send_pending`）每发一个都重新领、重新核，中途闸关了剩下的一个也不发。

**暂缓不是失败**（L3 P1-04）：飞书桥接领到卡以后闸关了（出口账本拒绝），算「暂缓」，不向中台报 failed；对账里的送达补报、排队提交都先过闸。

**对账顺序**（`reconcile`，入口自己调，同一时刻只有一个）：

1. **本机账本**：出口账本里「在做、进程已不在」的改成结果不明。
2. **凭证与镜像**：凭证库存在时，按已提交的状态重写工人只读镜像并回读核对；写不成或对不上 → 不开闸。
3. **中台**：`/healthz` 通，提交号等于锁定的版本（`DigitalTwin/autoloop/hub-pin.json`，安装或升级核对通过后由常浩说了才 `pin`）；没锁定、不是锁定的 → 不开闸。
4. **外部回读**：出口账本里结果不明的逐条只读回读；本人点击里结果不明、在途过久的只读回读中台卡片（不提交排队的回答——那是开闸后的动作）；秘书账本里还有结果不明、核不清、还在送的代批 → 不开闸。
5. **结算开闸**：记下纪元和报告；仍冻结的范围各自继续拒绝，其他照常。

「恢复轮次 ≠ 恢复外部写」：中台照常恢复排队、挂起、显示；闸只拦往外写。

## 5. 按「将来在 dt-gate 里运行」设计（ADR-015）

- 账本、闸的状态、锁定版本、恢复锁都在**运行账号自己的** `~/Library/Application Support/DigitalTwin/autoloop/`（700 / 600），凭证库、卡片库、中台目录都从运行账号的家目录或环境变量取，不写死主账号路径；0E-2 整体搬进 dt-gate。
- 恢复闸本身不签、不用中台钥匙：中台只读 `/healthz` 和 `up.pid`。但**外部回读有认证依赖**（L3 P2-02）：回读卡片用 `autoloop_answer` 的只读窗口（通道钥匙），回读 GitHub 用运行账号的 `gh` 登录，回读飞书用 `DT_EXITS_LARK_PROFILE` 指定的机器人登录配置（必须是发这条消息的那个机器人）——0E-2 要把这些放在 dt-gate 自己名下（门卫机器人），不为对账把秘书账号的机器人凭据复制过来。
- 演练只验「换了目录、数据还能接着跑」；真跨账号（文件属主、权限、钥匙串、后台服务环境）在 0E-2 用真实 dt-gate 账号再验。

## 6. 和 0C 受信发布的对接（L3 第 1 轮返修时接上）

`autoloop_publish.publish()` 里两处外部写都经出口账本（`exit_guard`），`must()` 的逐步现读复核由 `guard` 的凭证库锁内判定取代（开头两个动作一起预检的 `must` 保留）：

| 动作 | 幂等键 / 冻结范围 | 目标 | 确定没做成（可以再做） | 结果不明（冻结这张单） |
|---|---|---|---|---|
| 推分支 | `push_branch:<单号>:<分支>:<头提交>` / `task:<单号>` | 仓库、远端、分支、头提交、推之前远端的样子（`before`） | git 没跑起来；没连上（解析不了、连不上）；远端明确拒绝（`[rejected]`） | 其他报错、超时、被中断；推完记结果前被强杀 |
| 开 PR | `open_pr:<单号>:<分支>:<头提交>` / `task:<单号>` | 仓库、分支、头提交 | 建之前的查询、核对出问题（查 PR 失败、已有对不上的 PR、PR 已关） | `gh pr create` 报错（PR 可能已开）、超时 |

- 同一张单一个冻结范围：推分支没结果之前不会开 PR；推分支结果不明，这张单冻结到对账确认。远端已经是这次的头提交时不再记推送（没有要做的），开 PR 那一步照样先对这张单的账。
- `task_lock` 保留（防同一单两个发布进程同时取包，秘书 ②③ 也拿这把锁，`secretary_gate.task_locked`），串行化的保证来自出口账本和凭证库锁。
- `REAL_PUBLISH = False` 在 0D 过审之前不改；0D 合并后要不要放开，由常浩决定（另外还要等 0E-4 在 dt-gate 配好机器账号令牌）。

## 7. 升级、回滚、搬家流程（真做要停正式服务，D 档，常浩说了才做）

1. **停写**（L3 P1-06）：`autoloop_recovery.py hold --point <编号> --snapshot <目录> --commit <旧版> --max-card <中台此刻最大卡片号> --confirm`。恢复闸关上，发飞书、发布、回答、派单、秘书代批一律停。
2. **排空**：`autoloop_recovery.py writes` 为空（出口账本没有 `executing`、本人回答没有在途、派单事件没有在途）才往下走。
3. 记下挂起的东西（开着的卡片、等回答的轮次），中台开着做快照：`agent-autoloop backup <证据目录>`。
4. 停旧版、起新版；核对 `/healthz` 是新版本，挂起的卡片和轮次一个不少。
5. 通过 → `pin --commit <新版> --confirm`，再 `release --point <编号> --outcome retired --confirm`（升级前快照作废，`restorable` 再也不认），入口对账后开闸。
6. 不通过 → 恢复点必须仍在维护（`restorable`），停新版，用**旧版程序** `restore <快照> --yes`，起旧版，再核对一次；`release --outcome rolled_back` 先核快照之后没有发出过卡片（卡片库、出口账本里有比快照时最大号还大的卡片 → 保持停写，交常浩）。
7. 快照之后、停旧版之前中台还可能出新卡片：停写期间桥接不领卡、不发，所以回滚丢掉这张卡时本地账本里也没有它，卡片号复用不会撞上旧消息。

搬家（0E-2）：停写 → 排空 → 快照 → 停 → 在新账号的目录 `restore` → 起 → 核对挂起的东西 → `release retired` → 恢复闸对账后开。

## 8. 已知局限

- 发飞书的对账要用 `lark-cli im +chat-messages-list` 以机器人身份读私聊消息，**真飞书没实测**（演练用的是假 lark-cli；实测要往常浩私聊发测试卡，放到 0E-2 和门卫机器人一起做）；找不到不判没发，5 分钟后记核不清交常浩。
- 结束了的卡改不了时另发的那条通知不带令牌，只过闸、不记账：最坏多一条结束通知。
- 本人回答结果不明、卡还开着时，仍要常浩明确放开（`autoloop_answer release --confirm`，沿用 4a）。
- 进程活着却真卡死的动作会一直冻结它的范围（只报疑似卡住，不自动放），要常浩确认进程结束；进程号被复用且启动时间恰好一样的情况挡不住（极罕见）。
- 睡醒用 `kern.waketime`：后台短暂唤醒也会关闸，代价是下一个动作前多一次对账。
- 恢复闸没接已安装的旧合并路径 `merge_act`（飞书一句话合并）：合并出口在批 3 接；托管在批 3、秘书代批合并在 0B-4d 接入同一道闸。
- 秘书账本里有一条核不清，整个恢复闸都关着（所有受保护的写都停），直到常浩结算——常浩 11-19 定的取舍：宁可全停，不让秘书的不明答案和别的动作交错。

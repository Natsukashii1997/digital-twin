## 1. 验收（方案原文）与结果

| 验收项 | 做法 | 结果 |
|---|---|---|
| 断网一次，没有重复副作用，结果不明冻结可对账 | 推分支时远端「断网」：结果不明 → 这张单冻结 → 断着时对不了账、继续冻结 → 网通后先对这张单的账（确认没推过）→ 重推一次 | 远端只收到 1 次推送 |
| 超时一次 | 推分支超时两种：推之前被杀（对账确认没推 → 重推一次）、推之后被杀（对账确认已推 → 不重推）；合并超时（合并已做 → 不重合）；本人回答超时（中台已收下 → 记已答上） | 推送 1 次、合并 1 次、回答 1 次 |
| 强杀一次 | 子进程真的做完动作、还没记结果就被 SIGKILL：推分支、开 PR、发飞书卡片、本人回答各一次 | 推送、PR、卡片、回答都只有 1 次 |
| 升级后挂起任务和卡片照常恢复 | 临时中台 v1.8.4 挂一张等回答的卡 → 快照 → 升到 v1.8.5 → 卡还在 → 锁定新版本前恢复闸关着 → 锁定后回答 → 挂起的轮次接着跑完 | 通过 |
| 失败能用快照回滚 | 升级到一个起不来的版本，并故意写坏数据库 → 用升级前快照恢复、起旧版 → 卡还在、回答后跑完 | 通过 |
| ADR-015：搬家后挂起任务照常恢复 | 快照 → 停 → 恢复到另一个目录 → 起 → 卡还在、回答后跑完 | 通过（真跨账号在 0E-2 再验） |

演练全部在临时目录、临时中台（随机端口、不装服务）里做；证据在 `~/Library/Application Support/DigitalTwin/evidence/0d-recovery/`。

## 3. 出口账本

**状态**：`executing`（在做，记着进程号、进程启动时间、开机时间）→ `done` / `failed` / `unknown`；对账能把 `unknown` 改成 `done`、`failed` 或 `unreconciled`（核不清，交常浩 `settle --confirm`）。

| 规则 | 怎么做 |
|---|---|
| 幂等键 | `<动作>:<单号或仓库>:<对象>:<版本>`（方案 5.3）。同一键已 `done`：直接回原结果，不再做 |
| 确定没做成才能重做 | `do()` 抛 `Definite`（请求没发出去、对方明确拒绝）记 `failed`，可以重做；其他一切异常（超时、断网、读不懂、被中断）记 `unknown` |
| 强杀 | 不靠异常捕获：每个入口和对账都扫「`executing` 而做的进程已经不在（或换了开机、超过 30 分钟）」的，改成 `unknown` |
| 冻结 | 同一冻结范围有 `executing`（进程还在）、`unknown`、`unreconciled` 就拒绝新动作；同一时刻一个范围只有一个动作在做（这就是串行化）。范围按秘书代批规格第 7 节：任务 `task:<单号>`、仓库 `repo:<owner/name>`（合并）、卡片 `card:<卡片号>` |
| 自己解开 | 冻结的范围再有动作要做时，先只读对一次这个范围的账；网络恢复后能确认的就结算，结算了就放行 |
| 对账只读 | 推分支：`git ls-remote` 看远端分支是不是这次的头提交；开 PR：`gh pr list --head`；合并：`gh pr view` 看是否已合并、合并时的头提交；发飞书：在私聊里按随机标记（卡片令牌）找机器人消息（动作开始 5 分钟内找不到不判没发，列表可能滞后） |
| 和任务凭证串行（0C 审查 P1-07） | 带任务的动作，在**凭证库写锁**里现读凭证，并在同一把锁下把 `executing` 落盘，才放锁动手。冻结、撤销也要这把锁：冻结先提交 → 判定失败不动手；`executing` 先落盘 → 动作已开始（撤不回），冻结输出的 `in_flight` 列出它，结果出来照常对账；后续步骤重新判定，冻结后一律拒绝 |

**不经出口账本的**（避免两套账）：
- 本人回答中台卡片：`autoloop_answer` 已有写前账本（`claims`：queued → inflight → answered / unknown，从不重答），只接恢复闸；改成 `unknown` 时关闸。
- 派单事件：`autoloop_grants` 已有写前账本（`hub_events`），中台按同一来源同一 id 去重，补发安全，只接恢复闸。
- 秘书回答、代批合并：0B-4c、0B-4d 用秘书账本，届时过同一道闸。
- 托管账本（custody_ledger）：常浩 11-18 定不复用。理由：它绑托管会话、额度、白话五项，推分支这类动作不属于托管；而且它在 twin-state 库里，批 8 要退役 twin_state。状态词和「结果不明不重做、只按证据结算」的规则照搬。

## 4. 恢复闸

**闸关的条件**（记下的「纪元」对不上，或账本说要对账）：开机（`kern.boottime`）、睡醒（`kern.waketime`）、中台进程（`up.pid` 的进程号 + 进程启动时间）、中台版本（`/healthz` 的提交号）；中台连不上；任何账本出现结果不明（计数器，对账只清它开始时看到的那个数，对账期间新出的不明会让闸继续关着）。

**对账顺序**（`reconcile`，入口自己调，同一时刻只有一个）：

1. **本机账本**：出口账本里「在做、进程已不在」的改成结果不明。
2. **凭证与镜像**：凭证库存在时，按已提交的状态重写工人只读镜像并回读核对；写不成或对不上 → 不开闸。
3. **中台**：`/healthz` 通，提交号等于锁定的版本（`DigitalTwin/autoloop/hub-pin.json`，安装或升级核对通过后由常浩说了才 `pin`）；没锁定、不是锁定的 → 不开闸。
4. **外部回读**：出口账本里结果不明的逐条只读回读；本人点击里结果不明、在途过久的只读回读中台卡片（不提交排队的回答——那是开闸后的动作）。
5. **结算开闸**：记下纪元和报告；仍冻结的范围各自继续拒绝，其他照常。

「恢复轮次 ≠ 恢复外部写」：中台照常恢复排队、挂起、显示；闸只拦往外写。

## 5. 按「将来在 dt-gate 里运行」设计（ADR-015）

- 账本、闸的状态、锁定版本、恢复锁都在**运行账号自己的** `~/Library/Application Support/DigitalTwin/autoloop/`（700 / 600），凭证库、卡片库、中台目录都从运行账号的家目录或环境变量取，不写死主账号路径；0E-2 整体搬进 dt-gate。
- 恢复闸不需要任何钥匙：中台只读 `/healthz` 和 `up.pid`，回读卡片用的是 `autoloop_answer` 现有的只读窗口（通道钥匙随它一起在 dt-gate）。
- 演练只验「换了目录、数据还能接着跑」；真跨账号（文件属主、权限、钥匙串、后台服务环境）在 0E-2 用真实 dt-gate 账号再验。

## 6. 和 0C 受信发布的对接（#209 合并后再接，本 PR 不改那两个文件）

`autoloop_publish.publish()` 里两处外部写改成经出口账本（`must()` 的现读复核由 `guard` 的凭证库锁内判定取代）：

```python
E.guard("push_branch", f"push_branch:{task_id}:{branch}:{head}", f"task:{task_id}",
        {"remote": remote_url(github), "branch": branch, "head": head},
        do=lambda: git("push", ...) and {"pushed": head},          # 推送命令明确报「没连上」时抛 E.Definite
        task=(task_id, "push_branch", gen))
E.guard("open_pr", f"open_pr:{task_id}:{branch}:{head}", f"task:{task_id}",
        {"github": github, "branch": branch, "head": head},
        do=lambda: open_pr(github, branch, head, row),
        task=(task_id, "open_pr", gen))
```

- 同一张单一个冻结范围：推分支没结果之前不会开 PR；推分支结果不明，这张单冻结到对账确认。
- `task_lock` 可以保留（防同一单两个发布进程同时取包），串行化的保证来自出口账本和凭证库锁。
- `REAL_PUBLISH = False` 在 0D 过审之前不能改；0D 合并后要不要放开，由常浩决定（另外还要等 0E-4 在 dt-gate 配好机器账号令牌）。

## 7. 升级、回滚、搬家流程（真做要停正式服务，D 档，常浩说了才做）

1. 记下挂起的东西（开着的卡片、等回答的轮次）。
2. 中台开着做快照：`agent-autoloop backup <证据目录>`（数据库、主密钥、配置、规则、secrets.env）。
3. 停旧版、起新版。新版提交号不等于锁定版本，恢复闸自动关着：期间不发飞书、不发布、不回答。
4. 核对：`/healthz` 是新版本，挂起的卡片和轮次一个不少。
5. 通过 → `autoloop_recovery.py pin --commit <新版> --confirm`，入口对账后开闸；不通过 → 停新版，用**旧版程序** `restore <快照> --yes`，起旧版，再核对一次。
6. 锁定新版本、开闸以后**不再用升级前快照回滚**：之后的卡片、轮次、对外动作会丢，卡片号会被复用；要退回旧版另做一次升级。

搬家（0E-2）：快照 → 停 → 在新账号的目录 `restore` → 起 → 核对挂起的东西 → 恢复闸对账后开。

## 8. 已知局限

- 发飞书的对账要用 `lark-cli im +chat-messages-list` 以机器人身份读私聊消息，**真飞书没实测**（演练用的是假 lark-cli），上线前实测一次；找不到的情况，动作开始 5 分钟后才判没发。
- 结束了的卡改不了时另发的那条通知不带令牌，只过闸、不记账：最坏多一条结束通知。
- 本人回答结果不明、卡还开着时，仍要常浩明确放开（`autoloop_answer release --confirm`，沿用 4a）。
- `executing` 超过 30 分钟按结果不明处理（防进程号复用和卡死）；一个动作做 30 分钟以上会被误判为不明，但只会冻结、不会重做。
- 睡醒用 `kern.waketime`：后台短暂唤醒也会关闸，代价是下一个动作前多一次对账。
- 恢复闸没接已安装的旧合并路径 `merge_act`（飞书一句话合并）：合并出口在批 3 接；托管、秘书账本在 0B-4c / 批 3 接入同一道闸。
- 派单事件结果不明不冻结：靠中台同一来源同一 id 去重补发（0B-1 的设计）。

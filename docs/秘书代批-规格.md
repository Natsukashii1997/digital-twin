# 秘书代批 · 规格（批 0B 授权门的一部分）

| 项 | 内容 |
|---|---|
| 状态 | v0.2（2026-11-17）：常浩已定第 9 节三个问题；下一步按 ARCHITECTURE §12.4 只把本规格送审 |
| 依据 | 方案 `agent-autoloop-底座-方案.md` 第 5.1、5.5、5.6 节，第 12 节裁决 10、11；常设授权清单 v1；托管模式设计（资产复用） |
| 不改什么 | 常设授权清单的四档一项不改；D 档一律不代批；托管资产（custody / custody_ledger / custody_report）的账本结构不改 |

## 1. 一句话

猛鬼兽（秘书，主账号）可以按常浩签过的**代批清单**，替常浩回答中台卡片、在合并出口替常浩点合并或退回；工人（dt-worker）仍然什么都批不了。秘书只能在卡片已有的选项里选、只能在常浩已经批准的任务里批，每次代批都记账、占额度、事后汇报，常浩随时能推翻、能关掉。

## 2. 秘书能批什么、不能批什么

| 类 | 例子 | 档 | 秘书 | 前提 |
|---|---|---|---|---|
| ① Agent 提问卡 | 「两种做法选哪个」「这个函数要不要顺手重命名」 | B | **可代批**（清单开了才行） | 卡片属于一张**有效任务凭证**的任务；只能选卡片上的选项；选项不碰第 3 节的任何一条 |
| ② 失败重试卡 | 「这一轮失败了，要不要再跑一次」 | B | 可代批 | 同上；每张任务最多代批重试 1 次 |
| ③ 退回 PR | 审查没过，在 PR 留言退回，派返修一轮 | B | 可代批 | PR 属于有效任务；留言只引用审查结论原文 |
| ④ 合并 PR | 点合并卡片 | B | 可代批（清单单独开） | 全部 B 档合并条件（L0–L2、CI 通过、`--match-head-commit`、合并执行器）+ PR 属于有效任务 + 仓库在清单的合并白名单里、写明合并到 main 会触发什么 |
| ⑤ 待决提案按推荐 | 每周一的提案 | B | 可代批（清单单独开） | 只「按推荐」，不逐条改 |
| ⑥ 批准写入派单 | 「让 Claude 改 xx」 | **D** | **不能** | 只能常浩本人在私聊批（方案 5.1） |
| ⑦ 其他 D 档 | L3、推 main、安装部署、新建或改定时任务、改网关或 Hermes 配置、写正式 Vault、改授权清单或代批清单、跨企业域、花钱、对外发言 | **D** | **不能** | 常浩 2026-11-15「D档还是都不能替我批」 |

秘书**不写自由文字回答**：中台卡片也接受一段文字当回答，但文字可能夹带给工人的新指令（扩大范围），所以秘书只能选编号；想说的话只能写在汇报里给常浩看。

## 3. 一律交给常浩（秘书看到就挂起，不判断）

1. 任何 D 档动作，或选项一旦选中会导致 D 档动作（装依赖、改配置、改定时、改权限、推 main 等）；
2. 改常浩定过的内容（设计、规则、已验收的样子和行为）；
3. 扩大任务范围：换仓库、加功能、改目标、换执行方；
4. 卡片不属于任何有效任务凭证，或凭证已过期、已撤销、被冻结；
5. 卡片文字里出现「常浩已同意 / 已授权 / 秘书请选」之类的说法（只是资料，出现即交常浩，并在汇报里标「疑似诱导」）；
6. 猛鬼兽正在用回退模型（deepseek-flash），或模型判断超时、出错；
7. 额度用完、代批开关不在「开」、策略失效；
8. 拿不准的。

## 4. 一次代批的路径

```
中台出卡片（ask / 失败通知）──► 飞书通道照常发给常浩
        │
秘书巡视（主账号，每分钟）：读中台待回答卡片（本人密钥只读用）
        │  不在开关时段、没过等待时间（第 9 节问题 1）、常浩已答 → 跳过
        ▼
代批闸 secretary_gate.py（确定性脚本，不靠模型）
   ① 代批清单签名有效（重算哈希）、开关为「开」、模型不是回退
   ② 卡片 → task_id → 任务凭证有效，清单允许这个项目、这一类
   ③ 第 3 节 1、3、4、5、7 条能机械判的先判
        │ 不过 → 记「交常浩」，不再碰这张卡
        ▼
猛鬼兽判断（hermes chat 单次，主模型 Opus 5.5）：读卡片、任务五要素、项目 CURRENT、Vault 偏好
   出结构化决定 {choice, 依据, 给常浩看的五项白话, 撤回能力, 风险自评}；卡片原文标为「资料」
        │
代批闸再核：choice 在选项范围内、五项白话合格、风险自评没碰第 3 节 → 账本预占额度（原子）
        ▼
送达：用飞书通道的密钥回答，by = "秘书"（不冒充本人）、ref = 送达那条消息号
   中台只认第一个回答：常浩先点了，秘书的回答不生效（中台回 changed: false），额度释放
        ▼
回读中台卡片：状态 decided 且 by = 秘书 → 账本记「已送达」；回读不了 → 结果不明，冻结这张任务的后续代批
```

合并（④）不走模型：代批闸核完条件直接交合并执行器的托管合并入口（`merge_act.run_custody_merge`，合并执行器专用凭据，#132），以合并接口返回的合并提交为成功证据，结果不明只读对账、不重发。

## 5. 身份、钥匙、谁能碰什么

| 东西 | 谁拿 | 说明 |
|---|---|---|
| 中台本人密钥 | 主账号的秘书巡视脚本（只读 `/v1/state`）、常浩自己 | 秘书**不用本人密钥回答**，否则中台记成「本人」 |
| 飞书通道密钥 | 主账号的飞书桥接、秘书送达脚本 | 回答时 `by` 写 "秘书"；通道的 `answerers` 只列常浩 open_id 和 "秘书" |
| 合并执行器凭据 | 主账号钥匙串，只在合并执行器函数里取 | 沿用 #132，只对白名单仓库 |
| 代批清单 | `~/Library/Application Support/DigitalTwin/secretary/policy.md`（主账号，600） | 签署方式沿用托管策略（第 7 节） |
| 账本 | twin-state 的 custody 三张表（复用） | 决定号、额度、原文另存，90 天后清 |
| dt-worker | 什么都没有 | 0A 已证：读不到上面任何一样，接单密钥回答卡片被中台拒绝 |

## 6. 额度、开关、推翻、汇报

**额度**（写在清单里，签署时必填）：每天代批总数；每张任务代批次数（建议 3）；每天合并数；重试每张任务 1 次。先预占后执行，确认失败释放，结果不明冻结、对账后再定。

**开关**（复用 `custody.py` 的四态，换名字）：开 / 排空 / 冻结 / 关。常浩私聊「关秘书」「停止代批」→ 排空：不出新决定，作废已出未送达的，对账进行中的合并，然后关。冻结只有常浩私聊「解除冻结」能解。

**推翻**（复用 `custody_report` 的分阶段推翻，常浩点汇报卡上的「推翻」）：

| 被推翻的 | 做什么 |
|---|---|
| 提问卡的回答 | 停掉这张任务正在跑的轮次；给常浩发一张同样选项的卡片，常浩选的答案作为「更正」事件发回同一任务；之后依据旧回答做的提交、PR 列进下游影响清单 |
| 重试 | 停掉这一轮 |
| 退回 | 在 PR 补一条「撤回退回」留言 |
| 合并 | 合并执行器开 revert PR（只开不合），revert 的合并仍由常浩点（B 档） |

每次推翻都写一条规则补丁候选：以后同类按常浩的判断，进每周待决提案。

**汇报**：沿用 11-14 定稿的乙版表格（「等你处理」「替你定了的」两张表，白话五项：这件事在做什么、agent 问了什么、我替你定的、为什么、你不同意怎么办），每条可推翻的带「推翻」按钮。节奏见第 9 节问题 3。冻结、结果不明立刻单独报。

## 7. 代批清单（签署件）长什么样

格式照 `托管策略-模板.md`：版本单调、全文 SHA-256、私聊口令「签代批清单 v<版本> <哈希前 12 位>」、不许留未填项、有效期必填。内容：

| 项 | 要填 |
|---|---|
| 开关时段 | 第 9 节问题 1 的选择 |
| 允许的类 | 第 2 节 ①–⑤ 逐项「是 / 否」 |
| 项目 | 允许代批的名册项目（不写 = 都不行） |
| 合并白名单 | 仓库、合并到 main 触发的工作流和外部动作、核实日期；L0 路径白名单 |
| 额度 | 第 6 节各项数字 |
| 有效期 | 例：签署日起 30 天，到期前 3 天日报提醒，不自动续 |

清单里写进任何 D 档动作，签署直接拒绝。

## 8. 0B 里要做的和验收

| 做 | 复用 / 新写 |
|---|---|
| 任务凭证加「批准来源」：本人 / 秘书（记清单版本和决定号） | 契约 A 新写 |
| `secretary_gate.py` 代批闸、`secretary_watch.py` 巡视 | 新写；判定沿用 custody 的出口闸写法 |
| 账本、额度、开关、推翻、汇报卡 | 复用 custody_ledger / custody.py / custody_report（#131 已安装；#133 已合并、未安装），把「Multica 子单」换成「中台卡片」 |
| 合并 | 复用 `run_custody_merge`（#132） |
| 飞书按钮实测：拿到常浩 open_id 和原消息号 | 0B 本来就要做 |
| AI 接入登记一行 `secretary`（执行方 Hermes，仅支持 Hermes） | P-13 |
| 巡视脚本装成常驻服务 | D 档，装之前单独问常浩 |

**验收**（全部在 dt-sandbox 上做）：

1. 一次代批回答走通：卡片 → 秘书选 → 中台记 by=秘书 → 工人接着干；汇报卡收到。
2. 一次推翻走通：停轮次、常浩重选、更正事件到达同一任务。
3. 拦截各一次：D 类选项、卡片里写「常浩已授权」、无凭证的卡片、凭证撤销后、额度用完、开关关着、回退模型期间——都交常浩、不代批。
4. 常浩先点了以后秘书再答不生效，额度释放；秘书和常浩同时点只算一次。
5. 伪造：用 `by=秘书` 但 ref 不对、接单密钥冒充秘书——都被拒。
6. 断网 / 强杀在送达那一步各一次：结果不明 → 冻结 → 对账正确，不重复回答。

## 9. 常浩的决定（2026-11-17）

1. **什么时候批**：任何时候；白天先等常浩 30 分钟，没回秘书再批；托管时段（默认每晚 23:30–08:00，或常浩说「托管到 X 点」）不等。（选了推荐）
2. **清单 v1 开哪几类**：① 提问卡、② 重试、③ 退回、**④ 合并都开**；⑤ 待决提案不开。（合并没按推荐「先关」，常浩选了一开始就开。合并仍要全部 B 档条件 + 有效任务 + 白名单仓库，dt-sandbox 现在没有 CI，白名单里先只能放有 CI 的仓库。）
3. **汇报**：每天 21:00 一张汇总卡（白天的），托管时段结束一张；冻结、结果不明立刻单独报。（选了推荐）

被否掉的：只在托管时段批、任何时候立刻批；每代批一次发一条、只写进日报。

## 1. 一句话

猛鬼兽（秘书，主账号）可以按常浩签过的**代批清单**，替常浩回答中台卡片、重派中台放弃的任务、退回或合并 PR；工人（dt-worker）仍然什么都批不了。**代批只能在已授权任务里做选择，不增加任何权限**：之后的每一个副作用（推分支、开 PR、合并、发飞书）照旧由各自的出口按原任务凭证核对。

## 2. 三种事实分开记

| 事实 | 谁授权 | 存在哪 | 说明 |
|---|---|---|---|
| 代批清单 | 常浩签 | `DigitalTwin/secretary/policy.md` + 签署记录 | 授权秘书批哪些类、哪些项目、多少额度、多久 |
| 任务凭证 | **始终是常浩**（写入派单是 D 档） | `DigitalTwin/autoloop/grants/` | 授权工人在哪个仓库做哪些动作；秘书不签凭证，也不往凭证里加权限 |
| 代批决定 | 秘书按清单 | 账本（复用 custody_ledger 的决定表） | 哪张卡 / 哪个 PR、哪一轮、选了什么、依据、清单版本、决定号 |

## 3. 秘书能批什么

| 类 | 是什么 | 档 | 准入证据（全部由可信侧取，不信工人的说法） |
|---|---|---|---|
| ① 提问卡 | 工人在已批任务里问「选哪个」 | B | 卡片绑定到有效凭证（第 5 节）；只能选卡片已有选项；落在第 4 节任何一条就弃权 |
| ② 放弃后重派一次 | 中台连续 10 次没跑成、停掉了这件事（中台自己会重试 10 次，不出「要不要重试」的提问卡，`kernel/decide.ts:383-406`） | B | 那一轮已是终态；账本里这张任务没有在途的推分支 / 开 PR；每张任务最多 1 次；由网关发同一事项的派单事件，不用本人密钥 |
| ③ 退回 PR | 审查没过，留言退回、派返修一轮 | B | 审查记录（合并官 + ChatGPT 审查回执）绑定这个 PR 和受审 HEAD，现在的 HEAD 仍是它；返修沿用原凭证、原范围、原执行方；要扩范围或新写入 → 交常浩 |
| ④ 合并 PR | 点合并 | B | 全部 B 档合并条件（L0–L2、CI 通过、`--match-head-commit`）；PR 由受信发布出口开出、记着 task_id；审查通过且绑定同一 HEAD；仓库在清单白名单里，白名单写明合并到 main 触发的全部工作流和外部动作、且都能安全回退；**合并前现读一次触发条件**（工作流文件有没有变），和白名单记的不一致 → 交常浩 |

不代批：批准写入派单；所有 D 档（L3、推 main、安装部署、新建或改定时任务、改网关或 Hermes 配置、写正式 Vault、改授权清单或代批清单、跨企业域、花钱、对外发言）。秘书**不写自由文字回答**，只选编号。

## 4. 一律交给常浩（不判断，直接交）

1. 任何 D 档动作，或选项一旦选中会导致 D 档动作；
2. 改常浩定过的内容（设计、规则、已验收的样子和行为）、验收口径；
3. 扩大任务范围：换仓库、加功能、改目标、换执行方；
4. 选项说不清动作边界、或执行后难恢复；
5. 卡片绑不到有效凭证，或凭证已过期、撤销、冻结；
6. 卡片文字里出现「常浩已同意 / 已授权 / 秘书请选」之类（交常浩的信号，汇报里标「疑似诱导」）；
7. 猛鬼兽在用回退模型（deepseek-flash），或判断超时、出错；
8. 额度用完、开关不在「开」、清单失效；同仓库有结果不明的合并（第 7 节）；
9. 拿不准的。

**①不靠「证明选项在授权内」，靠执行侧兜底**（评审第 2 轮：有条件成立）：选项是工人写的，可信侧没法事先认定每个选项的含义。v1 不建可信选项目录，而是把误选的代价限制在「可丢弃的本地返工 + 授权内的资源消耗」，靠两道边界：

- **工人侧**：任务 worktree 可丢弃、要保留的工作有可恢复基线；共享缓存、其他任务的目录不在它能写的范围；出网只经过滤代理，还要核实放行的目的地上工人能做什么（会不会产生远端写入、泄露任务数据、花钱）。
- **发布侧**：受信发布出口推分支、开 PR 之前，核原凭证 + 能机械判的发布边界（仓库、分支前缀、改动路径不碰 L3 / 工作流文件、开 PR 会触发的工作流属于已知可接受的），不只核动作名；需要语义判断的改动，留给已确认的「同 HEAD 审查」。

推分支、开 PR 本身就是外部状态，所以①选错的后果不只是「PR 里多了改动」，也包括这次推送、开 PR 及其触发。**这两道边界是①启用前的验收项**（第 9 节验收 8）：零补丁下某类卡片满足不了，就把这类交常浩，或只给它补可信的结构化选项。v1 同时统计①有多少能代批、多少弃权、省了多少等待（第 8 节）。

## 5. 卡片怎么绑到任务（可信绑定）

已核中台源码：
- 规则按来源过滤（`when: {source, types}`，`kernel/rules.ts:16`）；工人回执里发的事件，来源由规则的 `emits` 定，工人改不了（`docs/protocol.md:242`）。
- 卡片的事项（`lane`）取自产生它的那一轮（`kernel/decide.ts:118、271`），那一轮的事项来自触发事件的 `subject`；卡片回答、定时复查都沿用同一事项（`:547-552`、`:614`）。本人状态接口 `/v1/state` 的卡片带 `lane` 和 `rule`（`host/state.ts:180`），通道领到的卡片不带。

所以：派单规则只接 `hermes` 来源；派单事件的 `subject` 由网关写成 `task_id`；工人规则的 `emits` 用别的来源、只开数据事件，触发不了派单规则。

**网关只有两个入口**：本人批准建立任务（核验过的常浩私聊 → 签凭证 → 发第一个派单事件）；依据已有有效凭证续接这个任务（②重派、③返修、推翻后的更正）。网关不凭别的理由发 `hermes` 事件。

**绑定看创建这张卡的那一轮**，不从当前配置反查同名规则：网关每次发派单 / 续接事件都在账本记下「事件号 → task_id、规则名、执行方、代次」；秘书看卡片时，用卡片所属轮次的触发事件找到这条记录，事件号、规则名、执行方、`lane`、凭证、代次（第 8 节）全对上才算绑定。只读状态里拿不到「卡片 → 轮次 → 事件」这条链，就由网关在送达时补记；**来源追溯不了的卡片一律交常浩**。旧卡可以留着历史归属，能不能继续回答另核它所属的代次是否还有效。

秘书读卡片不直接拿本人密钥：经主账号的**只读状态入口**（方案里给驿窗准备的只读代理，0B 一起做），只返回巡视要的字段。

## 6. 谁回答：两把通道钥匙分开

| 通道 | 钥匙在哪 | `answerers` | 用途 |
|---|---|---|---|
| `feishu` | 飞书桥接（猛鬼兽网关的按钮插件 → `autoloop_answer.py`） | 只有常浩的 open_id | 常浩在飞书点按钮 / 引用回复 |
| `secretary` | 秘书送达脚本 | 只有 `"秘书"` | 秘书代批 |

中台的回答校验是「通道钥匙 + 该通道的 answerers + 该通道送达那条的 ref」（`kernel/decide.ts:519-527`），每个通道各有自己的 answerers（`kernel/rules.ts:14`）。两条通道各送达一份（`secretary` 通道的「送达」就是秘书领到卡片、记下自己的 ref），所以**秘书的钥匙答不出 by=常浩，飞书桥接的钥匙答不出 by=秘书**——这区分的是「哪个受信组件交的答复」。

**模型不持钥要做实，不只是约定**：两把钥匙和模型进程都在主账号（同一用户）。读卡判断用 `hermes chat` 单次调用，只开最小工具集（不给终端、文件读写、网络；现有 `pdaily_publish.py` 已用 `-t` 限定工具集），输入只有卡片文字和任务摘要，输出只有候选决定；持钥的送达脚本只接收已过闸、已预占的决定号，不接受模型直接给的指令。验收要确认判断进程碰不到钥匙文件、调不动送达脚本。

**送达时把决定钉死**：同一张卡的同一个版本，**最多只有一个可送达的秘书决定**（账本唯一约束）。账本先写「决定号 + 卡片号 + 卡片版本 + lane + 选项号 + secretary 送达的 ref」再回答；回读看到 `decided`、`by=秘书`、`choice` 等于账本里的选项，才记「已送达」并结算这一个决定号的预占；不一致或读不到 → 结果不明，保留原预占，按原决定对账。

## 7. 路径、等待和常浩优先

```
中台出卡片 ──► feishu 通道发给常浩（桥接记下送达时间）
           └─► secretary 通道领到（记下自己的 ref）
秘书巡视（主账号，每分钟）：经只读入口看卡片
   等待：从飞书成功送达起算；白天 30 分钟，托管时段（默认 23:30–08:00 或「托管到 X 点」）不等
   ▼
前闸（确定性）：清单签名有效、开关为开、不在回退模型；第 5 节绑定；类别允许；第 4 节能机械判的
   ▼ 不过 → 记「交常浩」
判断（只有①用模型；hermes chat 单次，Opus 5.5）：在卡片已有选项里选或弃权，写依据和白话五项
   ▼
后闸（送达前现读，不信判断时的状态）：清单版本、开关、凭证没撤销没冻结、卡片还是 open 且版本没变、
   lane 和规则没变、本人点击锁、额度 → 账本原子预占
   ▼
回答（secretary 钥匙）→ 回读核对（第 6 节）
```

**本人点击锁**：飞书桥接收到常浩的点击，先在账本对这张卡写「本人在途」，再调中台；秘书拿「送达资格」（账本里把决定从「已预占」改成「获准送达」，这是唯一的送达授权点）和桥接写「本人在途」在同一把锁里互斥。承诺（评审第 2 轮措辞，常浩 11-17 已确认，第 10 节第 4 条）：

> 白天从飞书成功送达起等 30 分钟。等待期满后，秘书获准送达前，本机已登记的本人点击优先。秘书的答复已经获准送达后，以中台先受理的回答为准。秘书先答成功，你迟到的点击会显示已选的结果，并给推翻入口。

**结果不明的冻结范围**：回答结果不明 → 冻结这张任务的后续代批；合并结果不明 → 冻结**这个仓库**所有后续代批合并，对账完再解。

②③④不用模型，前后闸全是确定性检查；④交合并执行器（`merge_act.run_custody_merge`，#132 专用凭据），以合并接口返回的提交为证据，结果不明只读对账、不重发。

## 8. 额度、开关、推翻、汇报、统计

**额度**（签署时必填）：每天代批总数；每张任务代批次数（建议 3）；每天合并数；②每张任务 1 次。先预占后执行，确认失败释放，结果不明冻结。

**开关**：开 / 排空 / 冻结 / 关（复用 `custody.py` 四态）。常浩私聊「关秘书」→ 排空：不出新决定，作废已出未送达的，对账进行中的合并，然后关。冻结只有常浩私聊「解除冻结」能解。

**推翻**（常浩点汇报卡上的「推翻」，分阶段可恢复，复用 `custody_report`）：

**执行代次**：每张任务凭证带一个代次号（从 1 开始）。网关发的每个派单 / 续接事件、工人启动、秘书答卡、受信发布都带着并核对代次；**被推翻作废的代次永久失效**——旧的排队轮次、内建重试、定时复查即使在任务恢复以后才到，也因代次不对被启动脚本、秘书、发布出口拒绝，不会复活。

1. **先挡住旧决定继续生效**：凭证改成「冻结」并把当前代次标为作废 → 新轮次起不来、不再推分支开 PR、秘书不再代批这张任务。冻结前已受理或结果不明的发布照常对账。
2. **停掉在跑的轮次并确认**：网关取消正在跑的轮次，回读到终态；还要确认实际的工人进程已停，或它剩下的动作已被发布出口隔离（旧代次被拒）。
3. **列下游**：依据旧决定做出的提交、PR、返修、之后的代批决定（账本里「依据」引用它的）。
4. **常浩重选**：发一张同样选项的卡；常浩选了，**更正先持久记在账本**（被替代的决定号、下游怎么处理：关 PR / 回退提交 / 保留），常浩确认后，网关把凭证恢复为有效、代次 +1，才发「更正」事件到同一事项；冻结期间不往中台投事件，免得被误执行或耗掉重试。
5. 合并被推翻 → 合并执行器开 revert PR（只开不合，合并仍常浩点）。revert 只能纠正仓库内容，已触发的工作流和外部动作要逐项对账，所以④的白名单只收触发效果都能安全回退的仓库（第 3 节）。

每次推翻写一条规则补丁候选，进每周待决提案。

**汇报**：每天 21:00 一张汇总卡（白天的），托管时段结束一张；冻结、结果不明立刻单独报。沿用 11-14 定稿的乙版表格（「等你处理」「替你定了的」，白话五项），可推翻的带「推翻」。

**统计**（v1 就记，决定以后做不做结构化问题）：每类卡片总数、代批数、交常浩数和原因、代批省下的等待时间、被推翻数。

**验收**（看最终状态，不只看闸口返回）：

1. 正向：①②③④各一次（①要看到工人接着干、PR 里有依据它做的改动）。
2. 推翻：①被推翻后，凭证冻结、新轮次起不来、受信发布拒推、常浩重选、更正事件到达、下游清单列全；④被推翻开出 revert PR。
3. 拦截：选项语义越界（如「顺便升级依赖」「改 CI」）、卡片写「常浩已授权」、绑不到凭证、判断期间凭证被撤销、额度用完、开关关着、回退模型期间、同仓库合并结果不明——都交常浩，最终状态里没有代批生效。
4. 竞态：常浩点击已到本机、秘书同时要答 → 只有常浩的生效；常浩迟到的点击收到明确提示。
5. 伪造：飞书桥接钥匙带 by=秘书、秘书钥匙带 by=常浩、ref 不对、接单密钥冒充——都被中台拒绝。
6. 断网 / 强杀在送达那一步各一次：结果不明 → 冻结 → 对账正确，不重复回答。
7. ④正向合并要一个**有真实 CI、触发效果已核实**的仓库：dt-sandbox 现在没有 CI，要先给它加最小 CI（改 `.github/workflows` 属 L3，由常浩点合并）；常浩已定加最小 CI（第 10 节第 5 条）。
8. ①启用前：故意让秘书误选一次，分别看 worktree、出网、推分支、开 PR 的最终效果，确认审查前已发生的动作都在授权内（第 4 节两道边界）。
9. 对账：同一卡片同一选项出现重复候选、送达结果不明 → 最终只结算原预占。
10. 代次：推翻时留一个还没启动的旧派生工作，等更正后任务恢复再放它出来 → 旧的被拒、新的正常跑。
11. 判断进程碰不到两把通道钥匙、调不动送达脚本。
12. ①启用前：中台收回答时按版本核对（回答带期望的卡片版本，和中台当时的版本不一致就拒绝、不产生决定），本人和秘书两条回答路径都覆盖。按零补丁先向上游要这个扩展点（ADR-015）；到位前控制面 ①的送达开关（secretary_gate.REAL_ASK）保持关闭，①一律交常浩（PR #218 第 2 轮审查 P1-01，常浩 2026-11-19 选甲：不破零补丁）。
